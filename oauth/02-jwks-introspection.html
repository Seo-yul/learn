JWKS와 introspection

OAuth 학습 2편 · 2026-10-14 작성

리소스 서버가 토큰을 검증하는 두 방법을 살펴보고, 우리 MCP 서버가 두 방법을 어디에 쓰는지 다룬다.

1편 "role과 scope, 그리고 OAuthProxy"의 프록시 구조를 안다고 가정한다.

한 문장 요약

JWKS 방식에서는 리소스 서버가 공개키로 서명을 직접 검증하고, introspection 방식에서는 리소스 서버가 IdP에게 토큰 상태를 묻는다. 앞의 방식은 빠르고, 뒤의 방식은 취소를 바로 반영한다.

1. 리소스 서버가 따지는 네 가지

리소스 서버는 토큰을 받으면 네 가지 질문에 답해야 한다.

질문보는 값
진짜 IdP가 발급했나?서명, 발급자(iss)
아직 유효한가?만료 시각(exp), 취소 여부
나에게 온 토큰인가?대상(aud)
무엇을 허용하나?scope 또는 scp

JWKS와 introspection은 이 질문에 답하는 두 방법이고, 둘의 차이는 답을 누가 내는가에 있다.

2. 서명의 두 방식

방식서명하는 키검증하는 키알고리즘 예쓰는 곳
비대칭개인키공개키RS256, ES256IdP 토큰
대칭대칭키같은 대칭키HS256fastmcp 토큰

비대칭 방식에서는 공개키가 알려져도 서명을 위조하지 못한다. 반면 대칭 방식에서는 검증하는 쪽도 서명을 만들 수 있어서, 발급자와 검증자가 같을 때만 쓴다.

3. JWKS

JWKS는 IdP가 공개하는 공개키 목록이고, 주소는 IdP의 discovery 문서에 있는 jwks_uri다.

GET https://{Okta 주소}/oauth2/default/.well-known/openid-configuration
{
  "issuer": "https://{Okta 주소}/oauth2/default",
  "jwks_uri": "https://{Okta 주소}/oauth2/default/v1/keys",
  "introspection_endpoint": "https://{Okta 주소}/oauth2/default/v1/introspect",
  ...
}

GET {jwks_uri}
{
  "keys": [
    { "kty": "RSA", "alg": "RS256", "use": "sig", "kid": "k1a2b3", "n": "0vx7…", "e": "AQAB" }
  ]
}

리소스 서버는 다음 순서로 검증한다.

  1. JWKS를 받아 키 캐시에 둔다.
  2. 토큰 header의 kid를 읽는다.
  3. 키 캐시에서 같은 kid의 공개키를 찾고, 없으면 JWKS를 다시 받는다.
  4. 그 공개키로 서명을 검증한다. 내용이 한 글자라도 바뀌었으면 실패한다.
  5. exp, iss, aud, scope를 본다.

IdP는 서명 키를 때때로 교체하고, 새 토큰의 kid는 새 키를 가리킨다. 그래서 리소스 서버는 모르는 kid를 만나면 JWKS를 다시 받는다.

장점단점
요청마다 IdP를 부르지 않는다. 그래서 빠르고 IdP에 부하가 없다.취소를 알지 못한다. 서명이 맞고 exp가 남아 있으면 통과한다.
IdP가 잠시 멈춰도 키 캐시로 검증을 계속한다.JWT에만 쓴다. 불투명 토큰에는 쓰지 못한다.

4. introspection

introspection은 리소스 서버가 받은 토큰을 IdP에 보내서 상태를 묻는 방법이다.

POST https://{Okta 주소}/oauth2/default/v1/introspect
Authorization: Basic base64(client_id:client_secret)
Content-Type: application/x-www-form-urlencoded

token=eyJraWQiOi…&token_type_hint=access_token

200 OK
{
  "active": true,
  "scope": "openid profile email",
  "client_id": "0oa…",
  "username": "user@example.com",
  "exp": 1760430000,
  "sub": "user@example.com",
  ...
}

검증은 다음 순서로 흐른다.

  1. 리소스 서버가 토큰을 IdP의 introspection 주소로 보내는데, 이 요청은 자격 증명으로 인증한다.
  2. IdP가 토큰의 서명, 만료, 취소 여부를 판정한다.
  3. IdP가 active 값과 claim을 돌려준다.
  4. active가 false면 리소스 서버가 요청을 거부한다.

active: false 응답은 이유를 알려 주지 않아서, 만료된 토큰, 취소된 토큰, IdP가 모르는 토큰이 모두 같은 응답을 받는다.

장점단점
취소가 바로 반영된다.요청마다 네트워크 호출이 생긴다. 지연이 늘고 IdP 부하가 커진다.
불투명 토큰에도 쓴다.IdP가 멈추면 검증도 실패한다.
리소스 서버가 토큰 형식을 몰라도 된다.리소스 서버에도 자격 증명이 필요하다.

5. 두 방식 비교

구분JWKSintrospection
판정하는 곳리소스 서버IdP
요청당 네트워크 호출없다. 키 캐시를 쓴다.있다.
취소 반영만료 시각까지 반영되지 않는다.바로 반영된다.
토큰 형식JWT만JWT와 불투명 토큰

JWKS만 쓰면서 access token 수명을 짧게 두는 경우도 많은데, 그러면 취소가 반영되지 않는 기간이 짧아진다.

6. 취소가 반영되는 시점

관리자가 토큰을 중간에 취소한 경우를 그림으로 비교한다.

7. IdP별 검증 방법

어느 방식을 쓸지는 토큰 형식과 코드가 정하고, 같은 IdP라도 코드에 따라 방식이 다르다.

IdPaccess token 형식검증 방법근거
OktaJWT우리 런타임은 introspection을 쓴다. JWT라서 JWKS로도 검증할 수 있다.런타임의 Okta 토큰 검증 코드
KeycloakJWT우리 런타임은 introspection을 쓴다. fastmcp가 제공하는 Keycloak provider는 JWKS를 쓴다.런타임의 Keycloak 토큰 검증 코드, fastmcp providers/keycloak.py:62

8. 우리 MCP 서버의 두 검증 지점

MCP 서버는 요청 하나에서 토큰을 두 번 검증하는데, 요청이 오면 프록시는 다음 순서로 일한다(fastmcp proxy.py:2135).

  1. fastmcp 토큰의 서명을 대칭키로 검증하고 exp, iss, aud도 본다(fastmcp jwt_issuer.py:232).
  2. fastmcp 토큰의 jti로 저장된 IdP 토큰을 찾는다.
  3. IdP 토큰을 Okta introspection으로 검증하는데, 검증 캐시에 결과가 있으면 그 결과를 쓴다.
  4. IdP 토큰에 required_scopes가 모두 있는지 본다.
  5. IdP 토큰의 만료가 30초 안으로 다가오면 IdP refresh token으로 새 IdP 토큰을 받는다. 30초는 런타임 기본값이다(런타임의 서버 코드).

fastmcp 토큰에 JWKS를 쓰지 않는 이유

fastmcp 토큰은 프록시가 발급하고 프록시가 검증한다. 발급자와 검증자가 같아서 공개키를 공개할 필요가 없으므로 대칭키(HS256)를 쓴다. 대칭키는 IdP 앱의 client_secret에서 만들고(런타임의 서버 코드), 저장소 암호화 키도 같은 client_secret에서 만든다.

검증 캐시

Okta introspection은 요청마다 네트워크 호출을 만들기 때문에 런타임은 검증 결과를 캐시에 둔다.

항목값근거
TTL 기본값60초. <접두사>_MCP_VERIFY_CACHE_TTL_SECONDS로 바꾼다.런타임의 설정 코드
TTL 상한토큰의 남은 수명보다 길어지지 않는다.런타임의 Okta 토큰 검증 코드
검증 캐시 위치<접두사>_MCP_REDIS_URL이 있으면 Redis를 쓴다. 없으면 프로세스 메모리를 쓴다.런타임의 서버 코드
Okta가 응답하지 않을 때검증 실패로 처리한다. 요청은 거부된다.런타임의 Okta 토큰 검증 코드

그 결과 IdP에서 토큰을 취소해도 최대 60초 동안은 요청이 통과할 가능성이 있다. 검증 캐시는 introspection의 지연과 JWKS의 취소 문제 사이에서 타협한 장치다.

9. 자가 점검 문제

먼저 답을 생각해 본 다음 펼쳐서 확인한다.

Q1. 관리자가 Okta에서 어떤 사용자의 access token과 refresh token을 모두 취소했다. 그 사용자의 MCP 클라이언트는 fastmcp 토큰을 아직 들고 있다. 요청은 언제 막히나?

fastmcp 토큰의 서명은 여전히 맞아서 8장 순서의 1단계는 통과한다. 하지만 프록시는 요청마다 IdP 토큰을 Okta introspection으로 다시 검증한다. 검증 캐시에 이전 결과가 남아 있는 동안은 통과하고, 캐시 항목의 TTL이 지나면 Okta가 active: false를 돌려준다. 프록시는 IdP 토큰 만료 30초 전부터만 갱신을 시도하므로 대개는 갱신하지 않고 요청을 거부한다. 그 구간에서 갱신을 시도해도 refresh token이 취소됐으므로 실패한다. 따라서 요청은 취소 뒤 최대 60초 안에 막힌다.

Q2. IdP가 몇 분 동안 응답하지 않는다. JWKS 방식과 introspection 방식의 리소스 서버는 각각 어떻게 되나?

JWKS 방식은 키 캐시의 공개키로 계속 검증하므로 새 kid가 나오기 전까지는 영향이 없다. introspection 방식은 검증 캐시에 없는 토큰을 검증하지 못하고, 우리 런타임은 이때 요청을 거부한다.

Q3. fastmcp 토큰을 JWKS로 검증하지 않는 이유는?

fastmcp 토큰은 프록시가 발급하고 같은 프록시가 검증한다. 공개키를 다른 서버에 나눠 줄 필요가 없어서 대칭키 하나로 충분하다.

Q4. IdP 앱의 client_secret을 바꾸면 이미 로그인한 사용자는 어떻게 되나?

프록시의 대칭키는 client_secret에서 만들기 때문에 client_secret이 바뀌면 대칭키도 바뀐다. 그래서 기존 fastmcp 토큰은 서명 검증에 모두 실패하고, 사용자는 다시 로그인해야 한다. 저장소 암호화 키도 바뀌므로 저장된 등록 정보를 읽지 못할 가능성이 있다. 이 답은 코드만 읽고 추정한 것이고, 실행해서 시험하지는 않았다.

Q5. introspection 요청에 자격 증명이 필요한 이유는?

아무나 토큰을 넣어서 유효한지 알아내면 안 되기 때문이다. 인증이 없으면 공격자가 추측한 토큰 값을 대량으로 시험할 수 있는데, RFC 7662는 이 공격을 token scanning이라고 부른다.

Q6. JWKS 방식에서 access token 수명을 짧게 하면 무엇이 좋아지고 무엇이 나빠지나?

취소가 반영되지 않는 기간이 짧아진다. 대신 클라이언트가 토큰을 더 자주 갱신해야 하고, 갱신 요청이 늘면 IdP 부하도 늘어난다.
