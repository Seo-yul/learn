ID-JAG

OAuth 학습 5편 · 2026-11-12 작성 · 2026-11-18 보완

IdP가 발급하는 ID-JAG로 여러 MCP 서버의 로그인을 한 번으로 줄이는 방법을 정리했다.

한 문장 요약

ID-JAG는 IdP가 서명한 수명이 짧은 JWT다. MCP 클라이언트가 이 JWT를 MCP 인가 서버에 내고 access token을 받는 방식이라서, 브라우저 로그인은 IdP에서 한 번만 하면 된다.

2026-11-18 보완 요약
  • 14.3절에 다섯 번째 전제 조건을 더했다. MCP 런타임이 backend API에 보낼 토큰을 따로 얻어야 한다는 조건이다.
  • 같은 내용을 용어집, 14.4절 추천 표, 14.5절 PoC 순서, 15장 Q12에도 반영했다.
  • 지금 흐름과 ID-JAG의 비교는 6편에서 그림으로 다룬다.

1. 문제: 서버마다 반복되는 로그인초급

MCP 클라이언트는 MCP 서버마다 OAuth 흐름을 따로 거치는데, 기본 흐름은 다음과 같다(1편).

  1. MCP 서버가 401 응답을 준다.
  2. MCP 클라이언트가 Protected Resource Metadata에서 MCP 인가 서버를 찾는다.
  3. MCP 클라이언트가 DCR이나 CIMD로 MCP 인가 서버에 자기를 등록한다.
  4. MCP 클라이언트가 브라우저를 열어 사용자를 MCP 인가 서버로 보낸다.
  5. 사용자가 IdP에 로그인하고 동의 화면에서 허용한다.
  6. MCP 클라이언트가 authorization code를 access token으로 바꾼다.

MCP 서버가 세 개면 이 흐름도 세 번 일어나고, 세 서버가 같은 IdP를 써도 마찬가지다. IdP 세션이 남아 있으면 IdP가 비밀번호를 다시 묻지는 않지만, 브라우저 이동과 동의 화면은 서버마다 반복된다.

서버마다 따로 받는 이유

access token은 한 MCP 서버 앞으로 발급되고, 토큰의 aud에 그 서버가 들어 있다(4편 4장). MCP 권한 스펙은 MCP 서버가 자기 앞으로 발급된 토큰만 받도록 요구하고, 받은 토큰을 다른 서버로 그대로 넘기는 일(token passthrough)도 금지한다.

그래서 서버 A의 access token을 서버 B에 쓰면 안 된다. 그렇게 쓰면 토큰 하나가 샐 때 그 사용자의 모든 MCP 서버가 열린다.

ID-JAG는 이 규칙을 지키면서 반복을 줄인다. 사용자는 로그인을 한 번만 하고, access token은 여전히 서버마다 따로 받는다.

2. ID-JAG 한눈에 보기초급

ID-JAG 흐름은 세 단계로 나뉜다.

  1. SSO: 사용자가 MCP 클라이언트에서 IdP에 로그인하고, MCP 클라이언트는 ID token을 받는다.
  2. token exchange: MCP 클라이언트가 ID token을 IdP에 내고 서버 A용 ID-JAG를 받는다.
  3. JWT bearer grant: MCP 클라이언트가 ID-JAG를 서버 A의 MCP 인가 서버에 내면, 인가 서버가 access token을 준다.

대화형 로그인은 1단계에만 있고, 2단계와 3단계는 백채널 요청이다. 서버 B와 C에는 2단계와 3단계만 반복하면 된다.

비유

회사 건물 출입에 비유하면 다음과 같다.

  • 사원증은 ID token이고, 직원은 출근할 때 사원증을 한 번 받는다.
  • 안내 데스크는 IdP다. 사원증을 보고 B동 방문증을 써 주는데, 이 방문증이 ID-JAG다.
  • B동 경비실은 MCP 인가 서버다. 방문증을 확인하고 B동 출입 카드를 주는데, 이 카드가 access token이다.
  • 방문증에는 B동 이름과 짧은 유효 시간이 적혀 있어서 C동에서는 쓸 수 없다.

안내 데스크는 회사 규칙도 확인하는데, 이 직원이 B동에 들어가도 되는지를 정하는 것이 IdP의 정책이다.

부분뜻
Identity Assertion사용자가 IdP에 로그인했다는 증명을 근거로 한다.

정리하면 ID-JAG는 authorization code 자리에 들어가는 서명된 JWT다. authorization code는 브라우저를 거쳐 오지만, ID-JAG는 IdP가 백채널로 준다.

3. 등장인물과 신뢰 관계초급

같은 역할을 문서마다 다른 이름으로 부르기 때문에, 아래 표로 이름을 맞춰 둔다.

이 문서의 이름IETF 초안Okta 문서예
MCP 클라이언트Clientrequesting app에이전트, IDE
IdPIdP Authorization ServerIdPOkta, PingFederate
MCP 인가 서버Resource Authorization Serverresource authorization serverfastmcp OAuthProxy
MCP 서버Resource Serverresource appMCP endpoint

ID-JAG가 동작하려면 다음 세 신뢰 관계가 미리 있어야 한다.

  1. MCP 클라이언트는 IdP에 등록된 앱이라서 IdP가 이 클라이언트를 인증할 수 있다.
  2. MCP 인가 서버는 IdP를 신뢰하고, IdP의 issuer와 JWKS를 설정으로 가진다.
  3. IdP는 MCP 클라이언트와 MCP 인가 서버의 연결을 안다. 이 연결은 관리자가 정책으로 만든다.

세 관계는 모두 관리자가 미리 만든다. 그래서 처음 보는 MCP 서버에는 ID-JAG를 쓸 수 없는데, IdP가 그 서버의 인가 서버를 모르기 때문이다.

4. 1단계: SSO중급

MCP 클라이언트는 IdP의 OIDC 로그인으로 사용자를 인증하는데, 이 흐름은 일반 authorization code 흐름과 같다. 로그인이 끝나면 MCP 클라이언트는 다음 값을 받는다.

값쓰임
ID token2단계의 subject token이다. aud는 IdP에 등록된 MCP 클라이언트의 client_id다.
refresh token선택이다. ID token이 만료된 뒤 새 ID-JAG를 받을 때 subject token으로 쓴다. IdP에 따라 offline_access scope가 필요하다.
access tokenIdP 자체 API용이다. MCP 서버에는 쓰지 않는다.

SAML로 로그인하는 클라이언트도 있는데, 이런 클라이언트는 SAML assertion을 IdP의 refresh token으로 바꾼 뒤 2단계로 간다.

MCP 클라이언트는 ID token을 MCP 서버에 보내면 안 된다. ID token의 aud는 MCP 클라이언트이므로 MCP 서버는 이 값을 거부해야 한다(4편 4장).

IdP는 이 단계에서 MFA 같은 로그인 규칙을 적용하고, 2단계와 3단계에서는 사용자가 아무것도 하지 않는다.

5. 2단계: token exchange중급

MCP 클라이언트는 IdP의 token endpoint에 다음 요청을 보낸다. 예시의 주소와 값은 설명용이다.

POST /oauth2/token HTTP/1.1
Host: idp.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&requested_token_type=urn:ietf:params:oauth:token-type:id-jag
&audience=https://mcp-a.example.com
&resource=https://mcp-a.example.com/mcp
&scope=calendar.read
&subject_token=eyJraWQiOiJzMTZ0cVNt...
&subject_token_type=urn:ietf:params:oauth:token-type:id_token
&client_id=agent-app
&client_secret=...
파라미터필수 여부값과 뜻
grant_type필수token exchange를 뜻하는 URN
requested_token_type필수urn:ietf:params:oauth:token-type:id-jag. ID-JAG를 달라는 뜻이다.
audience필수MCP 인가 서버의 issuer 식별자. 값은 하나만 넣는다.
resource권장MCP 서버의 resource 식별자. MCP 확장 스펙은 이 값을 넣는다면 MCP 서버의 식별자여야 한다고 정한다.
scope선택원하는 scope. IdP 정책이 범위를 줄일 수 있다.
subject_token필수1단계에서 받은 ID token. IdP가 허용하면 refresh token도 된다.
subject_token_type필수subject token의 종류를 뜻하는 URN. id_token, refresh_token, saml2 중 하나다.
client_id, client_secret필수IdP에 등록된 MCP 클라이언트의 자격. IdP는 클라이언트를 반드시 인증한다.

IdP의 처리 순서

IdP는 다음 순서로 요청을 처리한다(초안 4.3.3절).

  1. MCP 클라이언트를 인증한다. 실패하면 invalid_client로 거부한다.
  2. subject token이 자기가 발급한 값인지 확인한다.
  3. ID token의 aud가 인증한 클라이언트인지 확인한다.
  4. audience가 하나인지 확인한다.
  5. audience가 신뢰하는 MCP 인가 서버인지 확인한다.
  6. 정책을 평가해서 이 사용자가 이 클라이언트로 이 서버를 써도 되는지 본다.
  7. 허용한 scope와 resource를 담아 ID-JAG를 서명한다.

응답

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "issued_token_type": "urn:ietf:params:oauth:token-type:id-jag",
  "access_token": "eyJ0eXAiOiJvYXV0aC1pZC1qYWcrand0Ii...",
  "token_type": "N_A",
  "scope": "calendar.read",
  "expires_in": 300
}

issued_token_type은 받은 값이 ID-JAG라는 뜻이다. ID-JAG 값이 access_token 필드에 들어 있는 것은 RFC 8693의 응답 형식이 이 필드 이름을 쓰기 때문이다. token_type은 N_A인데, 이 값으로 API를 부를 수 없다는 뜻이다.

필드 이름이 access_token이어도 ID-JAG는 access token이 아니므로, MCP 클라이언트는 이 값을 MCP 서버의 Authorization 헤더에 넣으면 안 된다.

오류

오류뜻
invalid_clientMCP 클라이언트 인증에 실패했다.
invalid_request요청 형식이 틀렸다. audience가 둘 이상인 경우도 여기에 든다. 초안 -06부터는 잘못된 subject token도 이 오류다.

insufficient_user_authentication더 강한 로그인이 필요하다. 10.6절에서 다룬다.

6. ID-JAG의 구조중급

ID-JAG를 디코딩하면 다음과 같다. 값은 설명용이다.

// header
{ "typ": "oauth-id-jag+jwt", "alg": "RS256", "kid": "idp-key-1" }

// payload
{
  "iss": "https://idp.example.com",
  "sub": "00u1abcd",
  "aud": "https://mcp-a.example.com",
  "resource": "https://mcp-a.example.com/mcp",
  "client_id": "agent-at-mcp-a",
  "scope": "calendar.read",
  "jti": "9e43f81b64a33f20",
  "iat": 1794000000,
  "exp": 1794000300,
  "email": "user@example.com"
}

IETF 초안 3.1절은 claim을 다음과 같이 정한다.

claim필수 여부뜻
typ (헤더)필수oauth-id-jag+jwt. 다른 JWT와 구분하는 값이다.
iss필수IdP의 issuer 식별자
sub필수사용자 식별자. IdP가 MCP 인가 서버 단위로 고른다(10.7절).
aud필수MCP 인가 서버의 issuer 식별자
client_id필수MCP 인가 서버에 등록된 MCP 클라이언트의 client_id. IdP에서 쓰는 client_id와 다를 수 있다.
jti필수이 ID-JAG의 고유 ID. replay를 막는 데 쓴다.

이 가운데 중요한 claim은 aud와 client_id다. aud는 이 ID-JAG를 받을 MCP 인가 서버를 정하고, client_id는 이 ID-JAG를 낼 클라이언트를 정한다.

7. 3단계: JWT bearer grant중급

MCP 클라이언트는 ID-JAG를 MCP 인가 서버의 token endpoint에 낸다.

POST /token HTTP/1.1
Host: mcp-a.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&assertion=eyJ0eXAiOiJvYXV0aC1pZC1qYWcrand0Ii...
&client_id=agent-at-mcp-a
&client_secret=...
&resource=https://mcp-a.example.com/mcp

ID-JAG는 assertion 파라미터에 넣고, 요청은 authorization code를 교환하는 token endpoint와 같은 주소로 보낸다.

MCP 인가 서버의 검증 순서

MCP 인가 서버는 다음 순서로 ID-JAG를 검증한다(초안 4.4.1절). 5번과 8번은 초안이 선택으로 둔 단계다.

  1. 헤더의 typ가 oauth-id-jag+jwt인지 확인한다.
  2. iss가 신뢰하는 IdP인지 확인한다. 아니면 invalid_grant로 거부한다.
  3. IdP의 JWKS로 서명을 검증한다. 허용한 알고리즘만 쓴다.
  4. aud가 자기 issuer 식별자인지 확인한다.
  5. exp를 확인한다. 수명이 정책보다 길면 거부한다.
  6. 요청한 클라이언트를 인증하고 client_id와 같은지 확인한다.
  7. resource가 자기가 맡은 MCP 서버인지 확인한다.
  8. jti를 기록한다. 같은 값이 다시 오면 거부한다.
  9. sub로 사용자를 찾는다.
  10. 허용할 scope를 정하고 access token을 발급한다.

서명을 먼저 검증하는 이유는 4편과 같은데, 서명이 맞아야 claim의 내용을 믿을 수 있기 때문이다.

응답과 refresh token

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "token_type": "Bearer",
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "expires_in": 300,
  "scope": "calendar.read"
}

MCP 인가 서버는 원칙적으로 refresh token을 주지 않고, 초안도 이를 SHOULD NOT으로 정한다. ID-JAG가 refresh token의 역할을 대신하기 때문이다.

access token이 만료되면 MCP 클라이언트는 다음 순서로 새 값을 받는다.

  1. 가진 ID token이나 IdP refresh token으로 2단계를 다시 한다.
  2. 새 ID-JAG로 3단계를 다시 한다.
  3. subject token도 모두 만료됐다면 사용자를 다시 로그인시킨다.

이 구조에서는 IdP가 세션의 수명을 정한다. 반대로 MCP 인가 서버가 refresh token을 주면 IdP가 세션을 끊어도 접근이 남는다.

8. discovery와 metadata중급

각 참여자는 metadata로 ID-JAG 지원을 알린다.

누가어디에필드와 값
MCP 인가 서버인가 서버 metadata (RFC 8414)grant_types_supported에 jwt-bearer grant URN을 넣는다. authorization_grant_profiles_supported에 urn:ietf:params:oauth:grant-profile:id-jag를 넣는다.
IdPIdP metadataidentity_chaining_requested_token_types_supported에 urn:ietf:params:oauth:token-type:id-jag를 넣는다. 서명 알고리즘 목록 id_jag_signing_alg_values_supported는 선택이다.
MCP 클라이언트DCR 요청이나 CIMDauthorization_grant_profiles_supported에 ID-JAG profile을 넣는다.

MCP 인가 서버가 grant type과 profile을 따로 알리는 것은 jwt-bearer grant가 ID-JAG가 아닌 용도에도 쓰이기 때문이다. profile을 알린 서버도 아무 IdP나 받지는 않고, 어떤 IdP와 클라이언트를 받을지는 MCP 인가 서버의 설정이 정한다.

MCP 확장

MCP는 이 흐름을 공식 확장으로 정했고, 확장 이름은 Enterprise-Managed Authorization이다.

  • 확장 식별자는 io.modelcontextprotocol/enterprise-managed-authorization이다.
  • SEP-990에서 시작했고, 2026-07-28 판이 stable 단계다.
  • MCP 클라이언트는 요청의 _meta에 이 확장을 지원한다고 적는다.
  • MCP 서버는 인가 metadata에 이 확장을 요구한다고 적는다.
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "...",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/clientCapabilities": {
        "extensions": {
          "io.modelcontextprotocol/enterprise-managed-authorization": {}
        }
      }
    }
  }
}

MCP 서버가 이 확장을 요구하면 MCP 클라이언트는 사용자를 authorize endpoint로 보내지 않아야 하고, 대신 2단계와 3단계를 한다.

MCP 인가 서버를 고르는 방법

기본 MCP 흐름에서 MCP 클라이언트는 MCP 서버가 알려 준 인가 서버를 따른다. MCP Python SDK의 ID-JAG 클라이언트는 이와 다르게 MCP 인가 서버의 issuer를 설정으로 받는다(13장).

그래서 MCP 서버가 다른 인가 서버를 알려 줘도 SDK는 ID-JAG와 비밀 값을 그쪽으로 보내지 않는다. 악성 MCP 서버가 ID-JAG를 가로채는 것을 막는 설계다.

게이트웨이 방식과의 차이

게이트웨이 방식은 MCP 서버 여러 개를 한 MCP 주소 뒤에 두고, MCP 클라이언트는 게이트웨이 하나에만 로그인한다. 게이트웨이가 뒤쪽 서버마다 토큰을 바꿔서 보낸다. 이 방식은 IdP의 ID-JAG 기능이 필요 없지만, 게이트웨이가 모든 접근의 관문이 된다.

ID-JAG는 MCP 서버의 구성을 그대로 두고, 대신 IdP가 서버마다 접근을 정한다.

10. 보안 설계고급

ID-JAG는 누가 발급했는지, 누가 낼 수 있는지, 어디에 쓸 수 있는지의 세 가지를 하나의 서명으로 묶는다.

10.1 받는 쪽 묶기: aud와 resource

aud는 MCP 인가 서버를 정하고, resource는 그 인가 서버가 맡은 MCP 서버를 정한다. 초안 9.4절은 한 ID-JAG를 다른 MCP 인가 서버에 다시 쓰지 못하게 하고, MCP 확장 스펙은 access token도 resource의 MCP 서버로 묶으라고 요구한다.

10.2 내는 쪽 묶기: client_id와 클라이언트 인증

client_id claim은 ID-JAG를 낼 수 있는 클라이언트를 정하고, MCP 인가 서버는 요청한 클라이언트를 인증한 뒤 이 값과 비교한다. 클라이언트 인증이 없으면 훔친 ID-JAG를 누구나 낼 수 있어서, 초안 4.4절은 다음 둘 중 하나를 요구한다.

  • 클라이언트 인증. MCP 클라이언트가 confidential client여야 한다.
  • sender-constrained ID-JAG. IdP가 cnf claim에 DPoP 키(jkt)나 mTLS 인증서(x5t#S256)를 묶는다.

MCP 인가 서버는 둘 다 없는 요청을 invalid_client로 거부해야 한다.

10.3 replay와 수명

ID-JAG는 수명이 짧고, 초안과 MCP 확장 스펙의 예시 수명은 300초다. MCP 인가 서버는 jti를 기록해서 같은 ID-JAG를 한 번만 받을 수 있는데, 수명이 짧으면 기록해 둘 jti도 적다.

10.4 typ로 종류 구분하기

ID token과 ID-JAG는 같은 IdP가 같은 키로 서명할 수 있어서 서명만으로는 둘을 구분하지 못한다. typ 검사가 없으면 공격자가 ID token을 ID-JAG처럼 낼 가능성이 있다. aud 검사도 이 공격을 막지만, typ는 종류 자체를 한 번 더 막는다.

10.5 subject token 보관

MCP 클라이언트가 가진 ID token과 IdP refresh token은 가치가 크다. 이 값이 있으면 허용된 모든 MCP 서버의 ID-JAG를 받을 수 있기 때문이다. 초안 9.2절은 MCP 클라이언트에게 다음을 권한다.

  • 저장할 때 암호화한다.
  • 클라이언트의 비밀 값과 따로 둔다.
  • 로그에 남기지 않는다.
  • 사용자 세션 단위로 두고, 필요가 없어지면 버린다.
  • ID-JAG를 캐시하지 않고 필요할 때 새로 받는다.

10.6 step-up 인증

민감한 MCP 서버에는 더 강한 로그인을 요구할 수 있다. 이때 IdP가 2단계에서 insufficient_user_authentication 오류를 주면, MCP 클라이언트는 사용자를 다시 로그인시킨 뒤 2단계를 다시 한다.

10.7 사용자 식별

IdP는 sub를 MCP 인가 서버 단위로 고르기 때문에, 같은 사용자는 어느 클라이언트가 요청해도 같은 sub를 받는다. 그래서 ID-JAG의 sub는 MCP 클라이언트가 받은 ID token의 sub와 다를 수 있는데, 서비스마다 다른 식별자(pairwise)를 주는 IdP가 그런 경우다.

MCP 인가 서버는 sub를 주 식별자로 써야 하고, email은 기존 계정과 처음 연결할 때만 보조로 쓴다.

10.8 아직 정해지지 않은 부분

MCP 확장 스펙의 보안 검토(ext-auth PR #12)는 다음 빈 곳을 지적했다.

  • 이미 발급한 access token과 ID-JAG를 취소하는 방법을 정하지 않았다.
  • 서버마다 scope 이름이 겹칠 수 있다.
  • ID-JAG replay를 막는 대책이 더 필요하다.

IdP 정책은 연결 단위로 동작하고, IdP는 MCP 요청 자체를 보지 못한다. 그래서 tool 단위 검사는 MCP 서버가 따로 해야 한다.

11. 운영 고려 사항고급

11.1 재교환 비용

refresh token이 없으므로 access token이 만료될 때마다 IdP에 한 번, MCP 인가 서버에 한 번씩 요청이 두 번 생긴다. 예를 들어 access token 수명이 5분이면 서버 하나에 한 시간에 12번 재교환하고, 서버 3개를 2시간 쓰면 ID-JAG를 72개 받는다.

11.2 IdP의 발급 한도

IdP는 ID-JAG 발급에 한도나 요금을 둘 수 있다. MCP 공식 문서의 지원 표에 따르면 Okta는 Okta SSO 기본 기능으로 ID-JAG를 발급하지만, 사용자 한 명, resource app 하나에 월 250개까지다. 그보다 많이 쓰려면 Okta for AI Agents가 필요하다.

access token 수명이 5분이면 한 서버를 한 달에 약 20시간만 연속으로 쓸 수 있는데, 250을 12로 나누면 약 20.8이기 때문이다. access token 수명을 늘리면 발급 수가 줄지만, IdP에서 접근을 막아도 그 수명 동안은 접근이 남는다.

한도와 요금은 벤더 정책이라 바뀔 수 있으므로, 도입 전에 IdP의 계약 조건을 다시 확인해야 한다.

11.3 서버 인스턴스가 여러 개일 때

MCP 인가 서버가 jti 기록을 프로세스 메모리에 두면 인스턴스끼리 기록을 나누지 않아서, 같은 ID-JAG가 인스턴스마다 한 번씩 통과할 가능성이 있다. ID-JAG의 수명이 짧으면 이 위험이 있는 기간도 짧지만, 위험을 없애려면 jti 기록을 Redis 같은 공유 저장소에 둬야 한다.

11.4 client_id 대응 관리

ID-JAG의 client_id는 MCP 인가 서버에 등록된 값이라서, IdP가 이 값을 알아야 ID-JAG를 만들 수 있다. 초안 5절은 두 방법을 든다.

  • 관리자가 클라이언트별, MCP 인가 서버별 client_id 대응을 IdP에 미리 등록한다.
  • CIMD를 쓴다. client_id가 클라이언트 metadata 문서의 URL이라서 모든 서버에서 같은 값이다.

DCR로 서버마다 무작위 client_id를 받는 클라이언트에는 첫 번째 방법을 쓰기 어려운데, IdP가 그 값을 미리 알 수 없기 때문이다.

11.5 MCP 인가 서버 등록

IdP는 신뢰하는 MCP 인가 서버만 audience로 받기 때문에, 관리자는 MCP 인가 서버를 IdP에 하나씩 등록해야 한다. MCP 서버를 자주 새로 만드는 환경에서는 이 등록이 운영 부담이 되므로 등록을 자동화하는 방법이 필요하다(14장).

12. 실무 적용: fastmcp 서버고급

fastmcp 4.0 이상의 OAuthProxy에는 ID-JAG를 받는 기능이 있는데, 아직 beta 단계다. 이 장의 내용은 fastmcp 4.0.3 소스를 읽고 확인했다.

from fastmcp.server.auth import OAuthProxy, IdentityAssertion

auth = OAuthProxy(
    ...,  # upstream IdP 설정은 그대로 둔다

토큰 검증ID-JAG로 받은 access token은 upstream 토큰 없이 그 자체로 검증한다.proxy.py:2159
취소취소한 access token의 jti를 프로세스 메모리에 둔다.proxy.py:2339

파일 경로의 기준은 fastmcp/server/auth/이고, proxy.py는 그 아래 oauth_proxy/에 있다.

클라이언트 인증

fastmcp 프록시에 등록된 클라이언트는 모두 public client이고, 프록시는 클라이언트의 비밀 값을 저장하지 않는다. 그래서 JWT bearer grant에서도 client_id만 확인하고, 클라이언트가 비밀 값을 보내도 검사하지 않는다(auth.py:83, MCP SDK client_auth.py:92).

fastmcp는 신뢰하는 IdP가 서명한 ID-JAG를 인가의 근거로 본다. 반면 초안 4.4절은 클라이언트 인증이나 sender-constrained ID-JAG를 요구하므로, 도입 전에 이 차이를 검토해야 한다.

등록된 클라이언트와 grant type

OAuthProxy는 DCR로 등록한 클라이언트에 jwt-bearer grant를 자동으로 더한다(proxy.py:1053). upstream IdP 앱의 client_id로 오는 클라이언트도 받는데, 이때 프록시는 등록 없이 클라이언트 정보를 만들고 jwt-bearer grant를 넣는다(proxy.py:955).

13. 실무 적용: MCP SDK 클라이언트고급

MCP Python SDK 2.2.0에는 3단계를 맡는 클라이언트가 있고, 이름은 IdentityAssertionOAuthProvider다. fastmcp 4.0.3의 클라이언트 모듈에는 이런 기능이 없다.

from mcp.client.auth.extensions.identity_assertion import (
    IdentityAssertionOAuthProvider,
)

async def fetch_id_jag(audience: str, resource: str) -> str:
    # 2단계: IdP에 token exchange를 보내고 ID-JAG를 돌려준다
    return await idp.exchange_for_id_jag(
        subject_token=user_id_token, audience=audience, resource=resource
    )

auth = IdentityAssertionOAuthProvider(
    server_url="https://mcp-a.example.com/mcp",
    storage=token_storage,
    client_id="agent-at-mcp-a",
    client_secret="...",
    issuer="https://mcp-a.example.com",
    assertion_provider=fetch_id_jag,
)

idp.exchange_for_id_jag는 설명용 이름이고, SDK에 없는 함수다.

특징내용
맡는 범위3단계만 맡는다. 1단계와 2단계는 assertion_provider 콜백이 맡는다.
인가 서버 선택issuer를 설정으로 받는다. Protected Resource Metadata와 DCR을 쓰지 않는다.
클라이언트 종류client_secret이 필수다. confidential client만 지원한다.
재교환 시점401 응답을 받으면 새 ID-JAG로 다시 교환한다. 403 insufficient_scope를 받으면 scope를 더해서 교환한다.
토큰 보관받은 access token을 storage에 저장한다.

SDK 문서는 2단계가 배포 환경마다 다르다고 설명한다. 그래서 SDK는 2단계를 만들지 않고, 2단계 요청은 MCP 클라이언트가 직접 구현해야 한다. 이 SDK 클라이언트를 fastmcp 프록시에 붙이면 SDK가 보내는 client_secret은 검사되지 않는다(12장).

14. 실무 적용: 우리 플랫폼고급

이 장은 우리 플랫폼에 ID-JAG를 넣는다고 가정하고 정리한 내용이고, 정해진 설계가 아니라 추천이다. 코드 근거는 2026-11-12에 받은 core와 MCP 런타임의 코드다. 14.3절 5번 조건과 그 관련 내용은 2026-11-18에 더했는데, 근거는 그때의 MCP 런타임 코드다.

14.1 역할 대응

14.2 지금 구조와 달라지는 점

core는 토큰을 사용자와 서버 URL의 조합으로 저장하는데, 이 저장 방식은 그대로 쓸 수 있다. 새로 필요한 것은 사용자별 subject token 하나다. core가 사용자의 Okta refresh token을 한 번 받아 두고, 서버별 access token은 이 값으로 ID-JAG를 받아서 얻는다.

ID-JAG에서 공유하는 것은 사용자의 로그인이고, 서버별 access token은 공유하지 않는다. 이 점에서 "사용자 키로 토큰 하나를 여러 서버에 쓰는 방식"과 다르다. 그 방식의 문제는 6편 7장에서 다룬다.

14.3 전제 조건

ID-JAG를 넣으려면 다음 다섯 조건이 필요하다.

  1. core가 사용자의 Okta identity assertion을 가져야 한다. 플랫폼 로그인 IdP가 Okta가 아니면 사용자는 Okta에 한 번 따로 로그인해야 한다.
  2. 관리자가 Okta에서 ID-JAG 발급을 켜고, MCP 인가 서버마다 연결과 정책을 만들어야 한다.
  3. MCP 런타임이 OAuthProxy에 identity_assertion 설정을 넘겨야 하는데, 지금 런타임에는 이 설정이 없다.
  4. core가 2단계 요청과 3단계 클라이언트를 붙여야 한다.
  5. 토큰 전달을 쓰는 MCP 서버는 backend API에 보낼 토큰을 따로 얻어야 한다. ID-JAG로 발급한 access token에는 upstream 토큰이 없기 때문이다.

지금 흐름에서 MCP 런타임은 backend API를 부를 때 Authorization 헤더에 upstream 토큰을 넣는다. 이 토큰 전달은 backend가 Bearer 인증을 쓰고 토큰 전달 설정이 켜졌을 때만 일어난다.

fastmcp는 ID-JAG로 발급한 access token을 검증할 때 upstream 토큰을 찾지 않고, 받은 토큰을 그대로 돌려준다(proxy.py:2159). 그래서 MCP 런타임은 backend API에 OAuthProxy가 서명한 토큰을 보내게 되고, IdP가 발급한 토큰을 검증하는 backend API는 이 토큰을 거부할 가능성이 높다.

이 내용은 코드를 읽은 결과이고, 실행해서 확인하지는 않았다. backend 토큰을 얻는 방법의 후보는 6편 9장에 있다.

14.4 정해야 할 것과 추천

항목추천이유
위임 scope처음에는 ID-JAG로 받은 토큰에 위임 scope를 주지 않는다. IdP가 준 scope를 위임 scope로 인정할 규칙은 나중에 따로 정한다.지금 런타임은 동의 화면을 거친 토큰만 위임 scope를 인정한다. ID-JAG 토큰에는 이 표시가 없으므로 scope가 걸린 tool은 막힌다. 동의 없이 tool이 열리지 않으므로 안전한 기본값이다.
audience스펙대로 MCP 인가 서버마다 자기 issuer를 쓴다.fastmcp에는 공통 audience 설정(IdentityAssertion.audience)도 있다. 공통 값을 쓰면 서버 구분을 resource claim 하나에 맡긴다. 초안 9.4절은 한 ID-JAG를 다른 인가 서버에 쓰지 못하게 한다.
client_id플랫폼 에이전트용 고정 client_id를 정한다. CIMD URL을 먼저 검토한다.DCR의 무작위 client_id는 IdP가 미리 알 수 없다. CIMD URL은 모든 서버에서 같은 값이다. CIMD 클라이언트는 private_key_jwt로 인증하므로 12장의 클라이언트 인증 차이도 줄일 가능성이 있다.
access token 수명Okta 한도와 접근 차단 지연 사이에서 정한다.5분이면 한도에 빨리 닿는다(11.2절). 수명이 길면 IdP에서 막은 접근이 늦게 끊긴다.
jti 기록인스턴스가 둘 이상이면 공유 저장소를 검토한다.fastmcp는 jti를 프로세스 메모리에 둔다(11.3절).
기존 흐름authorization code 흐름과 동의 화면을 그대로 둔다.ID-JAG를 지원하지 않는 외부 MCP 클라이언트가 많을 가능성이 있다. 두 흐름은 한 OAuthProxy에서 함께 동작한다.
backend 토큰처음에는 토큰 전달을 쓰지 않는 MCP 서버에만 ID-JAG를 켠다. 토큰 전달을 쓰는 서버는 authorization code 흐름만 쓴다.토큰 전달을 쓰지 않는 서버는 backend API에 upstream 토큰을 보내지 않는다. 그래서 ID-JAG 토큰만으로 동작한다. 토큰 전달을 쓰는 서버가 backend 토큰을 얻는 방법은 아직 정하지 않았다(14.3절 5번).

14.5 PoC 순서 추천

검증은 다음 순서를 추천한다. 가짜 IdP를 쓰면 Okta 설정 없이 1번부터 6번까지 확인할 수 있다.

  1. RSA 키로 ID-JAG를 서명하는 가짜 IdP를 만들고, JWKS와 discovery 문서도 공개한다.
  2. 런타임 OAuthProxy에 identity_assertion을 켜고 MCP 서버 세 개를 띄운다.
  3. core 쪽에 2단계 요청과 IdentityAssertionOAuthProvider를 붙이고, 로그인 한 번으로 세 서버를 쓰는지 본다.
  4. 다른 서버의 aud, 이미 쓴 jti, 다른 client_id, 다른 resource를 넣어 거부 사례를 확인한다.
  5. 위임 scope가 걸린 tool이 어떻게 보이는지 확인한다.
  6. 토큰 전달을 쓰는 MCP 서버에서 ID-JAG 토큰으로 tool을 부르고, backend API가 받는 Authorization 헤더 값을 확인한다.
  7. Okta 테스트 org에서 ID-JAG 발급 설정과 한도를 확인한다.

15. 자가 점검 문제

먼저 답을 생각해 본 다음 펼쳐서 확인한다.

Q1. MCP 서버 세 개가 같은 Okta를 쓴다. 기본 흐름에서 브라우저 로그인은 몇 번 일어나나? 그 이유는?

세 번 일어난다. MCP 서버마다 자기 MCP 인가 서버가 있고, access token은 서버마다 따로 발급되기 때문이다. Okta 세션이 남아 있으면 비밀번호 입력은 한 번으로 끝날 수도 있지만, 브라우저 이동과 동의 화면은 세 번 반복된다.

Q2. ID-JAG의 aud에는 무엇이 들어가나? MCP 서버의 주소인가?

MCP 인가 서버의 issuer 식별자가 들어가고, MCP 서버의 resource 식별자는 resource claim에 들어간다.

Q3. token exchange 응답의 token_type이 N_A인 이유는?

ID-JAG는 access token이 아니기 때문이다. ID-JAG는 3단계에서 access token을 받는 근거로만 쓰고, 이 값으로 MCP 서버를 부를 수는 없다.

Q4. MCP 클라이언트가 1단계에서 받은 ID token을 MCP 서버에 직접 보냈다. 무슨 일이 생겨야 정상인가?

MCP 서버가 거부해야 정상이다. ID token의 aud는 MCP 클라이언트이고, ID token은 2단계의 subject token으로 IdP에만 보내는 값이다.

Q5. 공격자가 클라이언트 X의 ID-JAG를 훔쳤다. 공격자는 자기 클라이언트 Y의 자격으로 MCP 인가 서버에 이 값을 냈다. 결과는?

거부된다. ID-JAG의 client_id는 X인데 인증된 클라이언트는 Y라서, MCP 인가 서버가 invalid_grant로 거부한다.

Q6. 서버 A용 ID-JAG를 서버 B의 MCP 인가 서버에 냈다. 결과는?

거부된다. ID-JAG의 aud는 A의 issuer 식별자라서, B의 MCP 인가 서버는 aud가 자기 issuer가 아닌 이 값을 받지 않는다.

Q7. access token이 만료됐다. MCP 인가 서버는 refresh token을 주지 않았다. MCP 클라이언트는 어떻게 해야 하나?

가진 ID token이나 IdP refresh token으로 2단계를 다시 하고, 그다음 새 ID-JAG로 3단계를 다시 해야 한다. subject token도 모두 만료됐다면 사용자를 다시 로그인시킨다.

Q8. 관리자가 Okta에서 한 사용자의 MCP 서버 접근을 막았다. 이미 발급된 access token은 어떻게 되나?

만료될 때까지 쓸 수 있다. fastmcp의 기본 수명은 300초이고, 그 뒤에는 IdP가 새 ID-JAG를 거부하므로 접근이 끊긴다.

Q9. fastmcp MCP 서버를 인스턴스 세 개로 띄웠다. 공격자가 같은 ID-JAG를 짧은 시간에 세 번 냈다. 몇 번 통과할 가능성이 있나?

세 번까지 통과할 가능성이 있다. fastmcp는 jti 기록을 프로세스 메모리에 두기 때문에, 요청이 인스턴스마다 한 번씩 가면 각 인스턴스가 처음 보는 jti로 판단한다.

Q10. 우리 런타임에서 identity_assertion만 켜면 위임 scope가 걸린 tool을 쓸 수 있나?

코드를 읽은 결과로는 쓸 수 없다. 런타임은 동의 화면을 거친 토큰에만 위임 scope를 인정하는데, ID-JAG로 받은 토큰에는 그 표시가 없어서 위임 scope가 비어 있다.

Q11. Okta 한도가 사용자 한 명, resource app 하나에 월 250개다. access token 수명은 5분이다. 한 서버를 한 달에 몇 시간 연속으로 쓸 수 있나?

약 20시간이다. 5분 수명이면 한 시간에 ID-JAG를 12개 받는다. 250을 12로 나누면 약 20.8이다.

Q12. 토큰 전달을 쓰는 MCP 서버에서 ID-JAG로 받은 access token으로 tool을 불렀다. backend API는 어떤 토큰을 받나?

코드를 읽은 결과로는 OAuthProxy가 서명한 access token을 받는다. ID-JAG로 받은 토큰에는 upstream 토큰이 없기 때문이다. IdP가 발급한 토큰을 검증하는 backend API는 이 토큰을 거부할 가능성이 높다.
