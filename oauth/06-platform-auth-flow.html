우리 플랫폼의 MCP 인증 흐름

OAuth 학습 6편 · 2026-11-18 작성

우리 MCP 서버의 인증 흐름을 코드로 따라가 보고, ID-JAG를 넣을 때 달라지는 점을 정리한다.

한 문장 요약

우리 MCP 서버마다 들어 있는 프록시는 IdP가 아니라 MCP 인가 서버다. Okta에서 받은 IdP 토큰은 Redis에 두고, MCP 클라이언트에는 자기가 서명한 fastmcp 토큰을 준다.

읽는 방법

장마다 난이도를 표시했다. 1편 6장, 3편 6장, 5편을 먼저 읽으면 이해하기 쉽다.

  • 초급 1장과 2장에서 구성 요소와 역할을 다룬다.
  • 중급 3장부터 6장까지는 로그인, MCP 요청, Redis, ID-JAG 비교를 다룬다.
  • 고급 7장부터 9장까지는 다른 구조 두 가지와 backend 토큰 문제를 다룬다.

1. 구성 요소와 배치초급

우리 플랫폼의 MCP 인증에는 구성 요소가 여섯 개 있다.

구성 요소하는 일
MCP 클라이언트(core)사용자를 대신해 MCP 서버를 부른다. fastmcp 토큰을 사용자 ID와 MCP 서버 주소별로 저장한다(core의 토큰 저장 코드).
MCP 서버tool을 제공한다. MCP 서버마다 프록시가 하나씩 들어 있다.
프록시Okta 로그인을 중개하고 fastmcp 토큰을 발급한다.
Okta사용자를 로그인시키고 IdP 토큰을 발급한다.
Redis프록시의 저장소다. 여러 MCP 서버가 Redis 하나를 함께 쓴다.
backend APItool이 부르는 API다.

프록시는 MCP 서버가 아니라 MCP 서버 프로세스 안에 들어 있는 인증 부품이다. 그래서 MCP 서버가 세 개면 프록시도 세 개다.

2. 프록시와 IdP의 차이초급

MCP 클라이언트가 보기에 프록시는 인가 서버다. 프록시에 authorize 주소, token 주소, DCR 주소가 있기 때문이다(1편 6장). 그래서 프록시가 IdP처럼 보인다. 하지만 두 역할은 다르고, 사용자가 누구인지는 끝까지 Okta가 판단한다.

항목Okta(IdP)프록시(MCP 인가 서버)
사용자 계정가진다.없다. 로그인은 Okta에 맡긴다.
발급하는 토큰ID token, IdP 토큰, ID-JAGfastmcp 토큰
서명 방식비대칭 키(RS256)로 서명한다. 공개 키는 JWKS로 공개한다.대칭 키(HS256)로 서명한다. 키는 IdP 앱의 secret에서 만든다(런타임의 서버 코드).
토큰을 받는 곳Okta를 믿고 aud가 맞는 서비스그 프록시가 든 MCP 서버 하나. aud가 그 서버의 MCP 주소다(3편 6장).
개수하나MCP 서버마다 하나

두 역할이 한 곳인 구성

MCP 서버가 프록시 없이 Okta를 직접 MCP 인가 서버로 쓰는 구성도 있는데, 이때 MCP 클라이언트는 Okta에서 바로 access token을 받는다. 이 구성에서는 ID-JAG를 발급하는 쪽과 받는 쪽이 같은 Okta가 되므로 ID-JAG가 필요 없다.

3. 로그인 흐름중급

로그인 한 번은 아래 순서로 흐른다. 1편 6장에서 설명한 순서와 같고, 이 장에서는 Redis에 값이 들어가는 시점을 더했다. 1번에 앞서 MCP 클라이언트는 DCR로 프록시에 자기를 등록한다.

  1. MCP 클라이언트가 브라우저를 프록시의 authorize 주소로 보내면, 프록시는 트랜잭션을 Redis에 저장한다(proxy.py:1204).
  2. 프록시가 프록시 동의 화면을 보여 주고, 사용자는 위임 scope를 골라 허용한다.
  3. 프록시가 브라우저를 Okta로 보내고, 사용자가 Okta에 로그인한다.
  4. Okta가 브라우저를 프록시의 콜백 주소로 보내는데, 이 주소에 IdP 인가 코드가 붙어 있다.
  5. 프록시가 IdP 앱의 client_id와 secret으로 IdP 인가 코드를 IdP 토큰으로 바꾼다(proxy.py:2753).
  6. 프록시가 프록시 인가 코드를 만들고, 이 코드와 IdP 토큰을 Redis에 5분 동안 둔다(proxy.py:2779).
  7. 프록시가 브라우저를 MCP 클라이언트의 콜백 주소로 보내는데, 이 주소에 프록시 인가 코드가 붙어 있다.
  8. MCP 클라이언트가 프록시 인가 코드를 프록시의 token 주소로 보낸다(proxy.py:1288).
  9. 프록시가 IdP 토큰 묶음을 Redis에 저장하고(proxy.py:1421), 그다음 fastmcp 토큰을 서명한다(proxy.py:1436).
  10. 프록시가 jti와 upstream_token_id의 대응을 Redis에 저장하고(proxy.py:1457), fastmcp 토큰을 MCP 클라이언트에 준다.

프록시는 IdP 토큰을 먼저 받고, fastmcp 토큰은 그다음에 준다. MCP 클라이언트는 IdP 토큰을 끝까지 보지 못한다.

4. MCP 요청과 backend 호출중급

로그인한 뒤의 MCP 요청 한 번은 아래 순서로 흐른다.

  1. MCP 클라이언트가 MCP 요청에 fastmcp 토큰을 붙여 보낸다.
  2. 프록시가 fastmcp 토큰을 서명 검증하고 jti를 꺼낸다(proxy.py:2151).
  3. 프록시가 jti로 upstream_token_id를 찾고, 그 값으로 IdP 토큰 묶음을 찾는다(proxy.py:2174, :2183).
  4. 프록시가 IdP 토큰을 검증하고, IdP 토큰이 곧 만료되면 Okta에서 새 IdP 토큰을 받는다(proxy.py:2200).
  5. tool이 backend API를 부르면 런타임이 IdP 토큰을 Authorization 헤더에 넣는다(런타임의 서버 코드).

5번이 토큰 전달인데, backend가 Bearer 인증을 쓰고 토큰 전달 설정이 켜졌을 때만 일어난다(런타임의 서버 코드). IdP 토큰에는 로그인용 scope만 들어 있고, 위임 scope는 fastmcp 토큰에만 들어간다(런타임의 위임 scope 코드).

프록시는 Redis에 값을 컬렉션별로 나눠 두는데, 아래 표에는 주요 컬렉션만 적었다.

서버별 접두사와 암호화

키 이름 앞에는 MCP 서버별 접두사가 붙고, 접두사의 기본값은 <접두사>-mcp:{서버 이름}이다(런타임 설정). 그래서 프록시는 다른 MCP 서버의 키를 찾지 않는다(런타임의 Redis 저장소 래퍼).

런타임은 Redis에 넣는 값을 모두 Fernet으로 암호화하는데(런타임의 서버 코드), 암호화 키도 IdP 앱의 secret에서 만든다.

IdP 토큰 묶음을 찾는 키

IdP 토큰 묶음을 찾는 키는 세션 ID도 사용자 ID도 아니다. 프록시는 fastmcp 토큰의 jti로 upstream_token_id를 찾고, 그 값으로 IdP 토큰 묶음을 찾는다.

IdP 토큰 묶음은 로그인 한 번마다 하나 생기고, 토큰을 갱신할 때는 기존 묶음을 고쳐 쓴다(proxy.py:1912). 예를 들어 MCP 클라이언트가 MCP 서버 세 개에 한 번씩 로그인하면 묶음이 세 개 생기고, 세 묶음은 서버별 접두사로 나뉜다.

6. ID-JAG와 비교중급

지금 흐름과 ID-JAG는 신뢰 구조가 같다. 둘 다 Okta가 사용자를 증명하고, 프록시는 그 증명을 믿고 fastmcp 토큰을 준다. 그래서 지금 흐름이 ID-JAG와 비슷해 보이는데, 다른 점은 증명이 오는 길과 Okta 토큰을 가진 쪽이다.

프록시 동의 화면MCP 서버마다 나온다.나오지 않는다. Okta 정책이 대신한다.
Okta 토큰을 가진 쪽각 프록시. Redis에 둔다.core. 사용자별 Okta refresh token을 둔다.
MCP 클라이언트가 받는 토큰서버마다 다른 fastmcp 토큰서버마다 다른 fastmcp 토큰

ID-JAG에서도 access token은 MCP 서버마다 따로 받고, 공유하는 것은 core가 가진 Okta 로그인이다(5편 14.2절).

7. 사용자 ID로 토큰 하나를 묶는 안고급

이 장에서는 검토한 안 하나를 다룬다. 안의 내용은 다음과 같다.

  1. 프록시가 사용자 ID별로 토큰을 모은다.
  2. 같은 사용자에게는 MCP 서버가 달라도 같은 토큰을 준다.
  3. MCP 클라이언트는 토큰 하나로 MCP 서버 세 개를 부른다.
  4. 뒤쪽에서는 프록시가 서버마다 다른 IdP 토큰으로 Okta와 통신한다.

이 안은 ID-JAG가 아니다. ID-JAG는 access token을 공유하지 않고, MCP 클라이언트가 가진 Okta 로그인을 공유한다.

문제 세 가지

  1. aud 규칙을 어긴다. 서버 세 개가 받는 토큰은 aud를 서버 하나로 정할 수 없어서, 이 토큰이 새면 서버 세 개가 모두 열린다(5편 1장).
  2. MCP 클라이언트 구분이 사라진다. 같은 사용자의 core 에이전트와 IDE가 같은 토큰을 쓰게 되고, 클라이언트마다 고른 위임 scope도 섞인다.
  3. 지금 구조로는 만들 수 없다. 프록시는 MCP 서버마다 따로 있고, fastmcp 토큰의 aud와 Redis 접두사도 서버마다 다르다. 서버 세 개가 토큰 하나를 믿게 하려면 프록시를 중앙 인가 서버로 옮겨야 한다.

사용자 단위로 묶는 곳

사용자 단위로 묶는 일은 이미 MCP 클라이언트 쪽에서 하고 있다. core는 토큰을 user:{사용자 ID}: 접두사와 MCP 서버 주소로 저장한다(core의 토큰 저장 코드). ID-JAG를 넣어도 이 구조는 그대로이고, core에 사용자별 Okta 로그인 하나만 더 생긴다.

8. 게이트웨이 방식고급

MCP 클라이언트가 토큰 하나만 가져야 한다면 게이트웨이 방식이 맞다(5편 9장). 그림 5의 (나)가 이 구조다.

  1. MCP 서버 여러 개를 게이트웨이의 MCP 주소 하나 뒤에 둔다.
  2. MCP 클라이언트는 게이트웨이 하나에만 로그인하고, 토큰의 aud는 게이트웨이다.
  3. 게이트웨이가 뒤쪽 MCP 서버마다 토큰을 바꿔서 보낸다.

이 구조에서 토큰을 관리하는 쪽은 게이트웨이라서, 7장의 안이 프록시에 맡기려던 일을 게이트웨이가 한다. 대신 게이트웨이가 모든 MCP 요청의 관문이 되므로, 게이트웨이가 멈추면 뒤쪽 MCP 서버를 하나도 쓸 수 없다.

9. ID-JAG와 backend 토큰고급

ID-JAG를 넣으면 4장 5번의 토큰 전달이 깨진다. 이 내용은 코드를 읽은 결과이고, 실행해서 확인하지는 않았다.

  1. fastmcp는 ID-JAG로 발급한 fastmcp 토큰에 IdP 토큰 묶음을 연결하지 않는다.
  2. 프록시는 이 토큰을 검증할 때 Redis를 찾지 않고, 받은 토큰을 그대로 돌려준다(proxy.py:2159).
  3. 런타임은 돌려받은 토큰을 Authorization 헤더에 넣는다(런타임의 서버 코드).
  4. 그래서 backend API는 Okta 토큰 대신 fastmcp 토큰을 받는다.

fastmcp 토큰은 프록시가 HS256으로 서명한 값이고, aud도 backend API가 아니라 MCP 서버다. 그래서 Okta 토큰을 검증하는 backend API는 이 토큰을 거부할 가능성이 높다.

backend 토큰을 얻는 방법과 추천

방법추천이유
① 토큰 전달을 쓰지 않는 MCP 서버에만 ID-JAG를 켠다.추천. 첫 단계로 쓴다.새 신뢰 관계가 필요 없다. 토큰 전달을 쓰는 서버는 지금 흐름을 그대로 쓴다. 두 흐름은 한 프록시에서 함께 동작한다(5편 14.4절).
② 프록시가 Okta에서 backend용 토큰을 따로 받는다.검토 후보. PoC에서 확인한다.표준 token exchange(RFC 8693)를 쓰는 방법이다. 다만 프록시에는 사용자의 Okta 토큰이 없다. subject token으로 무엇을 낼지와 Okta의 지원 여부를 확인하지 않았다.
③ backend API가 fastmcp 토큰을 받아들인다.추천하지 않는다.fastmcp 토큰은 대칭 키로 서명한다. backend API가 검증하려면 같은 키를 가져야 한다. 그러면 backend API도 fastmcp 토큰을 만들 수 있게 된다.
④ core가 backend용 토큰을 따로 받아 MCP 요청 헤더로 넘긴다.추천하지 않는다.런타임에는 MCP 요청 헤더를 backend API로 옮기는 기능이 있다(런타임의 서버 코드). 그러나 MCP 서버가 자기 앞으로 발급되지 않은 토큰을 넘기게 된다. MCP 권한 스펙이 금지하는 token passthrough에 해당할 가능성이 있다.
⑤ backend API를 서비스 자격(client credentials)으로 부른다.사용자별 권한이 없는 backend API에만 쓴다.client credentials로 받은 토큰에는 사용자 정보가 없다. 그래서 backend API는 사용자를 구분하지 못한다.

10. 자가 점검 문제

먼저 답을 생각해 보고, 그다음 펼쳐서 확인한다.

Q1. MCP 서버가 세 개다. 프록시는 몇 개이고 어디에 있나?

세 개다. 프록시는 따로 떠 있는 서버가 아니라 MCP 서버 프로세스마다 하나씩 들어 있다.

Q2. 프록시는 IdP인가?

아니다. 프록시는 MCP 인가 서버다. 사용자 계정이 없고, 사용자 로그인은 Okta에 맡긴다.

Q3. 로그인 중 프록시가 IdP 토큰을 받는 일과 fastmcp 토큰을 주는 일 중 어느 쪽이 먼저인가?

IdP 토큰을 받는 일이 먼저다. 프록시는 Okta가 콜백 주소로 돌아올 때 IdP 인가 코드를 IdP 토큰으로 바꾸고, fastmcp 토큰은 MCP 클라이언트가 프록시 인가 코드를 낸 뒤에 준다.

Q4. 프록시가 Redis에서 IdP 토큰 묶음을 찾을 때 쓰는 키는 세션 ID인가, 사용자 ID인가?

둘 다 아니다. 프록시는 fastmcp 토큰의 jti로 upstream_token_id를 찾고, 그 값으로 IdP 토큰 묶음을 찾는다.

Q5. MCP 클라이언트가 MCP 서버 세 개에 한 번씩 로그인했다. Redis에 IdP 토큰 묶음은 몇 개 생기나?

세 개 생긴다. 프록시가 서버마다 따로 로그인을 처리하기 때문이고, 세 묶음은 서버별 접두사로 나뉜다.

Q6. ID-JAG를 넣었다. MCP 서버 세 개를 쓰는 MCP 클라이언트는 access token을 몇 개 가지나?

세 개 가진다. ID-JAG에서도 access token은 서버마다 따로 받고, 공유하는 것은 core가 가진 Okta 로그인이다.

Q7. 같은 사용자의 core 에이전트와 IDE가 토큰 하나를 같이 쓰면 무엇을 잃나?

MCP 클라이언트의 구분을 잃는다. 클라이언트마다 고른 위임 scope가 섞이고, 한 클라이언트의 토큰을 취소하면 다른 클라이언트도 끊긴다.

Q8. MCP 클라이언트가 토큰 하나만 가져야 한다. aud 규칙을 지키는 구조는 무엇인가?

게이트웨이 방식이다. 토큰의 aud는 게이트웨이 하나이고, 게이트웨이가 뒤쪽 MCP 서버마다 토큰을 바꿔서 보낸다.

Q9. 토큰 전달을 쓰는 MCP 서버에 ID-JAG를 켰다. backend API는 어떤 토큰을 받나?

코드를 읽은 결과로는 fastmcp 토큰을 받는다. ID-JAG로 받은 fastmcp 토큰에는 연결된 IdP 토큰 묶음이 없기 때문이다. Okta 토큰을 검증하는 backend API는 이 토큰을 거부할 가능성이 높다.

Q10. backend API가 fastmcp 토큰을 직접 검증하게 하면 안 되는 이유는?

fastmcp 토큰은 대칭 키(HS256)로 서명하므로 backend API가 검증하려면 같은 키를 가져야 하고, 그러면 backend API도 fastmcp 토큰을 만들 수 있게 된다. 토큰의 aud도 backend API가 아니라 MCP 서버다.

다음 내용은 확인하지 않았다.

  • 배포된 MCP 서버의 실제 설정. 토큰 전달 설정, Redis 접두사, 프록시 동의 화면 설정을 클러스터에서 보지 않았다.

  • 9장 ④번 방법이 MCP 권한 스펙의 token passthrough 금지에 해당하는지. 스펙 문구와 대조하지 않았다.
  • 8장의 게이트웨이가 뒤쪽 MCP 서버용 토큰을 얻는 방법. 이 문서는 다루지 않았다.
  • Okta가 RS256으로 서명한다는 점. 이번에 Okta 문서와 다시 대조하지 않았다.

이 문서가 OAuth 학습의 마지막 편이다. 전체 목록은 목차에 있다.
