role과 scope, 그리고 fastmcp OAuthProxy

OAuth 학습 1편 · 2026-10-14 작성

role과 scope가 각각 어떻게 흐르는지 살펴보고, fastmcp의 OAuthProxy가 일반 OAuth 흐름을 어떻게 바꾸는지 다룬다.

코드 근거는 fastmcp 4.0.3 소스와 각 저장소의 코드이고, 저장소 코드는 2026-10-14에 받은 상태를 기준으로 한다.

한 문장 요약

scope는 사용자가 클라이언트에 맡긴 권한이고, role은 사용자 자신의 속성이다. OAuthProxy는 MCP 서버를 인가 서버처럼 보이게 만들기 때문에 등록, 토큰, 리다이렉트가 모두 두 층으로 나뉜다.

1. 일반 OAuth의 등장인물

OAuth 2.0에는 네 역할이 있다.

역할하는 일예
사용자로그인하고 권한을 맡긴다.플랫폼 사용자
클라이언트사용자 대신 토큰을 받아 API를 부른다.웹 앱, Claude Desktop
인가 서버사용자를 로그인시키고 토큰을 발급한다.Okta, Keycloak
리소스 서버토큰을 받고 API를 제공한다.MCP 서버, 백엔드 API

일반 OAuth에서는 IdP가 인가 서버 역할을 한다. 클라이언트가 IdP에 미리 등록돼 있어서, IdP는 지금 어느 클라이언트가 요청하는지 안다.

로그인 순서

가장 흔한 방식은 인가 코드 방식이고(RFC 6749 4.1절), 로그인은 다음 순서로 진행된다.

  1. 클라이언트가 브라우저를 IdP의 authorize 주소로 보내는데, 이 요청에 scope와 PKCE 값이 들어 있다.
  2. 사용자가 IdP에 로그인하고 IdP 동의 화면에서 승인한다.
  3. IdP가 브라우저를 클라이언트의 콜백 주소로 보내는데, 이 주소에 인가 코드가 붙어 있다.
  4. 클라이언트가 인가 코드를 IdP의 token 주소로 보내면, IdP가 그 코드를 확인하고 토큰을 준다.
  5. 클라이언트가 access token을 붙여 리소스 서버를 부른다.
  6. 리소스 서버가 토큰을 검증하고 응답한다. 검증 방법은 2편에서 다룬다.

2. scope의 흐름

scope는 OAuth 표준에 정의된 값이다(RFC 6749 3.3절). 클라이언트가 요청하면 인가 서버가 허용 범위를 정하는데, 흐름은 다음과 같다.

  1. 클라이언트가 authorize 요청에 scope를 담는다. 예: scope=openid profile email.
  2. IdP가 그 scope가 정의돼 있는지, 정책이 허용하는지 본다.
  3. 사용자가 IdP 동의 화면에서 승인한다.
  4. IdP가 허용한 scope를 토큰에 담고, 토큰 응답의 scope 필드로도 허용한 값을 알린다.
  5. 리소스 서버가 토큰의 scope를 보고 요청을 허용하거나 막는다.

요청한 scope와 허용된 scope의 차이

RFC 6749 3.3절에 따르면 인가 서버는 자기 정책이나 사용자의 선택을 근거로 클라이언트가 요청한 scope의 일부나 전부를 무시해도 된다. 다만 허용한 scope가 요청과 다르면 응답에 scope를 넣어야 한다.

결과예
거부Keycloak은 클라이언트에 연결되지 않은 scope를 받으면 invalid_scope 오류를 낸다. Okta는 access policy 규칙이 허용하지 않는 scope 요청을 실패로 처리한다.
줄임Google과 GitHub에는 사용자가 클라이언트의 요청 중 일부만 승인하는 기능이 있다. 토큰 응답의 scope에는 승인한 scope만 들어간다.
더함Keycloak은 클라이언트에 연결된 default client scope를 요청이 없어도 적용한다.

우리 환경에서는 openid, profile, email 같은 표준 scope만 쓰기 때문에 요청한 scope와 허용된 scope가 같아 보인다. Okta default authorization server는 이 scope를 처음부터 정의하고 있다.

3. role의 흐름

role은 OAuth 표준에 없고 IdP마다 따로 만든 기능이라서, 이름과 토큰 안의 위치가 IdP마다 다르다. role은 다음 순서로 흐른다.

  1. 관리자가 IdP에서 사용자에게 role을 붙인다. Okta에서는 그룹을 쓴다.
  2. 사용자가 로그인하면 IdP가 role을 claim으로 토큰에 넣는데, 어느 claim에 넣을지는 IdP 설정이 정한다.
  3. 리소스 서버가 그 claim을 읽고 판단한다.

클라이언트는 role을 요청하지 않고, 보통은 같은 사용자라면 어느 클라이언트로 로그인해도 같은 role이 들어간다.

IdProle이 들어가는 claim조건
Keycloakrealm_access.roles, resource_access.<클라이언트>.roles기본 설정에서 들어간다.
Oktagroups 같은 커스텀 claim관리자가 authorization server에 claim을 추가해야 들어간다.
Google, GitHub없다.access token이 불투명 토큰이라 리소스 서버가 claim을 읽지 못한다.

토큰 안의 위치scope 또는 scpIdP마다 다른 claim

실제 권한은 보통 두 값의 교집합이다. 예를 들어 admin role을 가진 사용자가 read scope만 요청한 클라이언트로 로그인하면 그 클라이언트는 읽기만 한다. role은 사용자가 할 수 있는 최대 범위이고, scope는 그중 이 클라이언트에 맡긴 부분이다.

MCP scope 위임 설계는 scope만 쓰는 안이다. 사용자가 이미 모든 권한을 가진다고 가정하므로, 판단할 질문은 "이 클라이언트에 무엇을 맡겼나?" 하나뿐이다.

5. MCP가 OAuth에 더한 것

MCP 클라이언트는 처음 보는 MCP 서버에도 붙어야 해서, MCP 권한 스펙(2026-07-28판)은 다음 표준을 쓴다.

표준스펙의 요구 수준하는 일
PRM (RFC 9728)MCP 서버는 반드시 구현한다.MCP 서버가 자기 인가 서버의 주소와 scope를 알린다. 경로는 /.well-known/oauth-protected-resource다.
CIMD권장(SHOULD)MCP 클라이언트가 자기 정보 문서의 URL을 client_id로 쓴다. 인가 서버는 그 문서를 읽고 클라이언트를 안다.
DCR (RFC 7591)선택(MAY). deprecated로 표시돼 있다.MCP 클라이언트가 실행 중에 인가 서버에 자신을 등록한다.

스펙은 클라이언트 등록 방법을 미리 등록한 client_id, CIMD, DCR, 사용자에게 묻기 순서로 권한다. core는 지금 DCR로 등록하고, fastmcp 4.0.3 프록시는 DCR과 CIMD를 모두 받는다(fastmcp proxy.py:345).

어느 방식이든 문제는 IdP 쪽에 있다. Google과 GitHub는 처음 보는 클라이언트가 스스로 등록하게 두지 않아서, MCP 클라이언트는 IdP에 직접 등록하지 못한다. fastmcp의 OAuthProxy는 이 문제를 MCP 서버 안에서 해결한다.

6. OAuthProxy의 구조

프록시는 MCP 서버를 인가 서버처럼 보이게 만든다. MCP 클라이언트가 보기에 MCP 서버는 인가 서버이고, IdP가 보기에는 클라이언트 하나다.

로그인 순서

로그인 한 번은 다음 순서로 흐르고, 그 과정에서 브라우저 리다이렉트가 두 번 일어난다.

  1. MCP 클라이언트가 토큰 없이 MCP 서버를 부르면, MCP 서버가 401 응답 헤더로 PRM 주소를 알린다.
  2. MCP 클라이언트가 PRM을 읽는데, PRM은 MCP 서버 자신을 인가 서버로 가리킨다.
  3. MCP 클라이언트가 프록시에 DCR로 등록하고, 프록시는 등록 정보를 자기 저장소에 둔다. CIMD를 쓰는 클라이언트에는 이 단계가 없다.
  4. MCP 클라이언트가 브라우저를 프록시의 authorize 주소로 보낸다.
  5. 프록시가 트랜잭션을 저장하고 프록시 동의 화면을 보여 준다.
  6. 사용자가 승인하면 프록시가 브라우저를 IdP의 authorize 주소로 보낸다. 이때 client_id는 IdP 앱의 값이다.
  7. 사용자가 IdP에 로그인한다.
  8. IdP가 브라우저를 프록시의 콜백 주소로 보내는데, 이 주소에 IdP의 인가 코드가 붙어 있다.
  9. 프록시가 IdP의 인가 코드를 IdP 토큰으로 바꾼다.
  10. 프록시가 자기 인가 코드를 만들고, 브라우저를 MCP 클라이언트의 콜백 주소로 보낸다.
  11. MCP 클라이언트가 그 코드를 프록시의 token 주소로 보낸다. 프록시는 IdP 토큰을 암호화해서 저장한 뒤 fastmcp 토큰을 준다.
  12. MCP 클라이언트가 fastmcp 토큰을 붙여 MCP 서버를 부른다.

7. 프록시가 바꾸는 다섯 가지

① 두 층으로 나뉘는 등록

MCP 클라이언트는 프록시에 DCR로 등록하고, 프록시는 IdP 앱 하나로만 IdP에 붙는다. 그래서 IdP는 모든 MCP 클라이언트를 같은 클라이언트로 보고 서로 구분하지 못한다. 클라이언트별 판단은 프록시가 해야 한다.

② 두 층으로 나뉘는 토큰

IdP 토큰은 MCP 서버 쪽 저장소(디스크나 Redis)에만 있고, MCP 클라이언트는 fastmcp 토큰만 받는다. 요청이 오면 프록시는 fastmcp 토큰으로 IdP 토큰을 찾아서 다시 검증한다(fastmcp proxy.py:2135). 토큰 구조는 3편에서 다룬다.

③ 두 벌의 리다이렉트와 PKCE

첫 번째 리다이렉트는 IdP에서 프록시로 돌아오고, 두 번째 리다이렉트는 프록시에서 MCP 클라이언트로 간다. PKCE 값도 구간마다 따로 만든다(fastmcp proxy.py:1171). 프록시가 트랜잭션을 저장해서 두 구간을 잇기 때문에, MCP 서버 pod가 둘 이상이면 Redis 같은 공유 저장소가 필요하다.

IdP 앱에는 프록시의 콜백 주소만 등록하는데, fastmcp의 기본 경로는 /auth/callback이다. MCP 클라이언트의 콜백 주소는 DCR로 프록시에 등록된다.

④ 프록시의 동의 화면

IdP는 IdP 앱 하나만 알기 때문에, 사용자가 그 앱을 이미 승인했다면 다시 묻지 않을 가능성이 있다. 악성 클라이언트도 DCR로 프록시에 등록할 수 있어서 이 틈은 악성 클라이언트에게 기회가 되는데, 이 공격을 confused deputy라고 부른다. 프록시 동의 화면은 어느 클라이언트가 어느 주소로 토큰을 받는지 사용자에게 보여 준다.

기본 프록시 동의 화면은 클라이언트 이름, 콜백 주소, scope 목록을 보여 준다(fastmcp ui.py:20). 사용자는 전체를 승인하거나 전체를 거부할 뿐이고, scope를 하나씩 고르는 기능은 없다. 위임 설계는 이 화면에 scope 체크박스를 더하는 안이다.

⑤ scope 전달과 role 처리

프록시는 MCP 클라이언트가 요청한 scope를 IdP에 그대로 전달하고, IdP가 허용한 scope는 fastmcp 토큰의 scope에 들어간다. role claim은 프록시가 읽지 않으므로, role로 판단하려면 토큰 검증 코드에서 claim을 직접 꺼내야 한다.

fastmcp의 tool별 권한 검사도 scope를 쓰는데, 이 검사는 IdP 토큰을 검증한 결과의 scope를 본다. 위임 설계는 이 검사가 fastmcp 토큰의 scope를 보도록 바꾸는 안이다.

8. 우리 플랫폼의 scope 경로

우리 MCP 서버는 required_scopes 값 하나를 세 곳에 쓴다.

PRM의 scopes_supportedMCP 클라이언트에게 요청할 scope를 알린다.fastmcp auth.py:885
DCR 기본값과 허용 범위등록 요청에 scope가 없으면 이 값을 준다. 범위 밖의 scope 등록은 거부한다.fastmcp proxy.py:453
IdP 토큰 검증IdP 토큰에 이 scope가 모두 있어야 통과한다.런타임의 Okta 토큰 검증 코드

플랫폼은 core의 MCP OAuth required_scopes 설정으로 이 값을 정하고, 기본값은 openid profile email이다. Google MCP 서버는 설정과 상관없이 같은 세 scope를 받는다. core는 다음 순서로 scope를 IdP까지 보낸다.

  1. core가 PRM의 scopes_supported를 읽고 그 값으로 DCR 등록을 한다(core의 MCP 서버 등록 코드).
  2. core가 등록한 scope를 authorize 요청에 담는다(core의 OAuth 흐름 코드).
  3. 프록시가 그 scope를 트랜잭션에 저장하는데, 요청에 scope가 없으면 required_scopes를 대신 쓴다(fastmcp proxy.py:1190).
  4. 프록시가 IdP authorize 주소의 scope 파라미터에 그 값을 넣는다(fastmcp proxy.py:891).
  5. IdP가 허용한 scope가 fastmcp 토큰에 들어가고, IdP 응답에 scope가 없으면 요청한 값을 쓴다(fastmcp proxy.py:1320).

core는 한 번 등록한 DCR 정보를 저장해 두고 다시 쓰기 때문에, required_scopes를 바꾼 뒤에도 예전 scope로 요청할 가능성이 있다. scope가 바뀌면 다시 등록하는 코드는 2026-10-14 기준 코드에 없다.

9. 자가 점검 문제

먼저 답을 생각해 본 다음 펼쳐서 확인한다.

Q1. Okta 관리 화면에서 "Cursor에는 read만 준다"고 설정할 수 있나?

설정할 수 없다. 프록시는 IdP 앱 하나로만 Okta에 붙어서, Okta는 Cursor와 Claude Desktop을 같은 클라이언트로 본다. 클라이언트별 제한은 프록시가 정해야 하는데, 지금 프록시 동의 화면은 전체 승인과 전체 거부만 한다. 클라이언트별 scope 선택은 위임 설계가 더하려는 기능이다.

Q2. admin role을 가진 사용자가 read scope만 받은 클라이언트로 로그인했다. 리소스 서버가 scope를 검사한다면 이 클라이언트는 쓰기를 할 수 있나?

할 수 없다. role은 사용자가 할 수 있는 최대 범위이고, 이 클라이언트에 맡긴 권한은 read뿐이라서 리소스 서버는 쓰기 요청을 거부한다.

Q3. 프록시 동의 화면이 없으면 어떤 공격이 가능한가?

악성 클라이언트가 DCR로 등록하면서 자기 콜백 주소를 적는다. 사용자가 악성 링크를 열면 프록시는 브라우저를 IdP로 보내는데, 사용자가 IdP 앱을 이미 승인했다면 IdP는 묻지 않고 통과시킬 가능성이 있다. 그러면 프록시는 자기 인가 코드를 악성 클라이언트의 콜백 주소로 보내게 되고, 이것이 confused deputy 공격이다.

Q4. IdP 앱에 콜백 주소로 등록해야 하는 값은?

프록시의 콜백 주소다. fastmcp 기본값은 MCP 서버 공개 주소 뒤에 /auth/callback을 붙인 값이다. MCP 클라이언트의 콜백 주소는 IdP에 등록하지 않고, MCP 클라이언트가 DCR로 프록시에 등록한다.

Q5. required_scopes에 Okta에 정의하지 않은 scope를 넣으면 어떻게 되나?

프록시가 그 scope를 Okta authorize 요청에 담는다. Okta의 access policy 규칙은 정의되지 않은 scope를 허용하지 않을 것으로 보이고, 그러면 로그인이 실패한다. Keycloak이라면 invalid_scope 오류로 로그인이 실패한다.

Q6. IdP가 요청보다 적은 scope를 허용했다. fastmcp 토큰의 scope에는 무엇이 들어가나?

IdP가 허용한 scope가 들어간다. 프록시가 IdP 토큰 응답의 scope 필드를 먼저 읽기 때문이다. 빠진 scope가 required_scopes에 있다면 문제가 하나 더 생기는데, 로그인은 끝나지만 요청마다 IdP 토큰 검증이 실패한다.
