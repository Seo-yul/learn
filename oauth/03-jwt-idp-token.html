JWT와 IdP 토큰의 구성

OAuth 학습 3편 · 2026-10-14 작성

이 문서는 JWT라는 형식과 IdP가 발급하는 토큰들을 다루고, fastmcp 토큰이 IdP 토큰과 어떻게 다른지도 함께 정리한다.

1편 "role과 scope, 그리고 OAuthProxy"와 2편 "JWKS와 introspection"을 안다고 가정한다.

한 문장 요약

JWT는 형식의 이름이고 IdP 토큰은 발급자에 따른 이름이며, IdP는 용도가 다른 토큰 세 개를 준다. fastmcp 토큰은 사용자 정보 없이 jti로 IdP 토큰을 가리키는 참조 토큰이다.

1. 토큰 이름의 세 기준

토큰 이름이 헷갈리는 것은 서로 다른 기준으로 붙인 이름이 섞여 쓰이기 때문이다. 기준은 형식, 발급자, 용도 세 가지다.

기준이름
형식JWT, 불투명 토큰
발급자IdP 토큰, fastmcp 토큰
용도access token, ID token, refresh token

예를 들어 Okta access token은 형식으로 보면 JWT이고, 발급자로 보면 IdP 토큰, 용도로 보면 access token이다. fastmcp 토큰은 형식이 JWT이고, 발급자는 프록시이며 용도는 access token이다.

2. JWT의 구조

서명만 한 JWT(JWS 형식)는 점(.)으로 나뉜 세 부분으로 되어 있고, 각 부분은 base64url로 인코딩돼 있다.

eyJhbGciOiJSUzI1NiIsImtpZCI6ImsxYTJiMyJ9 . eyJpc3MiOiJodHRwczovL…  . SflKxwRJSMeKKF2QT4fwpM…
               header                              payload                    signature
부분내용
header서명 방식. alg(예: RS256, HS256), typ, kid가 들어간다.
payloadclaim 목록.
signatureheader와 payload를 서명 키로 서명한 값.

서명만 한 JWT의 payload는 암호화되지 않는다. base64url은 인코딩일 뿐이라서 누구든 디코딩해서 읽을 수 있다. 서명은 위조를 막아 주지만 내용을 숨기지는 않으므로, 내용을 숨기려면 JWE(RFC 7516)를 써야 한다.

등록 claim

RFC 7519 4.1절은 다음 일곱 claim의 이름과 뜻을 정하는데, 모두 선택 사항이다. 어떤 claim을 반드시 넣을지는 JWT를 쓰는 쪽의 규칙이 정한다.

claim뜻
iss발급자
sub토큰의 주체. 보통 사용자 ID다.
aud이 토큰을 받아야 할 대상
exp만료 시각. 이 시각 뒤에는 무효다.
nbf이 시각 전에는 무효다.
iat발급 시각
jti토큰의 고유 ID

3. IdP의 토큰 응답

로그인이 끝나면 클라이언트는 인가 코드를 IdP의 token 주소로 보내고, IdP는 다음과 같은 토큰 응답을 돌려준다.

{
  "token_type": "Bearer",
  "expires_in": 3600,
  "access_token": "eyJraWQiOi…",
  "id_token": "eyJraWQiOi…",
  "refresh_token": "Uq9b…",
  "scope": "openid profile email offline_access"
}
필드필수 여부뜻
access_token필수리소스 서버에 보낼 토큰
token_type필수토큰을 보내는 방식. 보통 Bearer다.
expires_in권장access token의 남은 수명(초)
refresh_token선택새 access token을 받을 때 쓰는 토큰
scope요청과 같으면 선택, 다르면 필수실제로 허용한 scope
id_tokenOIDC에서 openid scope를 요청했을 때누가 로그인했는지 알리는 토큰

4. IdP 토큰 세 가지

토큰읽는 쪽용도audOkta에서의 형식
access token리소스 서버API 호출리소스 서버. Okta 기본값은 api://default다.JWT
ID token클라이언트누가 로그인했는지 알기클라이언트의 client_idJWT
refresh tokenIdP새 access token 받기해당 없음불투명 토큰

access token

Okta 커스텀 authorization server가 발급한 access token의 payload는 다음과 같다.

{
  "ver": 1,
  "jti": "AT.x1y2z3",
  "iss": "https://{Okta 주소}/oauth2/default",
  "aud": "api://default",
  "iat": 1760426400,
  "exp": 1760430000,
  "cid": "0oa1b2c3",
  "uid": "00u4d5e6",
  "scp": ["openid", "profile", "email"],
  "auth_time": 1760426390,
  "sub": "user@example.com"
}
  • cid: 토큰을 받은 클라이언트. 프록시 구조에서는 IdP 앱의 client_id다.
  • uid: Okta 사용자 ID. 사용자 없이 발급한 토큰에는 없다.
  • scp: 허용된 scope. 배열이다.
  • role에 해당하는 groups는 관리자가 claim을 추가해야 들어간다.

ID token

ID token은 OIDC가 더한 토큰이고, 클라이언트는 이 토큰을 보고 누가 로그인했는지 안다.

{
  "iss": "https://{Okta 주소}/oauth2/default",
  "sub": "00u4d5e6",
  "aud": "0oa1b2c3",
  "iat": 1760426400,
  "exp": 1760430000,
  "auth_time": 1760426390,
  "nonce": "n-0S6_WzA2Mj",
  "email": "user@example.com",
  "name": "홍길동"
}

OIDC Core 2절이 정한 필수 claim은 iss, sub, aud, exp, iat 다섯 개다. nonce는 요청에 nonce가 있었을 때 들어가고, aud에는 클라이언트의 client_id가 반드시 들어간다.

ID token은 API 호출에 쓰지 않는다. aud가 리소스 서버가 아니라 클라이언트이고, 리소스 서버는 aud가 자기가 아닌 토큰을 거부해야 하기 때문이다.

refresh token

refresh token은 보통 불투명 토큰이고, 클라이언트는 이 토큰을 IdP에 보내서 새 access token을 받는다. Okta에서는 offline_access scope가 허용돼야 refresh token이 나오는데, IdP 앱에서 Refresh Token grant도 켜 둬야 한다.

core가 넣는 required_scopes 기본값에는 offline_access가 없어서, core가 기본 설정으로 배포한 Okta MCP 서버는 refresh token을 받지 않는다. 런타임 이미지의 Okta 기본값에는 offline_access가 있지만, core가 값을 넣으면 이미지 기본값은 쓰이지 않는다. refresh token이 필요하면 core의 MCP OAuth required_scopes 설정에 offline_access를 더해야 한다.

6. fastmcp 토큰

프록시는 IdP 토큰을 MCP 클라이언트에게 주지 않고, 자기가 만든 JWT를 대신 준다(fastmcp jwt_issuer.py:139).

// header
{ "alg": "HS256", "typ": "JWT" }

// payload
{
  "iss": "https://{MCP 서버 주소}",
  "aud": "https://{MCP 서버 주소}/mcp",
  "client_id": "{DCR로 등록된 MCP 클라이언트 ID}",
  "scope": "openid profile email",
  "exp": 1760430000,
  "iat": 1760426400,
  "jti": "{무작위 값}"
}
claim값근거
iss프록시의 issuer 주소. MCP 서버 공개 주소다.fastmcp proxy.py:783
audMCP 엔드포인트 주소. 토큰을 이 MCP 서버에 묶는다.fastmcp proxy.py:783
client_idDCR로 등록된 MCP 클라이언트 IDfastmcp proxy.py:1436
scopeIdP가 허용한 scope. IdP 응답에 scope가 없으면 요청한 scope다.fastmcp proxy.py:1320
exp기본값은 IdP access token의 만료 시각과 같다.fastmcp proxy.py:1375
jti저장된 IdP 토큰 묶음을 찾는 열쇠fastmcp proxy.py:1436

fastmcp 토큰에는 sub도 없고 사용자 정보도 없다. fastmcp 토큰은 참조 토큰이라서, 사용자 정보는 서버 저장소의 IdP 토큰에 있다.

fastmcp에는 IdP claim을 fastmcp 토큰에 넣는 확장 지점이 있다(_extract_upstream_claims, proxy.py:1695). 다만 기본 구현은 아무것도 넣지 않고, 우리 런타임도 이 지점을 쓰지 않는다.

jti로 IdP 토큰을 찾는 구조

IdP 토큰 묶음의 필드는 fastmcp oauth_proxy/models.py:105에 있고, 이 묶음은 MCP 클라이언트에게 나가지 않는다.

fastmcp refresh token

IdP가 refresh token을 주면 프록시도 fastmcp refresh token을 만든다(fastmcp proxy.py:1444). 이 토큰도 JWT이고 payload에는 "token_use": "refresh"가 들어간다. 프록시는 이 값을 보고 refresh token을 access token 자리에 쓰는 요청을 거부한다(fastmcp jwt_issuer.py:232).

8. 위임 설계와의 연결

위 표에서 MCP 클라이언트를 하나씩 구분하는 토큰은 fastmcp 토큰뿐이다. 그래서 위임 설계는 클라이언트별로 위임한 scope를 fastmcp 토큰의 scope에 넣는 안이고, 이 안에서 IdP access token의 scp에는 신원 확인용 scope만 남는다.

9. 자가 점검 문제

먼저 답을 생각해 보고, 그다음 펼쳐서 확인한다.

Q1. 누군가 fastmcp 토큰을 훔쳐서 jwt.io에 붙여 넣었다. 사용자 이메일이 보이나?

JWT는 암호화되지 않기 때문에 payload는 보인다. 하지만 fastmcp 토큰에는 sub와 사용자 정보가 없어서 이메일은 나오지 않고, 사용자를 찾는 단서는 jti뿐이다. 우리 런타임은 IdP claim도 넣지 않는다.

Q2. 그 fastmcp 토큰으로 Okta API를 직접 부를 수 있나?

부를 수 없다. Okta가 발급한 토큰이 아니고, 서명 키도 Okta가 모르는 대칭키다. 다만 토큰을 훔친 사람은 만료 전까지 이 토큰으로 MCP 서버를 부를 수 있어서, 토큰을 훔치는 것 자체는 여전히 위험하다.

Q3. 클라이언트가 ID token을 리소스 서버에 보냈다. 리소스 서버는 어떻게 해야 하나?

거부해야 한다. ID token의 aud는 클라이언트의 client_id이고, 리소스 서버는 aud가 자기가 아닌 토큰을 통과시키면 안 된다.

Q4. JWT payload에 비밀 값을 넣으면 안 되는 이유는?

payload는 base64url로 인코딩만 돼 있어서 토큰을 가진 누구든 디코딩해서 읽을 수 있다. 비밀 값을 담으려면 JWE를 쓰거나 서버 저장소에 둬야 한다.

Q5. 플랫폼이 기본 설정으로 배포한 Okta MCP 서버가 있다. IdP access token이 만료되면 어떻게 되나?

core가 넣는 기본값에는 offline_access가 없어서 Okta는 refresh token을 주지 않고, 프록시는 IdP 토큰을 갱신하지 못한다. fastmcp 토큰도 IdP access token과 같은 시각에 만료되므로 사용자는 다시 로그인해야 한다.

Q6. fastmcp 토큰의 scope와 IdP access token의 scp는 다를 수 있나?

지금은 보통 같다. 프록시가 IdP 토큰 응답의 scope를 fastmcp 토큰에 옮기기 때문이다. 위임 설계를 적용하면 달라지는데, fastmcp 토큰에는 사용자가 위임한 scope가 들어가고, IdP 토큰에는 신원 확인용 scope만 남는다.
