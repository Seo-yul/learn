issuer, audience, jwks_uri

OAuth 학습 4편 · 2026-11-03 작성

이 문서는 리소스 서버가 JWT를 검증할 때 쓰는 세 설정 값을 다룬다.

2편 "JWKS와 introspection"과 3편 "JWT와 IdP 토큰의 구성"을 안다고 가정한다.

한 문장 요약

issuer는 토큰을 발급한 쪽의 식별자이고, audience는 토큰을 받을 쪽의 식별자다. jwks_uri는 서명을 확인할 공개키를 받는 주소다. 앞의 두 값은 토큰 안에 있고, jwks_uri는 discovery 문서에 있다.

0. 용어집

이 문서에서는 아래 용어를 표에 적은 뜻으로만 쓴다.

용어이 문서에서의 뜻
토큰IdP가 발급한 access token. 형식은 JWT다. ID token은 이름을 붙여 따로 부른다.
IdP사용자 계정을 가지고 토큰을 발급하는 외부 서비스. 예: Okta, Keycloak.
authorization serverOkta 안에서 토큰을 발급하는 단위. 종류는 org와 custom 두 가지다. org는 기본으로 있고, custom은 관리자가 만든다.
리소스 서버토큰을 받고 API를 제공하는 서버. MCP 서버가 여기에 해당한다.
claim토큰 안에 든 이름과 값 한 쌍.
discovery 문서IdP가 자기 주소와 설정을 공개하는 JSON. 주소는 {issuer}/.well-known/openid-configuration이다.
JWKSJSON Web Key Set. IdP가 공개하는 공개키 목록 JSON이다.
kidkey ID. 토큰 헤더와 JWKS의 각 키에 들어 있다. 서명에 쓴 키를 가리킨다.
issuer토큰을 발급한 IdP의 식별자. 토큰의 iss claim에 들어 있다.
audience토큰을 받아 쓸 리소스 서버의 식별자. 토큰의 aud claim에 들어 있다.
jwks_uriJWKS를 받는 주소. discovery 문서에 들어 있다. 토큰에는 없다.
검증리소스 서버가 토큰을 받아들일지 판단하는 전체 과정. 서명을 맞춰 보는 단계는 "서명 검증"이라고 부른다. 나머지 단계는 "확인"이라고 쓴다.
설정 값리소스 서버가 미리 가지고 있는 issuer, audience, jwks_uri 값. 토큰에 든 값과 구분한다.

1. 세 값이 답하는 질문

리소스 서버는 토큰을 받으면 세 가지를 확인해야 하고, 세 설정 값이 각 확인의 기준이 된다.

설정 값답하는 질문비교 대상통과 조건
issuer누가 발급했나토큰의 iss문자열이 정확히 같다
audience누구에게 쓰라고 발급했나토큰의 aud리소스 서버의 식별자가 aud에 들어 있다
jwks_uri발급자가 정말 서명했나토큰 헤더의 kid와 서명kid가 같은 공개키로 서명 검증에 성공한다

jwks_uri는 claim이 아니라서 토큰을 디코딩해도 나오지 않는다. 이 값은 IdP의 discovery 문서에 있다.

2. 토큰과 discovery 문서의 예

Okta custom authorization server가 발급한 토큰을 디코딩하면 다음과 같다.

// header
{ "alg": "RS256", "kid": "k1a2b3" }

// payload
{
  "iss": "https://{Okta 주소}/oauth2/default",
  "aud": "api://default",
  "sub": "00u1abcd...",
  "scp": ["openid", "profile"],
  "exp": 1793700000
}

같은 authorization server의 discovery 문서에는 다음 값이 있다.

GET https://{Okta 주소}/oauth2/default/.well-known/openid-configuration

{
  "issuer": "https://{Okta 주소}/oauth2/default",
  "jwks_uri": "https://{Okta 주소}/oauth2/default/v1/keys",
  "token_endpoint": "https://{Okta 주소}/oauth2/default/v1/token",
  ...
}

discovery 문서의 issuer와 토큰의 iss는 같은 문자열이고, 토큰 헤더의 kid는 JWKS 안의 키 하나를 가리킨다.

3. issuer

issuer는 토큰을 발급한 IdP의 식별자이고, 값은 보통 https 주소다.

IdPissuer 예
Okta custom authorization serverhttps://{Okta 주소}/oauth2/default
Okta org authorization serverhttps://{Okta 주소}
Keycloakhttps://{Keycloak 주소}/realms/{realm}

리소스 서버는 issuer 설정 값과 토큰의 iss를 주소로 해석하지 않고 문자열 그대로 비교한다.

그래서 끝의 / 하나만 달라도 검증에 실패하고, http와 https가 다르거나 포트가 달라도 마찬가지로 실패한다.

issuer는 discovery 문서를 찾는 기준 주소이기도 해서, issuer 뒤에 /.well-known/openid-configuration을 붙이면 discovery 문서의 주소가 된다.

자주 겪는 문제

  • Keycloak은 hostname 설정이 없으면 요청을 받은 주소로 iss를 만든다. 그래서 내부 주소로 받은 토큰은 iss도 내부 주소가 되고, 외부 주소를 issuer 설정 값으로 가진 리소스 서버는 이 토큰을 거부한다.
  • Okta의 org와 custom authorization server는 issuer가 다르다. org authorization server의 access token은 Okta 자체 API에 쓰는 토큰이라서 우리 리소스 서버가 검증할 토큰이 아니다.

4. audience

audience는 토큰을 받아 쓸 리소스 서버의 식별자이고, aud 값은 문자열 하나이거나 문자열 배열이다.

리소스 서버는 자기 식별자가 aud에 있는지 확인하고, 없으면 토큰을 거부해야 한다.

audience를 검사하는 이유

IdP 하나는 보통 여러 서비스에 토큰을 발급한다. 리소스 서버가 aud를 보지 않으면 다른 서비스용 토큰도 통과해서, 예를 들어 서비스 A용 토큰을 서비스 B에 보내도 B가 받아들인다.

MCP 권한 스펙도 같은 이유로 audience 검사를 요구한다. MCP 클라이언트가 resource 파라미터(RFC 8707)로 대상 MCP 서버를 지정하고, MCP 서버는 자기에게 발급된 토큰만 받아야 한다.

IdP별 aud 값

발급자access token의 aud
Okta custom authorization server그 authorization server의 Audience 설정 값이다. 기본값은 api://default다. 값이 하나이므로 같은 authorization server를 쓰는 서비스는 aud가 같다.
Keycloak기본 설정에서는 account 정도만 들어 있는 경우가 많다. 원하는 값은 Audience mapper를 추가해서 넣는다.
fastmcp 프록시MCP 엔드포인트 주소다(3편 6장).

ID token의 aud

ID token의 aud는 로그인한 클라이언트의 client_id이고, access token의 aud는 리소스 서버다. 그래서 ID token으로 API를 부르면 aud 검사에서 거부돼야 정상이다.

5. jwks_uri

jwks_uri는 IdP가 JWKS를 공개하는 주소이고, 이 값은 discovery 문서에 있다.

IdPjwks_uri 예
Okta custom authorization serverhttps://{Okta 주소}/oauth2/default/v1/keys
Keycloakhttps://{Keycloak 주소}/realms/{realm}/protocol/openid-connect/certs

jwks_uri는 다음과 같은 JWKS를 돌려준다.

{
  "keys": [
    { "kty": "RSA", "alg": "RS256", "use": "sig", "kid": "k1a2b3", "n": "0vx7...", "e": "AQAB" },
    { "kty": "RSA", "alg": "RS256", "use": "sig", "kid": "k9z8y7", "n": "xjlC...", "e": "AQAB" }
  ]
}

리소스 서버는 먼저 토큰 헤더의 kid를 읽고, 그다음 JWKS에서 kid가 같은 공개키로 서명을 검증한다.

키 교체와 캐시

IdP는 서명 키를 주기적으로 바꾸기 때문에 리소스 서버는 공개키를 코드에 고정하지 말아야 한다.

보통 리소스 서버는 JWKS를 캐시에 두고, 캐시에 없는 kid가 오면 JWKS를 다시 받는다. 다시 받은 JWKS에도 그 kid가 없으면 토큰을 거부한다.

JWKS에는 키가 여러 개 들어 있기도 한데, IdP가 키를 바꾸는 동안 새 키와 이전 키를 함께 공개하기 때문이다.

보안 규칙

리소스 서버는 다음 두 규칙을 지켜야 한다.

  • jwks_uri는 설정 값이나 신뢰하는 IdP의 discovery 문서에서만 가져온다. 토큰 헤더의 jku나 x5u가 가리키는 주소는 따르지 않는데, 그 주소를 따르면 공격자가 자기 키로 서명한 토큰도 통과하기 때문이다.
  • 허용할 알고리즘을 RS256 등으로 고정한다. 고정하지 않으면 alg: none 공격과 알고리즘 혼동 공격에 노출되는데, 알고리즘 혼동 공격은 공개키를 HS256의 대칭키로 쓰게 만드는 공격이다.

내부 주소와 외부 주소

jwks_uri는 JWKS를 받는 데만 쓰는 주소라서 클러스터 내부 주소를 써도 된다.

issuer 설정 값은 그렇지 않고, 토큰의 iss와 같은 문자열이어야 한다. 클러스터 안의 리소스 서버가 Keycloak을 내부 주소로 부를 때 두 값을 혼동하기 쉽다.

6. 검증 순서

리소스 서버는 다음 순서로 토큰을 검증한다.

  1. 헤더에서 alg와 kid를 읽는다.
  2. JWKS에서 kid가 같은 공개키를 찾는데, 캐시한 JWKS를 먼저 본다.
  3. 그 공개키로 서명을 검증한다.
  4. iss가 issuer 설정 값과 같은지 확인한다.
  5. aud에 audience 설정 값이 들어 있는지 확인한다.
  6. exp와 nbf를 확인하고, 필요하면 scope도 확인한다.

서명을 먼저 검증하는 것은 서명이 맞아야 claim의 내용을 믿을 수 있기 때문이다.

Python 예시

같은 순서를 PyJWT로 쓰면 다음과 같다.

import jwt

JWKS_URI = "https://{Okta 주소}/oauth2/default/v1/keys"
ISSUER = "https://{Okta 주소}/oauth2/default"
AUDIENCE = "api://default"

jwks_client = jwt.PyJWKClient(JWKS_URI)
signing_key = jwks_client.get_signing_key_from_jwt(token)

claims = jwt.decode(
    token,
    signing_key.key,
    algorithms=["RS256"],
    issuer=ISSUER,
    audience=AUDIENCE,
)

jwt.decode는 issuer와 audience 인자를 받으면 iss와 aud도 검사한다.

7. 실무 적용: fastmcp JWTVerifier

fastmcp의 JWTVerifier는 세 설정 값을 인자로 받는다(fastmcp jwt.py:225).

from fastmcp.server.auth.providers.jwt import JWTVerifier

verifier = JWTVerifier(
    jwks_uri="https://{Okta 주소}/oauth2/default/v1/keys",
    issuer="https://{Okta 주소}/oauth2/default",
    audience="api://default",
)
항목동작근거
알고리즘algorithm을 비우면 RS256만 허용한다.jwt.py:275, jwt.py:523
JWKS 캐시받은 JWKS를 3600초 동안 캐시한다.jwt.py:329
모르는 kid캐시에 없는 kid가 오면 캐시 기간 안이라도 JWKS를 다시 받는다.jwt.py:353
issuer 검사issuer 인자가 있을 때만 검사한다. 목록을 주면 그중 하나와 같아야 한다.jwt.py:468, jwt.py:552
audience 검사audience 인자가 있을 때만 검사한다. aud 배열에 그 값이 하나라도 있으면 통과한다.jwt.py:566

JWTVerifier는 issuer나 audience를 비워도 오류를 내지 않고 해당 검사를 건너뛴다. 그래서 두 값을 반드시 넣어야 한다.

우리 MCP 서버가 어느 지점에서 어떤 토큰을 검증하는지는 2편 8장에 있다.

8. 자가 점검 문제

먼저 답을 생각해 보고, 그다음 펼쳐서 확인한다.

Q1. issuer 설정 값이 https://{Okta 주소}/oauth2/default/다. Okta 토큰이 모두 거부된다. 원인은?

설정 값 끝에는 /가 있는데 토큰의 iss에는 끝 /가 없다. issuer는 문자열로 비교하므로 두 값은 다르다.

Q2. jwt.io에 토큰을 붙여 넣었다. jwks_uri가 보이지 않는다. 정상인가?

정상이다. jwks_uri는 claim이 아니고 IdP의 discovery 문서에 있는 값이다. 토큰에는 키를 가리키는 kid만 있다.

Q3. IdP 하나가 서비스 A와 B에 서로 다른 aud로 토큰을 발급한다. B는 audience를 검사하지 않는다. 무슨 일이 생기나?

A용 토큰으로 B를 부를 수 있다. 서명과 iss는 같은 IdP의 값이라서 통과하고, B가 이 토큰을 막을 근거는 aud뿐이다.

Q4. 토큰 헤더의 kid가 캐시한 JWKS에 없다. 리소스 서버는 어떻게 해야 하나?

IdP가 키를 바꿨을 가능성이 있으므로 JWKS를 다시 받아야 한다. 다시 받은 JWKS에도 그 kid가 없으면 토큰을 거부해야 한다. fastmcp JWTVerifier는 캐시 기간 안이라도 JWKS를 다시 받는다.

Q5. 공격자가 토큰 헤더의 jku에 자기 서버의 JWKS 주소를 넣었다. 리소스 서버는 어떻게 해야 하나?

리소스 서버는 jku를 무시하고, 설정한 jwks_uri에서 받은 키만 써야 한다. jku를 따르면 공격자의 키로 서명 검증에 성공한다.

Q6. 클러스터 안의 MCP 서버가 Keycloak을 내부 주소로 부른다. Keycloak의 hostname은 외부 주소로 고정돼 있다. 두 설정 값에는 각각 어떤 주소를 넣나?

jwks_uri는 JWKS를 받는 데만 쓰는 주소라서 내부 주소를 넣어도 된다. issuer 설정 값에는 외부 주소를 넣어야 하는데, hostname이 고정돼 있어서 토큰의 iss가 항상 외부 주소이기 때문이다.

  • OpenID Connect Discovery 1.0. issuer와 jwks_uri를 담은 discovery 문서.
  • MCP 권한 스펙(Authorization). 토큰의 audience 검사 요구사항.
