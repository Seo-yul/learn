1. 질의 변환

사용자의 질문은 검색하기에 좋은 모양이 아닌 경우가 많아서, 검색 전에 질문을 고치는 단계를 둔다.

문제 예 처리
앞 대화에 기대는 질문 "그럼 그건 며칠까지 돼?" 대화를 보고 혼자서도 뜻이 통하는 질문으로 다시 쓴다
질문이 둘 이상 섞임 "연차와 병가의 신청 방법과 차이는?" 질문을 나눠 각각 검색하고 결과를 합친다
표현이 문서와 다름 사용자는 "재택", 문서는 "원격근무" 같은 뜻의 질문을 여러 개 만들어 함께 검색한다
질문이 너무 짧음 "출장비" 가상의 답을 먼저 쓰게 하고 그 글로 검색한다(HyDE)
검색이 필요 없는 질문 "고마워", "방금 답을 표로 바꿔 줘" 검색을 건너뛴다

질문을 다시 쓰는 데도 모델 호출이 들어서 지연과 비용이 늘어나므로, 필요한 경우에만 켠다. 다만 대화형 서비스라면 첫째 줄(대화 맥락 반영)은 거의 필수다.

2. 프롬프트 조립

찾아온 조각을 어떻게 넣느냐도 답의 품질을 바꾼다.

  • 출처를 붙여 넣는다. 조각마다 문서 이름과 조항을 함께 넣고, 답에 출처를 달게 한다. 그러면 사용자가 답을 검증할 수 있고, 틀렸을 때 원인을 찾기도 쉽다.
  • 모르면 모른다고 하게 한다. "제공된 문서에 답이 없으면 없다고 답한다"를 지시에 넣는다. 이 문장이 없으면 모델은 빈 곳을 지어서 채운다.
  • 많이 넣는다고 좋아지지 않는다. 관계없는 조각이 섞이면 모델이 엉뚱한 조각을 근거로 삼고, 긴 프롬프트의 가운데에 있는 내용을 놓치는 경향도 있다.
  • 토큰 예산을 정한다. 지시문, 조각, 대화 이력, 답의 길이를 합쳐 한도를 정하고, 조각 수는 이 예산에서 거꾸로 계산한다.

3. 틀린 답의 원인을 찾는 법

답이 틀리면 먼저 "찾아온 조각에 정답이 있었는가"를 본다. 이것만 확인해도 원인이 검색 쪽인지 생성 쪽인지 나뉜다.

증상 흔한 원인 고치는 곳
문서에 있는데 "모른다"고 답한다 검색이 해당 조각을 못 찾았다 하이브리드 검색, 청킹, 질의 변환
번호나 코드를 물으면 엉뚱한 문서가 나온다 벡터 검색만 쓰고 있다 키워드 검색 추가
옛 규정으로 답한다 개정 전 문서가 색인에 남아 있다 버전 메타데이터와 필터, 삭제 동기화
조각은 맞는데 답이 틀리다 조각에 앞뒤 맥락이 없다, 조각이 너무 많다 부모와 자식 방식, 조각 수 줄이기
표의 숫자를 틀리게 읽는다 표를 글자로 풀면서 행과 열이 섞였다 표 추출 방식, 표를 한 조각으로
문서에 없는 내용을 말한다 지시문에 "없으면 없다고" 가 없다 지시문, 근거성 평가
비슷한 조각이 다섯 개 나온다 중복 문서, 겹침이 너무 크다 중복 제거, 다양성을 고려한 선택

4. 운영에서 조심할 것

이 절의 항목은 시연에서는 보이지 않다가 운영에서 드러나는 것들인데, 대부분 검색 품질이 아니라 데이터 관리의 문제다.

문서 품질

  • PDF는 겉보기와 추출된 글자가 다르다. 2단 편집, 머리글과 바닥글, 스캔 이미지가 섞이기 때문에 추출 결과를 눈으로 확인한다.
  • 같은 문서의 사본과 여러 버전이 함께 색인되면 검색 결과가 중복으로 채워지므로, 색인 전에 중복을 걸러낸다.
  • 품질이 낮은 문서를 넣으면 답도 그만큼 나빠진다. 회의 메모와 초안까지 다 넣으면 틀린 내용이 근거가 되므로, 무엇을 색인할지 먼저 정한다.

최신성

  • 원본이 바뀌면 색인도 바뀌어야 하므로, 수정과 삭제를 어떻게 감지하고 언제 반영할지 정한다.
  • 삭제가 특히 빠지기 쉬운데, 그러면 폐기된 규정이 색인에 남아 계속 답의 근거가 된다.
  • 조각마다 원본 위치, 수정 시각, 색인 시각을 기록해 두면 답이 틀렸을 때 추적할 수 있다.

권한

  • 사용자가 볼 수 없는 문서가 답에 섞이면 사고인데, 모델에게 "보여 주지 마라"고 지시하는 것으로는 막을 수 없다.
  • 조각에 접근 권한을 메타데이터로 붙이고, 검색할 때 사용자의 권한으로 필터를 건다. 조각이 모델에 들어가기 전에 걸러야 하기 때문이다.
  • 원본의 권한이 바뀌면 색인의 권한도 따라 바뀌어야 한다. 멀티테넌트 플랫폼이면 테넌트 구분이 가장 먼저다.

개인정보

  • 한번 색인에 들어간 개인정보는 검색 결과, 로그, 캐시로 퍼지므로 넣기 전에 판단한다.
  • 인사 정보 같은 데이터는 색인에 넣지 않고, 원본 시스템의 API를 감싼 도구로 불러온다. 이렇게 하면 원본 시스템의 권한과 감사 기록을 그대로 쓸 수 있다.

문서 안의 지시문

  • 색인된 문서에 "이전 지시를 무시하고 …" 같은 문장이 들어 있으면 모델이 따를 수 있고, 외부에서 들어온 문서일수록 위험하다.
  • 찾아온 조각은 지시가 아니라 자료라고 프롬프트에서 구분한다. Agent가 도구를 쓸 수 있다면 조각의 내용만으로 위험한 동작이 실행되지 않게 한다.

비용과 지연

  • 질의 한 번에 임베딩, 검색, 재순위, 생성이 차례로 돌기 때문에, 단계마다 시간을 재서 어디가 느린지 본다.
  • 프롬프트에 넣는 조각이 비용의 대부분이라서, 조각 수와 크기를 줄이는 것이 가장 큰 절감이다.
  • 같은 질문이 반복되면 검색 결과나 답을 캐시한다. 다만 권한이 다른 사용자끼리는 캐시를 나누지 않는다.

5. 예시 상황 네 가지

아래는 흔한 실패를 설명하려고 만든 상황이고, 실제 측정 사례가 아니다.

상황 일어난 일 원인 조치
사내 규정 Agent "제17조 내용 알려 줘"에 다른 조항이 나왔다 조항 번호는 뜻이 없어 벡터가 서로 비슷하다 키워드 검색을 더하고, 조항 번호를 메타데이터로 둔다
사내 규정 Agent 작년에 바뀐 출장비 한도를 옛 금액으로 답했다 개정 전 문서가 색인에 남아 있었다 문서에 시행일과 버전을 붙이고 현행만 검색한다
운영 문서 검색 장애 대응 문서를 찾는데 회의록만 나왔다 회의록이 많고 길어 검색 결과를 차지했다 문서 종류로 필터를 걸고, 색인 대상을 줄인다
API 명세 질의 "주문 취소 API의 파라미터"를 틀리게 답했다 명세가 고정 길이로 잘려 파라미터 표가 둘로 나뉘었다 엔드포인트 단위로 자른다. 정확한 값은 명세를 도구로 조회한다

넷째 줄은 OpenAPI 명세 같은 자료에서 자주 나오는데, 명세처럼 구조가 분명한 자료는 검색보다 구조 그대로 조회하는 쪽이 정확한 경우가 많다.

6. 평가

RAG를 고칠 때마다 좋아졌는지 확인할 방법이 있어야 하고, 이때 검색과 생성은 따로 잰다.

검색 평가

질문과 "이 질문에는 이 조각이 나와야 한다"는 쌍을 만드는데, 30개에서 50개면 시작할 수 있다.

지표 뜻 쓰는 때
Recall@k 정답 조각이 상위 k개 안에 들어 있는 비율 가장 먼저 본다. 여기서 낮으면 뒤는 볼 필요가 없다
MRR 첫 정답 조각이 몇 번째에 나오는가 재순위의 효과를 볼 때
Precision@k 상위 k개 중 관련 있는 조각의 비율 관계없는 조각이 많이 섞일 때

생성 평가

재는 것 질문 채점 방법
근거성 답의 모든 주장이 조각에 있는가 LLM 채점. 주장을 나눠 하나씩 확인시킨다
관련성 질문에 실제로 답했는가 LLM 채점
정확성 기대한 답과 내용이 같은가 기대 답과 비교
거절 문서에 없는 질문에 "없다"고 답했는가 답이 없는 질문을 데이터셋에 넣어 확인

임베딩 모델을 고르는 실험도 같은 틀로 한다. 같은 문서와 같은 질문 쌍으로 모델만 바꿔 Recall@k를 비교하면 된다. 청크 크기, 하이브리드 여부, 재순위 여부도 한 번에 하나씩 바꿔 가며 잰다.

데이터로는 실제 질문이 가장 좋다. 운영 로그에서 답이 틀렸던 질문을 데이터셋에 넣으면 같은 실패가 다시 나올 때 잡힌다.

7. 심화 기법

아래 기법은 기본을 다 잡은 뒤에 보는 것들이고, 기본이 안 된 상태에서 붙이면 복잡도만 늘어난다.

기법 생각 맞는 경우 비용
Agentic RAG 검색을 도구로 주고 모델이 필요할 때 여러 번 검색하게 한다 여러 문서를 이어 봐야 하는 질문 호출 수와 지연이 는다. 끝나지 않는 검색을 막아야 한다
조각에 문서 맥락 붙이기 색인할 때 모델로 "이 조각이 문서에서 무엇에 관한 것인지"를 한두 문장 써서 조각 앞에 붙인다 조각만으로는 뜻이 불분명한 문서 색인 비용이 는다
그래프 기반 RAG 문서에서 개체와 관계를 뽑아 그래프로 두고 함께 검색한다 "누가 무엇을 담당하나" 같은 관계 질문, 전체를 요약하는 질문 구축과 갱신이 무겁다
토큰 단위 대조 (late interaction) 문서를 벡터 하나가 아니라 토큰마다의 벡터로 두고 비교한다 세밀한 일치가 중요한 검색 저장 공간이 크게 는다
멀티모달 도표, 스캔 문서, 화면 캡처를 이미지째 임베딩하거나 설명문으로 바꿔 색인한다 그림과 표가 핵심인 문서 처리 비용과 품질 편차

첫째 줄은 LangGraph 같은 Agent 프레임워크로 만들 수 있는데, 검색을 노드나 도구 하나로 두고 결과가 부족하면 질문을 바꿔 다시 검색하게 하는 구조다.

8. 직접 해 보는 순서

  1. 문서 30개에서 50개를 고른다. 사내 문서를 쓸 수 없으면 공개된 기술 문서를 쓴다.
  2. 고정 길이 청킹, 벡터 검색, 상위 5개라는 가장 단순한 구성으로 만든다.
  3. 질문 30개와 정답 조각 쌍을 만들고, 번호나 코드를 묻는 질문과 답이 없는 질문을 섞는다.
  4. Recall@5를 재서 기준선으로 삼는다.
  5. 한 번에 하나씩 바꾼다. 구조 기준 청킹, 하이브리드, 재순위 순서로 넣고 매번 잰다.
  6. 임베딩 모델을 하나 더 골라 같은 표로 비교한다.
  7. 틀린 문항을 3절의 진단 순서로 분류한다.

끝나면 임베딩 모델과 검색 방식을 내 데이터로 비교한 표가 남는다.

9. 스스로 답해 볼 질문

  • RAG와 파인튜닝은 언제 무엇을 쓰는가.
  • 답이 틀렸을 때 검색 문제인지 생성 문제인지 어떻게 가리는가.
  • 벡터 검색만으로 부족한 경우는 언제인가.
  • 청크 크기는 어떻게 정하는가.
  • 사용자마다 볼 수 있는 문서가 다를 때 어떻게 설계하는가.
  • 문서가 바뀌거나 삭제되면 어떻게 반영하는가.
  • 임베딩 모델을 바꿔야 할 때 무엇이 필요한가.
  • RAG의 품질을 어떻게 측정하는가.
