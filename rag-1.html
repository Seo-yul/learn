1. RAG가 푸는 문제

한 문장

RAG(Retrieval-Augmented Generation)는 질문과 관련된 문서 조각을 찾아 프롬프트에 붙인 뒤 모델에게 답하게 하는 방식이다.

모델은 학습한 뒤의 일과 사내 문서를 모르고, 모르는 것을 물으면 그럴듯하게 지어낸다. RAG는 답의 근거를 모델 밖에서 가져와 이 문제를 줄인다.

방법 맞는 경우 맞지 않는 경우
RAG 문서가 많고 자주 바뀐다. 답의 출처를 보여 줘야 한다 숫자 집계, 실시간 상태 조회
문서를 통째로 프롬프트에 넣기 문서가 적고 짧다 문서가 많다. 호출마다 비용과 지연이 커진다
도구 호출 (API, DB 질의) 정형 데이터, 실시간 값, 권한이 걸린 데이터 긴 설명문에서 답을 찾는 일
파인튜닝 말투, 형식, 특정 작업 방식을 익히게 할 때 사실 지식을 넣는 용도. 바뀔 때마다 다시 학습해야 한다

셋째 줄의 예로는 인사 정보가 있다. 이런 데이터는 색인에 넣지 않고 원본 시스템의 API를 감싼 도구로 불러오는데, 개인정보이면서 정형 데이터라서 검색 대상이 아니라 조회 대상이기 때문이다.

2. 전체 흐름

RAG에는 미리 해 두는 색인과 질문이 올 때마다 도는 질의, 이렇게 두 갈래의 흐름이 있다.

답이 틀렸을 때 원인은 이 단계 중 하나에 있으므로, 단계를 알아야 어디를 고칠지 알 수 있다.

3. 임베딩이 하는 일

임베딩 모델은 글을 숫자 수백 개에서 수천 개로 이루어진 벡터로 바꾸는데, 뜻이 비슷한 글은 벡터가 가깝게 나온다. 그래서 검색은 질문 벡터와 가까운 문서 벡터를 찾는 일이 된다.

  • 가까움의 기준: 보통 코사인 유사도를 쓰는데, 두 벡터의 방향이 얼마나 같은지를 보는 값이다.
  • 뜻으로 찾는다: 단어가 달라도 "휴가를 며칠 쓸 수 있나"라는 질문이 "연차 일수" 조항을 찾는다.
  • 질문과 문서는 모양이 다르다: 질문은 짧고 문서는 길어서, 질문용과 문서용을 구분해 임베딩하는 모델이 많다.

임베딩은 글자 그대로를 찾는 일에는 약하다. 조항 번호 "제17조", 에러 코드 "E-4031", 제품 코드 같은 것은 뜻이 없어서 벡터가 서로 비슷하게 나오기 때문이다. 이 약점은 6절의 키워드 검색으로 메운다.

4. 임베딩 모델에 따라 달라지는 것

같은 문서와 질문이라도 임베딩 모델을 바꾸면 찾아오는 조각이 달라진다. 모델을 고를 때는 다음 항목을 본다.

항목 왜 중요한가 실무에서 확인할 것
언어 영어로만 학습한 모델은 한국어에서 품질이 크게 떨어진다 한국어 문서면 다국어 모델이나 한국어 지원을 명시한 모델인지
도메인 일반 글로 학습한 모델은 법률, 의료, 코드, 사내 용어에 약하다 사내 약어와 제품명이 들어간 질문으로 직접 시험
최대 입력 길이 넘는 부분은 잘려서 임베딩에 반영되지 않는다 청크 크기가 한도 안인지. 토큰 수로 센다
차원 수 클수록 저장 공간과 검색 시간이 는다. 품질이 늘 좋아지는 것은 아니다 문서 수 × 차원 수로 메모리를 계산
질문·문서 구분 접두어나 입력 유형을 지정해야 하는 모델이 있다 색인과 질의에 각각 맞는 설정을 넣었는지
정규화 벡터 길이를 1로 맞췄는지에 따라 유사도 계산식이 달라진다 인덱스의 거리 설정과 모델 권장 설정이 같은지
운영 방식 API는 쉽지만 문서가 밖으로 나간다. 자체 호스팅은 GPU와 운영이 필요하다 문서의 보안 등급, 호출량과 지연

실무에서 자주 겪는 일

  • 모델을 바꾸면 전부 다시 색인한다. 서로 다른 모델의 벡터는 비교할 수 없어서다. 문서가 많으면 재색인에 시간과 비용이 들기 때문에 모델 이름과 버전을 벡터와 함께 기록해 둔다.
  • 질문·문서 구분을 빠뜨린다. 색인할 때는 문서용 접두어를 넣고 질의할 때는 안 넣는 식의 실수다. 오류는 나지 않고 검색 품질만 조용히 떨어져서 찾기 어렵다.
  • 공개 순위표를 믿고 고른다. 순위표의 데이터는 내 문서가 아니라서, 후보 두세 개를 내 질문 30개로 직접 비교하는 편이 정확하다. 방법은 2부의 평가 절에 있다.
  • 긴 청크가 잘린 줄 모른다. 한국어는 같은 글자 수라도 토큰이 더 많이 나오는 경우가 있으므로, 글자 수가 아니라 그 모델의 토크나이저로 센다.

구체적인 모델 이름과 수치는 빠르게 바뀌므로, 고를 때는 각 모델의 공식 문서에서 지원 언어, 최대 입력 길이, 차원 수를 확인한다.

5. 청킹 기준

문서를 통째로 임베딩하면 여러 주제가 한 벡터에 섞여 흐려지기 때문에 조각으로 자른다. 자르는 방식이 검색 품질을 크게 좌우한다.

방식 방법 맞는 문서 약점
고정 길이 토큰 수로 자르고 앞뒤를 조금 겹친다 구조가 없는 긴 글 문장과 표가 중간에 잘린다
구조 기준 제목, 조항, 문단 단위로 자른다 규정집, 매뉴얼, 기술 문서 조각 크기가 들쭉날쭉하다
부모와 자식 작은 조각으로 찾고, 그 조각이 속한 큰 단락을 모델에 준다 찾기는 정밀하게, 읽기는 넉넉하게 해야 할 때 저장과 구현이 복잡해진다
맥락 붙이기 조각 앞에 문서 제목과 절 제목을 붙여 임베딩한다 조각만 봐서는 무슨 문서인지 모를 때 조각이 길어진다

조각 크기에는 맞바꿈이 있다. 작게 자르면 정확히 찾지만 답에 필요한 앞뒤가 빠지고, 크게 자르면 앞뒤는 있지만 관계없는 내용이 섞여 검색이 흐려진다.

예시 상황: 규정집의 "전항"

"전항의 경우에는 팀장의 승인을 받아야 한다"는 조각만 찾아오면 모델은 "전항"이 무엇인지 모른다. 조항 단위로 자르고, 조각 앞에 "취업규칙 > 제3장 휴가 > 제17조"를 붙이면 조각이 혼자서도 읽힌다. 이 상황은 설명하려고 만든 예시다.

표와 코드는 따로 다룬다. 표를 글자로 풀면 행과 열의 관계가 사라지므로, 표는 통째로 한 조각으로 두거나 행마다 열 이름을 붙여 문장으로 바꾼다. 코드는 함수나 클래스 단위로 자른다.

6. 검색 방식

방식 찾는 기준 강한 질문 약한 질문
벡터 검색 뜻이 가까운가 "재택근무 신청은 어떻게 하나" "E-4031 오류"
키워드 검색 (BM25) 같은 단어가 있는가 코드, 번호, 고유명사, 약어 표현이 다른 질문
하이브리드 두 결과를 합친다 대부분의 실무 질문 구현과 조정이 하나 더 는다

실무 기본값은 하이브리드다. 두 검색의 결과를 순위 기준으로 합치는 방법(RRF)을 많이 쓰는데, 점수의 단위가 서로 달라도 순위만으로 합칠 수 있어서다.

한국어 키워드 검색에는 형태소 분석이 필요하다. "휴가를", "휴가는", "휴가에"를 같은 "휴가"로 봐야 하는데, 공백으로만 자르면 조사가 붙은 단어가 서로 다른 단어가 되기 때문이다.

메타데이터 필터도 검색의 일부다. 문서 종류, 부서, 개정일, 버전 같은 값을 조각에 붙여 두고 검색 범위를 좁히는 방식이다. "2026년 개정 규정에서만 찾는다" 같은 조건은 뜻으로는 찾을 수 없고 필터로만 걸 수 있다.

7. 재순위

검색은 빠른 대신 거칠어서, 넉넉히 찾아온 뒤 느리지만 정확한 모델로 다시 줄을 세운다.

  • 더 정확한 이유: 임베딩은 질문과 문서를 따로 벡터로 만들지만, 재순위 모델은 질문과 조각을 한꺼번에 읽고 관련도를 매긴다.
  • 비용: 후보마다 모델을 한 번씩 돌리므로 후보 수가 곧 지연 시간이 된다. 50개 안팎에서 시작해 조정한다.
  • 효과가 큰 경우: 비슷한 문서가 많아 1등과 5등의 차이가 작을 때이고, 규정집의 비슷한 조항들이 그런 경우다.

8. 벡터 인덱스와 저장소

문서가 많으면 모든 벡터와 거리를 재는 방식은 느려서 근사 최근접 이웃 검색(ANN)을 쓴다. ANN은 조금 틀릴 수 있는 대신 훨씬 빠르다.

고려할 것 내용
인덱스 방식 HNSW는 빠르고 정확하지만 메모리를 많이 쓴다. IVF 계열은 메모리가 적게 들지만 조정이 필요하다
정확도와 속도 탐색 범위를 넓히면 정확해지고 느려진다. 이 값을 조정해 맞춘다
필터와의 관계 검색한 뒤에 필터를 걸면 결과가 0개가 될 수 있다. 필터를 먼저 적용하는 방식을 지원하는지 확인한다
저장소 선택 이미 쓰는 PostgreSQL(pgvector)이나 OpenSearch로 시작하면 운영 부담이 적다. 규모가 커지면 전용 벡터 DB를 본다
갱신과 삭제 문서가 바뀌면 조각을 지우고 다시 넣어야 한다. 삭제가 실제로 반영되는 시점을 확인한다

문서가 수만 조각 수준이면 저장소 선택보다 청킹과 검색 방식이 품질에 훨씬 큰 영향을 주므로, 저장소는 운영하기 쉬운 것을 고르면 된다.

1부 정리

  • 품질은 모델보다 찾아온 조각에서 갈린다.
  • 임베딩 모델은 언어와 도메인이 맞아야 하고, 바꾸면 전부 다시 색인한다.
  • 청킹은 조각이 혼자서도 읽히게 한다.
  • 뜻 검색과 글자 검색을 함께 쓰고, 재순위로 다듬는다.

2부에서는 질의 변환, 실패 진단, 권한과 최신성 같은 실무 주의점, 평가 방법, 심화 기법을 다룬다.
