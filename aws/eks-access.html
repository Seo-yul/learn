EKS 클러스터 접속

AWS 학습 · 2026-10-28 작성

이 문서는 내 PC의 kubectl이 대상 클러스터에 붙는 경로를 다루고, 그 경로가 끊기는 경우와 고치는 방법도 함께 정리한다.

대상은 계정 111122223333의 EKS 클러스터 my-cluster(리전 ap-northeast-2)이고, dev와 QA가 이 클러스터에 함께 있다.

한 문장 요약

내 IAM user에는 클러스터 권한이 없어서, kubectl은 매번 role ClusterAccessRole을 assume해서 EKS 토큰을 만든다. 그래서 kubeconfig에 이 role이 빠지면 Unauthorized가 난다.

1. 접속 경로 한눈에 보기

아래 그림은 kubectl 명령 하나가 클러스터에 닿기까지의 경로다. 실선은 정상 경로이고, 점선은 role이 빠졌을 때의 경로다.

2. 단계별 동작

kubectl 명령 하나는 다음 순서로 처리된다.

  1. kubectl이 kubeconfig의 user 항목을 읽는다. 이 항목에는 aws eks get-token을 실행하라고 적혀 있다.
  2. aws CLI가 AWS 프로필 me의 로그인 세션을 읽는데, 이 신원은 IAM user다.
  3. user 항목에 role이 있으면, aws CLI가 STS에 그 role의 assume을 요청한다.
  4. STS가 role의 trust policy를 확인하고, 허용되면 임시 자격 증명을 돌려준다.
  5. aws CLI가 임시 자격 증명으로 서명한 EKS 토큰을 만들고, kubectl은 이 토큰을 요청에 담는다.
  6. EKS가 토큰의 신원을 access entry와 비교한다. 이 role에는 cluster admin 권한이 연결돼 있다.

EKS가 보는 신원은 arn:aws:sts::111122223333:assumed-role/ClusterAccessRole/EKSGetTokenAuth인데, 끝의 EKSGetTokenAuth는 aws CLI가 붙이는 role 세션 이름이다.

3단계가 빠지면 토큰이 IAM user 신원으로 만들어지는데, IAM user에는 access entry가 없어서 6단계에서 거절된다.

3. kubeconfig 만들기

kubeconfig를 처음 만들거나 다시 만들 때는 다음 순서로 실행한다.

  1. 로그인 세션을 만든다. 
    aws login --profile me
  2. 기존 kubeconfig를 백업한다. 
    cp ~/.kube/my-cluster ~/.kube/my-cluster.bak.$(date +%Y%m%d)
  3. role과 context 이름을 넣어 kubeconfig를 만든다. --role-arn과 --alias는 빼면 안 된다. 
    aws eks update-kubeconfig --name my-cluster --region ap-northeast-2 \
  --profile me \
  --role-arn arn:aws:iam::111122223333:role/ClusterAccessRole \
  --kubeconfig ~/.kube/my-cluster --alias my-cluster
  4. 클러스터 ARN 이름의 context가 남아 있으면 지우고, my-cluster를 기본 context로 고른다. 
    export KUBECONFIG=~/.kube/my-cluster
kubectl config delete-context arn:aws:eks:ap-northeast-2:111122223333:cluster/my-cluster
kubectl config use-context my-cluster
  5. 4장의 명령으로 접속을 확인한다.

3번 명령이 만든 user 항목은 kubectl을 실행할 때마다 AWS_PROFILE=me로 aws eks get-token --cluster-name my-cluster --role <role ARN>을 실행한다.

role 프로필을 따로 두는 방법

--role-arn을 매번 적는 대신 role을 AWS 프로필에 넣어 둘 수도 있다. 아래 묶음을 ~/.aws/config에 더하면 된다.

[profile my-cluster]
role_arn = arn:aws:iam::111122223333:role/ClusterAccessRole
source_profile = me
region = ap-northeast-2

이 프로필을 쓰면 aws CLI가 me의 로그인 세션으로 role을 assume하므로, kubeconfig는 아래 명령으로 만든다.

aws eks update-kubeconfig --name my-cluster --profile my-cluster \
  --kubeconfig ~/.kube/my-cluster --alias my-cluster

이 방법은 이 PC에서 아직 시험하지 않았고, 9장의 확인 범위에 적어 두었다.

6. 클러스터 권한을 주는 방법

IAM 신원에 클러스터 권한을 주는 방법은 세 가지다. 이 클러스터의 인증 모드는 API_AND_CONFIG_MAP이라서 앞의 두 방법을 모두 쓸 수 있다.

방법동작지금 상태
access entryEKS API로 IAM 신원을 등록하고 access policy를 연결한다. 범위는 클러스터 전체나 namespace로 정한다.role ClusterAccessRole에 AmazonEKSClusterAdminPolicy가 연결돼 있다.
aws-auth ConfigMapkube-system/aws-auth의 mapUsers·mapRoles에 IAM ARN과 쿠버네티스 그룹을 적는다.예전 방식이다. 이 문서는 내용을 확인하지 않았다.
role assumeaccess entry가 있는 role을 assume해서 들어간다. 클러스터 설정은 바꾸지 않는다.지금 쓰는 방식이다. IAM user me는 이 role을 assume할 수 있다.

IAM user에 access entry를 직접 줄 때

role 없이 IAM user로 바로 들어가려면 아래 두 명령이 필요하다. 이 명령은 공유 클러스터의 권한을 바꾸므로 클러스터 관리자와 먼저 정해야 한다.

aws eks create-access-entry --cluster-name my-cluster \
  --principal-arn arn:aws:iam::111122223333:user/me --type STANDARD
aws eks associate-access-policy --cluster-name my-cluster \
  --principal-arn arn:aws:iam::111122223333:user/me \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSEditPolicy \
  --access-scope type=namespace,namespaces=app-dev,app-qa

실행하는 신원에는 eks:CreateAccessEntry와 eks:AssociateAccessPolicy IAM 권한이 있어야 한다.

추천

role assume을 그대로 쓰기를 추천한다. 클러스터 권한이 role 한 곳에 모여 있어서 회수와 감사가 쉽고, 개인마다 access entry를 두면 관리할 곳이 사람 수만큼 늘어나기 때문이다.

직접 접근이 꼭 필요하면 namespace 범위의 AmazonEKSEditPolicy처럼 좁게 주기를 추천한다. cluster admin은 노드와 모든 Secret까지 다룰 수 있기 때문이다.

7. 반대 방향: IRSA와 Pod Identity

6장은 사람이 쿠버네티스 API에 들어오는 방법이다. IRSA와 Pod Identity는 방향이 반대여서, 클러스터 안의 파드가 AWS API를 부를 때 쓴다.

방법동작
IRSA관리자가 클러스터의 OIDC provider를 IAM에 등록하고, ServiceAccount에 eks.amazonaws.com/role-arn annotation을 단다. 그러면 그 ServiceAccount를 쓰는 파드가 그 role로 AWS API를 부른다.
EKS Pod Identity관리자가 클러스터에 Pod Identity Agent add-on을 설치하고, aws eks create-pod-identity-association으로 ServiceAccount와 role을 묶는다. OIDC provider는 등록하지 않는다.

예를 들어 studio 파드가 정적 key 없이 S3를 쓰려면 이 방법이 필요하다. 두 방법 모두 내 kubectl 접속과는 관계가 없다.

8. 자가 점검 문제

먼저 답을 생각해 본 다음 펼쳐서 확인한다.

Q1. aws eks update-kubeconfig --name my-cluster --region ap-northeast-2만 실행했다. kubectl이 거절된다. 왜인가?

이 명령에는 role이 없어서 EKS 토큰이 IAM user 신원으로 만들어진다. IAM user me에는 access entry가 없으므로 EKS가 이 토큰을 거절한다.

Q2. aws sts get-caller-identity --profile me가 user/me를 보여 준다. 설정이 잘못된 것인가?

잘못된 것이 아니다. 이 명령은 AWS 프로필의 신원을 보여 주는데, 프로필 me는 IAM user 신원이 맞다. role은 kubeconfig의 user 항목이 EKS 토큰을 만들 때 assume하므로, 클러스터가 보는 신원은 kubectl auth whoami로 확인한다.

Q3. kubeconfig는 정상인데 kubectl이 "session has expired"를 낸다. 무엇을 해야 하나?

aws login --profile me를 다시 실행해야 한다. 로그인 세션이 만료되면 aws CLI가 assume을 요청하지 못하기 때문이다. kubeconfig는 다시 만들지 않아도 된다.

Q4. IRSA를 설정하면 내 kubectl 접속 문제가 풀리나?

풀리지 않는다. IRSA는 파드가 AWS API를 부를 때 쓰는 방법이고, 사람이 쿠버네티스 API에 들어오는 권한은 access entry나 aws-auth ConfigMap이 정한다.

Q5. update-kubeconfig를 두 번 실행했다. 처음에는 --role-arn을 넣었고 두 번째에는 뺐다. 결과는?

user 항목 이름이 클러스터 ARN 하나로 같아서 두 번째 실행이 user 항목을 덮어쓴다. 그래서 role이 빠진 설정만 남고 접속이 끊긴다.

Q6. IAM user me에 access entry를 직접 주면 무엇이 좋아지고 무엇이 나빠지나?

좋아지는 점은 role 없이 바로 접속할 수 있다는 것 하나다. 나빠지는 점은 관리할 곳이 늘어나는 것인데, 사람마다 access entry가 생기므로 회수할 때 빠뜨릴 가능성이 있다. 그래서 6장은 role assume을 추천한다.
