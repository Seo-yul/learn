1. tool 설계

tool을 쓰는 쪽

REST API는 개발자가 문서를 읽고 호출하지만, MCP tool은 모델이 이름과 설명과 스키마를 읽고 호출한다. tool 설계의 기준은 대부분 여기에서 나온다.

  • 이름은 모델이 tool을 찾는 단서다. get_data보다 search_customer_orders가 낫다. 동사와 명사를 쓰고, 도메인을 넣고, snake_case로 쓴다.
  • 설명에는 언제 쓰는지를 적는다. 무엇을 하는지는 이름으로 알 수 있으므로, 모델이 헷갈리기 쉬운 경계 조건, 전제 조건, 비슷한 tool과의 차이를 적는다.
  • 인자는 적게 둔다. 선택 인자가 많아질수록 모델이 인자를 잘못 만들 가능성이 커진다. 자주 쓰는 조합은 별도 tool로 나눈다.
  • tool의 전체 개수를 관리한다. tool이 수십 개에서 수백 개가 되면 목록만으로 컨텍스트를 많이 쓰고 모델이 tool을 잘못 고르기 쉬워진다. mount()로 도메인을 나누고 tag나 scope로 노출 범위를 줄인다.

나쁜 예 · 이름이 모호하고 설명에 정보가 없으며 mode 인자의 뜻을 알 수 없다

@mcp.tool
def query(q: str, opt1: str = "",
          opt2: int = 0, mode: str = "a"):
    """쿼리한다."""

좋은 예

@mcp.tool
def search_support_tickets(
    customer_email: str,
    status: Literal["open", "closed"] = "open",
    limit: int = Field(default=10, le=50),
) -> list[Ticket]:
    """고객 이메일로 상담 티켓을 검색한다.
    주문 내역이 아니라 상담 이력이 필요할 때 쓴다.
    결과가 limit보다 많으면 next_cursor를 반환한다."""

Literal, Field, Enum을 쓰면 제약이 스키마에 드러난다. 예를 들어 status: Literal["open", "closed"]는 스키마에 enum으로 나오기 때문에 모델이 다른 값을 만들 가능성이 줄어든다. 잘못된 값을 검증으로 걸러내는 것보다 스키마로 미리 알려 주는 편이 낫다.

2. 반환값 설계

tool의 반환값은 그대로 LLM의 컨텍스트에 들어가므로, 크기가 곧 비용이고 정확도에도 영향을 준다.

고려할 점기준
응답 크기목록은 기본 limit과 cursor 방식의 페이지 나누기를 둔다. 본문이 크면 요약만 반환하고 전체는 resource URI로 읽게 한다.
구조화된 출력반환 타입을 선언하면 결과가 structuredContent로도 나가서 모델이 텍스트를 해석하지 않고 필드를 쓸 수 있다. dict, dataclass, Pydantic 모델을 반환한다.
필요 없는 필드내부 ID, 디버그용 필드, 값이 없는 필드는 응답에서 뺀다.
에러 메시지ToolError("인증이 만료됐다. 토큰을 갱신한 뒤 다시 시도한다")처럼 모델이 다음 행동을 정할 수 있는 내용을 쓴다. stack trace는 로그에만 남긴다.
예외 노출 범위FastMCP(mask_error_details=True)로 설정하면 ToolError의 메시지만 클라이언트에 전달되고 다른 예외의 상세 내용은 가려진다. 모델에게 보여 줄 내용은 ToolError로 올린다.
from fastmcp.exceptions import ToolError

@mcp.tool
def get_order(order_id: str) -> Order:
    order = db.find(order_id)
    if order is None:
        # 모델이 이 문장을 읽고 사용자에게 ID를 다시 확인할 수 있다
        raise ToolError(
            f"주문 {order_id}를 찾을 수 없다. "
            "ID 형식은 ORD-숫자 8자리다. 사용자에게 확인한다.")
    return order

3. 보안

tool의 인자는 모델이 만들고, 모델은 prompt injection의 영향을 받을 수 있다. 그래서 tool은 인증된 사용자가 직접 부르는 내부 함수가 아니라 외부에 열린 API로 보고 설계한다.

항목내용
입력 검증인자는 LLM이 만든 문자열이라서 오염됐을 수 있다. SQL, shell, 파일 경로로 이어지는 인자는 허용 목록으로 검증한다. subprocess에 문자열을 그대로 넘기지 않고, 경로는 기준 디렉터리 안인지 확인하고, SQL은 파라미터 바인딩을 쓴다.
tool poisoningtool의 설명문은 모델에게 지시문처럼 읽힐 수 있고, 설명에 지시를 숨기는 공격이 알려져 있다. 신뢰할 수 없는 원격 MCP 서버를 프록시로 붙일 때는 설명문을 검토한다.
secretAPI key를 tool 인자로 받지 않는다. 인자는 모델의 컨텍스트와 로그에 남기 때문이다. key는 서버의 환경 변수나 secret 저장소에 두고, 사용자의 자격 증명은 토큰으로만 받는다.
되돌릴 수 없는 작업삭제, 결제, 발송 같은 tool에는 annotation을 붙인다. host가 이 힌트를 보고 사용자에게 확인을 요청할 수 있다.
@mcp.tool(annotations={
    "readOnlyHint": False,       # 상태를 바꾸는가
    "destructiveHint": True,     # 되돌릴 수 없는가
    "idempotentHint": False,     # 다시 불러도 결과가 같은가
})
def delete_customer_data(customer_id: str) -> str: ...

4. 인증과 인가

로컬 STDIO 서버에는 인증이 필요 없지만, HTTP로 여는 서버에는 인증이 먼저 있어야 한다.

from fastmcp import FastMCP
from fastmcp.server.auth import JWTVerifier

auth = JWTVerifier(
    jwks_uri="https://idp.example.com/.well-known/jwks.json",
    issuer="https://idp.example.com",
    audience="mcp-server",
    required_scopes=["mcp:read"],   # 서버에 들어오기 위한 최소 scope
)
mcp = FastMCP("SecureServer", auth=auth)
정할 것선택지와 기준
인증 방식IdP가 발급한 JWT를 검증만 하면 되는 경우에는 JWTVerifier를 쓴다. IdP가 클라이언트 동적 등록을 지원하지 않으면 FastMCP의 OAuthProxy를 앞에 두고, OIDC 설정을 읽어서 구성하려면 OIDCProxy를 쓴다.
인가 위치세 곳에서 할 수 있다. 서버 진입(required_scopes), 목록 필터링(scope에 따라 tools/list 결과를 다르게 준다), 실행 시점(middleware에서 토큰의 claim을 검사한다)이다. 목록 필터링과 실행 시점 검사를 함께 해야 목록에는 없는 tool이 호출되는 일을 막을 수 있다.
backend로 토큰 전달tool 안에서 get_access_token()으로 사용자 토큰을 꺼내 backend API 호출에 넘긴다. 서비스 계정으로 바꿔서 호출하면 누가 요청했는지 추적할 수 없게 된다.
세션별로 보이는 toolmiddleware의 on_list_tools에서 claim을 보고 목록을 걸러낸다. 관리자용 tool은 목록에서 아예 숨긴다.
자주 생기는 누락

tools/list만 필터링하고 tools/call은 검사하지 않는 서버가 있다. 이런 서버는 누군가 JSON-RPC 요청을 직접 보내면 목록에 없는 tool도 실행된다. 실행 경로인 on_call_tool에서 반드시 검증하고, 목록 필터링은 그 위에 더하는 방어로 본다.

5. 성능

tool 호출은 대화 중간에 끼어드는 작업이라서, tool이 느리면 그동안 대화가 멈춘다.

항목내용
I/O는 async로동기 함수는 thread pool에서 돌고 async def는 event loop에서 바로 처리된다. 외부 API를 부르는 tool이 많은 서버에서는 동시에 처리할 수 있는 요청 수가 크게 달라진다.
timeoutbackend 호출(httpx의 timeout=)에 timeout을 두고, 넘으면 ToolError로 실패시킨다. 그래야 모델이 다시 시도할지 범위를 줄일지 정할 수 있다.
페이지 나누기목록 tool은 항목과 next_cursor를 함께 반환하는 것으로 정해 둔다. 모델이 다음 페이지를 이어서 요청할 수 있다.
rate limit외부에 공개한 서버는 middleware에서 토큰이나 IP별로 요청 수를 제한한다. 모델이 실패한 호출을 계속 다시 시도할 수 있기 때문이다. FastMCP에는 rate limit middleware가 들어 있다.

느린 backend에 대응하는 예 · timeout과 명확한 실패

import httpx
from fastmcp.exceptions import ToolError

@mcp.tool
async def get_inventory(sku: str) -> dict:
    try:
        async with httpx.AsyncClient(timeout=8.0) as c:
            r = await c.get(f"https://erp.example.com/inv/{sku}")
            r.raise_for_status()
            return r.json()
    except httpx.TimeoutException:
        raise ToolError("ERP 응답이 8초를 넘겼다. 잠시 후 다시 시도하거나 "
                        "SKU 하나로 범위를 좁힌다.")

6. 상태와 세션

서버를 여러 대로 늘릴 수 있는지는 상태를 어디에 두는지에 달려 있어서, 개발을 시작할 때 정해 두는 것이 좋다.

방식설명쓰는 경우
stateless모든 상태를 요청 안에서 해결한다(DB, 토큰, 인자). 서버 인스턴스는 아무것도 기억하지 않는다.기본으로 삼는다. load balancer 뒤에 여러 대를 둘 수 있고 재시작해도 영향이 없다.
외부 세션 저장소FastMCP(session_state_store=...)에 Redis 같은 key-value 저장소를 연결한다.여러 턴에 걸친 작업처럼 대화 상태가 꼭 필요할 때 쓴다.
메모리 안의 상태전역 dict에 상태를 저장한다.프로세스 하나가 세션 하나인 STDIO 로컬 서버에서만 쓴다. HTTP 서버에서는 장애의 원인이 된다.
HTTP와 메모리 안의 세션

Streamable HTTP에는 세션 ID가 있지만, 세션을 메모리에 두고 load balancer 뒤에 여러 대를 두면 재시작하거나 대수를 늘릴 때 세션이 사라진다. 상태가 필요하면 처음부터 외부 저장소를 전제로 설계한다.

7. 배포와 운영

transport는 연결 방식만 정하는 것이 아니라 서버를 운영하는 방식도 함께 정한다.

항목STDIOStreamable HTTP
프로세스클라이언트가 서버를 자식 프로세스로 띄운다독립된 서비스로 띄운다(systemd, 컨테이너, Kubernetes)
인증필요 없다(로컬 사용자를 신뢰한다)필요하다(JWT 검증, OAuth 프록시)
health check해당 없음@mcp.custom_route("/health")를 둔다. load balancer와 컨테이너 probe가 쓴다
확장해당 없음stateless를 전제로 대수를 늘린다. 상태는 외부 저장소에 둔다
업데이트클라이언트가 다시 실행하면 끝난다rolling 배포를 하고, tool 스키마가 바뀔 때 하위 호환을 확인한다
  • 패키징. 로컬용 서버는 PyPI 패키지로 만들어 uvx my-mcp-server로 실행할 수 있게 하는 방식이 널리 쓰인다. 원격 서버는 컨테이너 이미지로 만들고 0.0.0.0에 바인딩한 뒤 TLS는 앞단의 프록시에서 처리한다.
  • 버전 관리. tool 스키마를 바꾸면 호환이 깨질 수 있다. 인자는 선택 인자로 추가하고, 인자를 없애거나 이름을 바꿀 때는 새 tool을 만든 뒤 옛 tool의 설명에 폐기 예정이라고 적어 단계적으로 넘어간다.

8. 관측과 테스트

일반 API 테스트로는 코드가 맞는지만 확인된다. 모델이 tool을 제대로 고르고 인자를 제대로 만드는지는 따로 확인해야 한다.

항목내용
감사 로그누가(subject), 언제, 어떤 tool을, 어떤 인자로 불렀는지와 결과 요약, 걸린 시간을 on_call_tool에서 구조화된 로그로 남긴다. 인자는 민감한 값을 가린 뒤 기록한다.
진행 상황 전달오래 걸리는 작업은 ctx.report_progress()와 ctx.info()로 host에 진행 상황을 알린다. 사용자에게도 디버깅에도 도움이 된다.
테스트 세 단계메모리 안의 Client(mcp)로 단위 테스트를 하고, fastmcp dev inspector로 직접 호출해 확인하고, 실제 모델에 과제를 주어 tool을 맞게 고른 비율과 인자의 정확도를 잰다.
스키마 회귀 테스트tools/list 결과를 snapshot으로 저장해 CI에서 비교한다. 스키마나 설명이 의도치 않게 바뀌면 모델의 행동도 바뀌므로 배포 전에 잡는다.

감사 middleware의 예 · audit과 elapsed는 직접 만드는 함수다

import time
from fastmcp.server.dependencies import get_access_token
from fastmcp.server.middleware import Middleware

class AuditMiddleware(Middleware):
    async def on_call_tool(self, ctx, call_next):
        start = time.monotonic()
        token = get_access_token()
        sub = token.claims.get("sub") if token else None
        try:
            result = await call_next(ctx)
            audit(tool=ctx.message.name, sub=sub,
                  ms=elapsed(start), ok=True)
            return result
        except Exception as e:
            audit(tool=ctx.message.name, sub=sub, ms=elapsed(start),
                  ok=False, err=type(e).__name__)
            raise

9. 피해야 할 설계와 출시 전 점검 목록

9-1. 피해야 할 설계

  • tool 100개를 서버 하나에 모두 넣는다. mount()와 scope로 나눈다.
  • REST endpoint를 1:1로 tool로 바꾼다. 모델이 하는 작업 단위로 다시 설계한다.
  • DB 행 전체나 파일 전체를 그대로 반환한다.
  • 에러가 나면 stack trace를 모델에게 보여 준다.
  • 목록만 필터링하고 호출은 검증하지 않는다.
  • HTTP 서버가 메모리 안의 전역 상태를 쓴다.
  • API key를 tool 인자로 받는다.
  • 외부 API를 동기 I/O로 호출한다.

9-2. 출시 전 점검 목록

  • 모든 tool에 명확한 이름과 설명, Literal이나 Field 제약이 있는가
  • 반환 크기에 제한이 있고 페이지 나누기 방식이 정해져 있는가
  • 되돌릴 수 없는 tool에 annotation이 붙어 있는가
  • 에러 메시지가 다음에 할 일을 알려 주는가
  • 목록 필터링과 호출 검증을 둘 다 하는가
  • backend 호출에 timeout이 있고 ToolError로 바꿔서 올리는가
  • /health 경로와 구조화된 감사 로그가 있는가
  • 재시작해도 문제가 없는 stateless 구조인가
  • tools/list snapshot 비교가 CI에 있고 모델을 붙인 평가를 했는가
