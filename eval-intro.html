1. eval의 정의

eval이란

정해 둔 입력 묶음을 Agent에 넣고, 정해 둔 규칙으로 채점해, 점수를 기록으로 남기는 일이다. 프롬프트나 모델을 바꿀 때마다 같은 시험을 다시 돌려 좋아졌는지 나빠졌는지 본다.

일반 테스트와 다른 점은 두 가지다.

  • 답이 매번 조금씩 다르다. 같은 질문에도 문장이 달라지므로 "글자가 같은가"로 채점할 수 없는 경우가 많다.
  • 합격이 0과 1이 아니다. 20문제 중 17문제 통과처럼 비율로 보기 때문에, 기준선을 정해 두고 비교한다.

2. eval의 세 부품

부품 하는 일 예 (면접 질문 추천 Agent)
데이터셋 입력과 기대 결과의 묶음 지원자 정보와 직무, 그리고 "나와야 하는 질문의 조건"
실행기 문항마다 Agent를 돌리고 결과를 모은다 20문항을 3번씩 실행
채점기 결과가 기대에 맞는지 판정한다 질문이 5개인가, 채점 기준의 항목을 다루는가

"eval 프레임워크"는 이 세 부품을 미리 만들어 둔 도구이고, 개념 자체는 도구 없이도 구현할 수 있다.

3. 채점기 세 종류

종류 방법 장점 약점
코드 채점 정확히 일치, 포함 여부, 정규식, JSON 스키마, 숫자 범위 빠르고 싸고 결과가 늘 같다 문장의 품질은 못 본다
LLM 채점 다른 모델에게 채점 기준표를 주고 판정시킨다 요약, 어조, 근거 같은 것을 볼 수 있다 채점 모델도 틀린다. 사람 판정과 맞는지 먼저 확인해야 한다
사람 채점 사람이 직접 읽고 판정한다 가장 믿을 수 있다 느리고 비싸다. 자주 못 돌린다

실무에서는 순서가 정해져 있다. 코드로 채점할 수 있는 것은 코드로 하고, 안 되는 것만 LLM 채점으로 넘긴다. 사람은 LLM 채점기가 맞는지 표본으로 확인한다.

LLM 채점 기준표는 구체적으로 쓴다. "좋은 답인가"는 나쁜 기준이고, "답이 제공된 문서에 없는 사실을 말하면 실패"가 좋은 기준이다.

4. Agent에서 재는 것

Agent는 답 하나만 내는 것이 아니라 여러 단계를 거치기 때문에 재는 곳이 네 군데다.

재는 곳 질문 예 (일일 점검 Agent)
최종 답 결론이 맞는가 장애가 있는 서비스를 "비정상"으로 판정했는가
과정 올바른 도구를 올바른 인자로 불렀는가 로드밸런서 조회 도구를 점검 대상 모두에 불렀는가
끝 상태 일이 실제로 끝났는가 보고서 메일이 발송됐는가
비용과 속도 토큰, 시간, 단계 수가 얼마인가 한 번 점검에 든 모델 호출 수

과정 채점은 조심해서 쓴다. 도구 호출 순서까지 고정하면 Agent가 더 나은 길을 찾아도 실패로 나오므로, 꼭 지켜야 하는 것만 본다. 예를 들면 "개인정보는 반드시 지정된 조회 도구로 가져온다" 같은 조건이다.

답이 매번 다르므로 같은 문항을 여러 번 돌린다. 5번 중 5번 통과와 5번 중 3번 통과는 품질이 다르기 때문이다.

5. RAG 평가의 두 단계

RAG는 "찾기"와 "답하기"가 따로 실패하기 때문에 둘을 따로 잰다.

단계 재는 것 실패의 모습
검색 필요한 문서가 찾아온 결과에 들어 있는가 규정집의 해당 조항을 못 찾았다
답변의 근거 답이 찾아온 문서에만 근거하는가 문서에 없는 내용을 지어냈다
답변의 관련성 질문에 실제로 답했는가 맞는 말이지만 묻지 않은 것을 답했다

나눠 재면 답이 틀렸을 때 어느 단계가 원인인지 알 수 있다. 사내 규정 Agent라면 "이 질문에는 이 조항이 나와야 한다"는 쌍을 데이터셋으로 만든다.

6. eval을 돌리는 시점

시점 목적 방식
바꾸기 전 프롬프트, 모델, 도구를 바꿔도 되는지 판단 고정된 데이터셋 전체를 돌려 이전 점수와 비교
병합할 때 품질이 떨어진 변경을 막는다 CI에서 작은 묶음을 돌리고 기준선 아래면 실패
운영 중 실제 사용에서 품질이 유지되는지 본다 실제 대화의 표본을 채점하고, 실패 사례를 데이터셋에 추가

이 가운데 운영에서 나온 실패를 데이터셋에 넣는 일이 가장 중요하다. 그래야 같은 실수가 다시 나왔을 때 다음 변경에서 바로 잡힌다.

7. 익숙한 일과의 연결

eval이 낯설어도 그 부품은 평소 하던 일에 이미 들어 있다.

익숙한 일 eval 용어로는 빠져 있는 것
QA 때 베스트 시나리오의 정답과 대조 골든 데이터셋으로 한 사람 채점 반복 실행과 점수 기록
좋은 모델부터 낮은 모델까지 돌려 같은 결과가 나오는 범위에서 가장 싼 모델 선택 모델 비교 eval 문항 수와 통과 기준의 명시
권한별 시나리오를 돌리는 화면 회귀 테스트 기능 회귀 테스트 이것은 화면 기능 검사다. 모델 품질 eval과는 구분한다
도구 코드의 골든 테스트와 변이 검사(mutation test) 고정 기대값 채점, 그리고 채점기가 잡아내는지 검증 Agent의 답이 아니라 도구 코드를 대상으로 한다

변이 검사의 발상은 eval에서도 그대로 통한다. 일부러 틀린 답을 넣었을 때 채점기가 실패로 판정하는지 확인하는 것인데, 통과만 시키는 채점기는 쓸모가 없기 때문이다.

8. 가장 작은 eval의 모습

eval_upgrade_agent.py · 스케치

CASES = [
    {"q": "httpx 0.27에서 0.28로 올려도 되나?",
     "must_call": "analyze_upgrade_impact",        # 과정: 이 도구를 불렀는가
     "must_mention": ["confirmed", "needs_review"]},  # 답: 두 구분을 말했는가
    {"q": "kubernetes 1.33에서 1.34 주의점은?",
     "must_call": "get_release_changes",
     "must_mention": ["Urgent Upgrade Notes"]},
]

def grade(case, answer, tool_calls):
    called = any(c.name == case["must_call"] for c in tool_calls)
    mentioned = all(w in answer for w in case["must_mention"])
    return called and mentioned

def run(agent, runs=3):
    for case in CASES:
        passed = sum(grade(case, *agent(case["q"])) for _ in range(runs))
        print(f'{passed}/{runs}  {case["q"]}')

이 정도만 있어도 eval이다. 여기서 문항을 20개로 늘리고, 모델을 바꿔 두 번 돌려 표를 비교하면 모델 비교 eval이 된다.

9. 직접 해 볼 순서

  1. Agent 하나를 고른다. 답의 근거가 문서에 있는 Agent가 정답을 정하기 쉬워서 시작하기 좋다.
  2. 질문 20개를 쓰는데, 쉬운 것, 어려운 것, 답이 "모른다"여야 하는 것을 섞는다.
  3. 문항마다 통과 조건을 쓰고, 코드로 확인할 수 있는 조건부터 쓴다.
  4. 문항마다 3번씩 돌려 통과 수를 기록하고, 이 값을 기준선으로 삼는다.
  5. 프롬프트를 한 줄 바꾸거나 모델을 바꿔 다시 돌린 다음 표 두 개를 비교한다.
  6. 틀린 답을 일부러 넣어 채점기가 실패로 잡는지 확인한다.

작은 Agent라면 반나절이면 끝난다.
