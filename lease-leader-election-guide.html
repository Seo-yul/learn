Lease와 리더 선출

Kubernetes 학습 · 2026-10-08 작성

watch를 pod 하나에서만 돌리는 방법

1. 용어

용어뜻
watch쿠버네티스 API 서버에 오래 열어 두는 연결이다. 리소스가 바뀔 때마다 그 변경을 알려 준다.
reconcile리소스에 적힌 내용과 클러스터 상태가 같아지도록 클러스터를 바꾸는 일이다.
Lease쿠버네티스가 기본으로 제공하는 리소스 종류다. 지금 자리를 가진 pod의 이름과 그 pod가 마지막으로 갱신한 시각을 기록한다.
리더Lease에 이름이 적힌 pod다.
팔로워리더가 아닌 나머지 pod다. Lease를 읽으며 기다린다.
갱신리더가 Lease의 renewTime을 현재 시각으로 바꿔 API 서버에 다시 저장하는 일이다. 리더가 아직 살아 있다는 표시다.
반납리더가 Lease의 이름 칸을 비우는 일이다. 그러면 팔로워가 다음에 Lease를 읽을 때 바로 획득할 수 있다.

2. watch를 여러 pod가 돌릴 때의 문제

모든 pod는 같은 코드를 돌리기 때문에, pod마다 watch를 돌리면 같은 변경을 pod마다 받아서 같은 일을 pod 수만큼 반복하게 된다.

  • studio는 같은 status를 pod 수만큼 DB에 쓰고, agent registry에도 pod 수만큼 반영한다.
  • studio pod들이 만료된 sandbox pod를 동시에 지우려 한다.
  • operator pod들이 같은 AiAgent나 McpServer 리소스를 동시에 reconcile하면서 서로의 Deployment와 Service를 덮어쓴다.

그래서 watch는 pod 하나만 돌리고 나머지 pod는 기다린다. 어느 pod가 watch를 돌릴지는 Lease가 정한다.

3. Lease

Lease는 쿠버네티스가 기본으로 제공하는 리소스 종류다. ConfigMap처럼 API 서버에 저장되는 기록이고, 스스로 하는 일은 없다.

이름 그대로 기한이 있는 사용권을 적어 두는 기록이라서 도서관 대출 기록을 떠올리면 이해하기 쉽다. 대출 기록에는 빌린 사람과 반납 기한이 적혀 있고, 기한 안에 연장하지 않으면 다른 사람이 그 책을 빌릴 수 있다. Lease에도 지금 자리를 가진 pod의 이름, 마지막으로 연장한 시각, 유효 기간이 적혀 있다.

쿠버네티스 자신도 Lease를 쓴다. 각 노드의 kubelet은 kube-node-lease namespace에 있는 자기 Lease를 주기적으로 갱신해서 노드가 살아 있다고 알리고, kube-scheduler와 kube-controller-manager도 Lease로 리더를 정한다.

studio가 쓰는 Lease의 예시다. 이름, 시각, 버전은 예시 값이다.

apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  name: studio-leader
  resourceVersion: "4810233"
spec:
  holderIdentity: studio-7c9d5b6f8-x2kqp
  leaseDurationSeconds: 15
  acquireTime: "2026-10-08T01:12:40.118Z"
  renewTime: "2026-10-08T01:20:02.531Z"
  leaseTransitions: 3
필드뜻바뀌는 시점
holderIdentity지금 자리를 가진 pod의 이름팔로워가 Lease를 획득할 때 자기 이름으로 바꾼다. studio pod는 종료할 때 이 칸을 비운다.
renewTime리더가 마지막으로 갱신한 시각리더가 2초마다 현재 시각으로 바꾼다.
leaseDurationSeconds갱신 없이 유효한 시간(초)리더가 갱신할 때마다 같은 값(15)을 다시 적는다.
acquireTime지금 리더가 Lease를 획득한 시각새 pod가 Lease를 획득할 때 바뀐다.
leaseTransitions리더가 바뀐 횟수새 pod가 Lease를 획득할 때 1 늘어난다.
resourceVersionLease 객체의 버전쿠버네티스가 Lease를 저장할 때마다 새 값을 붙인다.

3-1. 갱신

갱신은 리더가 Lease의 renewTime을 현재 시각으로 바꿔 API 서버에 다시 저장하는 일이다. 리더는 이 일을 2초마다 하고 다른 필드는 그대로 둔다.

갱신 전

metadata:
  resourceVersion: "4810233"
spec:
  holderIdentity: studio-7c9d5b6f8-x2kqp
  leaseDurationSeconds: 15
  renewTime: "2026-10-08T01:20:02.531Z"

갱신 후 (2초 뒤)

metadata:
  resourceVersion: "4810241"                # 바뀜
spec:
  holderIdentity: studio-7c9d5b6f8-x2kqp
  leaseDurationSeconds: 15
  renewTime: "2026-10-08T01:20:04.536Z"     # 바뀜

리더가 바꾼 것은 renewTime뿐이고, resourceVersion은 쿠버네티스가 저장하면서 새로 붙인 값이다.

팔로워는 renewTime이 바뀌는 것을 보고 리더가 살아 있다고 판단하고, leaseDurationSeconds(15초) 동안 바뀌지 않으면 Lease가 만료됐다고 본다.

3-2. 만료

만료는 쿠버네티스가 처리하지 않는다. 만료된 Lease도 지워지지 않고 그대로 남는다. 쿠버네티스는 Lease를 저장하고 버전을 확인하는 일만 하고, 만료를 판단하고 리더를 정하는 규칙은 모두 pod 쪽 코드에 있다.

클러스터에서 직접 보려면 다음 명령을 쓴다. HOLDER 열에 지금 리더인 pod의 이름이 나온다.

kubectl get lease -n <namespace>
kubectl get lease <Lease 이름> -n <namespace> -o yaml

4. 리더 선출 규칙

모든 pod가 Lease 하나를 함께 쓰고, 다음 네 가지 규칙을 따른다.

  • 리더만 watch를 돌린다.
  • 리더는 2초마다 Lease를 갱신한다.
  • 팔로워는 2초마다 Lease를 읽고, Lease가 15초 동안 바뀌지 않으면 자기 이름을 Lease에 적는다.
  • pod가 Lease에 쓸 때는 자기가 읽은 Lease의 버전(resourceVersion)을 함께 보낸다. 쿠버네티스는 버전이 오래된 쓰기를 409 Conflict로 거절하므로, 팔로워 둘이 동시에 쓰면 먼저 쓴 쪽만 성공한다.

studio의 팔로워도 API 요청은 리더와 똑같이 처리한다. 리더 혼자 하는 일은 watch와 sandbox 정리뿐이다. operator의 팔로워는 기다리기만 한다.

5. 타이머 세 개

타이머값하는 일
lease duration15초팔로워는 Lease가 이 시간 동안 바뀌지 않으면 Lease를 획득한다.
renew deadline10초리더는 이 시간 동안 갱신하지 못하면 스스로 물러난다.
retry period2초각 pod는 이 간격으로 Lease를 갱신하거나 읽는다.

operator는 controller-runtime 기본값을 쓰고, core도 같은 값을 쓴다. core에서는 lease duration이 renew deadline보다 커야 하고 renew deadline은 retry period보다 커야 하는데, 이 순서가 아니면 앱이 시작할 때 에러를 낸다.

6. 리더가 연결을 잃었을 때의 순서

시점일어나는 일
0초Pod A가 Lease를 갱신한다. 그 직후 API 서버와의 연결이 끊긴다.
2~8초Pod A가 2초마다 갱신을 시도하지만 모두 실패한다.
약 10초Pod A가 renew deadline에 닿아서 스스로 물러나고 watch를 끈다.
약 15초Pod B는 약 0초에 마지막 변경을 봤고, 그때부터 잰 자신의 타이머가 15초에 닿는다. Pod B가 Lease를 획득하고 watch를 켠다.

10초부터 15초까지는 어떤 pod도 watch를 돌리지 않는다. 이 5초는 옛 리더와 새 리더가 동시에 watch를 돌리지 않도록 둔 여유다.

Pod A가 연결을 잃는 대신 죽으면 watch는 0초에 바로 멈추는데, Pod B는 그래도 15초를 기다리므로 공백은 약 15초가 된다.

7. pod마다 따로 쓰는 시계

Lease에 적힌 갱신 시각은 리더의 시계로 적은 값이고, 팔로워의 시계는 리더의 시계와 다를 수 있다.

그래서 팔로워는 적힌 시각을 자신의 시계와 비교하지 않는다. Lease가 바뀌는 것을 볼 때마다 자신의 타이머를 새로 시작하고, 이 타이머가 15초에 닿으면 Lease를 획득한다.

core는 client-go와 같은 방식을 쓰고, operator는 controller-runtime을 거쳐 client-go를 쓴다.

8. 새 리더의 상태 복구

새 리더는 먼저 리소스 전체 목록을 읽고 각 리소스의 현재 상태를 처리한 다음, 그 목록의 버전부터 watch를 시작한다.

그래서 공백 동안 생긴 변경도 새 리더가 받는다. 중간 상태는 놓칠 수 있지만 지금 남아 있는 리소스의 최신 상태는 받는다.

operator도 같은 방식으로 동작한다. 각 controller는 시작할 때 자신의 리소스를 모두 나열하고 하나씩 reconcile한다.

10. studio가 watch를 Lease에 연결하는 방식

core는 Lease만 관리하고, 어떤 일이 리더 전용인지는 모른다. 그래서 studio가 core에 listener 목록을 넘기고, core는 pod가 리더가 되거나 리더 자리를 잃을 때 각 listener를 호출한다.

  • pod가 리더가 되면 watch listener가 watch를 켠다. 최대 3번 시도하고, 모두 실패하면 그 pod는 Lease를 잃었다가 다시 획득할 때까지 watch 없이 동작한다.
  • pod가 리더 자리를 잃으면 watch listener가 watch를 끈다.
  • sandbox 정리 listener도 같은 방식으로 동작한다.
  • studio는 선출을 시작하기 전에 모든 listener를 core에 넘긴다. 순서가 바뀌면 listener가 등록되기 전에 pod가 Lease를 획득할 수 있고, 그러면 그 listener는 일을 시작하지 못한다.

11. pod 하나로 돌릴 때

  • 클러스터 밖의 studio. leader election을 켜고 끄는 환경 변수를 false로 설정한다. 그러면 studio는 선출을 건너뛰고, 하나뿐인 프로세스가 바로 watch를 돌린다.
  • 클러스터 안의 studio. 기본값 true를 그대로 둔다. 선출에는 in-cluster 설정이 필요해서, 클러스터 밖에서 true로 두면 시작할 때 선출이 에러로 멈추고 watch도 켜지지 않는다.
  • operator. chart가 항상 --leader-elect를 넘긴다. pod가 하나여도 그 pod가 Lease를 획득하고 controller를 돌린다. 기본 pod 수(replicaCount)는 1이다.
