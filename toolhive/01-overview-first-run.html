ToolHive 개요와 첫 실행

ToolHive 학습 01편 · 2026-10-14 작성 · 2026-11-07 갱신

이 문서는 ToolHive가 무엇이고 어떤 문제를 푸는지 설명하고, 구성 요소와 배포 모드를 지도로 보여 준다. 마지막에는 MCP 서버 하나를 실제 명령으로 실행하고 지우는 과정을 따라간다.

기준 버전은 ToolHive v0.63.0(2026-11-06)이다. 처음에는 v0.53.0 기준으로 썼고, 2026-11-07에 v0.63.0 기준으로 갱신했다. 공식 문서는 2026-10-13 사본을 읽었고, 설치 문서와 CLI quickstart는 2026-11-07에 사이트에서 다시 읽었다. ToolHive는 자주 바뀌므로 실제로 쓰기 전에 공식 문서를 다시 확인해야 한다.

한 문장 요약

ToolHive는 MCP 서버를 컨테이너 안에서 실행하고, 서버마다 proxy를 앞에 두는 플랫폼이다. 로컬에서는 thv CLI나 ToolHive UI로 쓰고, 클러스터에서는 Kubernetes operator로 쓴다. 8장에서는 서버 하나를 thv 명령으로 실행하고 지우는 일곱 단계를 따라간다.

v0.63.0 갱신 요약
  • Homebrew tap이 thv를 cask로 배포하게 됐지만 설치 명령은 그대로다. 7장에 적었다.
  • ToolHive가 설정을 고치는 MCP 클라이언트 목록에 Pi coding agent가 들어가서 2장의 표에 넣었다.
  • thv client connector 명령이 생겼는데, Claude Desktop에 원격 MCP 서버를 proxy 없이 적는 명령이다. 용어집과 2장에 적었다.
  • thv llm setup이 Pi와 Codex도 설정하고, --scopes 플래그가 생겼다. 3장에 적었다.
  • proxy가 RunConfig를 다시 저장할 때 상태 파일을 다시 읽고 secret 값을 지운다. 2장에 적었다.
  • Go 버전, 내장 registry 버전, UI와 registry server 버전을 갱신해서 7장과 10장에 적었다.
  • 인용한 행 번호를 v0.63.0에 맞췄다. 인용한 줄의 동작은 바뀌지 않았고, 아키텍처 문서 네 편도 그대로다.

1. MCP 한눈에 보기

MCP는 AI 앱을 외부 데이터, tool, 작업 흐름에 연결하는 공개 표준이다(docs concepts/mcp-primer). AI 앱은 서비스마다 통합 코드를 따로 만드는 대신 MCP 하나로 파일, 데이터베이스, API에 접근한다.

MCP 메시지는 JSON-RPC 2.0 형식이고, 상태가 있는 session 안에서 오간다. session이 시작되면 양쪽이 지원하는 기능을 서로 알린다.

MCP 명세는 참여자를 셋으로 나눈다.

  • host: AI 앱 자체다. Claude Desktop, Cursor, 직접 만든 agent가 여기에 든다.
  • client: host 안의 커넥터로, 서버 하나와 1:1로 연결한다.
  • server: 기능을 MCP로 제공하는 프로세스다. 로컬 프로세스일 수도 있고 원격 서비스일 수도 있다.

이 문서에서는 host와 client를 합쳐 "MCP 클라이언트"라고 부르는데, ToolHive 문서도 Claude Code 같은 앱을 client라고 부른다(source docs/arch/02-core-concepts.md "Client").

MCP 서버는 세 가지 기능을 제공한다.

기능뜻예
tool모델이 호출하는 함수다. 입력과 출력의 형식은 JSON schema로 정한다.코드베이스 검색, Jira 이슈 만들기
resourcehost나 모델이 읽는 데이터다.파일, 데이터베이스 행, API 응답
prompt사용자가 골라서 쓰는 정형 작업이다."이 PR을 요약해 줘"

transport는 메시지를 나르는 방식이고, 명세의 현행판은 표준 transport를 두 개 정한다.

transport동작상태
stdiohost가 서버를 하위 프로세스로 띄운다. 표준 입력과 표준 출력으로 줄 단위 JSON-RPC를 주고받는다.현행 표준이다. 로컬 서버에 권장한다.
streamable HTTP서버가 독립된 HTTP 서비스로 돈다. endpoint 하나가 POST와 GET을 받는다.현행 표준이다. 원격 서버에 쓴다.
SSEPOST endpoint와 SSE endpoint를 따로 둔다. 2024-11-05판의 방식이다.2025-03-26판에서 streamable HTTP로 바뀌었다. 지금은 deprecated다.

ToolHive는 세 transport를 모두 지원하고(source pkg/transport/types/transport.go:146), 디버깅용 inspector transport도 따로 있다. stdio 서버 앞의 proxy가 HTTP 요청을 stdio로 바꾸는 방법은 02편에서 다룬다.

HTTP transport에서는 MCP가 OAuth 2.1 기반의 인가 흐름을 정한다. stdio transport는 OAuth를 쓰지 않고, stdio 서버가 자격 증명을 환경 변수에서 읽는다(docs concepts/mcp-primer). 인증과 인가는 05편에서 다룬다.

2. ToolHive가 푸는 문제

ToolHive는 MCP 서버를 실행하고 관리하는 오픈소스 플랫폼으로(docs index), Stacklok이 만들고 Apache 2.0 라이선스로 배포한다. 공식 문서는 MCP 서버를 쓸 때의 걸림돌이 주로 운영 쪽에 있다고 본다(docs index "Why ToolHive?").

남이 만든 MCP 서버를 그대로 실행하면 아래 세 문제를 만나는데, ToolHive는 문제마다 답을 하나씩 둔다.

문제 1. 내 컴퓨터에서 도는 남의 코드

stdio 서버는 host가 하위 프로세스로 띄운다(docs concepts/mcp-primer). 하위 프로세스는 보통 사용자와 같은 권한으로 돌기 때문에, 서버 코드가 사용자 파일과 네트워크에 제한 없이 접근할 가능성이 있다.

ToolHive는 서버마다 격리된 컨테이너를 쓴다. 공식 FAQ는 기본 권한이 최소라고 설명한다(docs faq "Is it safe to run MCP servers?"). 컨테이너의 mount와 네트워크 연결은 permission profile이 정하는데(source docs/arch/02-core-concepts.md), profile에는 읽기 mount, 쓰기 mount, 허용할 host와 port가 들어간다. thv run은 네트워크 격리를 기본으로 켜지만(source cmd/thv/app/run_flags.go:302), 격리가 켜져도 어떤 연결을 허용할지는 permission profile이 정한다. registry에 없는 이미지가 받는 기본 profile은 5장에 적었고, 자세한 내용은 03편에서 다룬다.

문제 2. 평문으로 남는 secret

MCP 서버는 API 키 같은 secret을 자주 요구한다(docs guides-cli/secrets-management). stdio 서버는 이 값을 환경 변수로 받는데, 값을 설정 파일에 그대로 적으면 평문이 파일에 남는다.

ToolHive는 secret을 secret provider에 둔다. encrypted provider는 OS keyring에 둔 비밀번호로 secret 파일을 암호화하고, 1Password provider와 environment provider도 있다(docs guides-cli/secrets-management). 실행할 때는 secret을 환경 변수로 넘기기 때문에 설정 파일에는 평문 값이 남지 않는다(docs faq).

thv run은 secret을 처리하기 전에 RunConfig를 저장하는데, 상태 파일에 secret 값이 남지 않게 하려는 순서다(source cmd/thv/app/run.go:254). proxy가 나중에 RunConfig를 다시 저장할 때도 secret 값을 걸러 내며, 원격 서버 인증의 토큰 참조를 적을 때가 그 예다. 이때 proxy는 메모리의 실행 값을 그대로 쓰지 않고, 상태 파일을 다시 읽어 secret 값을 지운 뒤 저장한다(source pkg/runner/runner.go:952).

문제 3. 클라이언트마다 다른 설정 파일

MCP 클라이언트는 각자 자기 설정 파일에서 서버 목록을 읽는데, 파일 위치와 키 이름이 클라이언트마다 다르다. ToolHive 코드에 적힌 네 예는 아래와 같다.

MCP 클라이언트macOS의 설정 파일서버 목록 키근거
VS Code~/Library/Application Support/Code/User/mcp.jsonserverspkg/client/config.go:455
Cursor~/.cursor/mcp.jsonmcpServerspkg/client/config.go:493
Claude Code~/.claude.jsonmcpServerspkg/client/config.go:530
Pi coding agent~/.pi/agent/mcp.jsonmcpServerspkg/client/config.go:1055

Pi는 v0.54.0에서 목록에 들어왔다. PI_CODING_AGENT_DIR 환경 변수가 있으면 ToolHive는 그 디렉터리의 mcp.json을 쓴다(source pkg/client/config.go:1073).

사람이 직접 관리하면 서버를 바꿀 때마다 파일을 하나씩 고쳐야 한다. ToolHive는 사용자가 등록한 클라이언트의 클라이언트 설정을 대신 고쳐 주고, workload가 시작되면 proxy URL을 넣는다(source pkg/runner/runner.go:694). 이 부분은 04편에서 자세히 다룬다.

다만 Claude Desktop의 클라이언트 설정에는 ToolHive가 workload를 넣지 않는다. 대신 v0.55.0부터 thv client connector add가 Claude Desktop에 원격 MCP 서버를 connector로 적는다. 이때는 ToolHive가 proxy를 두지 않고 Claude Desktop이 그 서버에 직접 로그인한다. 이 명령은 thv llm setup --client claude-desktop을 먼저 실행한 상태를 전제로 한다(source cmd/thv/app/client_connector.go:22).

CLI에는 thv llm 명령도 있는데, Claude Code 같은 코딩 도구를 OIDC로 보호된 LLM gateway에 연결하는 기능이다(source cmd/thv/app/llm.go:32). v0.63.0의 thv llm setup은 코딩 도구 여덟 가지를 찾아 설정하고, Pi, Claude Desktop, Codex도 그 안에 있다(source cmd/thv/app/llm.go:300). --scopes 플래그는 요청할 OIDC scope를 정한다(source cmd/thv/app/llm.go:87). --bedrock-compat 플래그는 AWS Bedrock으로 가는 gateway에 쓰는데, 이때 setup은 Claude Code와 Codex의 모델을 Bedrock 모델로 고정한다(source cmd/thv/app/llm.go:431). 이 문서에서는 이 기능을 다루지 않는다.

로컬 CLI

사용자가 thv run을 실행하면 ToolHive는 다음 순서로 움직인다(source docs/arch/01-deployment-modes.md "How It Works").

  1. thv가 인자를 읽고 RunConfig를 만든다.
  2. thv가 컨테이너 런타임을 찾는데, Podman, Docker, Colima 순서로 소켓을 확인한다(source pkg/container/docker/sdk/factory.go:57).
  3. thv가 이미지를 받고 RunConfig를 저장한다(source cmd/thv/app/run_flags.go:452, cmd/thv/app/run.go:255).
  4. thv가 자식 프로세스를 띄우는데, 이때 쓰는 명령은 thv start <이름> --foreground다(source pkg/workloads/manager.go:747).
  5. 자식 프로세스가 컨테이너를 만들고 proxy를 연다(source pkg/runner/runner.go:492). proxy는 MCP 클라이언트가 접속할 로컬 HTTP endpoint다.
  6. 부모 thv는 곧바로 끝나고, 자식 프로세스는 부모와 분리된 채 계속 돈다.

아키텍처 문서의 "How It Works" 목록은 부모 쪽이 컨테이너를 만든다고 적지만, 같은 문서의 그림과 v0.63.0 코드에서는 자식 프로세스가 만든다. 이 문서는 코드를 따랐다.

로컬 모드는 상태를 파일로 남기는데, 위치는 운영체제마다 다르다(source docs/arch/01-deployment-modes.md "File Locations").

로컬 UI

ToolHive UI는 Electron으로 만든 데스크톱 앱이다(source toolhive-studio package.json). UI는 시작할 때 함께 들어 있는 thv로 API 서버를 띄우는데, 실행 인자는 thv serve --openapi --socket=<경로>다(source toolhive-studio main/src/toolhive-manager.ts:142).

이때 API 서버는 TCP 포트 대신 UNIX socket으로 요청을 받고, Windows에서는 named pipe를 쓴다. 그래서 같은 컴퓨터의 프로세스만 API에 접근한다(source docs/arch/01-deployment-modes.md "Local Mode: UI").

REST API 경로는 대부분 /api/v1beta/로 시작하고, 그 아래에 workloads, registry, clients, groups, secrets, skills 등이 있다(source pkg/api/server.go:451). --socket을 주지 않으면 API 서버는 127.0.0.1:8080에서 연결을 받는다(source cmd/thv/app/server.go:157).

2026-11-07 기준 UI의 최신 릴리스는 v0.40.2(2026-10-14)이고, 여기에 들어 있는 thv는 v0.53.0이다(source toolhive-studio utils/constants.ts:6). 따라서 UI로 쓸 때의 동작은 이 문서의 기준 버전 v0.63.0과 다를 가능성이 있다.

Kubernetes

사용자가 MCPServer를 적용하면 다음 일이 차례로 일어난다(source docs/arch/01-deployment-modes.md).

  1. operator가 MCPServer를 watch하고 reconcile한다.
  2. operator가 thv-proxyrunner를 실행하는 Deployment와 Service를 만들고, RunConfig는 ConfigMap으로 넣는다.
  3. proxy runner가 Kubernetes API로 MCP 서버 StatefulSet을 만든다(source pkg/container/kubernetes/client.go:518).
  4. MCP 클라이언트의 요청은 Service, proxy runner, MCP 서버 pod 순서로 흐른다.

operator는 proxy를 직접 실행하지 않고 MCP 서버 컨테이너도 직접 만들지 않는다. 두 일은 proxy runner가 맡는다(source docs/arch/01-deployment-modes.md "Why Two Binaries?"). 다만 StatefulSet의 수명 주기는 operator가 관리하고, 그 StatefulSet에 owner reference도 operator가 붙인다. StatefulSet이 지워지면 operator가 proxy Deployment를 다시 시작하고, 그러면 proxy runner가 StatefulSet을 다시 만든다(source cmd/thv-operator/controllers/mcpserver_statefulset.go:29). 07편에서 자세히 다룬다.

모드 사이 옮기기

로컬 workload를 Kubernetes로 옮기려면 다음 순서로 작업해야 한다.

  1. 로컬 workload를 MCPServer YAML로 내보낸다: thv export my-server ./my-server.yaml --format k8s
  2. 출력에 빠진 설정을 따로 만든다. secret, OIDC, telemetry, tool 필터 설정은 별도 리소스가 필요하다.
  3. 클러스터에 적용한다: kubectl apply -f my-server.yaml

--format k8s는 v0.63.0 코드에 있다(source cmd/thv/app/export.go:46). 아키텍처 문서는 이 변환을 "계획 중"이라고 적는데, 이 부분은 문서가 코드보다 늦다. 원격 서버는 이 방식으로 내보내지 못하고(source pkg/export/k8s.go:42), permission profile도 내보내지 않는다. 코드 주석은 operator가 spec.permissionProfile을 무시하기 때문이라고 적는다(source pkg/export/k8s.go:63).

반대 방향은 아키텍처 문서가 손으로 옮기는 순서만 적고 있어서, 다음 순서로 직접 옮겨야 한다.

  1. MCPServer 정의를 읽는다: kubectl get mcpserver my-server -o yaml
  2. 필요한 필드를 RunConfig 형식으로 옮겨 적는다.
  3. 로컬에서 실행한다: thv run --from-config runconfig.json

로컬끼리는 thv export의 기본 JSON 형식과 thv run --from-config를 쓴다(source docs/arch/01-deployment-modes.md "Migration Paths").

6. MCP 서버를 실행하는 다섯 가지 방법

thv run은 MCP 서버를 다섯 가지 방법으로 실행한다(source cmd/thv/app/run.go:36).

방법명령ToolHive가 하는 일
1. registry에서thv run server-nameregistry 항목의 이미지, transport, 권한, 환경 변수를 그대로 쓴다.
2. 컨테이너 이미지로thv run ghcr.io/example/mcp-server:latest지정한 이미지를 바로 실행한다.
3. 프로토콜 scheme으로thv run uvx://package-name
npx://, go://도 받는다.		패키지를 실행하는 이미지를 실행 시점에 만든다. go://는 ./나 ../로 시작하는 로컬 경로도 받는다.
4. 내보낸 설정으로thv run --from-config <path>예전에 내보낸 RunConfig로 같은 workload를 다시 만든다.
5. 원격 서버로thv run <URL> [--name <name>]컨테이너를 만들지 않는다. 원격 URL 앞에 proxy만 둔다.

registry에 없는 이미지는 transport 정보가 없어서, --transport가 없으면 thv run은 streamable-http를 쓴다(source cmd/thv/app/run_flags.go:595). 공식 문서는 stdio를 기본으로 적는데, 이 차이는 02편 6장에서 다룬다.

다섯 방법의 결과는 모두 workload 하나다. ToolHive는 원격 서버도 로컬 workload처럼 관리해서 클라이언트 설정, tool 필터, 내보내기를 똑같이 쓴다(source cmd/thv/app/run.go:74).

방법 3의 scheme은 셋이다(source docs/arch/00-overview.md "Protocol Builds"). uvx://는 Python 패키지에, npx://는 Node.js 패키지에, go://는 Go 패키지에 쓴다.

7. 설치

준비물

ToolHive는 macOS, Linux, Windows에서 돌고, 로컬 모드에는 컨테이너 런타임이 하나 필요하다(docs guides-cli/install).

  • Docker 또는 Docker Desktop
  • Podman 또는 Podman Desktop
  • Colima (Docker 모드)
  • Rancher Desktop (dockerd/moby 모드, 실험 단계)

공식 문서는 ToolHive가 CPU, 메모리, 디스크를 조금만 쓴다고 설명하는데, 실제 양은 실행하는 서버 수에 달려 있다.

CLI 설치

공식 문서는 macOS와 Linux에 Homebrew를 권하고, Windows에 WinGet을 권한다(docs guides-cli/install).

# macOS, Linux
brew tap stacklok/tap
brew install thv

# Windows
winget install stacklok.thv

# 소스에서 빌드
git clone https://github.com/stacklok/toolhive.git
cd toolhive
go install ./cmd/thv

v0.55.1부터 Homebrew tap은 thv를 cask로 배포한다(source .goreleaser.yaml:103). 설치 명령은 그대로이고, 공식 설치 문서도 cask를 따로 말하지 않는다. macOS에서는 cask가 설치 뒤 바이너리의 quarantine 속성을 지우는데, 바이너리가 서명은 됐지만 notarize는 되지 않았기 때문이다(source .goreleaser.yaml:115).

릴리스 페이지에는 운영체제별 바이너리 압축 파일도 있다. 공식 문서는 소스 빌드에 Go 1.24 이상이 필요하다고 적지만, v0.63.0의 go.mod는 go 1.27을 적는다(source go.mod:3). 그래서 소스로 빌드하려면 Go 1.27 이상을 준비해야 한다.

설치 뒤에는 두 명령으로 확인해야 한다.

thv version          # 버전, commit, 빌드 날짜를 보여 준다
thv runtime check    # 컨테이너 런타임이 응답하는지 확인한다

thv runtime check는 컨테이너 런타임에 ping을 보낸다(source cmd/thv/app/runtime.go:26).

UI 설치

UI는 운영체제별 설치 파일로 설치한다(docs guides-ui/install).

운영체제설치 파일
macOSApple silicon용 ToolHive-arm64.dmg, Intel용 ToolHive-x64.dmg
WindowsToolHive.Setup.exe
LinuxRPM 패키지, DEB 패키지, tarball

UI는 CLI를 함께 설치하고 관리한다. 함께 들어 있는 CLI를 가리키는 symlink를 만들고 셸의 PATH를 바꾸기 때문에, 터미널의 thv는 UI가 관리하는 CLI가 된다(docs guides-ui/cli-access).

UI가 설치된 상태에서 따로 설치한 CLI를 실행하면 충돌 오류가 나는데, Homebrew, WinGet, 직접 설치가 모두 해당한다. 공식 문서는 새 터미널을 열어 UI가 관리하는 CLI를 쓰는 방법을 먼저 권하고, 따로 설치한 CLI를 지우는 방법도 있다(docs guides-cli/install "CLI conflict resolution").

ToolHive는 익명 사용 지표를 기본으로 모은다. 공식 문서는 tool 호출 횟수만 모은다고 밝히고 있으며, 끄려면 thv config usage-metrics disable을 실행해야 한다(docs faq).

    thv mcp list tools --server toolhive-doc-mcp

    이 명령은 MCP 클라이언트 대신 workload의 URL에 접속해 tool 목록을 받는다. --server에는 URL이나 실행 중인 workload 이름을 준다(source cmd/thv/app/mcp.go:239). 공식 quickstart는 이 서버의 tool로 query_docs와 get_chunk를 든다.

    클라이언트를 다시 시작해야 설정이 반영될 수도 있다. 공식 quickstart는 아래 질문을 예로 든다.

    What is a Virtual MCP Server and how do I use it with ToolHive?

    모델은 query_docs tool로 문서를 검색하고 답한다.

  7. 서버를 멈추고 지운다.

    thv stop toolhive-doc-mcp
thv rm toolhive-doc-mcp

    stop은 proxy 프로세스를 끝내고 컨테이너를 멈춘다. 컨테이너를 지우지는 않으므로 thv start를 실행하면 서버가 빨리 다시 시작되고, 등록한 클라이언트의 클라이언트 설정에서는 이 서버를 뺀다(source pkg/workloads/manager.go:1659). rm은 컨테이너까지 지운다.

컨테이너를 쓰고 싶지 않으면 thv run toolhive-doc-mcp-remote를 대신 실행하면 된다. 이 항목은 원격 endpoint https://toolhive-doc-mcp.stacklok.com/mcp에 proxy만 붙인다(docs guides-cli/quickstart).

9. 첫 실행: UI

UI quickstart는 같은 서버를 화면에서 실행한다(docs guides-ui/quickstart). 버튼 이름은 앱의 영어 표기를 그대로 적었다.

다음 순서로 따라 하면 된다.

  1. 설치 파일로 앱을 설치하고 연다.
  2. 위쪽 메뉴에서 Registry 화면을 연다. 내장 registry의 서버 목록이 나온다.
  3. ToolHive Docs 항목을 누른다. registry 이름은 toolhive-doc-mcp다.
  4. Install server 버튼을 누른다. 서버가 MCP Servers 화면에 나타난다.
  5. Clients 화면에서 쓰려는 클라이언트의 스위치를 켠다.
  6. 클라이언트에서 ToolHive에 관해 질문한다. 설정이 반영되지 않았으면 클라이언트를 다시 시작한다.

화면 뒤에서는 CLI와 같은 일이 일어난다. UI가 API 서버에 요청을 보내면 API 서버가 proxy 자식 프로세스를 띄운다. 서버가 시작되지 않으면 컨테이너 런타임이 돌고 있는지 먼저 확인해야 한다.

12. 자가 점검 문제

먼저 답을 생각한 다음 펼쳐서 확인한다.

Q1. stdio MCP 서버를 MCP 클라이언트가 직접 실행할 때 누가 서버 프로세스를 띄우는가? ToolHive를 쓰면 무엇이 바뀌는가?

MCP 명세에서는 host가 서버를 하위 프로세스로 띄우고, 이 프로세스는 보통 사용자와 같은 권한으로 돈다. ToolHive를 쓰면 서버가 격리된 컨테이너에서 돌고, MCP 클라이언트는 하위 프로세스 대신 proxy의 HTTP endpoint에 접속한다.

Q2. ToolHive가 푸는 세 문제와 각각의 답을 말해 보라.

첫째는 남의 코드가 내 권한으로 도는 문제이고, ToolHive는 컨테이너, permission profile, 네트워크 격리로 서버의 접근 범위를 줄인다. 둘째는 secret이 평문으로 남는 문제이고, ToolHive는 secret provider에 값을 두고 실행할 때만 넘긴다. 셋째는 클라이언트마다 설정 파일이 다른 문제이고, ToolHive는 등록한 클라이언트의 클라이언트 설정을 대신 고친다.

Q3. 로컬 CLI 모드에서 thv run이 끝난 뒤에도 proxy가 살아 있는 이유는?

thv run은 자식 프로세스 thv start <이름> --foreground를 띄우고 끝난다. 자식 프로세스는 부모와 분리돼 있어서, 부모가 끝나도 계속 돌면서 proxy를 연다.

Q4. ToolHive UI는 컨테이너를 직접 만드는가?

만들지 않는다. UI는 thv serve로 API 서버를 띄우고 UNIX socket으로 요청을 보낸다. API 서버는 CLI와 같은 함수로 proxy 자식 프로세스를 띄우고, 컨테이너는 그 자식 프로세스가 만든다.

Q5. Kubernetes 모드에서 MCP 서버 StatefulSet은 누가 만드는가?

proxy runner(thv-proxyrunner)가 만든다. operator는 proxy runner의 Deployment와 Service를 만들고, MCP 서버의 컨테이너는 직접 만들지 않는다.

Q6. registry, 이미지 저장소, registry server는 어떻게 다른가?

registry는 ToolHive가 읽는 MCP 서버 목록이고, 이미지 저장소는 ghcr.io처럼 컨테이너 이미지를 보관하는 곳이다. registry 항목이 이미지 저장소의 이미지를 가리킨다. registry server는 registry를 API로 제공하는 별도 서버다. 내장 registry는 바이너리 안에 들어 있어서 별도 서버가 필요 없다.

Q7. thv run에 --proxy-port를 주지 않으면 proxy는 어느 포트에서 연결을 받는가?

ToolHive가 10000부터 65535 사이의 빈 포트를 임의로 고르고, host는 기본으로 127.0.0.1이다. 그래서 같은 서버라도 실행할 때마다 URL의 포트가 달라지는데, 등록한 클라이언트의 클라이언트 설정은 ToolHive가 새 URL로 고친다.

Q8. thv stop과 thv rm은 무엇이 다른가?

thv stop은 proxy 프로세스를 끝내고 컨테이너를 멈춘다. 컨테이너를 지우지는 않으므로 thv start를 실행하면 서버가 빨리 다시 시작된다. thv rm은 컨테이너까지 지운다.

Q9. 로컬 workload를 Kubernetes로 옮길 때 thv export --format k8s만으로 충분한가?

서버가 secret, OIDC, telemetry, tool 필터를 쓰면 충분하지 않다. 이 설정은 출력에 빠지기 때문에 Kubernetes Secret, MCPOIDCConfig, MCPTelemetryConfig, MCPToolConfig를 따로 만들어야 한다. permission profile도 출력에 빠지고, 원격 서버는 이 방식으로 내보내지 못한다.

Q10. skill은 MCP 서버와 무엇이 다른가?

MCP 서버는 MCP 클라이언트가 호출하는 tool을 제공한다. skill은 SKILL.md로 된 지시 묶음이라서, 호출할 tool이 아니라 지식과 규칙을 준다. ToolHive는 skill을 workload로 실행하지 않고 MCP 클라이언트에 설치한다.

Homebrew cask는 .goreleaser.yaml에서 확인했고, stacklok/homebrew-tap의 Casks/thv.rb도 읽었는데 그 파일의 version은 0.63.0이다. toolhive-studio와 toolhive-registry-server의 최신 태그는 GitHub API로 확인했다.

문서와 코드가 다른 곳

아키텍처 문서는 Kubernetes 변환 도구를 "계획 중"이라고 적지만 코드에는 thv export --format k8s가 있다. 아키텍처 문서의 --tool 플래그는 코드에서 --tools다. 아키텍처 문서는 permission profile의 기본값을 none으로 적는데, 플래그 설명은 registry 항목의 profile을 쓰고 없으면 network를 쓴다고 적는다. 공식 설치 문서는 소스 빌드에 Go 1.24 이상을 적지만 go.mod는 1.27을 적는다. 공식 설치 문서는 Homebrew 명령만 적고 cask를 말하지 않는데, tap은 v0.55.1부터 cask로 배포한다. 아키텍처 문서의 로컬 CLI 단계 목록은 부모가 컨테이너를 만든다고 적지만 코드에서는 자식 프로세스가 만든다. 공식 FAQ는 기본 권한이 최소라고 적는데, 코드에서 registry에 없는 이미지는 나가는 연결을 모두 허용하는 network profile을 받는다. 공식 quickstart는 thv run이 알려 주는 로그 파일을 서버 로그라고 부르지만, 코드에서 그 파일은 proxy 프로세스의 출력을 받는다.

대조하지 못한 것

이 문서를 쓰면서 명령을 실제로 실행하지는 않았고, 출력 예는 공식 quickstart의 것이다. toolhive-doc-mcp의 transport와 tool 목록은 catalog 모듈 원본과 대조하지 않았다. 공식 문서는 remote 변형이 컨테이너 런타임 없이 돈다고 적지만 코드로 확인하지 않았다. UI 화면의 버튼 이름은 공식 문서에서 가져왔고 앱에서 확인하지 않았다. Windows와 Linux의 UI 파일 위치는 다루지 않았다. 공식 문서 사본은 2026-10-13 것이고, 2026-11-07에는 설치 문서와 CLI quickstart만 사이트에서 다시 읽었다. toolhive-studio v0.40.2는 utils/constants.ts와 main/src/toolhive-manager.ts만 GitHub API로 읽었고, package.json의 내용은 v0.40.1에서 읽은 것이다. Homebrew cask 설치는 실제로 실행하지 않았고, Windows용 Claude Desktop credential helper는 코드로 확인하지 않았다.

회사의 주장

README는 semantic tool search가 LLM 토큰 사용량을 최대 85% 줄인다고 적는다(README.md:31). 이 수치는 Stacklok의 주장이고, 이 문서에서는 확인하지 않았다. 이 기능은 08편에서 다룬다. 익명 사용 지표가 tool 호출 횟수만 모은다는 내용도 공식 문서의 설명이다.
