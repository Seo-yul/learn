ToolHive와 agentgateway 비교

MCP gateway와 AI gateway의 차이 · 2026-10-13 작성

이 문서는 2026-10-13에 두 프로젝트의 GitHub 저장소와 공식 문서를 확인해서 썼다.

기준 버전은 ToolHive v0.52.0과 agentgateway v1.6.0이다. 두 프로젝트 모두 자주 바뀌기 때문에 실제로 쓰기 전에 공식 문서를 다시 확인해야 한다.

한 문장 요약

ToolHive는 MCP 서버를 컨테이너로 실행하고 관리하는 플랫폼이고, agentgateway는 에이전트의 요청을 목적지로 전달하는 프록시다.

ToolHive는 MCP만 다루는 대신 MCP 서버의 실행까지 맡는다. agentgateway는 MCP, A2A, LLM 요청을 모두 다루지만, MCP 서버의 실행은 보통 다른 시스템이 맡는다.

1. 질문의 전제 확인

질문은 ToolHive를 MCP gateway로, agentgateway를 Solo.io의 AI gateway로 불렀는데, 두 이름은 각각 일부만 맞다.

  1. ToolHive는 gateway보다 넓다. ToolHive의 중심 기능은 MCP 서버 실행이고, MCP gateway 기능은 vMCP라는 구성 요소 하나가 맡는다.
  2. agentgateway는 AI gateway보다 넓다. LLM 요청 외에 MCP 요청과 A2A 요청도 전달하며, Linux Foundation은 agentgateway를 "AI-native proxy"라고 소개한다.
  3. 오픈소스 agentgateway는 재단 프로젝트다. Solo.io가 만들어 2025-08-25에 Linux Foundation에 기증했고, 2026-06-04부터는 Agentic AI Foundation(AAIF)이 호스팅한다. Solo.io는 상용판인 Solo Enterprise for agentgateway를 판매한다.
  4. Stacklok에도 AI Gateway가 있다. 다만 이 제품은 상용판인 Stacklok Enterprise에 들어 있고, 오픈소스 ToolHive에는 없다.

이 문서는 오픈소스판끼리 비교하고, 상용판 기능은 따로 표시한다.

MCP 서버를 실행하는 방식

ToolHive는 MCP 서버 하나를 다음 순서로 실행한다.

  1. 컨테이너 런타임에서 MCP 서버 컨테이너를 시작한다. Docker, Podman, Colima를 지원한다.
  2. 서버 앞에 proxy를 하나 붙인다.
  3. proxy는 요청마다 미들웨어를 적용하는데, 미들웨어에는 인증, 인가, 감사 로그 등이 있다.
  4. stdio 서버면 proxy가 HTTP 요청을 표준 입력으로 보내고, 응답은 표준 출력에서 읽는다.

Kubernetes에서는 operator가 같은 일을 하는데, proxy runner를 Deployment로, MCP 서버를 StatefulSet으로 만든다.

ToolHive는 이미지가 없는 서버도 실행한다. npx://, uvx://, go:// 형식을 주면 ToolHive가 이미지를 빌드해서 실행하는 방식이다.

ToolHive는 원격 MCP 서버에도 연결한다. 이때는 서버를 실행하지 않고 proxy만 붙이며, Kubernetes에서는 MCPRemoteProxy가 이 일을 한다.

격리와 secret

ToolHive는 컨테이너마다 다음 제한을 건다.

  • 파일 시스템: permission profile에 읽기 mount와 쓰기 mount를 지정한다.
  • 네트워크: 나가는 연결의 host와 port를 허용 목록으로 지정한다. --isolate-network의 기본값은 true다.
  • secret: 암호화 저장소(AES-256-GCM), 1Password, 환경 변수 중 하나에 두고, Kubernetes에서는 Secret을 쓴다.
  • 이미지 검증: registry의 Sigstore 정보로 이미지 출처를 확인하며, 기본 모드는 warn이다.

MCPServer는 실행할 컨테이너 이미지를 가지는데, 이 점이 agentgateway의 리소스와 가장 크게 다르다.

5. agentgateway의 구조

설정을 받는 방식

agentgateway는 세 가지 방식으로 설정을 받는다.

  1. 정적 설정
  2. 로컬 YAML 파일이나 JSON 파일. 파일이 바뀌면 agentgateway가 다시 읽는다.
  3. control plane이 xDS로 보내는 설정. Envoy의 xDS transport를 쓰지만, 메시지 형식은 agentgateway 자체 protobuf다.

LLM gateway 기능

  • failover: provider 우선순위 그룹을 8개까지 두고, v1.6부터는 상태가 나쁜 provider를 기본으로 제외한다.
  • LLM 토큰 rate limit: 요청 시점과 응답 시점에 모두 확인한다.
  • 비용 추적: v1.6부터 모델 비용 표를 내장하고, 로그, trace, 메트릭에 USD 비용을 기록한다.
  • guardrail: regex, PII 탐지, OpenAI moderation, 외부 webhook 등이 있고, 여러 guardrail을 겹쳐서 건다.
  • inference routing: Gateway API Inference Extension을 지원해서 HTTPRoute가 InferencePool을 목적지로 가리킨다.

gateway 쪽 응답 캐시는 찾지 못했다. promptCaching은 provider에 캐시 표시만 붙인다.

Kubernetes 리소스

agentgateway는 Gateway API를 따른다. GatewayClass 이름은 agentgateway이고, 경로는 HTTPRoute, GRPCRoute, TCPRoute, TLSRoute로 정한다.

자체 CRD는 agentgateway.dev/v1alpha1에 4종이 있다.

kind하는 일
AgentgatewayBackend목적지를 정의한다. MCP 서버, LLM provider, A2A 에이전트 등이다.
AgentgatewayPolicy인증, 인가, rate limit 같은 정책을 정의한다.
AgentgatewayParameters, AgentgatewayModel이름만 확인했다. 세부 역할은 공식 문서에서 확인해야 한다.

아래 예는 공식 문서에서 가져왔고, MCP 서버는 사용자가 미리 배포해야 한다.

  name: mcp-backend

kind: HTTPRoute
metadata:
  name: mcp

  parentRefs:
    - name: agentgateway-proxy

      - path:
          type: PathPrefix
          value: /mcp

      - name: mcp-backend
        group: agentgateway.dev

AgentgatewayBackend는 이미 실행 중인 서버의 주소를 가지고, 컨테이너 이미지 필드는 없다.

standalone 모드의 예는 다음과 같은데, 이 예에서는 agentgateway가 npx 프로세스를 직접 시작한다.

mcp:
  port: 3000
  targets:
  - name: everything
    stdio:
      cmd: npx
      args: ["@modelcontextprotocol/server-everything"]

Rust를 고른 이유와 성능 주장

  • 프로젝트는 성능과 메모리 안전성 때문에 Rust를 골랐다고 설명하는데, Istio ztunnel과 같은 이유다.
  • Envoy를 쓰지 않은 이유도 밝혔는데, 에이전트 프로토콜을 지원하려면 Envoy 구조를 크게 바꿔야 했다는 설명이다.
  • 프로젝트 발표 수치: 512 연결에서 약 50만 QPS, 3만 QPS에서 P99 0.2 ms 미만.

모든 성능 수치는 프로젝트가 직접 발표한 것이고, 제3자 벤치마크는 찾지 못했다.

7. 같은 일을 다르게 하는 부분

7.1 집계

두 제품 모두 여러 MCP 서버를 endpoint 하나로 묶지만, 이름이 겹칠 때의 처리가 다르다.

vMCP는 MCPGroup 하나에 속한 서버를 집계하고, tool, 리소스, 프롬프트를 모두 묶는다. 이름이 겹치면 세 전략 중 하나를 쓴다.

전략동작
prefix (기본)모든 tool 이름 앞에 서버 이름을 붙인다.
priority순위가 가장 높은 서버의 tool만 남긴다. 순위는 priorityOrder로 정한다.
manual겹치는 tool마다 사용자가 이름을 정한다. 하나라도 빠지면 vMCP가 시작하지 않는다.

agentgateway는 MCP backend 하나에 target 여러 개를 두고, target이 둘 이상이면 tool 이름 앞에 target 이름을 붙인다. 이 동작은 prefixMode로 바꾸며, 값은 Conditional, Always, Never다.

ToolHive는 집계 위에 기능을 더 얹는다.

  • composite tool: 여러 tool 호출을 DAG workflow 하나로 묶는다.
  • optimizer: 클라이언트에게 find_tool과 call_tool만 보여 주고, 키워드 검색과 의미 검색으로 tool을 찾는다.
  • code mode: 에이전트가 Starlark 스크립트로 tool 여러 개를 호출하는 기능이고, 기본으로 꺼져 있다.

Stacklok은 optimizer가 LLM 토큰을 60~85% 줄인다고 주장하는데, 이 수치는 회사 발표다. agentgateway 오픈소스판에서 같은 기능은 확인하지 못했고, Solo.io 상용판이 tool search와 code mode를 제공한다.

7.2 인가

두 제품은 허용하지 않은 tool을 목록 응답에서 지워서, 클라이언트는 호출이 허용된 tool만 본다. 정책 언어는 서로 다르다.

ToolHive는 Cedar를 쓰고, Cedar 정책은 principal, action, resource를 명시한다.

permit(principal, action == Action::"call_tool", resource == Tool::"calculator");

agentgateway는 CEL 식을 쓰는데, 식 하나가 access token의 claim과 MCP 요청 정보를 함께 검사한다.

jwt.sub == "test-user" && mcp.tool.name == "add"

외부 판단 서버도 두 제품 모두 지원한다. ToolHive는 HTTP PDP를, agentgateway는 gRPC 서버(ExtMCP)를 쓰고, ExtMCP는 tool 호출을 허용하거나, 바꾸거나, 거부한다.

7.3 rate limit

  • ToolHive는 MCP 요청 수를 세고, 범위는 전체 공유, 사용자별, tool별이다.
  • agentgateway는 요청 수와 LLM 토큰 수를 센다.

출력 토큰 수는 응답이 와야 알 수 있어서 LLM 토큰 rate limit은 응답 시점에도 확인해야 한다. agentgateway는 요청 시점과 응답 시점에 모두 확인한다.

7.4 Kubernetes 모델

ToolHive는 MCP 서버 자체를 리소스로 정의해서, MCPServer 하나가 실행할 서버 하나다. 그래서 ToolHive CRD는 워크로드를 만든다.

agentgateway는 Gateway API의 모델을 따라서 Gateway와 HTTPRoute가 경로를 정하고, AgentgatewayBackend가 목적지를 정한다. 그래서 agentgateway CRD는 라우팅 규칙을 만든다.

프로젝트 버전과 CRD 버전은 반대 방향이다. ToolHive는 v0.52지만 CRD는 v1beta1이고, agentgateway는 v1.6이지만 CRD는 v1alpha1이다.

9. 함께 쓰는 구성

두 제품은 겹치는 부분보다 다른 부분이 커서, 두 제품을 함께 쓰는 구성도 생각할 수 있다.

이 구성에서 두 제품은 다음과 같이 일을 나눈다.

  1. ToolHive operator가 MCP 서버를 컨테이너로 실행한다.
  2. vMCP가 그 서버들을 endpoint 하나로 집계한다.
  3. agentgateway가 vMCP endpoint를 MCP backend로 등록한다.
  4. agentgateway는 같은 proxy에서 LLM 요청과 A2A 요청도 받는다.

이 구성은 작성자가 두 제품의 기능을 조합한 예다. 두 프로젝트의 공식 문서에서 이 조합을 확인하지 않았고, 실제로 동작하는지도 시험하지 않았다.

작성자 의견: 이 구성에서는 인증이 두 번 일어날 수 있어서 access token 흐름을 먼저 설계해야 한다. 집계, 인가, 감사 로그처럼 겹치는 기능은 한쪽에서만 켜는 편이 단순하다.

10. 자가 점검 문제

먼저 답을 생각한 다음 펼쳐서 확인한다.

Q1. 팀이 MCP 서버 20개를 Kubernetes에서 직접 운영해야 한다. 서버 실행은 어느 제품이 맡는가?

ToolHive가 맡는다. ToolHive operator가 MCPServer CRD를 읽고 서버를 pod로 실행한다. agentgateway의 Kubernetes 모드는 서버를 실행하지 않고, 이미 실행 중인 서버로 요청을 전달만 한다.

Q2. agentgateway가 MCP 서버를 직접 시작하는 경우가 있는가?

standalone 모드에서 stdio target을 쓰는 경우가 그렇다. 이때 agentgateway가 자식 프로세스를 시작하지만, 컨테이너의 권한 제한이나 이미지 검증은 하지 않는다.

Q3. 에이전트의 LLM 호출 비용을 팀별로 제한해야 한다. 오픈소스판 기준으로 어느 제품을 쓰는가?

agentgateway를 쓴다. agentgateway는 LLM 토큰 rate limit, 비용 기록, 예산을 제공한다. 오픈소스 ToolHive는 LLM 트래픽을 다루지 않고, 이 기능은 Stacklok 상용판의 AI Gateway가 제공한다.

Q4. 두 MCP 서버가 같은 이름의 search tool을 제공한다. 각 제품은 어떻게 처리하는가?

vMCP는 prefix, priority, manual 중 하나를 쓰고, 기본값인 prefix는 서버 이름을 앞에 붙인다. agentgateway는 target이 둘 이상이면 target 이름을 앞에 붙이며, 이 동작은 prefixMode로 바꾼다.

Q5. 사용자 A에게 특정 tool만 보이게 하려면 각 제품에서 무엇을 쓰는가?

ToolHive는 Cedar 정책을, agentgateway는 CEL 인가 규칙을 쓴다. 두 제품 모두 허용하지 않은 tool을 목록 응답에서 지운다.

Q6. 두 제품의 rate limit은 무엇을 세는가? LLM 토큰 rate limit을 응답 시점에도 확인하는 이유는?

ToolHive는 MCP 요청 수를 세고, agentgateway는 요청 수와 LLM 토큰 수를 센다. 출력 토큰 수는 응답이 와야 알 수 있어서 응답 시점에도 확인한다.

Q7. ToolHive의 MCPServer와 agentgateway의 AgentgatewayBackend는 무엇이 다른가?

MCPServer는 컨테이너 이미지를 가지고, operator가 그 이미지로 서버를 실행한다. AgentgatewayBackend는 이미 실행 중인 서버의 주소를 가진다. 하나는 워크로드를 정의하고, 다른 하나는 목적지를 정의한다.

Q8. 에이전트끼리 A2A로 통신한다. 이 트래픽에 인증과 관측을 붙이려면 어느 제품을 쓰는가?

agentgateway를 쓴다. agentgateway는 A2A backend를 지원하고, ToolHive 저장소에서는 A2A 코드와 문서를 찾지 못했다.
