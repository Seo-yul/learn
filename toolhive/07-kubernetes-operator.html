Kubernetes operator

ToolHive 학습 07편 · 2026-10-14 작성 · 2026-11-07 갱신

ToolHive Kubernetes operator의 구조와 reconcile 동작을 정리한 문서다. 설치, CRD 목록, MCPServer reconcile을 차례로 보고, proxy가 StatefulSet을 만드는 과정과 운영 방법까지 다룬다. 주요 설명에는 소스 행 번호를 붙였다. 인증과 인가의 의미는 05편에, vMCP는 08편에 있다.

기준 버전은 ToolHive v0.63.0(2026-11-06)이다. 2026-10-14에 v0.53.0 기준으로 썼던 것을 2026-11-07에 v0.63.0 기준으로 갱신했고, 공식 문서도 2026-11-07 상태를 읽었다. ToolHive는 자주 바뀌므로 실제로 쓰기 전에 공식 문서를 다시 확인해야 한다.

한 문장 요약

operator는 MCPServer 하나를 받아 proxy Deployment와 Service를 만들고, RunConfig ConfigMap과 RBAC 객체도 함께 만든다. MCP 서버를 돌리는 StatefulSet은 proxy pod 안의 thv-proxyrunner가 server-side apply로 만든다. operator는 그 StatefulSet에 owner reference를 붙여 두고, StatefulSet이 사라지면 proxy를 재시작해 다시 만들게 한다.

v0.63.0 갱신 요약
  • proxy용 Role의 pods/attach 권한은 transport가 stdio일 때만 들어간다. HTTP transport의 proxy는 pod에 attach하지 않기 때문이다(5장, 6장).
  • operator 전역 Redis 기본값에 TLS 설정이 생겼다. operator는 이 기본값을 시작할 때 한 번 읽어 controller에 넘긴다(1장, 2장, 12장).
  • MCPRemoteProxy의 phase 판단이 MCPServer와 같은 함수를 쓴다. Running이어도 컨테이너가 Ready가 아니면 Pending이고, 컨테이너 오류는 Failed다(8장).
  • MCPOIDCConfig controller는 참조 CR의 변경 중 oidcConfigRef 이름이 바뀐 것만 받는다(9장).
  • 내장 인가 서버에 tlsListener가 있으면 operator가 proxyPort 8443을 거부하는데, 이 검사는 RunConfig를 만들 때 한다(4장).
  • vMCP static mode에서 backend 건강 상태 변동은 rollout을 일으키지 않고, embedding 경고는 spec generation이 바뀔 때 한 번만 낸다(10장).
  • chart 버전은 0.63.0이고 이미지 태그는 v0.63.0이다. values.yaml과 소스의 행 번호를 모두 다시 맞췄고, MCPServer reconcile 순서는 그대로다(2장, 4장).

1. operator 구조와 controller

ToolHive는 Kubernetes에서 바이너리 두 개를 쓴다(source docs/arch/09-operator-architecture.md:7).

  • thv-operator는 CRD를 watch하고 Kubernetes 객체를 reconcile한다.
  • thv-proxyrunner는 pod 안에서 MCP 서버 컨테이너를 만들고 트래픽을 중계한다.

아키텍처 문서는 둘을 나눈 이유로 책임 경계와 독립 확장을 든다(source docs/arch/09-operator-architecture.md:12). 배포 모드 문서는 여기에 thv가 로컬 Docker와 Podman API에 맞춰져 있다는 점을 이유로 하나 더 든다(source docs/arch/01-deployment-modes.md:317).

진입점과 manager

operator의 진입점은 Run()이다(source cmd/thv-operator/app/app.go:68). Run()은 controller-runtime manager를 만들고 controller를 등록하는데, manager를 만들기 전에 전역 Redis 기본값을 환경 변수에서 한 번 읽는다(source cmd/thv-operator/app/app.go:84). 이 값이 잘못되어 있으면 operator가 종료하고, controller는 reconcile 중에 이 환경 변수를 다시 읽지 않는다.

leader election ID는 toolhive-operator-leader-election이다(source cmd/thv-operator/app/app.go:98). Helm chart가 --leader-elect 인자를 넘기기 때문에(source deploy/charts/operator/templates/deployment.yaml:42), operator replica가 여러 개여도 reconcile하는 replica는 하나다(docs guides-k8s/deploy-operator).

watch 범위는 환경 변수 WATCH_NAMESPACE가 정한다(source cmd/thv-operator/app/app.go:462). 변수가 없으면 manager cache가 클러스터 전체를 보고, 값이 있으면 쉼표로 나눈 namespace만 본다.

바이너리만 따로 띄우면 storage version migrator가 꺼진다. 환경 변수 TOOLHIVE_ENABLE_STORAGE_VERSION_MIGRATOR가 없을 때 기본값이 false이기 때문인데(source cmd/thv-operator/app/app.go:222), Helm chart는 이 값을 true로 넣는다.

2. 설치: Helm chart 두 개와 RBAC

설치는 Helm chart 두 개로 나뉘어 있어서(docs guides-k8s/deploy-operator), CRD chart를 먼저 설치하고 그다음 operator chart를 설치해야 한다.

helm upgrade --install toolhive-operator-crds \
  oci://ghcr.io/stacklok/toolhive/toolhive-operator-crds \
  -n toolhive-system --create-namespace

helm upgrade --install toolhive-operator \
  oci://ghcr.io/stacklok/toolhive/toolhive-operator \
  -n toolhive-system --create-namespace
chart (v0.63.0)설치하는 것주요 값
toolhive-operator-crdsCRD 14개crds.install(기본 true), crds.keep(기본 true)
toolhive-operatoroperator Deployment, ServiceAccount, ClusterRole, binding, leader election Roleoperator.rbac.scope, operator.toolhiveRunnerImage, operator.features.*

operator가 등록하는 controller가 각 CRD를 요구하기 때문에, CRD가 없으면 operator pod가 시작하지 못한다(docs guides-k8s/deploy-operator). crds.keep: true는 CRD에 helm.sh/resource-policy: keep annotation을 붙이는 값이라서, helm uninstall을 해도 CRD와 CR은 지워지지 않는다(docs reference/helm/operator-crds). CRD chart는 늘 같은 namespace로 업그레이드해야 하는데, Helm이 CRD에 meta.helm.sh/release-namespace annotation을 찍기 때문이다(docs guides-k8s/deploy-operator).

공식 문서의 kubectl 설치 예시는 v0.21.0 기준 CRD 12개만 나열하는데, v0.63.0 chart에는 CRD 파일이 14개 있다(source deploy/charts/operator-crds/files/crds/). 예시에 없는 두 개는 MCPAuthzConfig와 MCPWebhookConfig다. kubectl로 설치한다면 파일 목록을 직접 맞춰야 한다.

operator.toolhiveRunnerImage는 환경 변수 TOOLHIVE_RUNNER_IMAGE로 operator에 들어간다(source deploy/charts/operator/templates/deployment.yaml:77). 변수가 비어 있으면 operator가 proxyrunner:latest 태그를 쓰므로(source cmd/thv-operator/controllers/mcpserver_controller.go:2395), chart 없이 operator를 띄운다면 이 값을 직접 고정해야 한다.

operator.defaultRedis도 환경 변수로 operator에 들어간다. 주소는 TOOLHIVE_DEFAULT_REDIS_ADDR이고 비밀번호는 Secret 참조 변수 두 개이며(source deployment.yaml:175~182), TLS를 켜면 TOOLHIVE_DEFAULT_REDIS_TLS_ENABLED와 CA Secret 변수 두 개가 더 들어간다(source deployment.yaml:186~191). chart는 주소 없이 TLS를 켠 값이나 TLS 없이 CA Secret을 넣은 값처럼 모순된 값을 렌더링 단계에서 거부한다(source deployment.yaml:126~173). operator는 이 변수를 시작할 때 한 번 읽기 때문에(source cmd/thv-operator/pkg/controllerutil/defaultredis.go:37), 값을 바꿨다면 operator를 재시작해야 한다(source docs/arch/09-operator-architecture.md:585).

chart는 ClusterRole toolhive-operator-manager-role을 만들고(source deploy/charts/operator/templates/clusterrole/role.yaml), binding 방식은 설치 모드가 정한다(source deploy/charts/operator/templates/clusterrole/rolebinding.yaml).

leader election용 Role과 RoleBinding은 release namespace에 따로 생기고, 이 Role은 configmaps, leases, events 권한만 가진다(source deploy/charts/operator/values.yaml의 leaderElectionRole).

ClusterRole에는 pods/attach, pods/log, statefulsets, roles, rolebindings 권한이 있고, operator가 proxy에 주는 Role(5장)의 권한도 모두 이 안에 들어 있다. 다만 proxy Role의 pods/attach는 stdio transport일 때만 들어간다(5장).

namespace 모드와 storage version migrator는 함께 쓰지 못한다. chart의 validate-features.yaml이 이 조합에서 렌더링을 실패시키기 때문에(source deploy/charts/operator/templates/validate-features.yaml), namespace 모드로 설치할 때는 아래처럼 migrator를 꺼야 한다.

operator:
  rbac:
    scope: namespace
    allowedNamespaces:
      - team-frontend
      - team-backend
  features:
    storageVersionMigrator: false

namespace 배치

공식 문서 예시는 operator를 toolhive-system에 설치한다. cluster 모드에서는 MCPServer를 어느 namespace에나 만들 수 있고, namespace 모드에서는 allowedNamespaces 안에만 만들 수 있다(docs guides-k8s/run-mcp-k8s).

참조 필드는 같은 namespace의 CR만 가리킨다. 예를 들어 MCPToolConfig는 namespace를 넘는 참조를 지원하지 않아서(source cmd/thv-operator/api/v1beta1/toolconfig_types.go:110), 팀 namespace마다 공유 설정 kind를 따로 둬야 한다.

3. CRD 카탈로그와 참조 관계

CRD의 API group은 toolhive.stacklok.dev이고, v0.63.0 CRD chart에는 CRD 파일 14개가 있다(source deploy/charts/operator-crds/files/crds/).

이 가운데 13개 kind는 v1alpha1과 v1beta1을 함께 제공하고 storage version은 v1beta1이다. v1alpha1에는 deprecated 표시와 경고 문구가 붙어 있다(source deploy/charts/operator-crds/files/crds/toolhive.stacklok.dev_mcpservers.yaml:37). MCPWebhookConfig만 v1alpha1 하나를 제공하므로, 이 kind에서는 v1alpha1이 storage version이다(source toolhive.stacklok.dev_mcpwebhookconfigs.yaml:350).

CRD는 전부 scope: Namespaced이고 toolhive category에 속해서, kubectl get toolhive -A로 ToolHive CR을 한꺼번에 볼 수 있다(docs guides-k8s/migrate-to-v1beta1).

4.1 준비 단계

controller는 회차마다 아래 순서로 움직인다.

  1. MCPServer를 읽는다. 없으면 끝낸다(276~292행).
  2. 삭제 중이면 finalizer 작업을 하고 끝낸다(296~309행). 이 작업은 4.4절에 있다.
  3. spec.permissionProfile이 있으면 Warning event를 남긴다. operator는 이 필드를 적용하지 않는다(311행).
  4. finalizer mcpserver.toolhive.stacklok.dev/finalizer가 없으면 붙인다(314~320행).
  5. 재시작 annotation을 처리하고, 재시작을 실행했으면 requeue한다(323~330행).
  6. 검증 condition을 쓴다. 대상은 groupRef, CA bundle, stdio replica 제한이고, 세션 저장소와 rate limit도 검증한다(332~344행).
  7. podTemplateSpec이 잘못됐으면 error 없이 끝낸다. 이때는 사용자가 spec을 고쳐야 다음 회차가 온다(346~352행).
  8. 참조한 공유 설정 kind를 차례로 읽고 hash를 status에 적는다. 하나라도 실패하면 phase를 Failed로 쓰고 error를 반환한다(354~452행).

4.2 객체 단계

준비가 끝나면 controller는 아래 순서로 객체를 맞춘다.

  1. pod 상태를 세어 status를 갱신한다(455행).
  2. proxy용 ServiceAccount, Role, RoleBinding을 만든다(461행).
  3. inline 인가 정책이 있으면 그 ConfigMap을 만든다(473행).
  4. RunConfig ConfigMap <이름>-runconfig를 upsert한다(485행).
  5. ConfigMap의 checksum을 읽는다. 아직 보이지 않으면 5초 뒤 다시 온다(506~514행).
  6. Deployment가 없으면 만들고 requeue한다(525~555행).
  7. stdio인데 Deployment replica가 1보다 크면 1로 줄인다(564~577행).
  8. Service mcp-<이름>-proxy가 없으면 만들고 requeue한다(579~598행).
  9. status.url이 비어 있으면 클러스터 내부 URL을 쓴다(605~620행).
  10. Deployment가 원하는 모양과 다르면 고치고 requeue한다(623~658행).
  11. Service가 다르면 고치고 requeue한다(661~679행).
  12. MCP 서버 StatefulSet이 있는지 확인한다(681행). 이 단계는 6장에 있다.

error를 다루는 방식은 네 가지다.

  • 참조 CR이 없거나 잘못된 경우에는 controller가 phase를 Failed로 쓰고 error를 반환한다. 설계 문서는 이때 지수 backoff로 다시 시도한다고 쓴다(source docs/operator/toolconfig-reconciliation.md).
  • podTemplateSpec이 잘못된 경우에는 controller가 nil을 반환한다. 무한 재시도를 막으려는 선택이다(348~351행 주석).
  • 내장 인가 서버 설정이 spec 오류인 경우다. 예를 들어 참조한 설정에 tlsListener가 있는데 proxyPort가 8443이면, controller는 phase를 Failed로 쓰고 nil을 반환한다(487~493행). 이 검사는 RunConfig를 만드는 단계에 있다(source mcpserver_runconfig.go:230, cmd/thv-operator/pkg/controllerutil/authserver.go:440).
  • RunConfig ConfigMap이 아직 안 보이는 경우에는 controller가 RequeueAfter: 5s로 기다린다.

4.3 Deployment와 Service 갱신 규칙

Deployment의 차이는 deploymentNeedsUpdate가 판단한다. 차이가 있으면 operator는 pod template, selector, label을 덮어쓰고(641~643행) Deployment annotation은 병합한다(644행). 이때 pod template의 kubectl.kubernetes.io/restartedAt은 살려 두기 때문에(639~640행), operator가 kubectl rollout restart를 drift로 보고 되돌리는 일은 없다.

replica 수는 spec.replicas가 있을 때만 쓰고(645~647행), 비어 있으면 HPA나 KEDA가 정한 값이 남는다. Service의 label과 annotation은 덮어쓰지 않고 병합하므로(666~670행) GKE NEG 같은 외부 controller가 붙인 키가 남는다.

4.4 삭제와 finalizer

삭제 요청이 오면 finalizeMCPServer가 아래 순서로 정리한다(1925~1949행).

  1. phase를 Terminating으로 쓴다.
  2. StatefulSet <이름>을 지운다.
  3. Service mcp-<이름>-headless와 mcp-<이름>을 지운다.

6. proxy: 설정 전달과 StatefulSet 생성

설정이 proxy에 닿는 경로

설정은 다섯 경로로 proxy pod에 닿는다. 행 번호는 mcpserver_controller.go 기준이다.

  • RunConfig: runconfig.json에 tool 필터, OIDC, 인가, audit 값이 들어가고, telemetry와 환경 변수도 들어간다(1298~1300행 주석).
  • pod patch: MCP 서버 pod에 넣을 ServiceAccount와 Kubernetes Secret 참조이고, --k8s-pod-patch 인자로 간다.
  • proxy 환경 변수: OIDC client secret과 token exchange 값이 들어가고, Redis 비밀번호는 Kubernetes Secret 참조로 들어간다(1325~1398행).
  • volume: OIDC CA, telemetry CA, 내장 인가 서버 설정을 마운트한다(1446~1486행). 세션 저장소 Redis의 CA Secret도 여기서 volume으로 붙이는데, spec.sessionStorage가 없으면 operator 전역 기본값의 TLS 설정을 쓴다(1470행).
  • downward API: MCPServer generation 값이 환경 변수 THV_MCPSERVER_GENERATION으로 들어간다(1408~1417행).

Kubernetes Secret의 값은 RunConfig에 들어가지 않는다. 코드 주석에 따르면 secret은 pod patch로 처리하므로(source cmd/thv-operator/controllers/mcpserver_runconfig.go:96), ConfigMap을 읽어도 secret 값은 나오지 않는다. secret 처리 방식 전반은 03편에 있다.

proxy가 설정을 읽는 순서

thv-proxyrunner run은 RunConfig 파일을 아래 순서로 찾는다(source cmd/thv-proxyrunner/app/run.go:117).

  1. /etc/runconfig/runconfig.json
  2. /etc/toolhive/runconfig.json
  3. ./runconfig.json

파일을 찾으면 proxy는 설정 flag를 쓰지 않고 이미지 인자와 --k8s-pod-patch만 반영한다(source cmd/thv-proxyrunner/app/run.go:201). 그다음 CLI와 같은 runner.NewRunner(...).Run을 부른다(source run.go:249).

proxy는 컨테이너 런타임을 factory로 고르는데(source run.go:86), pod 안에는 KUBERNETES_SERVICE_HOST가 있으므로 Kubernetes 구현이 뽑힌다(source pkg/container/runtime/types.go:349). 이 구현의 DeployWorkload가 StatefulSet을 apply한다(source pkg/container/kubernetes/client.go:362).

그래서 proxy는 thv run과 같은 runner 코드로 MCP 서버를 띄운다. StatefulSet을 operator가 아닌 proxy가 만드는 구조는 이 재사용에서 나온 것으로 보이지만, 아키텍처 문서가 직접 밝힌 이유는 책임 경계와 독립 확장이다(1장). transport와 proxy의 일반 구조는 02편에 있다.

StatefulSet apply 과정

DeployWorkload는 아래 순서로 움직인다(source pkg/container/kubernetes/client.go:362).

  1. pod template을 만들고 pod patch를 적용한다(382~391행).
  2. mcp 컨테이너를 설정한다. stdio이면 stdin: true, tty: false다(410~419행, 1454~1458행).
  3. 기존 StatefulSet의 generation annotation을 읽고, 그 값이 더 크면 apply를 건너뛴다(424~436행).
  4. server-side apply로 StatefulSet을 쓴다. field manager는 toolhive-container-manager이고 Force: true다(494~528행).
  5. HTTP transport이면 Service 두 개를 apply한다. 두 Service의 owner는 StatefulSet이다(594~626행).
  6. StatefulSet이 Ready가 될 때까지 기다린다(451~461행).

StatefulSet 이름은 MCPServer 이름과 같고 selector는 app: <이름>이다(579~584행). replica 수는 RunConfig에 backendReplicas가 있을 때만 쓰고(585~587행), 값이 없으면 HPA 같은 다른 field manager가 replica를 계속 맡는다.

rolling update 중의 경쟁 막기

rolling update 중에는 옛 proxy pod와 새 proxy pod가 함께 실행되고 ConfigMap volume은 실시간으로 갱신된다. 그래서 두 pod가 StatefulSet을 번갈아 덮어쓸 위험이 있는데(source cmd/thv-proxyrunner/app/run.go:166 주석), operator와 proxy는 아래 방식으로 이 경쟁을 막는다.

  1. operator가 Deployment pod template에 annotation toolhive.stacklok.dev/mcpserver-generation을 찍는다. 값은 MCPServer의 metadata.generation이다(mcpserver_controller.go:1531).
  2. operator가 같은 값을 downward API로 THV_MCPSERVER_GENERATION에 넣는다(mcpserver_controller.go:1408). 이 값은 pod가 생길 때 고정된다.
  3. proxy가 이 환경 변수로 RunConfig의 generation을 덮어쓴다(run.go:174).
  4. proxy가 StatefulSet pod template에 자기 generation을 찍는다(client.go:503).
  5. 기존 StatefulSet의 값이 더 크면 proxy는 apply를 건너뛰고, Service apply도 함께 건너뛴다(client.go:429, client.go:546).

이 annotation은 StatefulSet pod template에 들어가기 때문에, MCPServer spec을 고쳐 generation이 오르면 MCP 서버 pod도 다시 만들어질 가능성이 높다. 이 동작은 코드에서 추론한 것이고 시험하지는 않았다.

stdio와 attach

stdio이면 proxy는 Service를 만들지 않고(source client.go:1223), 대신 pods/attach로 MCP 서버 pod의 stdin과 stdout에 붙는다(source client.go:173). attach가 끊기면 지수 backoff로 최대 90초 동안 다시 붙어 보고(source client.go:94), 그래도 실패하면 exit code 1로 끝난다. 그 뒤 Kubernetes가 proxy 컨테이너를 다시 띄우면 새 MCP 서버 pod에 붙는다(source client.go:159 주석).

이 구조 때문에 stdio MCPServer의 proxy replica는 1로 묶인다(source mcpserver_controller.go:561). 공식 문서는 stdio가 클라이언트 연결을 한 번에 하나만 받는다고 쓴다(docs guides-k8s/run-mcp-k8s). 같은 이유로 v0.63.0부터 pods/attach 권한은 stdio MCPServer의 Role에만 들어간다(5장).

operator가 StatefulSet을 지키는 방법

StatefulSet spec은 proxy가 만들지만 수명은 operator가 관리한다(source cmd/thv-operator/controllers/mcpserver_statefulset.go:29 주석). operator의 동작은 아래와 같다.

  • toolhive=true label이 붙은 StatefulSet을 watch하고, label toolhive-name으로 MCPServer를 찾는다(mcpserver_statefulset.go:137, mcpserver_statefulset.go:167).
  • StatefulSet이 있으면 MCPServer를 controller owner로 붙인다(mcpserver_statefulset.go:114).
  • StatefulSet이 없는데 proxy pod가 돌면 phase를 Pending으로 쓴다(mcpserver_controller.go:1892).
  • proxy Deployment가 Available이면 pod template에 restarted-at을 찍어 재시작한다. 재시작 뒤 2분 안에는 다시 재시작하지 않는다(mcpserver_statefulset.go:27, mcpserver_statefulset.go:79).
  • 10초 뒤 다시 확인한다(mcpserver_statefulset.go:62).

MCP 서버를 재시작하려면 StatefulSet을 지우지 말고 재시작 annotation을 써야 한다(source docs/operator/mcpserver-workloads.md). 방법은 11장에 있다.

MCPServer phase는 다섯 값 중 하나다(source cmd/thv-operator/api/v1beta1/mcpserver_types.go:1032). pod 하나의 분류는 categorizePodStatus가 맡고(source mcpserver_controller.go:1753), phase 판단은 mcpserver_controller.go:1787부터다.

8. MCPRemoteProxy, MCPServerEntry, MCPGroup

MCPRemoteProxy

MCPRemoteProxy는 클러스터 밖 MCP 서버 앞에 proxy를 두는 kind다. 원격 서버를 고치지 않고 인증, 인가, audit, tool 필터, telemetry를 적용하는 용도다(docs guides-k8s/remote-mcp-proxy).

spec:
  remoteUrl: https://mcp.analytics.example.com
  proxyPort: 8080
  transport: streamable-http
  oidcConfigRef:
    name: analytics-oidc
    audience: https://mcp.analytics.example.com

operator는 사설 대역이나 *.cluster.local을 가리키는 remoteUrl을 거부하므로, 클러스터 안 서버를 앞에 두려면 spec.allowPrivateEndpoint: true를 넣어야 한다. loopback, link-local, cloud metadata 주소는 이 값과 관계없이 막힌다(docs guides-k8s/remote-mcp-proxy).

MCPServerEntry

MCPServerEntry는 원격 MCP 서버를 그룹 멤버로 선언만 하는 kind라서, controller는 Deployment, Service, pod를 만들지 않는다(source cmd/thv-operator/controllers/mcpserverentry_controller.go:43). controller는 참조 대상인 MCPGroup, MCPExternalAuthConfig, CA bundle ConfigMap이 있는지만 보고 원격 URL로는 요청을 보내지 않는다. 이 URL에는 vMCP가 직접 연결한다(source docs/arch/09-operator-architecture.md:356).

transport와 groupRef는 필수이고, transport는 sse나 streamable-http만 받는다(source cmd/thv-operator/api/v1beta1/mcpserverentry_types.go:35). MCPServerEntry에는 proxy 단계가 없기 때문에 인가, audit, telemetry가 필요하면 MCPRemoteProxy를 써야 한다(docs guides-k8s/mcp-server-entry).

MCPGroup

MCPGroup spec에는 description 하나만 있다(source cmd/thv-operator/api/v1beta1/mcpgroup_types.go:11). controller는 멤버를 찾아 status에 쓰는데, status에는 servers, remoteProxies, entries 목록과 개수가 들어간다(source mcpgroup_controller.go:189).

MCPGroup의 삭제는 막히지 않는다. controller가 멤버 CR의 GroupRefValidated를 False로 바꾸고 finalizer를 떼는데(source mcpgroup_controller.go:240), 이 점이 공유 설정 kind(9장)와 다르다. CLI에서 그룹이 하는 일은 04편에 있다.

9. 공유 설정 kind와 MCPToolConfig

공유 설정 kind는 Kubernetes 객체를 만들지 않고, 각 controller는 아래 세 가지를 맡는다.

  • spec의 config hash를 계산해 status에 쓴다.
  • spec 검증 결과를 Valid condition으로 쓴다.
  • finalizer로 삭제를 막는다. 참조 CR이 남아 있으면 DeletionBlocked를 True로 쓰고 30초 뒤 다시 확인한다.

근거는 toolconfig_controller.go:81, toolconfig_controller.go:138, mcpoidcconfig_controller.go:225다.

MCPOIDCConfig controller는 참조 CR 세 kind를 watch한다. v0.63.0에서는 참조 CR의 update 중 oidcConfigRef 이름이 바뀐 것만 받고, 생성과 삭제는 모두 받는다(source mcpoidcconfig_controller.go:371, mcpoidcconfig_controller.go:411). 그래서 이미지나 라우팅만 바뀐 CR은 MCPOIDCConfig의 reconcile을 일으키지 않는다.

MCPOIDCConfig는 서버마다 달라야 하는 값을 참조 쪽에 둔다. audience는 필수이고 scopes의 기본값은 ["openid"]다(source docs/arch/09-operator-architecture.md:255). 문서는 access token 재사용을 막으려면 audience를 서버마다 다르게 둬야 한다고 쓴다.

MCPToolConfig의 변경 전파

MCPToolConfig는 toolsFilter와 toolsOverride를 가지고(source cmd/thv-operator/api/v1beta1/toolconfig_types.go:32, toolconfig_types.go:37), 이 중 toolsOverride는 tool 이름, 설명, tool 힌트 값을 바꾼다.

apiVersion: toolhive.stacklok.dev/v1beta1
kind: MCPToolConfig
metadata:
  name: github-tools-config
  namespace: toolhive-system
spec:
  toolsFilter:
    - create_pull_request
    - get_pull_request
  toolsOverride:
    create_pull_request:
      name: github_create_pr
    get_pull_request:
      description: Retrieve details of a specific GitHub pull request
---
# MCPServer 쪽 참조
spec:
  toolConfigRef:
    name: github-tools-config

위 YAML은 공식 문서 예시를 줄인 것이고(docs guides-k8s/customize-tools), toolsOverride의 키는 원래 tool 이름이다.

그림의 단계는 아래 코드에 있고, 행 번호는 각 단계 끝에 적었다.

  1. ToolConfig controller가 spec hash를 계산하고, 값이 바뀌면 status.configHash와 observedGeneration을 쓴다(toolconfig_controller.go:91).
  2. MCPServer controller는 MCPToolConfig를 watch하다가 같은 이름을 참조하는 MCPServer를 enqueue한다(mcpserver_controller.go:3211, mcpserver_controller.go:3336).
  3. MCPServer controller가 hash 차이를 보고 status.toolConfigHash를 고친다(mcpserver_controller.go:1085).
  4. 같은 회차에서 RunConfig를 다시 만들고, 새 toolsFilter가 runconfig.json에 들어간다(mcpserver_runconfig.go:103).
  5. ConfigMap checksum이 바뀌면 pod template의 toolhive.stacklok.dev/runconfig-checksum도 바뀌고, 그러면 Deployment가 rolling update를 시작한다(mcpserver_controller.go:1517, mcpserver_controller.go:2243).

hash는 dump.ForHash로 spec을 직렬화한 뒤 FNV-1a 32비트로 계산한다(source cmd/thv-operator/pkg/controllerutil/config.go:26).

삭제 보호와 참조 찾기

사용자가 MCPToolConfig를 지우면 controller가 참조 MCPServer를 찾는다(source toolconfig_controller.go:138). 이때 field index spec.toolConfigRef를 쓰고(source toolconfig_controller.go:184), 참조가 남아 있으면 finalizer를 떼지 않는다.

설계 문서 docs/operator/toolconfig-reconciliation.md는 status에 referencingWorkloads와 referenceCount가 있다고 쓰지만, v0.63.0 타입에도 두 필드가 없다(source cmd/thv-operator/api/v1beta1/toolconfig_types.go:84). 공식 문서는 v0.42.0에서 두 필드를 지웠다고 쓴다(docs guides-k8s/migrate-to-v1beta1).

v0.63.0의 findReferencingWorkloads는 MCPServer만 찾는다(source toolconfig_controller.go:203). 코드로 보면 MCPRemoteProxy만 참조하는 MCPToolConfig는 삭제가 막히지 않는데, 이 동작은 시험하지 않았다.

참조 상태를 보려면 참조 CR을 직접 조회해야 한다. 공식 문서는 MCPOIDCConfig를 예로 아래 조회를 보여 준다(docs guides-k8s/migrate-to-v1beta1).

kubectl get mcpservers,mcpremoteproxies,virtualmcpservers -n toolhive-system \
  -o json | jq -r --arg n my-oidc '.items[]
    | select((.spec.oidcConfigRef.name // .spec.incomingAuth.oidcConfigRef.name) == $n)
    | "\(.kind)/\(.metadata.name)"'

10. EmbeddingServer, MCPRegistry, VirtualMCPServer

EmbeddingServer

EmbeddingServer는 embedding 모델 서버를 StatefulSet으로 띄운다(source docs/arch/09-operator-architecture.md:310). 컨테이너는 HuggingFace text-embeddings-inference이고 기본 모델은 BAAI/bge-small-en-v1.5다(source cmd/thv-operator/api/v1beta1/embeddingserver_types.go:45).

controller가 소유하는 객체는 StatefulSet, Service, PVC다(source embeddingserver_controller.go:1025). VirtualMCPServer의 optimizer가 spec.embeddingServerRef로 이 kind를 참조하는데, optimizer는 08편에서 다룬다.

MCPRegistry와 대체 방법

MCPRegistry는 registry server를 Deployment로 띄운다. operator는 spec.configYAML을 해석하지 않고 ConfigMap에 그대로 넣는다(source docs/arch/09-operator-architecture.md:705).

MCPRegistry는 kind 전체가 deprecated다. 두 API 버전 모두 kubectl 경고를 내고(source toolhive.stacklok.dev_mcpregistries.yaml:40, toolhive.stacklok.dev_mcpregistries.yaml:334), controller도 MCPRegistryDeprecated Warning event를 남긴다(source mcpregistry_controller.go:236).

대체 방법은 toolhive-registry-server Helm chart인데, 이 chart는 operator 없이 registry server를 설치한다(docs guides-registry/deploy-helm).

VirtualMCPServer

VirtualMCPServer는 MCPGroup 멤버를 MCP endpoint 하나로 묶는다. controller는 Deployment, Service, ConfigMap을 만들고, 세션 바인딩에 쓰는 HMAC Kubernetes Secret도 만든다(source virtualmcpserver_controller.go:1333). Service 이름은 vmcp-<이름>이다(source virtualmcpserver_controller.go:2628, virtualmcpserver_controller.go:3204). spec.serviceAccount가 없으면 RBAC 객체도 만든다(source virtualmcpserver_controller.go:1461).

이 controller는 MCPGroup과 멤버 kind 세 개를 watch한다(source virtualmcpserver_controller.go:3208). 멤버 kind는 MCPServer, MCPRemoteProxy, MCPServerEntry이고, 이 watch 때문에 그룹 멤버가 바뀌면 vMCP의 reconcile도 다시 돈다. backend 탐색과 tool 집계는 08편에서 다룬다.

static mode에서는 controller가 backend 설정을 ConfigMap에 넣고, 그 ConfigMap의 checksum이 바뀌면 rollout이 일어난다. v0.63.0부터는 이 ConfigMap에 backend의 workload_status를 넣지 않아서, backend가 Ready와 Pending을 오가도 vMCP pod는 다시 뜨지 않는다(source docs/arch/09-operator-architecture.md:455). config.optimizer.embeddingService를 embeddingServerRef 없이 넣으면 controller가 Warning event를 내는데, 이 event는 spec generation이 바뀐 회차에만 한 번 낸다(source cmd/thv-operator/controllers/virtualmcpserver_vmcpconfig.go:180).

v0.63.0 CRD에는 spec.authServerUpstreamFilter도 있다. 내장 인가 서버의 upstream provider를 그룹별로 좁히는 필드인데(source cmd/thv-operator/api/v1beta1/virtualmcpserver_types.go:136), 이 문서에서는 다루지 않는다.

11. 운영: 재시작과 API 버전 이전

재시작 annotation

MCPServer에는 spec을 고치지 않고 재시작하는 annotation이 있다(source docs/operator/restart-annotation.md).

annotation 키값뜻
mcpserver.toolhive.stacklok.dev/restarted-atRFC3339 시각값이 바뀌면 재시작한다.

kubectl annotate mcpserver my-mcpserver \
  mcpserver.toolhive.stacklok.dev/restarted-at="$(date -u +%Y-%m-%dT%H:%M:%SZ)"

# immediate 재시작
kubectl annotate mcpserver my-mcpserver \
  mcpserver.toolhive.stacklok.dev/restarted-at="$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  mcpserver.toolhive.stacklok.dev/restart-strategy="immediate"

아래 행 번호는 mcpserver_controller.go 기준이다. operator는 시각이 마지막 처리 값보다 늦을 때만 재시작하고(954~966행), 형식이 틀린 값은 로그만 남기고 무시한다(945~952행). rolling은 Deployment pod template에 annotation을 찍고(1028~1053행), immediate는 label이 맞는 pod를 바로 지운다(1056~1082행).

immediate가 고르는 label은 labelsForMCPServer이고 app: mcpserver를 포함한다(2376~2384행). 반면 MCP 서버 StatefulSet의 pod는 app: <이름> label을 쓴다(source client.go:374). 그래서 코드로 보면 immediate는 proxy pod만 지우는데, 이 동작은 시험하지 않았다.

kubectl rollout restart도 통한다. operator와 proxy가 kubectl.kubernetes.io/restartedAt 값을 지우지 않기 때문이다(639~640행, source client.go:508). 다만 공식 문서는 GitOps 환경에서 CR annotation 방식을 권하는데, 재시작 요청이 CR에 남기 때문이다(source docs/operator/restart-annotation.md).

지우지 말아야 할 객체

kubectl get pods는 stdio 서버마다 pod 두 개를 보여 주는데, 이 중 StatefulSet pod는 남은 객체가 아니다(source docs/operator/mcpserver-workloads.md). 운영할 때는 아래 두 가지를 지켜야 한다.

  • MCP 서버를 재시작할 때는 StatefulSet을 지우지 말고 재시작 annotation을 써야 한다.
  • StatefulSet이 사라져도 MCPServer CR을 지우지 않아야 한다. operator가 proxy를 재시작해 StatefulSet을 되살리기 때문이다(6장).

storage version 정리

v0.23.0에서 CRD API가 v1alpha1에서 v1beta1로 올라갔다. 두 버전의 스키마가 같아서 데이터 형식 이전은 없다(docs guides-k8s/migrate-to-v1beta1).

남는 문제는 CRD의 status.storedVersions다. Kubernetes API 서버는 저장에 쓴 적이 있는 버전을 이 목록에 남기는데, 목록에 v1alpha1이 남아 있으면 그 버전을 spec.versions에서 지우지 못한다(source docs/operator/storage-version-migration.md).

StorageVersionMigrator controller는 opt-in label이 있는 CRD를 아래 순서로 정리한다. 근거는 storage-version-migration.md의 "How it works"와 storageversionmigrator_controller.go:162다.

  1. CRD를 cache 없이 Kubernetes API 서버에서 직접 읽는다.
  2. storage: true인 버전을 찾는다.
  3. storedVersions가 이미 그 버전 하나뿐이면 끝낸다.
  4. 해당 kind의 CR을 페이지 단위로 읽고 Get과 Update를 한다. 그러면 Kubernetes API 서버가 현재 storage version으로 다시 저장한다.
  5. 모든 CR이 성공하면 storedVersions를 현재 버전 하나로 patch한다.

Update가 conflict를 내면 CR 하나당 세 번까지 다시 시도하고(source storageversionmigrator_controller.go:69), 그래도 끝나지 않으면 30초 뒤 다시 돈다(source storageversionmigrator_controller.go:220).

opt-in label은 toolhive.stacklok.dev/auto-migrate-storage-version: "true"이고, CRD를 생성할 때 kubebuilder marker가 넣는다. migrator의 RBAC 권한은 CRD 읽기, CRD status 쓰기, *.toolhive.stacklok.dev의 get, list, update다.

migrator의 Update 요청도 admission webhook을 거친다. Kyverno, Gatekeeper, OPA 같은 정책이 내용이 같은 Update를 거부하면 이전이 끝나지 않으므로, migrator를 켜기 전에 정책을 확인해야 한다(source docs/operator/storage-version-migration.md).

버전을 건너뛰는 업그레이드도 위험하다. migrator가 한 번도 돌지 않은 클러스터를 옛 버전을 빼는 릴리스로 바로 올리면 helm upgrade가 실패하므로 릴리스를 차례로 설치해야 한다.

정리가 끝났는지는 아래 명령으로 확인한다.

kubectl get crd mcpservers.toolhive.stacklok.dev \
  -o jsonpath='{.status.storedVersions}'
# ["v1beta1"]

manifest 쪽 작업은 따로 해야 한다. apiVersion을 v1beta1로 바꿔 다시 apply해야 하고, 공식 문서는 v0.15.0부터 v0.23.0까지 한 버전씩 올리라고 권한다(docs guides-k8s/migrate-to-v1beta1).

배포 모드 문서는 proxy replica 여러 개를 시험하지 않았다고 적는데(source docs/arch/01-deployment-modes.md:380), 같은 시점의 공식 문서는 replica 여러 개와 Redis 구성을 안내한다(docs guides-k8s/redis-session-storage).

세션 저장소

MCP 세션 상태는 기본으로 proxy pod 메모리에 있어서, replica가 둘 이상이면 다른 pod로 간 요청이 Session not found로 실패한다(docs guides-k8s/remote-mcp-proxy). 그래서 replica를 늘리기 전에 Redis 세션 저장소를 설정해야 한다.

apiVersion: toolhive.stacklok.dev/v1beta1
kind: MCPServer
metadata:
  name: my-server
  namespace: toolhive-system
spec:
  image: ghcr.io/example/my-mcp-server:latest
  replicas: 2
  sessionStorage:
    provider: redis
    address: redis.toolhive-system.svc.cluster.local:6379
    db: 0
    keyPrefix: mcp-sessions
    passwordRef:
      name: redis-password
      key: password

위 YAML은 공식 문서의 예다(docs guides-k8s/redis-session-storage). replica가 1보다 큰데 Redis가 없으면 SessionStorageWarning이 True가 되지만, 이 경우에도 operator는 replica 수를 그대로 적용한다(source mcpserver_controller.go:3028).

proxy Service의 sessionAffinity 기본값은 ClientIP다(source mcpserver_controller.go:1685). Redis를 쓰는 MCPRemoteProxy 예시는 sessionAffinity: None을 권하는데, ClientIP가 클라이언트 하나를 pod 하나에 묶어 부하 분산을 막기 때문이다(docs guides-k8s/remote-mcp-proxy).

proxy가 만드는 mcp-<이름> Service도 ClientIP affinity를 쓰고 시간은 1800초다. 코드 주석은 이것이 L4 고정이고 MCP 세션 단위 라우팅이 아니라고 쓴다(source client.go:1177).

Helm 값 operator.defaultRedis를 넣으면 spec.sessionStorage가 없는 CR이 이 Redis를 쓴다. v0.63.0부터는 Helm 값 operator.defaultRedis.tls.enabled로 이 연결에 TLS를 켠다. caCertSecretRef로 사설 CA를 고르면 그 Secret은 workload의 namespace에 있어야 하고, Secret이 없으면 pod가 ContainerCreating에 머문다(docs guides-k8s/deploy-operator, source docs/arch/09-operator-architecture.md:585).

이 기본값은 Sentinel과 ACL을 다루지 않으므로, 그런 Redis는 CR마다 spec.sessionStorage에 적어야 한다. operator는 기본값을 시작할 때 한 번 읽으므로 값을 바꿨다면 operator를 재시작해야 한다(2장).

rate limit은 Redis 세션 저장소를 요구하고, CRD의 CEL 규칙이 이 조건을 강제한다(source mcpserver_types.go:229). rate limit의 의미는 06편에 있고, 내장 인가 서버가 쓰는 Redis Sentinel 설정은 05편 범위다.

13. 자가 점검 문제

먼저 답을 생각해 본 다음 펼쳐서 확인한다.

Q1. streamable-http MCPServer osv를 만들었다. operator가 만드는 객체와 proxy가 만드는 객체를 나눠 보라.

operator는 Deployment osv와 Service mcp-osv-proxy를 만들고, ConfigMap osv-runconfig와 RBAC 객체 osv-proxy-runner도 만든다. spec.serviceAccount가 없으면 ServiceAccount osv-sa도 만든다.

proxy는 StatefulSet osv를 만들고, HTTP transport이므로 Service mcp-osv와 mcp-osv-headless도 만든다.

Q2. 누군가 StatefulSet osv를 지웠다. 그다음 무슨 일이 일어나는가?

StatefulSet watch가 MCPServer osv를 enqueue하고, operator는 StatefulSet이 없음을 보고 phase를 Pending으로 쓴다.

proxy Deployment가 Available이면 operator가 pod template에 restarted-at을 찍고, 새 proxy pod가 시작하면서 StatefulSet을 다시 apply한다. operator는 2분 안에는 다시 재시작하지 않고 10초마다 확인한다.

Q3. stdio MCPServer에 spec.replicas: 3을 넣었다. 결과는?

operator는 Deployment replica를 1로 만들고, StdioReplicaCapped condition은 True가 된다.

proxy가 MCP 서버 pod의 stdin에 attach하는 구조라서 proxy는 하나만 둔다. 공식 문서도 stdio가 클라이언트 연결을 한 번에 하나만 받는다고 쓴다.

Q4. MCPToolConfig를 지웠는데 Terminating에서 멈췄다. 원인과 확인 방법은?

finalizer toolhive.stacklok.dev/toolconfig-finalizer가 남아 있어서다. 이 MCPToolConfig를 참조하는 MCPServer가 아직 있다는 뜻이고, controller는 DeletionBlocked condition을 True로 쓰고 30초마다 다시 확인한다.

v0.63.0에도 status.referencingWorkloads가 없으므로, condition 메시지를 읽거나 MCPServer의 spec.toolConfigRef를 직접 조회해야 한다. 참조를 먼저 지우면 삭제가 끝난다.

Q5. MCPServer에 spec.serviceAccount: my-sa를 넣었다. proxy pod의 ServiceAccount도 my-sa가 되는가?

코드로 보면 그렇지 않다. proxy Deployment는 늘 <이름>-proxy-runner를 쓰고, my-sa는 pod patch로 MCP 서버 pod에 쓰인다. 이때 operator는 <이름>-sa를 만들지 않는다.

공식 문서의 설명은 이와 다르다. 한편 MCPRemoteProxy에서는 spec.serviceAccount가 proxy pod에 쓰이고 RBAC 생성도 건너뛴다.

Q6. rolling update 중인 두 proxy pod가 StatefulSet을 번갈아 덮어쓰지 않는 이유는?

operator는 proxy pod template에 MCPServer generation을 찍고, 그 값을 downward API 환경 변수로도 넣는다. 그래서 각 proxy pod는 생성 시점의 generation을 고정해서 갖는다.

proxy는 이 값을 StatefulSet pod template에 찍고, 기존 StatefulSet의 값이 자기 값보다 크면 apply를 건너뛴다. 따라서 옛 pod는 새 pod가 쓴 StatefulSet을 되돌리지 못한다.

Q7. namespace 모드로 설치하면서 다른 값은 기본값으로 두었다. 무슨 일이 일어나는가?

Helm 렌더링이 실패한다. storageVersionMigrator 기본값 true와 namespace 모드를 함께 쓸 수 없기 때문이다.

설치하려면 operator.features.storageVersionMigrator: false를 넣어야 하고, 그러면 storedVersions 정리는 kube-storage-version-migrator 같은 다른 수단으로 해야 한다.

Q8. restart-strategy: immediate로 재시작하면 MCP 서버 pod도 지워지는가?

코드로 보면 지워지지 않는다. immediate는 app: mcpserver label을 가진 pod만 지우는데, 이 label은 proxy Deployment의 pod에 있고 MCP 서버 StatefulSet의 pod는 app: <이름> label을 쓴다. 이 답은 코드에서 추론한 것이고 시험하지는 않았다.

Q9. MCPServer에 replicas: 2를 넣고 세션 저장소를 설정하지 않았다. operator와 클라이언트는 어떻게 되는가?

operator는 SessionStorageWarning을 True로 쓰고 replica 2를 그대로 적용한다. MCP 세션은 각 pod 메모리에만 있다.

proxy Service는 기본으로 ClientIP affinity를 쓰므로, 클라이언트가 같은 pod로 가는 동안에는 요청이 성공한다. 요청이 다른 pod로 가면 그 pod에는 세션이 없어서 Session not found로 실패한다.

Q10. MCPRegistry를 쓰는 클러스터가 있다. 앞으로 무엇으로 옮겨야 하고 configYAML은 어디로 가는가?

MCPRegistry kind 전체가 deprecated이므로 toolhive-registry-server Helm chart로 옮겨야 한다.

spec.configYAML 문자열의 내용은 Helm 값 config 아래에 구조화된 YAML로 들어간다. 공식 문서는 두 배포를 나란히 띄운 뒤 클라이언트를 옮기라고 안내한다.

대조한 것

소스 행 번호는 v0.63.0 태그 트리에서 다시 확인했고, v0.53.0과 v0.63.0 사이에 바뀐 파일은 diff로 읽었다. mcpserver_controller.go의 변경은 RBAC 규칙과 전역 Redis 처리뿐이고 reconcile 순서는 그대로였다. controller 목록은 app.go의 등록 코드와 대조했고, CRD 버전, 짧은 이름, deprecated 표시는 chart의 CRD YAML 14개로 대조했다. 14개 중 v0.63.0에서 바뀐 파일은 MCPExternalAuthConfig와 VirtualMCPServer 두 개다. Helm 값은 chart 0.63.0의 values.yaml과 템플릿으로 대조했다. 공식 문서는 2026-11-07에 guides-k8s/run-mcp-k8s와 guides-k8s/deploy-operator 두 쪽을 다시 읽었고, 나머지 공식 문서 인용은 2026-10-13에 읽은 내용이다.

공식 문서와 코드가 다른 곳

ServiceAccount 이름, spec.serviceAccount의 대상, spec.resources의 대상은 5장에 적었고, 세 곳 모두 v0.63.0에서도 그대로다. toolconfig-reconciliation.md의 status 필드는 9장에 적었다. 아키텍처 문서는 webhook을 controller와 함께 등록한다고 쓰지만(source docs/arch/09-operator-architecture.md:498), v0.63.0 app.go에도 webhook 등록 코드가 없고 operator chart에도 webhook 템플릿이 없다. cmd/thv-operator/config/webhook/manifests.yaml에만 정의가 있는데, 이 차이의 이유는 확인하지 못했다.

추론이고 시험하지 않은 것

StatefulSet을 proxy가 만드는 이유 중 runner 코드 재사용은 코드에서 읽은 해석이다. MCPServer generation이 오르면 MCP 서버 pod가 다시 만들어진다는 점, immediate 재시작이 proxy pod만 지운다는 점, MCPRemoteProxy만 참조하는 MCPToolConfig의 삭제가 막히지 않는다는 점도 추론이다. 모두 클러스터에서 실행해 보지 않았다.

확인하지 못한 것

MCPRemoteProxy, EmbeddingServer, MCPRegistry의 reconcile 세부 순서는 읽지 않았다. vMCP의 authServerUpstreamFilter와 MCPExternalAuthConfig의 DCR 상한 필드는 존재만 확인하고 동작은 읽지 않았으며, 공식 문서 중 위의 두 쪽 외에는 2026-11-07에 다시 읽지 않았다.
