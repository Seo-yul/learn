실행 모델: workload, transport, proxy

ToolHive 학습 02편 · 2026-10-14 작성

이 문서는 ToolHive가 MCP 서버 하나를 띄우고 관리하는 방식을 다룬다. 앞부분에서는 workload 수명 주기와 RunConfig를 보고, 뒷부분에서는 transport, proxy 구현, 원격 MCP 서버, protocol build를 본다. 끝에서는 middleware 순서, API 서버, 소스 지도를 정리한다.

기준 버전은 ToolHive v0.63.0(2026-11-06)이다. 2026-10-14에 v0.53.0 기준으로 썼고, 2026-11-07에 v0.63.0 기준으로 갱신했다. 공식 문서는 2026-11-07 상태를 읽었는데, ToolHive는 자주 바뀌므로 실제로 쓰기 전에 공식 문서를 다시 확인해야 한다.

한 문장 요약

ToolHive는 MCP 서버마다 proxy 프로세스를 하나 띄우고, proxy는 transport에 맞는 전달 구현 앞에 middleware 체인을 둔다. workload 설정은 RunConfig 하나에 모두 담기고, 상태는 디스크 파일로 남는다.

v0.63.0 갱신 요약

v0.53.0과 견줘 이 문서의 주제에서 바뀐 것을 모았는데, 큰 구조는 그대로다.

  • mcp-parser middleware는 POST가 아닌 요청에 body가 있으면 400으로 거부하고, body 없는 GET, DELETE, OPTIONS는 그대로 넘긴다(7장, 10장).
  • transparent proxy는 Connection 헤더에 hop-by-hop이 아닌 헤더 이름을 적은 요청을 400으로 거부한다. 이 검사는 middleware 체인보다 먼저 돌고, --stateless와 2026-07-28 revision의 405 검사도 같은 자리에서 돈다(6장, 7장, 8장).
  • health check를 켠 transparent proxy의 /health는 요청마다 MCP 서버를 찌르지 않고 마지막 검사 결과를 답한다(6장).
  • streamable HTTP 쪽 stdio 변환기는 요청 ID를 세션 ID와 요청마다 만든 무작위 토큰으로 바꾸는데, 전에는 세션 ID와 원래 ID를 합쳤다(6장, 자가 점검 Q7).
  • proxy는 OAuth refresh token이나 client 정보를 저장할 때 디스크의 RunConfig를 다시 읽고, secret 값을 지운 뒤 쓴다(5장, 8장).
  • CLI의 --thv-ca-bundle, --jwks-auth-token-file, --jwks-allow-private-ip, --oidc-insecure-allow-http 값이 auth middleware 설정에 들어간다(5장).
  • 내장 인가 서버의 TLS listener 포트가 proxy 포트와 겹치면 실행을 멈춘다. operator는 전체 기본 Redis 설정을 세션 저장소로 쓴다(7장).

아래 이름은 용어집의 단어를 포함하지만 뜻이 달라서, 이 문서에서는 아래처럼 구분한다.

  • thv proxy 명령: transparent proxy만 띄우는 별도 명령이고 workload를 만들지 않는다(source cmd/thv/app/proxy.go:34). 이 문서의 proxy와 다르다.
  • egress proxy: 네트워크 격리에서 나가는 연결을 거르는 프로세스다. 03편이 다룬다.
  • StdioTransport, HTTPTransport: proxy 안에서 전달 구현을 띄우고 감시하는 Go 객체다. 이 문서는 "transport 객체"라고 쓰고, transport(통신 방식)와 구분한다.
  • templates.TransportType: 이름과 달리 protocol build 종류(npx, uvx, go)를 뜻한다. transport가 아니다.
  • pkg/state, SaveState: 코드는 저장된 RunConfig를 state라고 부른다. 이 문서는 "저장된 RunConfig"라고 쓴다.
  • --runtime-image, runtime_config: build 설정이다. 컨테이너 런타임과 다르다.
  • backend: ToolHive 설계 문서는 proxy 뒤의 MCP 서버를 backend라고 부르기도 한다. 이 시리즈에서 backend는 vMCP가 묶는 MCP 서버만 뜻하므로, 이 문서는 "MCP 서버"라고 쓴다.

1. 큰 그림: thv run이 만드는 것

thv run은 MCP 서버 하나를 workload로 만들고, 이때 ToolHive는 다음을 남긴다.

  • 저장된 RunConfig 파일 하나(5장)
  • 상태 파일 하나(4장)
  • proxy 프로세스 하나
  • MCP 서버 컨테이너 하나. 원격 workload에는 컨테이너가 없다.
  • 네트워크 격리가 켜져 있으면 DNS, egress proxy 같은 보조 컨테이너(03편)
  • 클라이언트 설정 안의 항목 하나(04편)

thv run의 기본 동작은 detached 실행이다. 터미널의 thv 프로세스는 설정을 저장하고 바로 끝나고, 실제 proxy 일은 따로 떼어 낸 자식 프로세스가 맡는다.

detached 실행 순서

기본 실행에서 터미널의 thv 프로세스(부모)는 다음 순서로 일한다.

  1. RunConfig를 만들고 정책 검사(policy gate)를 한다(source cmd/thv/app/run.go:249).
  2. RunConfig를 디스크에 저장한다. secret 값을 풀기 전에 저장하므로 값은 파일에 들어가지 않는다(source cmd/thv/app/run.go:254).
  3. 상태를 starting으로 쓴다(source pkg/workloads/manager.go:788).
  4. 자기 실행 파일을 start <이름> --foreground 인자로 다시 실행한다(source pkg/workloads/manager.go:747).
  5. 자식 프로세스의 PID를 상태 파일에 적고 끝난다(source pkg/workloads/manager.go:698).

자식 프로세스는 setsid로 터미널에서 분리되고(source pkg/workloads/sysproc_unix.go:15), 표준 출력과 표준 오류는 proxy 로그 파일로 간다(source pkg/workloads/manager.go:727). 자식에는 환경 변수 TOOLHIVE_DETACHED=1도 붙는다(source pkg/process/detached.go:12).

이 자식 프로세스가 proxy이고, --foreground를 주면 터미널의 thv 프로세스가 직접 proxy가 된다.

proxy 안에서 일어나는 일

proxy 프로세스에서 Runner.Run은 다음 순서로 일한다(source pkg/runner/runner.go:220).

  1. secret 참조를 실제 값으로 푼다.
  2. middleware 목록을 채운다. 맨 앞에는 body 크기 제한과 Origin 검사를 차례로 둔다(source pkg/runner/runner.go:350, pkg/runner/runner.go:359).
  3. 정책 검사를 한 번 더 한다(source pkg/runner/runner.go:480).
  4. 컨테이너 workload면 runtime.Setup으로 컨테이너를 만든다(source pkg/runner/runner.go:492).
  5. transport 팩토리로 transport 객체를 만들고 시작한다(source pkg/runner/runner.go:556).
  6. HTTP 계열이면 initialize가 성공할 때까지 최대 5분 기다린다(source pkg/runner/runner.go:679).
  7. 클라이언트 설정에 proxy 주소를 쓴다(source pkg/runner/runner.go:694).
  8. 상태를 running으로 바꾼다. 이후 1초마다 transport 객체가 살아 있는지 본다(source pkg/runner/runner.go:772).

HTTP 계열에서 5분이 지나도 실패하면 경고만 남기고 다음 단계로 간다(source pkg/runner/runner.go:680). stdio workload는 6단계를 건너뛰는데, stdio MCP 서버는 initialize를 여러 번 받으면 거부할 가능성이 있기 때문이다(source pkg/runner/runner.go:659).

2. workload 상태와 전이

workload의 상태 값은 11가지다(source pkg/container/runtime/types.go:25). 그림 2는 주요 전이만 보여 주고, 모든 상태는 그림 뒤의 표에 정리했다.

상태뜻들어가는 경우
starting실행 직전이다thv run, thv start, 자동 재시작
runningproxy가 요청을 받는다Runner.Run이 준비를 마쳤다
stopping멈추는 중이다thv stop
stopped멈췄다. 컨테이너와 저장된 RunConfig는 남는다thv stop 완료
removing지우는 중이다thv rm. running에서 바로 들어가는 경우도 있다
error실행이나 정지에 실패했다실행 실패, 자동 재시작 10회 소진, 컨테이너 정지 실패
unhealthy실행 중이지만 정상으로 동작하지 못한다상태 파일은 running인데 컨테이너나 proxy가 없다. 원격 health check가 실패했다
unauthenticated원격 MCP 서버에 인증하지 못한다원격 서버가 401을 돌려줬다. access token 갱신이 끝내 실패했다

policy_stopped정책이 시작을 막았다thv start 때 정책 검사에 걸렸다
unknown컨테이너 런타임이 상태를 모른다컨테이너 런타임이 알 수 없는 값을 돌려줬다

표의 근거는 다음 위치에 있다. (source pkg/workloads/manager.go:535, pkg/workloads/statuses/file_status.go:950, pkg/runner/runner.go:609, pkg/container/runtime/types.go:47)

auth_retrying은 10분마다 갱신을 다시 시도하고, 24시간이 지나면 unauthenticated로 바뀐다(source pkg/auth/monitored_token_source.go:48). proxy 프로세스의 환경 변수로 두 값을 바꾸는 기능도 있다(source docs/arch/08-workloads-lifecycle.md:51).

자동 재시작

컨테이너가 예기치 않게 끝나면 proxy의 Runner.Run이 먼저 판단한다. workload가 지워졌으면 재시작 없이 끝내고, 남아 있으면 재시작이 필요하다는 오류를 돌려준다(source pkg/runner/runner.go:810).

workload 관리자는 이 오류를 받으면 아래 규칙으로 다시 실행한다(source pkg/workloads/manager.go:535).

  • 최대 10회 시도한다.
  • 대기 시간은 5초에서 시작해 두 배씩 늘고, 60초에서 더 늘지 않는다.
  • 재시작 전에 클라이언트 설정에서 항목을 뺀다(source pkg/workloads/manager.go:577).
  • 30초 이상 돌다 끝났으면 횟수를 처음부터 다시 센다(source pkg/workloads/manager.go:585).
  • 10회를 다 쓰면 상태를 error로 바꾼다.

ToolHive 설계 문서의 그림은 컨테이너 종료를 stopped로 그리지만(source docs/arch/08-workloads-lifecycle.md:26), v0.63.0 코드는 상태를 starting으로 바꾸고 다시 실행한다.

3. 수명 주기 명령

수명 주기 명령은 Docker 명령과 비슷하다. 아래 표는 명령마다 실제로 하는 일을 코드 기준으로 정리한 것이다.

명령컨테이너 workload원격 workload
thv run컨테이너와 proxy를 만든다proxy만 만든다
thv stopproxy를 끝내고 컨테이너를 멈춘다. 클라이언트 설정 항목을 뺀다proxy를 끝내고 클라이언트 설정 항목을 뺀다
thv start (별칭 restart)저장된 RunConfig로 다시 실행한다proxy를 다시 띄운다. 공식 문서는 OAuth 흐름을 다시 탄다고 적는다
thv rm컨테이너를 지우고 proxy를 끝낸다. 상태 파일과 저장된 RunConfig도 지운다proxy를 끝낸다. 상태 파일과 저장된 RunConfig를 지운다
thv logs컨테이너 로그를 보인다. --proxy를 주면 proxy 로그를 보인다--proxy를 줘야 한다
thv list기본은 running과 auth_retrying만 보인다. --all은 모두 보인다같다

표의 근거는 다음 위치에 있다. (source pkg/workloads/manager.go:455, pkg/workloads/manager.go:1648, pkg/workloads/manager.go:897, cmd/thv/app/logs.go:92, cmd/thv/app/list.go:55, docs guides-cli/manage-mcp-servers)

thv start는 workload가 running이고 proxy가 살아 있으면 아무것도 하지 않고(source pkg/workloads/manager.go:1462), proxy가 죽어 있으면 컨테이너를 멈춘 뒤 다시 시작한다.

thv rm은 컨테이너를 먼저 지우고 proxy를 나중에 끝내는데(source pkg/workloads/manager.go:960), proxy가 컨테이너를 다시 만들지 못하게 하는 순서다. 설계 문서는 proxy를 먼저 끝낸다고 적지만 코드 순서는 반대다.

stop과 rm은 상태 파일의 PID로 proxy를 끝낸다. PID가 없거나 PID로 끝내지 못하면 proxy 포트를 잡은 프로세스를 찾고, 그 프로세스가 이 workload의 proxy일 때만 끝낸다(source pkg/workloads/manager.go:1086).

일괄 처리

thv stop과 thv rm은 이름을 여러 개 받지만 thv start는 이름을 하나만 받는다. 세 명령 모두 --all과 --group으로 대상을 고르는 기능이 있다(source cmd/thv/app/restart.go:36).

workload 관리자는 이름마다 goroutine을 하나씩 띄워 병렬로 처리하고(source pkg/workloads/manager.go:411), 작업 하나에는 5분 제한이 있다(source pkg/workloads/manager.go:216). 호출한 쪽은 돌려받은 CompletionFunc를 불러 끝날 때까지 기다린다.

관리자는 처리 전에 모든 이름을 먼저 검사하는데, 파일 경로를 벗어나는 이름을 막는 검사다(source pkg/workloads/manager.go:413).

수명 주기

RunConfig는 다음 단계를 거친다.

  1. 만들기: CLI 플래그, registry 정보, API 요청으로 builder가 만든다(source pkg/runner/config_builder.go:1077).
  2. 저장: 실행 전에 저장된 RunConfig 파일로 쓴다. WriteJSON은 2칸 들여쓰기 JSON을 쓴다(source pkg/runner/config.go:367).
  3. 읽기: thv start, export, list가 ReadJSON으로 읽는다(source pkg/runner/config.go:378).
  4. 실행: proxy가 읽은 RunConfig로 Runner.Run을 실행한다.
  5. 지우기: thv rm이 파일을 지운다(source pkg/workloads/manager.go:1193).

ReadJSON은 비어 있는 버전을 v0.1.0으로 채우고, 원격 인증 정보가 평문으로 남아 있으면 secret 참조로 바꾼다(source pkg/runner/config.go:404). 대상은 OAuth client secret과 bearer token이다. Go 기본 JSON decoder를 쓰므로 모르는 필드는 무시하고(source pkg/state/runconfig.go:134), 버전이 다를 때 거부하는 코드는 ReadJSON에 없다.

proxy도 저장된 RunConfig를 고쳐 쓸 때가 있는데, 원격 workload가 OAuth refresh token이나 DCR client 정보를 받았을 때다. proxy는 그 값을 secret으로 저장하고 참조만 RunConfig에 적는다. 이때 메모리의 RunConfig를 쓰지 않고 디스크 파일을 다시 읽은 다음, secret 대상 환경 변수와 secret에서 온 헤더 값을 지우고 저장한다(source pkg/runner/runner.go:952, pkg/runner/runner.go:1007). v0.53.0은 메모리의 RunConfig를 그대로 저장했다.

export와 재사용

thv export <이름> <경로>는 저장된 RunConfig를 JSON 파일로 쓴다(source cmd/thv/app/export.go:87). --format k8s를 주면 MCPServer YAML을 쓰는데, 이 YAML에는 secret, OIDC, telemetry 설정이 빠지고 명령은 경고만 낸다(source cmd/thv/app/export.go:93).

thv run --from-config <경로>는 그 파일로 workload를 다시 만든다(source cmd/thv/app/run.go:447). 이 플래그와 함께 쓸 수 있는 플래그는 --foreground와 --debug뿐인데(source cmd/thv/app/run.go:523), 공식 문서는 다른 플래그를 쓸 수 없다고만 적는다.

다른 PC에서 다시 실행하려면 그 PC에도 같은 이름의 secret이 있어야 한다(docs guides-cli/run-mcp-servers).

thv export weather ./weather.json
thv export weather ./weather.yaml --format k8s
thv run --from-config ./weather.json

transparent proxy는 middleware 체인을 MCP 전달 경로에만 씌우고, /health, /metrics, /.well-known/ 경로는 체인 밖에서 처리한다(source pkg/transport/proxy/transparent/transparent_proxy.go:1313). /.well-known/은 인증을 끈 경우에도 등록하는데, 그래야 OAuth 탐색 요청이 MCP 서버로 넘어가지 않고 404 JSON을 받는다(source pkg/transport/proxy/transparent/transparent_proxy.go:1338). 내장 인가 서버의 /oauth/token 같은 경로도 체인 밖에 있다(source docs/arch/03-transport-architecture.md:174).

MCP 전달 경로에는 middleware 체인보다 먼저 도는 검사가 두 개 있는데(source pkg/transport/proxy/transparent/transparent_proxy.go:1346), 둘 다 헤더만 보고 body를 읽지 않는다.

  • Connection 헤더에 hop-by-hop이 아닌 헤더 이름이 있으면 400으로 거부한다(source pkg/transport/proxy/transparent/transparent_proxy.go:1650). Go ReverseProxy는 Connection에 적힌 헤더를 지우고 넘기므로, 클라이언트가 이 동작으로 middleware가 넣은 헤더를 지우지 못하게 막는 검사다.
  • proxy가 --stateless이면 GET, HEAD, DELETE에 405를 돌려주고(source pkg/transport/proxy/transparent/transparent_proxy.go:1692), 요청의 MCP-Protocol-Version 헤더가 2026-07-28일 때도 같다. 응답에는 Allow: POST, OPTIONS 헤더가 붙는다. 그 밖의 GET, HEAD, DELETE는 middleware 체인으로 들어간다.

health check를 켠 transparent proxy는 MCP 서버를 주기마다 검사하고, /health는 요청마다 MCP 서버를 찌르지 않고 마지막 검사 결과를 답한다(source pkg/transport/proxy/transparent/transparent_proxy.go:525, pkg/healthcheck/healthcheck.go:90). 그래서 느린 MCP 서버가 Kubernetes probe를 제한 시간 너머로 붙잡지 못한다. 검사 실패는 MCP 서버가 initialize를 마친 뒤부터만 종료 횟수에 세고(source pkg/transport/proxy/transparent/transparent_proxy.go:1486), 실패한 검사는 HTTP 200에 degraded로 답한다(source docs/arch/03-transport-architecture.md:481). v0.53.0의 /health는 요청마다 MCP 서버를 찔렀다.

StdioBridge

StdioBridge는 방향이 반대라서, stdio만 쓰는 MCP 클라이언트가 HTTP 주소의 workload에 붙을 때 쓴다(source pkg/transport/bridge.go:22). thv proxy stdio <이름>이 이 연결을 열고(source cmd/thv/app/proxy_stdio.go:18), StdioBridge는 workload의 proxy 주소에 MCP 클라이언트로 붙는다.

stdio 컨테이너에 붙는 방법

stdio workload에서 ToolHive는 다음 순서로 컨테이너와 메시지를 주고받는다.

  1. runtime.Setup이 환경 변수 MCP_TRANSPORT=stdio를 넣고, stdin을 연 채로 컨테이너를 만든다(source pkg/runtime/setup.go:67, pkg/runtime/setup.go:106).
  2. stdio transport 객체가 attach API로 컨테이너의 표준 입출력을 연다(source pkg/transport/stdio.go:226).
  3. Docker 클라이언트는 스트림을 나눠 stdout만 넘기고 stderr는 버린다(source pkg/container/docker/client.go:694).
  4. proxy mode에 맞는 stdio 변환기를 띄운다(source pkg/transport/stdio.go:233).
  5. HTTP 쪽 메시지를 JSON-RPC로 인코딩하고 줄바꿈을 붙여 stdin에 쓴다(source pkg/transport/stdio.go:720).
  6. stdout은 4096바이트씩 읽고 줄바꿈 단위로 자른다(source pkg/transport/stdio.go:582).
  7. 각 줄은 첫 {와 마지막 } 사이만 JSON-RPC로 해석한다(source pkg/transport/stdio.go:650).

MCP 서버는 stdout에 JSON-RPC 메시지만 써야 한다. proxy는 stdout의 로그 줄을 버리거나 파싱 오류 로그만 남기고 넘어가므로, fastmcp 기반 이미지라면 로그를 stderr로 보내야 한다. thv logs는 컨테이너 로그를 읽기 때문에 stderr도 보여 준다(source pkg/container/docker/client.go:582).

stdout이 닫히면 stdio transport 객체는 컨테이너가 살아 있는지 보고, 살아 있으면 다시 attach한다(source pkg/transport/stdio.go:484). 대기 시간은 2초에서 시작해 최대 30초이고, 10회까지 시도한다(source pkg/transport/stdio.go:41). 컨테이너가 끝나면 컨테이너 감시기(monitor)가 이를 알리고 stdio transport 객체가 멈추는데(source pkg/container/runtime/monitor.go:36, pkg/transport/stdio.go:741), 그 뒤는 2장의 자동 재시작 흐름이다.

응답을 세션에 돌려주는 방법

stdio 컨테이너 하나에서는 모든 세션이 파이프 하나를 나눠 쓰는데, 컨테이너가 내는 메시지에는 세션 정보가 없다. 그래서 stdio 변환기가 요청 ID를 바꿔 세션을 표시한다(source docs/arch/03-transport-architecture.md:679).

  • streamable HTTP 쪽 변환기는 요청 ID를 세션 ID와 요청마다 새로 만든 무작위 토큰을 합친 키로 바꾸고, 원래 ID는 따로 보관했다가 응답에 되돌린다(source pkg/transport/proxy/streamable/streamable_proxy.go:1028, pkg/transport/proxy/streamable/streamable_proxy.go:1666). 같은 세션이 같은 ID로 요청을 두 번 보내도 응답이 섞이지 않는 방식이고, v0.53.0은 세션 ID와 원래 ID를 합쳤다.
  • SSE 쪽 변환기는 숫자 ID를 <session_id>|n:<정수> 꼴로, 문자열 ID를 <session_id>|s:<문자열> 꼴로 바꾼다(source pkg/transport/proxy/httpsse/routing.go:70).
  • MCP 서버가 먼저 보내는 요청은 클라이언트에 넘기지 않고, 변환기가 -32601 오류로 MCP 서버에 바로 답한다(source pkg/transport/proxy/streamable/dispatcher.go:63).
  • list_changed 알림은 모든 세션에 보내고, notifications/message 로그는 버린다(source docs/arch/03-transport-architecture.md:707).

그래서 v0.63.0의 stdio workload에서는 sampling/createMessage, elicitation/create 요청이 MCP 클라이언트에 닿지 않는다.

7. 포트, 세션, 오류, 성능

포트

proxy 포트와 target 포트는 서로 다른 포트이고(source docs/arch/03-transport-architecture.md:537), 포트를 정하는 규칙은 다음과 같다.

  • --proxy-port를 주면 그 포트가 비었는지 확인하고, 비어 있지 않으면 오류로 끝낸다(source pkg/runner/config.go:599).
  • 주지 않으면 10000~65535에서 무작위로 10번 고르고, 모두 실패하면 앞에서부터 차례로 찾는다(source pkg/networking/port.go:74).
  • target 포트는 SSE와 streamable HTTP에만 있고, --target-port가 없으면 같은 방법으로 고른다(source pkg/runner/config.go:620).
  • ToolHive는 target 포트를 MCP_PORT와 FASTMCP_PORT 환경 변수로 알린다(source pkg/runtime/setup.go:72).
  • MCP_HOST에는 target host를 넣고, 기본값은 127.0.0.1이다(source cmd/thv/app/run_flags.go:198).
  • runtime.Setup은 target 포트와 같은 번호로 호스트 연결을 요청하고, 연결 주소는 --host 값이다(source pkg/runtime/setup.go:116).
  • 최종 호스트 포트는 네트워크 격리에 따라 달라진다(source pkg/container/docker/client.go:381). --isolate-network의 기본값은 true이고(source cmd/thv/app/run_flags.go:302), 격리가 켜지면 MCP 서버 컨테이너 앞에 ingress용 보조 컨테이너가 선다(source pkg/container/docker/client.go:352). 이 구조는 03편이 다룬다.
  • operator 경로에서는 포트를 호스트에서 확인하지 않는다(source pkg/runner/config.go:580).
  • 내장 인가 서버의 TLS listener를 켜면 그 listener는 8443 포트에 고정되고, proxy 포트나 진단 포트가 8443이면 Runner.Run은 오류로 끝낸다(source pkg/runner/runner.go:1342, pkg/authserver/runner/embeddedauthserver.go:42). 내장 인가 서버는 05편이 다룬다.

세션

  • transparent proxy는 Mcp-Session-Id 헤더와 SSE 응답의 sessionId로 세션을 추적한다(source docs/arch/03-transport-architecture.md:601).
  • streamable HTTP 쪽 stdio 변환기는 세션 ID를 직접 발급하고, DELETE /mcp는 세션을 닫는다(source docs/arch/03-transport-architecture.md:667).
  • 세션은 2시간 동안 쓰지 않으면 만료되고, --session-ttl로 바꾸는 기능이 있다(source pkg/transport/session/proxy_session.go:27).
  • 세션은 기본으로 proxy 메모리에 있고, Kubernetes에서 Redis를 고르면 proxy 여러 개가 세션을 나눠 쓴다(source pkg/runner/runner.go:527). operator에는 전체 기본 Redis 설정을 두는 기능이 있어서, 그 설정이 있으면 MCPServer spec에 Redis 세션 저장소가 없어도 그 Redis를 쓴다(source cmd/thv-operator/controllers/mcpserver_runconfig.go:303).
  • 세션은 처음 인증한 사용자의 iss, sub에 묶여서 다른 사용자가 쓰면 404를 받는다(source docs/arch/03-transport-architecture.md:233). 자세한 내용은 05편이 다룬다.
  • MCP 클라이언트가 붙어 있지 않을 때 나온 메시지는 나중에도 보내지 않는다(source docs/arch/03-transport-architecture.md:613).

8. 원격 MCP 서버

원격 workload는 다른 곳에서 도는 MCP 서버 앞에 proxy만 둔다(docs guides-cli/run-remote-mcp-servers).

thv run https://api.example.com/mcp --name example
thv run https://api.example.com/sse --transport sse
thv run https://example.com/mcp --name my-server --transport streamable-http --stateless

이름을 주지 않으면 ToolHive는 URL의 도메인에서 이름을 만들고, 원격 workload의 기본 transport는 streamable-http다(docs guides-cli/run-remote-mcp-servers).

원격 URL을 받으면 proxy는 다음처럼 동작한다.

  1. remote_url이 있으므로 컨테이너를 만들지 않는다(source pkg/runner/runner.go:484).
  2. transparent proxy의 대상을 원격 URL의 scheme과 host로 잡는다(source pkg/transport/http.go:285).
  3. 요청마다 경로를 원격 URL의 경로로 바꾼다. 원격 URL의 query는 요청의 query 앞에 붙인다(source pkg/transport/proxy/transparent/transparent_proxy.go:1256).
  4. 나가는 인증이 필요하면 access token을 얻고, Authorization 헤더를 넣는 middleware를 맨 안쪽에 붙인다. token exchange middleware가 있으면 붙이지 않는다(source pkg/transport/http.go:330).
  5. 원격 서버가 401을 돌려주면 상태를 unauthenticated로 바꾼다(source pkg/runner/runner.go:621).
  6. health check는 기본으로 끄고, TOOLHIVE_REMOTE_HEALTHCHECKS를 true나 1로 두면 켠다(source pkg/transport/http.go:224).

--stateless는 POST만 받는 서버에 쓰고, 이때 proxy는 GET, HEAD, DELETE에 405를 돌려준다(source pkg/transport/proxy/transparent/transparent_proxy.go:1696, docs guides-cli/run-remote-mcp-servers). 요청의 MCP-Protocol-Version 헤더가 2026-07-28이면 --stateless가 없어도 같은 405를 받는데, 이 검사는 6장이 자세히 다룬다.

나가는 인증 개요

ToolHive는 원격 서버의 인증 요구를 자동으로 찾는데(source docs/remote-mcp-authentication.md:63), 순서는 다음과 같다.

  1. 시험 요청을 보내고 401 응답과 WWW-Authenticate 헤더를 본다.
  2. 헤더가 없으면 RFC 9728의 /.well-known/oauth-protected-resource를 찾는다.
  3. 인가 서버를 찾는다. client 정보가 없으면 CIMD나 DCR(RFC 7591)로 client를 얻는다(docs guides-cli/run-remote-mcp-servers).
  4. PKCE를 쓰는 OAuth 흐름으로 access token을 받는다.

받은 refresh token과 DCR client 정보는 secret으로 저장하고, 저장된 RunConfig에는 그 참조만 적는다. 이때 proxy는 디스크의 RunConfig를 다시 읽고 secret 값을 지운 뒤 쓴다(5장).

bearer token 직접 지정, 고정 헤더 주입(--remote-forward-headers) 같은 방법도 있다(docs guides-cli/run-remote-mcp-servers). 자세한 흐름은 05편 8.4절이 다룬다. Kubernetes에서는 MCPRemoteProxy 리소스가 같은 일을 한다(07편).

9. protocol build

protocol build는 패키지 주소만으로 이미지를 만드는 기능이라서, 사용자 PC에 Node.js, Python, Go가 없어도 된다(docs guides-cli/run-mcp-servers).

thv run --transport stdio --name pulumi npx://@pulumi/mcp-server@latest
thv run --transport stdio uvx://mcp-server-git@latest
thv build --tag ghcr.io/myorg/mcp-git:v1.0.0 uvx://mcp-server-git@1.0.0
thv build --dry-run -o Dockerfile.mcp-git uvx://mcp-server-git

ToolHive는 protocol build를 다음 순서로 한다(source pkg/runner/protocol.go:51).

  1. 주소에서 build 종류와 패키지 이름을 읽는다(source pkg/runner/protocol.go:84).
  2. build 설정을 정한다. RunConfig 값, 설정 파일 값, 기본값 순서로 앞의 것을 쓴다(source pkg/runner/protocol.go:192).
  3. 템플릿으로 Dockerfile을 만든다(source pkg/container/templates/npx.tmpl).
  4. 이미지를 build한다. 이름은 toolhivelocal/<종류>-<패키지>:<시각>이다(source pkg/runner/protocol.go:575).
  5. 만든 이미지로 일반 실행 경로를 탄다.

10. middleware 순서

요청은 MCP 서버에 닿기 전에 middleware 체인을 지나는데, 목록의 첫 항목이 가장 바깥에서 먼저 돈다(source pkg/transport/proxy/transparent/transparent_proxy.go:1297). transparent proxy에서는 6장의 Connection 헤더 검사와 405 검사가 이 목록보다 더 바깥에서 돈다. 아래 표는 operator 경로의 순서이고, operator는 RunConfig를 만들 때 PopulateMiddlewareConfigs로 목록을 채운다(source cmd/thv-operator/controllers/mcpserver_runconfig.go:292, pkg/runner/middleware.go:67). 각 middleware의 자세한 동작은 05편과 06편이 다룬다.

1번과 2번은 Runner.Run이 맨 앞에 붙인다(source pkg/runner/runner.go:350, pkg/runner/runner.go:359). Origin 허용 목록은 loopback 주소에 바인드하면 자동으로 생기고, 다른 주소인데 --allowed-origins가 없으면 origin middleware를 빼고 경고만 남긴다(source pkg/runner/middleware.go:755).

operator는 proxy를 기본으로 0.0.0.0에 바인드하고 Origin 허용 목록을 넣지 않아서, operator 경로에는 기본으로 origin middleware가 없다(source cmd/thv-operator/controllers/mcpserver_runconfig.go:88).

ratelimit은 Redis 세션 저장소를 요구해서, 세션 저장소가 Redis가 아니면 middleware 목록을 채울 때 오류가 난다(source pkg/runner/middleware.go:783).

표에 없는 middleware도 있다. 내장 인가 서버가 upstream access token을 넘기지 않는 설정이면 5번 자리에 strip-auth가 들어가는데, upstream이 없거나 upstream access token 주입을 끈 경우가 여기에 해당한다. 이 middleware는 클라이언트의 인증 헤더를 지운다(source pkg/runner/middleware.go:495). 외부 인증 handler가 넣은 middleware는 15번과 16번 사이에 들어간다(source pkg/runner/middleware.go:281).

원격 workload에 access token이 있으면 middleware가 하나 더 붙는데, HTTP transport 객체가 oauth-token-injection을 맨 안쪽에 붙인다. token exchange middleware가 있으면 붙이지 않는다(source pkg/transport/http.go:330).

CLI의 thv run과 API 서버는 operator와 다른 함수로 목록을 채워서 순서가 조금 다르다(source pkg/runner/config_builder.go:715, pkg/api/v1/workload_service.go:476).

  • tool-filter와 tool-call-filter가 auth보다 앞에 온다.
  • usagemetrics가 webhook보다 앞에 오고, telemetry는 webhook 뒤에 온다.
  • ratelimit, upstreamswap, awssts는 들어가지 않는다.
  • header-forward는 recovery 뒤에 붙는다(source pkg/runner/runner.go:329).

API 서버는 CLI와 같은 workload 관리자 코드를 쓰기 때문에(source pkg/api/server.go:451), CLI로 만든 workload도 API에 보이고 둘은 같은 RunConfig와 상태 파일을 쓴다.

ToolHive 데스크톱 앱 v0.40.1은 thv serve --openapi --socket=<경로>로 API 서버를 띄운다(source toolhive-studio main/src/toolhive-manager.ts:142).

13. 자가 점검 문제

먼저 답을 생각해 본 다음 펼쳐서 확인한다.

Q1. 기본 옵션으로 thv run을 실행했다. 명령이 끝난 뒤 남는 thv 프로세스는 몇 개이고, 무슨 일을 하는가?

thv 프로세스 하나가 남는다. 터미널의 부모 thv는 RunConfig를 저장하고 끝나고, 부모가 띄운 자식 thv가 proxy로 남아 MCP 서버 컨테이너를 만들고 요청을 넘긴다.

Q2. stdio workload와 streamable HTTP workload에서 proxy 안의 전달 구현은 각각 무엇인가?

stdio workload는 stdio 변환기를 쓰고, 변환기는 HTTP 요청을 JSON-RPC 한 줄로 바꿔 컨테이너 stdin에 쓴다. streamable HTTP workload는 transparent proxy를 쓰는데, 요청을 컨테이너의 HTTP 서버로 그대로 넘긴다.

Q3. 컨테이너가 예기치 않게 끝났다. 상태는 어떻게 바뀌고, 언제 error가 되는가?

상태는 starting으로 바뀌고 workload 관리자가 다시 실행한다. 대기 시간은 5초에서 시작해 60초까지 늘어나고, 10회를 다 써도 실패하면 error가 된다. 다만 30초 이상 돈 뒤 끝났으면 횟수를 처음부터 다시 센다.

Q4. thv stop 뒤와 thv rm 뒤에 디스크에 남는 파일은 어떻게 다른가?

thv stop 뒤에는 저장된 RunConfig와 상태 파일이 남아서 thv start가 그 RunConfig로 다시 실행한다. thv rm 뒤에는 둘 다 지워진다. proxy 로그 파일은 두 경우 모두 남고, thv logs prune이 정리한다.

Q5. 동료가 export한 RunConfig JSON으로 thv run --from-config를 실행했다. 서버가 secret을 찾지 못한다. 왜인가?

RunConfig에는 secret 값이 없고 이름,target=환경 변수 참조만 있어서, 실행하는 PC의 secret 저장소에 같은 이름의 secret이 있어야 한다. 그 secret이 없으므로 값을 풀지 못한다.

Q6. fastmcp로 만든 stdio MCP 서버가 시작 로그를 stdout에 찍는다. 어떤 일이 생기는가?

proxy는 stdout의 각 줄을 JSON-RPC로 해석한다. 중괄호가 없는 로그 줄은 버리고, 중괄호가 있는 로그 줄은 파싱 오류 로그만 남긴다. stdout은 JSON-RPC 전용이라서 로그는 stderr로 보내야 하고, stderr는 thv logs로 본다.

Q7. MCP 클라이언트 두 개가 같은 stdio workload에 붙어 있다. 응답이 섞이지 않는 이유는 무엇인가?

stdio 변환기가 요청을 컨테이너에 보내기 전에 ID를 바꾸기 때문이다. 새 ID는 세션 ID와 요청마다 만든 무작위 토큰을 합친 값이고, 응답이 돌아오면 변환기가 그 값으로 기다리는 요청을 찾아 그 세션에만 보낸다. 원래 ID도 이때 되돌린다.

Q8. thv run npx://some-package를 --transport 없이 실행했다. v0.63.0 코드에서 transport는 무엇이 되고, 무엇을 주의해야 하는가?

protocol build 이미지에는 registry 정보가 없기 때문에 transport는 streamable-http가 된다. 공식 문서는 stdio를 기본으로 적으므로 문서와 다르다. 패키지가 stdio로만 말한다면 --transport stdio를 적어야 한다.

Q9. 원격 workload에 thv logs <이름>을 실행하면 오류가 난다. 왜이고, 대신 무엇을 써야 하는가?

원격 workload에는 컨테이너가 없어서 컨테이너 로그가 없다. 대신 thv logs <이름> --proxy로 proxy 로그를 봐야 한다.

Q10. 같은 설정을 CLI의 thv run과 operator로 띄웠다. tool filter와 auth의 순서는 어떻게 다른가?

CLI 경로에서는 tool filter가 auth보다 바깥에 있어 먼저 돈다. operator 경로에서는 auth가 먼저 돌고, tool filter는 token exchange 다음에 온다.

Q11. 클라이언트가 transparent proxy에 body가 있는 GET 요청을 보냈다. proxy는 어떻게 답하는가?

proxy가 --stateless이거나 요청에 MCP-Protocol-Version: 2026-07-28 헤더가 있으면 middleware 체인에 들어가기 전에 405를 받는다. 그 밖의 경우에는 요청이 체인에 들어가고 mcp-parser middleware가 body를 보고 400을 돌려준다. body가 없는 GET이었다면 그대로 MCP 서버로 간다.
