skill과 plugin

ToolHive 학습 09편 · 2026-10-14 작성

이 문서는 ToolHive가 MCP 서버 말고도 관리하는 두 가지 배포물을 다룬다. 하나는 AI 클라이언트가 읽는 지시문인 skill이고, 다른 하나는 여러 구성 요소를 묶은 AI plugin이다. 두 기능의 수명 주기와 project lock file, 서명 기반 신뢰 모델을 차례로 설명한다.

기준 버전은 ToolHive v0.63.0(2026-11-06)이다. 이 문서는 2026-10-14에 v0.53.0 기준으로 작성했고, 2026-11-07에 v0.63.0 기준으로 갱신했다. 공식 문서도 2026-11-07에 다시 읽었다. ToolHive는 자주 바뀌므로 실제로 쓰기 전에 공식 문서를 다시 확인해야 한다.

한 문장 요약

skill과 plugin은 실행 프로세스가 아니라 AI 클라이언트가 읽는 파일 묶음이다. ToolHive는 이 묶음을 OCI artifact나 git으로 배포해서 클라이언트 디렉터리에 풀어 놓고, project 범위로 설치할 때는 서명을 검증한 뒤 toolhive.lock.yaml에 digest와 서명자를 고정한다.

v0.63.0 갱신 요약
  • skill 지원 클라이언트에 Pi coding agent가 들어왔다. user 범위 경로는 ~/.pi/agent/skills/, project 범위 경로는 .pi/skills/이고, 환경 변수 PI_CODING_AGENT_DIR이 있으면 user 범위 경로와 클라이언트 감지가 그 디렉터리를 따른다(3장).
  • ToolHive는 SKILL.md frontmatter와 lock file을 go.yaml.in/yaml/v3로 읽는다. 이전 라이브러리는 특정 frontmatter에서 panic했다. 라이브러리만 바뀌었고 형식, 크기 제한, lock file 필드는 그대로다(3장, 7장).
  • SKILL.md 파서와 plugin manifest 파서에 Go fuzz 테스트가 생겼다(9장).
  • skill과 plugin의 설계 문서, CLI 문서, service 코드는 두 버전 사이에 바뀌지 않았으므로 설치 흐름, 서명, sync, upgrade 설명은 그대로다.
  • 공식 문서는 2026-11-02에 갱신됐지만, 기본 대상 클라이언트와 그룹 자동 설치 설명은 여전히 코드와 다르다(3장, 6장, 10장, 13장).
  • 줄 번호를 v0.63.0 트리에서 다시 확인하고 3장, 9장, 10장의 인용을 고쳤다.

0. 용어집

이 문서에서는 아래 용어를 표에 적은 뜻으로만 쓰고, 표에 없는 시리즈 공통 용어는 공통 뜻을 따른다.

용어이 문서에서의 뜻
skillSKILL.md 하나와 보조 파일을 담은 지시문 묶음. Agent Skills 규격을 따른다.
pluginAI 코딩 도구용 plugin. .claude-plugin/plugin.json이 기술하는 구성 요소 묶음이다. ToolHive 자체의 확장 기능이 아니다.
구성 요소plugin 안의 단위. commands, agents, skills, hooks, mcpServers, lspServers 여섯 종류다.
AI 클라이언트skill이나 plugin을 읽는 AI 코딩 도구. Claude Code, Cursor, Codex 등이다.
설치 범위파일을 둘 위치의 종류. user 범위와 project 범위가 있다. flag 이름은 --scope다. 인가의 scope와 다른 뜻이다.
project rootproject 범위 설치의 기준 디렉터리. git 저장소여야 한다.
git 저장소git으로 관리하는 소스 코드 저장소.
이미지 저장소OCI artifact를 올리는 원격 저장소. ghcr.io, Docker Hub 등이다.
OCI artifactOCI 형식으로 묶은 배포 단위. 여기서는 컨테이너 이미지가 아니라 tar.gz 층 하나를 담은 파일 묶음이다.
로컬 OCI storebuild 결과와 내려받은 artifact를 두는 로컬 저장 공간.
registryToolHive가 읽는 목록. 이 문서에서는 MCP 서버 항목과 함께 skill과 plugin 항목도 담는다.
API serverthv serve가 띄우는 로컬 HTTP 서버. thv skill과 thv ai-plugin은 이 서버를 호출한다.
digest내용을 가리키는 고정 값. OCI manifest의 sha256 값이나 git commit hash다.
contentDigest설치된 파일 전체로 계산한 hash. 디스크 위 내용이 바뀌었는지 판단한다.
lock fileproject root의 toolhive.lock.yaml. project 범위 설치의 소스, digest, 서명자를 기록한다.
drift설치된 상태가 lock file 기록과 다른 상태.
keyless 서명Sigstore 방식 서명. 짧게 쓰는 OIDC identity token으로 인증서를 받고 투명성 로그에 기록한다.
key-pair 서명cosign 개인 키로 하는 서명. 인증서와 투명성 로그 기록이 없다.
identity tokenkeyless 서명에 쓰는 OIDC 자격 증명. access token과 다른 용도다.
서명 검증artifact의 서명이 lock file에 기록된 기준과 맞는지 암호학적으로 따지는 것.
신뢰 기준lock entry에 기록한 서명자 정보. keyless는 인증서 identity, key-pair는 public key다.
TOFUtrust on first use. 첫 설치 때 본 서명자를 신뢰 기준으로 기록하는 방식.
materializeplugin tree를 AI 클라이언트 경로에 풀고 클라이언트 등록 파일을 고치는 작업.
marketplaceAI 클라이언트가 plugin 목록을 찾는 JSON 파일. marketplace.json이다.

1. skill, plugin, MCP 서버

MCP 서버는 tool과 resource를 제공하는 실행 프로세스인 반면, skill은 실행 프로세스가 아니라 AI 클라이언트가 읽는 Markdown 지시문이다(source docs/arch/12-skills-system.md). 공식 문서는 둘의 관계를 MCP 서버가 tool을 주고 skill이 그 tool을 언제, 어떻게 쓸지 알려 주는 것으로 정리한다(docs concepts/skills).

plugin은 더 큰 묶음이라서 plugin 하나에 여러 구성 요소가 함께 들어간다. commands, agents, skills, hooks와 MCP 서버, LSP 서버 선언이 그 구성 요소다(source docs/arch/14-plugins-system.md). plugin 안의 skill은 plugin 전체가 한 단위로 설치되기 때문에 독립 skill과 다른 수명 주기를 따른다.

항목skillpluginMCP 서버
정체지시문과 지식여러 구성 요소 묶음tool과 resource
형식SKILL.md (YAML frontmatter + Markdown).claude-plugin/plugin.json + 디렉터리 tree컨테이너 이미지나 원격 endpoint
실행AI 클라이언트가 prompt 시점에 읽는다AI 클라이언트가 읽고 해석한다프로세스로 실행한다
배포OCI artifact, gitOCI artifact, git컨테이너 이미지
지원 클라이언트skill을 지원하는 여러 클라이언트Claude Code, Codex 두 개MCP 클라이언트
CLIthv skillthv ai-pluginthv run 등

plugin이 MCP 서버를 선언해도 ToolHive는 그 서버를 workload로 실행하지 않고, 선언된 서버를 쓸지는 AI 클라이언트가 정한다(source docs/arch/14-plugins-system.md, Component Inventory).

2. ToolHive가 관리하는 이유와 전체 구조

ToolHive가 없으면 팀은 SKILL.md를 손으로 복사하고 버전도 손으로 맞춰야 하며, 찾아볼 중앙 목록도 없다. ToolHive는 MCP 서버에 쓰던 기반을 skill에도 써서 다음과 같은 기능을 준다(source docs/arch/12-skills-system.md).

  • registry에서 이름으로 찾는다.
  • OCI artifact로 배포하고 버전을 붙인다.
  • 설치 범위를 user와 project로 나눈다.
  • 여러 AI 클라이언트에 한 번에 설치한다.

skill과 MCP 서버는 registry, 그룹, OCI 배포를 공유하지만, 목적과 형식, 수명 주기가 다른 별개 시스템이다.

CLI와 API server

thv skill과 thv ai-plugin은 로컬에서도 HTTP로 API server를 호출하기 때문에, 사용자는 먼저 thv serve를 띄워 두어야 한다. ToolHive 데스크톱 앱이 실행 중이면 앱이 API server를 제공한다(docs guides-cli/skills-management).

  1. CLI는 TOOLHIVE_API_URL이나 로컬 discovery 파일로 API server를 찾는다(source docs/arch/12-skills-system.md).
  2. API server는 skill 요청을 /api/v1beta/skills, plugin 요청을 /api/v1beta/plugins로 받는다.
  3. service 계층이 소스 해석, 서명 검증, 추출, 저장, lock file 기록을 맡는다. skill은 pkg/skills/skillsvc, plugin은 pkg/plugins/pluginsvc다.

CLI의 기본 API 대기 시간은 10분이라서 큰 OCI artifact는 이 시간 안에 다 받지 못할 가능성이 있다. 그때는 TOOLHIVE_API_TIMEOUT으로 늘려야 한다(docs guides-cli/skills-management, Troubleshooting).

3. SKILL.md와 설치 범위

SKILL.md 형식

skill은 SKILL.md가 있는 디렉터리이고, 이 디렉터리에는 scripts/, references/, assets/ 같은 보조 파일도 들어간다(docs concepts/skills).

---
name: code-review
description: Reviews code for best practices and security patterns
version: 1.0.0
allowed-tools: Read Glob Grep
toolhive.requires: ghcr.io/org/base-skill:v1
license: Apache-2.0
---

# Code Review Skill

Instructions for how the AI assistant should perform code reviews...
필드필수규칙
name예2~64자. 소문자, 숫자, 하이픈. 처음과 끝은 영숫자다. 디렉터리 이름과 같아야 한다.
description예최대 1024자
version아니요semantic version. 기본 규격이 아니라 ToolHive 확장 필드다
allowed-tools아니요미리 허용할 tool 이름 목록
toolhive.requires아니요의존하는 다른 skill의 OCI 참조
license, compatibility, metadata아니요SPDX 라이선스, 호환 클라이언트 문자열, 임의 key-value

ToolHive는 이름 규칙을 정규식으로 확인한다(source pkg/skills/validator.go:18). frontmatter는 64KB를 넘을 수 없고 의존 skill은 100개까지다(source pkg/skills/parser.go:17-23). v0.57.0부터는 frontmatter를 go.yaml.in/yaml/v3로 읽는데, 이 라이브러리는 gopkg.in/yaml.v3를 이어받아 유지 관리하는 fork다(source pkg/skills/parser.go:11, go.mod:92). 이전 라이브러리는 merge key 옆에 mapping key가 오는 frontmatter에서 panic했지만, 새 파서는 같은 입력을 frontmatter 오류로 거부한다(source pkg/skills/parser_test.go:193-197). frontmatter 형식과 제한은 바뀌지 않았다.

설치 범위

설치 범위Claude Code 경로 예특징
user (기본값)~/.claude/skills/<이름>/모든 project에서 보인다. 서명 검증과 lock file이 없다.
project<project root>/.claude/skills/<이름>/그 project에서만 보인다. project root는 git 저장소여야 한다. 서명 검증과 lock file 기록을 한다.

클라이언트마다 skill 디렉터리가 달라서, 예를 들어 Cursor는 ~/.cursor/skills/를 쓴다(docs guides-cli/skills-management). ToolHive는 이런 클라이언트별 경로 규칙을 pkg/client 설정에 둔다(source pkg/client/config.go:248-249).

v0.54.0부터 Pi coding agent도 skill 지원 클라이언트다. user 범위 경로는 ~/.pi/agent/skills/<이름>/이고 project 범위 경로는 <project root>/.pi/skills/<이름>/다(source pkg/client/config.go:1055-1076, docs reference/client-compatibility). Pi에는 설정 디렉터리를 환경 변수 PI_CODING_AGENT_DIR로 옮기는 기능이 있는데, 이 변수가 있으면 ToolHive는 user 범위 skill을 그 디렉터리의 skills/ 아래에 둔다(source pkg/client/skills.go:129-131). 클라이언트 감지도 그 디렉터리가 있는지를 본다(source pkg/client/discovery.go:116-124). 값 앞의 ~는 home 디렉터리로 바꾸고, 상대 경로는 작업 디렉터리 기준으로 푼다(source pkg/client/config.go:1484-1503). project 범위 경로는 이 변수와 무관하다.

대상 클라이언트

--clients를 주지 않으면 ToolHive는 설치된 모든 skill 지원 클라이언트에 설치하고, --clients all도 같은 뜻이다(source pkg/skills/skillsvc/clients.go:40-49). API server는 이 목록에서 시스템에 없는 클라이언트를 뺀다(source pkg/api/server.go:1000-1011). 한 클라이언트라도 설치에 실패하면 그 설치 작업 전체를 되돌린다(docs guides-cli/skills-management).

CLI 안내 문서는 "처음 찾은 클라이언트 하나에 설치한다"고 적고, 2026-11-02에 갱신된 문서도 같다. 그러나 v0.63.0 코드는 감지된 클라이언트 전부에 설치한다(source pkg/skills/skillsvc/clients.go:40-49). 이 문서는 코드를 따른다. 특정 클라이언트에만 설치하려면 --clients를 명시해야 한다.

4. skill 배포 흐름

validate와 build

작성자는 다음 순서로 skill을 artifact로 만든다(source docs/arch/12-skills-system.md, Building).

  1. thv skill validate ./my-skill로 frontmatter, 이름, symlink, 경로 문제를 확인한다.
  2. thv skill build ./my-skill --tag ghcr.io/my-org/skills/my-skill:v1.0.0을 실행한다.
  3. ToolHive는 디렉터리 전체를 tar.gz 층 하나로 묶어 로컬 OCI store에 저장한다.
  4. thv skill builds로 로컬 build 목록을 보고, thv skill builds remove <tag>로 지운다.

push와 서명

thv skill push는 기본으로 서명하고, 서명 없는 push는 명시해야만 가능하다. 사용자는 아래 셋 중 하나를 고른다(source docs/arch/12-skills-system.md, Publishing).

방식flag동작
keyless (기본)없음 또는 --identity-tokenOIDC identity token으로 Fulcio 인증서를 받고 Rekor 투명성 로그에 기록한다
key-pair--key cosign.keycosign 개인 키로 서명한다. 서명은 API server가 한다
서명 없음--no-sign서명하지 않는다

flag를 하나도 주지 않으면 CLI가 다음 순서로 identity token을 구한다(source pkg/skills/identitytoken, docs/arch/12-skills-system.md).

  1. GitHub Actions에서 id-token: write 권한이 있으면 ambient OIDC token을 쓴다.
  2. 대화형 terminal이면 y/N을 묻고 브라우저로 Sigstore 로그인을 한다.
  3. 둘 다 안 되면 push 전에 오류로 끝나며, 서명 없이 조용히 올리지는 않는다.

--key는 자동 탐색한 로컬 API server에서만 받고, 원격 API server나 수동으로 정한 URL로 key 서명을 요청하면 403이다(docs guides-cli/skills-management). 개인 키 서명 기능이 원격에 노출되지 않게 하는 제한이다.

skill push는 artifact를 먼저 올리고 그다음 서명하기 때문에(source pkg/skills/skillsvc/build.go:139-154), 서명 단계가 실패하면 서명 없는 artifact가 이미지 저장소에 남는다. project 범위 설치는 서명을 요구하므로 이 artifact는 --allow-unsigned 없이는 project 범위로 설치되지 않는다. plugin push는 순서가 다른데, 이 차이는 11장에서 비교한다.

install

thv skill install code-review                                   # registry 이름
thv skill install ghcr.io/org/skill:v1.0.0                      # OCI 참조
thv skill install git://github.com/org/repo@v1#skills/my-skill  # git
thv skill install code-review --scope project --project-root .  # project 범위

ToolHive는 install 요청을 다음 순서로 처리한다(source docs/arch/12-skills-system.md, Installation).

  1. 참조 형식으로 소스 종류를 정한다. 다음 장에서 자세히 다룬다.
  2. artifact를 받거나 git 저장소를 clone한다.
  3. 압축을 풀고 symlink, 경로 탈출, 크기를 확인한다.
  4. 파일 권한을 정리하고 각 클라이언트의 skill 디렉터리에 쓴다.
  5. SQLite에 설치 기록을 만들고 그룹에 등록한다.
  6. project 범위이면 lock file에 항목을 쓴다.

OCI 설치에서는 artifact 안의 skill 이름이 이미지 저장소 경로의 마지막 부분과 같아야 한다. plugin 아키텍처 문서는 같은 확인을 이름 덮어쓰기 방지로 설명하는데, 이 확인이 게시자의 신원을 증명하는 것은 아니다.

uninstall은 클라이언트의 파일, DB 기록, 모든 그룹에 등록된 이름 세 가지를 지운다(source pkg/skills/skillsvc/uninstall.go, pkg/groups/skills.go).

5. 소스 해석: git, OCI, registry

해석 순서

skill service는 함수 하나로 소스 문자열을 분류한다(source pkg/skills/skillsvc/source_dispatch.go:48-90). install과 upgrade가 같은 함수를 쓰며, 분류 순서는 다음과 같다.

  1. git://로 시작하면 git resolver로 보낸다.
  2. OCI 참조 모양이면 이미지 저장소에서 받는다. org/name처럼 애매한 이름이 실패하면 registry 이름으로 다시 찾는다.
  3. 나머지는 skill 이름 규칙을 확인한 뒤 registry 이름으로 찾는다. install은 로컬 OCI store를 먼저 본다.

git 참조

git://github.com/org/repo                       # 기본 branch의 root
git://github.com/org/repo@v1.0.0                # tag
git://github.com/org/repo#skills/my-skill       # 하위 디렉터리
git://github.com/org/repo@main#skills/my-skill  # branch + 하위 디렉터리
  • clone 제한 시간은 2분이다(source pkg/skills/gitresolver/resolver.go:26).
  • 인증 정보는 host별로 보낸다. GITHUB_TOKEN은 github.com에만, GITLAB_TOKEN은 gitlab.com에만 보내고, GIT_TOKEN은 모든 host에 보내는 대체 값이다(source pkg/skills/gitresolver/auth.go:22-24).
  • host가 localhost나 사설 IP이면 SSRF를 막으려고 거부한다.

SSRF 검사는 IP 문자열과 알려진 localhost 이름만 보기 때문에 DNS가 사설 IP로 풀리는 hostname은 막지 못한다. 이 한계는 소스 주석에도 적혀 있다(source pkg/skills/gitresolver/reference.go:122-128).

registry와 registry server

이름으로 설치하면 ToolHive는 설정된 registry에서 skill을 찾는데, registry server는 skill을 MCP 서버와 다른 확장 경로로 제공한다(docs guides-registry/skills).

용도경로
목록, 조회, 검색GET /registry/{registryName}/v0.1/x/dev.toolhive/skills
특정 버전 조회GET .../skills/{namespace}/{name}/versions/{version}
게시POST /v1/entries (본문에 skill 객체)
버전 삭제DELETE /v1/entries/skill/{namespace%2Fname}/versions/{version}

registry 항목은 namespace, name, version이 필수이고, packages에는 OCI나 git 위치를 적는다. registry server는 더 높은 버전이 오면 latest를 옮기지만, 낮은 버전을 나중에 올려도 latest는 그대로다. registry 항목에 기대하는 서명자(provenance)가 있으면 첫 project 설치가 그 값으로 서명을 확인한다(7장). registry 자체는 04편이 다룬다.

그룹

skill은 MCP 서버처럼 그룹에 속하고, --group을 주지 않으면 ToolHive가 default 그룹에 넣는다(source pkg/skills/skillsvc/install.go:271-290). 그룹은 이름 목록만 가지며, thv skill list --group dev-tools는 이 목록으로 설치 기록을 거른다(source pkg/skills/skillsvc/list.go:48-59).

CLI 안내 문서는 "그룹의 skill이 그 그룹에 등록된 클라이언트에 자동 설치된다"고 적는다. 그러나 v0.63.0 코드에서도 그룹의 skill 목록을 읽는 곳은 목록 거르기와 삭제뿐이고(source pkg/skills/skillsvc/list.go:48-59, pkg/groups/skills.go), 자동 설치 경로는 찾지 못했다. 그룹 개념은 04편을 보면 된다.

데스크톱 UI

ToolHive UI에는 Skills 화면이 있고, 탭은 Registry, Installed, Local Builds 세 개다(docs guides-ui/skills). 사용자는 UI에서 찾기, 설치, 삭제, 로컬 build를 할 수 있지만, 이미지 저장소로 push하는 기능은 CLI에만 있다(docs guides-ui/skills-build). UI에는 --force 동작이 없어서 덮어쓰려면 지우고 다시 설치해야 한다. toolhive-studio v0.40.1에는 plugin 화면이 없다(source renderer/src/routes/).

7. project lock file과 신뢰 모델

lock file이 하는 일

project 범위로 설치하면 ToolHive는 project root의 toolhive.lock.yaml에 항목을 쓴다(source pkg/skills/lockfile/lockfile.go:37-39). 이 파일은 package-lock.json이나 go.sum과 같은 일을 해서, 팀원과 CI는 같은 git 저장소를 받아 thv skill sync로 같은 내용을 복원한다. 이때 sync가 복원하는 것은 소스의 최신 내용이 아니라 lock file에 기록된 내용이다.

아래는 스키마 필드로 만든 예이고, 값은 설명용이다(source pkg/skills/lockfile/lockfile.go:54-166). ToolHive는 이 파일을 go.yaml.in/yaml/v3로 읽고 쓴다(source pkg/skills/lockfile/lockfile.go:31). v0.57.0에 YAML 라이브러리만 바뀌었고 필드는 그대로다.

version: 1
skills:
  - name: code-review
    version: "1.0.0"
    source: code-review                       # 사용자가 요청한 그대로. sync는 고치지 않는다
    resolvedReference: ghcr.io/org/code-review:1.0.0
    digest: sha256:9f2b1e...                  # 고정 값: OCI manifest digest 또는 git commit
    contentDigest: sha256:a1b2c3...           # 설치된 파일 전체의 hash
    explicit: true                            # 이름으로 직접 설치했는지
    provenance:                               # keyless 서명의 신뢰 기준
      signerIdentity: https://github.com/org/skills/.github/workflows/release.yml@refs/tags/v1.0.0
      certIssuer: https://token.actions.githubusercontent.com
      repositoryRef: refs/tags/v1.0.0
      runnerEnvironment: github-hosted
plugins:
  - name: release-toolkit
    source: ghcr.io/org/plugins/release-toolkit:1.0.0
    digest: sha256:4c1d...
    publicKey: MFkwEwYHKoZIzj0CAQY...          # key-pair 서명의 신뢰 기준

ToolHive는 항목을 이름순으로 정렬하기 때문에 diff가 안정적이다. 설치 중 lock file 쓰기가 실패하면 설치 전체를 실패로 끝내는데, 설계 문서가 고정되지 않은 설치를 설치 실패보다 나쁜 상태로 보기 때문이다(source docs/arch/12-skills-system.md).

TOFU와 catalog provenance

신뢰 모델의 중심은 TOFU이고, project 범위 설치는 다음 규칙을 따른다(source docs/arch/12-skills-system.md, Project Lock File).

  1. 첫 설치 때 ToolHive는 서명을 검증하고, 그때 본 서명자를 provenance에 기록한 뒤 사용자에게 보여 준다.
  2. 그 뒤의 install, sync, upgrade는 기록한 서명자를 Sigstore 정책 안에서 강제한다.
  3. 서명 workflow의 git ref와 runner 종류도 기록하고, 이 값이 달라지면 서명자 변경과 똑같이 막는다.
  4. 다른 서명자로 바꾸려면 upgrade에 --allow-signer-change를 명시해야 한다.

registry 이름으로 설치할 때는 첫 설치도 맹목적이지 않다. registry 항목이 기대 서명자를 선언하면 첫 project 설치가 그 조건으로 서명 검증을 하기 때문이다. 이미 lock 항목이 있으면 lock 항목이 registry보다 우선한다. user 범위 설치는 lock file 검증을 하지 않으므로 registry의 provenance도 적용하지 않는다.

keyless와 key-pair

항목keylesskey-pair
증거Fulcio 인증서와 Rekor 기록분리된 서명만 있음
알 수 있는 것누가, 언제 서명했는지고정한 public key로 확인되는지만
첫 project 설치추가 입력 없음--public-key cosign.pub 필요
lock 기록signerIdentity, certIssuer 등publicKey (DER SPKI)
registry provenance적용 가능적용 불가

아키텍처 문서는 key-pair 서명을 더 낮은 보증 단계로 본다. key-pair 서명으로는 서명자와 서명 시각을 알 수 없고, 개인 키가 유출되면 project마다 새 key로 신뢰 기준을 다시 잡아야 한다(source docs/arch/12-skills-system.md). public key는 artifact에서 얻을 수 없어서 게시자가 별도 경로로 배포해야 한다.

서명 없는 skill과 lock file 검토

  • 서명 없는 skill을 project 범위로 설치하려면 --allow-unsigned가 필요하다. ToolHive는 이 예외를 unsigned: true로 lock file에 기록하고 이후 sync에서는 다시 묻지 않는다.
  • --allow-unsigned는 서명이 아예 없는 경우에만 통하고, 서명이 깨졌거나 key가 틀린 경우는 통과하지 않는다.
  • lock file은 git 저장소에 커밋하는 정책 문서라서 git 저장소에 쓰기 권한이 있는 누구에게나 열려 있다. provenance를 unsigned: true로 바꾸는 diff는 신뢰 수준을 낮추는데, sync는 그 값을 그대로 따른다.

리뷰어가 특히 볼 필드는 provenance, publicKey, unsigned, digest, resolvedReference이고, 이 필드의 변경은 skill 본문 변경만큼 신중하게 봐야 한다(source docs/arch/12-skills-system.md).

8. sync와 upgrade

sync: 기록대로 복원

thv skill sync는 설치 상태를 lock file에 맞추는 명령으로, 소스를 다시 해석하지 않고 고정한 digest로 설치한다(source docs/arch/12-skills-system.md, Sync).

lock file과 설치 상태결과
digest와 contentDigest가 모두 같음최신으로 보고
DB 기록은 있으나 digest나 contentDigest가 다름drift. 고정 참조로 다시 설치 (--check는 보고만)
lock 항목은 있으나 DB 기록이 없음missing. 고정 참조로 새로 설치
설치돼 있고 lock 관리 대상이나 lock 항목이 없음보고 (--prune이면 삭제)
설치돼 있고 lock 관리 대상이 아님보고 (--adopt이면 lock 항목 생성)

sync는 저장해 둔 서명 bundle을 내장 trust root로 오프라인 재검증한다. 기본 대상이 설치된 모든 skill 지원 클라이언트라서 CI에서는 --clients로 대상을 좁히는 편이 안전하다. 새 버전의 thv가 클라이언트를 더 지원하면 그 클라이언트가 drift로 잡힐 가능성이 있기 때문이다(docs guides-cli/skills-management).

# CI 검사: drift가 있으면 종료 코드 2
thv skill sync --project-root . --clients claude-code --check

# 새 장비에서 복원
thv skill sync --project-root . --yes

upgrade: 새 내용으로 다시 고정

thv skill upgrade는 각 항목의 source를 install과 같은 순서로 다시 해석하고, digest가 바뀌었으면 새 내용을 설치한 뒤 lock을 갱신한다(source pkg/skills/skillsvc/upgrade.go).

flag뜻
--preview바뀔 내용을 보고만 한다. OCI는 비교하려고 artifact를 받는다
--fail-on-changes바뀔 내용이 있으면 실패한다. CI 최신성 검사용이다
--allow-ref-changeartifact가 다른 경로, 조직, 이미지 저장소로 옮겨 가도 진행한다
--allow-signer-change서명자가 바뀌어도 진행하고 새 서명자를 기록한다
--public-key--allow-signer-change와 함께 새 key로 신뢰 기준을 바꾼다

같은 이미지 저장소 경로 안의 tag 변경은 --allow-ref-change 없이 진행하고, 더 오래된 tag로 가는 경우도 같다. 전체 git commit hash로 고정한 항목은 upgrade 대상이 아니다. OCI digest로 고정한 항목은 내용이 그대로여도 서명이 따로 바뀔 가능성이 있는데, 이 경우 upgrade는 내용 대신 신뢰 기준만 바꾼다. 게시자가 key를 바꿨을 때 쓰는 기능이다(docs guides-cli/skills-management).

upgrade는 서명 없는 후보를 서명자 변경이 아니라 실패(unsigned-rejected)로 처리하며, 서명 없는 후보를 허용하는 flag도 upgrade에는 없다.

확인 질문과 종료 코드

skill 내용은 AI가 따르는 지시문이라서 sync와 upgrade는 실제로 설치하기 전에 확인을 묻고, 비대화형 환경에서 --yes가 없으면 CLI가 실행을 거부한다. ToolHive는 확인 문구에 넣는 이름에서 제어 문자도 지우는데, 악성 이름이 terminal 화면을 바꾸지 못하게 하는 장치다(source docs/arch/12-skills-system.md, CLI Confirmation).

종료 코드뜻

2검사 실패. sync --check가 drift를 찾았거나 upgrade --fail-on-changes가 변경을 찾음
3일부 실패
4정책 거부. 비대화형 확인 거부나 --allow-ref-change 없는 경로 변경

출처는 cmd/thv/app/exitcode.go:15-25다.

9. skill의 보안 장치

skill 시스템은 여러 층에서 방어한다. 출처는 docs/arch/12-skills-system.md의 Security Model과 pkg/skills/installer.go:16-33다.

층장치

v0.56.0부터 SKILL.md 파서와 plugin manifest 파서에는 Go fuzz 테스트가 있어서, 임의 입력에 파서가 panic하지 않는지 확인한다(source pkg/skills/parser_fuzz_test.go:8-9, pkg/plugins/parser_fuzz_test.go:8-10). 입력 확인 층의 제한값은 바뀌지 않았다.

user 범위 설치는 서명을 검증하지 않는다(docs guides-cli/skills-management). skill은 AI가 따르는 지시문이고 scripts/에 실행 코드가 들어 있을 가능성도 있으므로, 조직에서 배포 통제가 필요하면 project 범위와 lock file을 써야 한다.

10. AI plugin의 구성과 수명 주기

manifest와 구성 요소

plugin은 .claude-plugin/plugin.json이 있는 디렉터리다. manifest에는 이름, 버전, 설명, 작성자, 라이선스, keyword를 적고, 이름은 kebab-case로 쓴다(docs guides-cli/ai-plugins).

{
  "name": "my-plugin",
  "version": "1.0.0",
  "description": "What this plugin does and when to use it.",
  "license": "Apache-2.0",
  "keywords": ["review", "python"],
  "commands": ["./commands/review.md"],
  "agents": ["./agents/reviewer.md"],
  "skills": ["./skills/code-review"],
  "hooks": ["./hooks/post-tool-use.js"]
}
  • 구성 요소 경로는 ./로 시작해야 하고, ..는 거부한다.
  • 구성 요소는 종류마다 100개까지이고 manifest는 64KB까지다(source pkg/plugins/parser.go:21-30).
  • plugin 안의 skill에도 skill 검증 규칙을 다시 적용한다(source pkg/plugins/validator.go:76-79).

build는 구성 요소 수를 OCI config에 기록한다. 종류는 commands, agents, skills, hooks, mcpServers, lspServers다(source pkg/plugins/adapter.go:15-26).

클라이언트별 materialize

plugin을 받는 클라이언트는 Claude Code와 Codex 두 개이고, 클라이언트마다 adapter가 경로와 등록 방법을 맡는다(source docs/arch/14-plugins-system.md).

클라이언트user 범위 경로등록adapter가 지원한다고 보고하는 구성 요소

사용자는 아래 명령으로 plugin을 다룬다(source docs/cli/thv_ai-plugin.md).

이름으로 설치하면 ToolHive는 로컬 OCI store를 먼저 보고 그다음 registry를 검색한다. 검색 결과에서는 대소문자를 무시한 정확한 이름 일치만 남기는데, 일치가 0개이면 not found이고 2개 이상이면 거부한다. 첫 번째 검색 결과를 골라 설치하지는 않는다(source docs/arch/14-plugins-system.md, Discovery).

--clients를 주지 않으면 감지된 plugin 지원 클라이언트 전부가 대상이다(source pkg/plugins/pluginsvc/install_extraction.go:585-609). CLI 안내 문서의 "처음 찾은 클라이언트"라는 표현은 코드와 다르고, 2026-11-02에 갱신된 문서도 같다.

설치 중 뒤 단계가 실패하면 ToolHive는 이전 파일, 클라이언트 등록, DB, 그룹 상태를 되돌린다. 같은 digest로 다시 설치하면 새로 요청한 클라이언트만 추가한다.

11. plugin의 lock, 보안, skill과의 차이

skill과 공유하는 lock file과 신뢰 모델

plugin은 skill과 같은 toolhive.lock.yaml을 쓰고 plugins: key 아래에 기록한다(source pkg/skills/lockfile/lockfile.go:157-166). 신뢰 규칙도 같아서 project 범위 설치는 서명을 검증하고 TOFU로 신뢰 기준을 기록한다. key-pair 서명은 첫 설치에 --public-key가 필요하고, 서명 없는 plugin은 --allow-unsigned가 필요하다.

project 범위의 skill과 plugin 작업은 같은 transaction lock을 쓰며, lock 디렉터리 이름은 옛 ToolHive와 맞추려고 skills-project-locks를 그대로 쓴다(source pkg/projecttxn/transaction.go:25).

skill과 다른 점

항목skillplugin
push 순서tag로 먼저 올린 뒤 서명한다. 서명이 실패하면 서명 없는 artifact가 남는다digest로 먼저 올리고 서명한 뒤 tag를 옮긴다. 요청한 tag가 서명 없는 내용을 가리키는 순간이 없다

push 순서의 출처는 skill이 pkg/skills/skillsvc/build.go:139-154, plugin이 pkg/plugins/pluginsvc/build.go:166-212다. 권한 상한의 출처는 pkg/skills/installer.go:26-32, :121-161이고, 의존성의 출처는 docs/arch/14-plugins-system.md의 Storage다.

plugin 쪽 보안 장치

  • identity token과 key 서명 권한은 loopback이 아닌 HTTP로 보내지 않고, 자격 증명을 담은 요청은 redirect를 따라가지 않는다.
  • git clone 저장 공간은 100MB와 파일 10,000개로 제한한다(source docs/arch/14-plugins-system.md).
  • git 항목의 서명은 commit에 있어서 sync는 바뀌지 않은 git 항목을 오프라인으로 다시 검증하지 않는다. 서명자 기록은 git 내용을 다시 해석할 때 확인한다.
  • plugin 이름은 경로를 만들기 전에 확인하므로 이름으로 user 범위나 project 범위 밖으로 나갈 수 없다.
  • Claude Code adapter는 uninstall 때 자기가 넣은 항목만 지우고, 공유 marketplace 등록은 마지막 ToolHive plugin이 빠질 때만 지운다.

plugin이 선언한 MCP 서버는 ToolHive의 workload 관리, 격리, 인증 밖에 있어서, ToolHive가 관리하는 MCP 서버로 쓰려면 thv run이나 operator로 따로 띄워야 한다(02편, 07편).

12. 자가 점검 문제

먼저 답을 생각해 본 다음 펼쳐서 확인한다.

Q1. skill과 MCP 서버의 가장 큰 차이는 무엇인가?

MCP 서버는 프로세스로 실행되고 tool과 resource를 제공한다. skill은 실행되지 않는 Markdown 지시문이고, AI 클라이언트가 prompt 시점에 읽는다. 두 시스템은 registry, 그룹, OCI 배포를 공유하지만 수명 주기는 따로다.

Q2. thv skill install code-review를 실행했더니 연결 오류가 났다. 가장 먼저 무엇을 확인해야 하는가?

thv serve로 API server가 떠 있는지 확인해야 한다. thv skill은 로컬에서도 API server를 HTTP로 호출하기 때문이다. 데스크톱 앱이 실행 중이면 앱이 API server를 제공한다.

Q3. --clients 없이 skill을 설치했다. 어떤 클라이언트에 설치되는가?

v0.63.0 코드 기준으로 시스템에서 감지된 모든 skill 지원 클라이언트에 설치되고, 감지된 클라이언트가 하나도 없으면 오류가 난다. 한 클라이언트라도 실패하면 그 설치 작업 전체를 되돌린다.

Q4. 같은 skill을 user 범위로 설치했을 때와 project 범위로 설치했을 때, 서명 처리는 어떻게 다른가?

user 범위 설치는 서명을 검증하지 않고 lock file에도 기록하지 않는다. project 범위 설치는 서명을 검증하고 서명자를 lock file에 신뢰 기준으로 기록한다. 서명이 없으면 --allow-unsigned가 있어야 설치한다.

Q5. 팀원이 PR에서 lock 항목의 provenance 블록을 지우고 unsigned: true를 넣었다. sync는 어떻게 동작하는가? 리뷰어는 무엇을 해야 하는가?

sync는 lock file을 정책으로 따르기 때문에 그 항목을 서명 없는 예외로 다룬다. 이 변경은 신뢰 수준을 낮추므로 리뷰어는 이 diff를 skill 본문 변경만큼 신중하게 검토하고 이유를 확인해야 한다.

Q6. key-pair로 서명한 skill을 처음 project 범위로 설치한다. 무엇이 더 필요하고, 왜 필요한가?

--public-key cosign.pub가 필요하다. key-pair 서명에는 인증서가 없고 public key도 artifact나 서명 bundle에서 얻을 수 없어서, 사용자가 key를 직접 주어야 한다. ToolHive는 그 key로 서명을 검증하고 lock 항목에 publicKey로 고정하며, 이후 sync와 upgrade는 고정한 key를 다시 쓴다.

Q7. CI에서 thv skill sync --check가 종료 코드 2로 끝났다. 무슨 뜻인가?

설치 상태가 lock file과 다르다는 뜻으로, drift이거나 missing 항목이 있다. --check는 아무것도 쓰지 않고 보고만 한다. 기본 대상은 설치된 모든 클라이언트라서 새로 지원된 클라이언트가 원인일 가능성도 있다. CI에서는 --clients로 대상을 고정하는 편이 낫다.

Q8. push 중 서명 단계가 실패했다. skill과 plugin 중 어느 쪽에서 서명 없는 내용이 tag로 노출될 가능성이 있는가?

skill push다. skill은 tag로 먼저 올리고 그다음 서명하지만, plugin은 digest로 먼저 올리고 서명한 뒤에 tag를 옮긴다. 그래서 plugin의 요청 tag는 서명 없는 내용을 가리키지 않는다.

Q9. Codex에 plugin을 설치했는데 Codex에서 보이지 않는다. ToolHive가 하지 않는 단계는 무엇인가?

ToolHive는 plugin 파일을 ~/.agents/plugins/toolhive/<이름>/에 풀고 marketplace.json을 고치는 데까지만 하고 Codex 쪽 설치는 하지 않는다. 사용자가 codex plugin install <이름>@toolhive를 직접 실행해야 한다.

Q10. plugin이 mcpServers에 MCP 서버를 선언했다. ToolHive가 그 서버를 격리된 컨테이너로 실행하는가?

실행하지 않는다. ToolHive는 plugin이 선언한 MCP 서버와 LSP 서버를 workload로 관리하지 않고, 그 선언을 쓸지는 AI 클라이언트가 정한다. ToolHive의 격리와 인증을 적용하려면 MCP 서버를 따로 workload로 띄워야 한다.

문서와 코드가 다른 곳은 아래와 같다. 이 문서는 코드를 따랐고, 세 항목 모두 2026-11-02 갱신본에서도 그대로다.

  • CLI 안내 문서 두 곳(skill, plugin)은 --clients가 없으면 처음 찾은 클라이언트 하나에 설치한다고 적지만, 코드는 감지된 지원 클라이언트 전부에 설치한다.
  • CLI 안내 문서는 그룹의 skill이 그룹에 등록된 클라이언트에 자동 설치된다고 적는데, 그 경로는 v0.63.0 코드에서도 찾지 못했다.
  • 공식 문서 concepts/skills의 페이지 설명문은 skill을 "MCP 서버 설정 묶음"이라고 적지만, 같은 페이지 본문과 코드는 skill을 지시문 묶음으로 다룬다.

대조하지 못한 내용은 다음과 같다. OCI 패키징, 로컬 OCI store 경로, Sigstore 서명 검증의 세부는 이 코드가 toolhive-core 패키지 안에 있어서 확인하지 못했고, 이 부분은 아키텍처 문서를 따랐다. TOFU, catalog provenance, git 서명의 provisional 처리도 아키텍처 문서만 따랐으며, plugin push의 자격 증명 전송 제한과 plugin git clone 제한도 같다. 7장 lock file 예의 값은 설명용으로 만든 값이다. toolhive-studio의 plugin 화면 유무와 guides-ui 문서는 이번 갱신에서 다시 확인하지 않았으므로, 6장과 11장의 UI 설명은 2026-10-13 확인 결과다.

thv llm config는 OIDC로 보호된 LLM gateway의 연결 설정이다. pkg/llm과 cmd/thv/app/llm.go에서 skill이나 plugin을 참조하는 코드를 찾지 못해서 이 문서에서는 다루지 않았다.
