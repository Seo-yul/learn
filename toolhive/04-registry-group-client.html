registry, 그룹, 클라이언트 설정

ToolHive 학습 4편 · 2026-10-14 작성 · 2026-11-07 갱신

이 문서는 ToolHive가 registry를 읽는 방식과 registry server를 다루고, 서버를 그룹으로 묶는 방법과 MCP 클라이언트 설정을 고치는 방식도 함께 다룬다. 중급 수준이며 소스 코드 위치를 함께 적는다.

기준 버전은 ToolHive v0.63.0(2026-11-06)이다. 2026-10-14에 v0.53.0 기준으로 작성했고 2026-11-07에 v0.63.0 기준으로 갱신했다. 공식 문서는 2026-10-13 상태를 읽었고 일부를 2026-11-07에 다시 읽었다. ToolHive는 자주 바뀌므로 실제로 쓰기 전에 공식 문서를 다시 확인해야 한다.

한 문장 요약

registry는 ToolHive가 읽는 MCP 서버, skill, plugin 목록이다. 그룹은 workload에 붙이는 이름인데, 어떤 클라이언트 설정에 어떤 서버를 넣을지를 이 그룹이 정한다. thv는 서버를 시작할 때 그 그룹에 등록된 클라이언트의 설정 파일에 proxy URL을 쓴다.

v0.63.0 갱신 요약
  • 내장 registry의 catalog 모듈이 v0.20261026.0으로 올라갔다. catalog에서 filesystem 같은 참고 서버가 빠지면서 thv 도움말의 예시 서버는 fetch가 됐다(2.1장).
  • 지원 MCP 클라이언트에 Pi coding agent가 더해져 26종이 됐다. Pi에는 환경 변수 PI_CODING_AGENT_DIR로 설정 디렉터리를 옮기는 기능이 있는데, thv는 감지와 설정 파일 경로에 모두 그 값을 쓴다(10.1장, 10.2장, 10.4장).
  • 새 명령 thv client connector가 Claude Desktop 설정에 원격 MCP 서버를 넣는다. 그 서버에는 Claude Desktop이 직접 접속하고, workload 등록은 여전히 지원하지 않는다(10.1장).
  • Claude Desktop의 LLM gateway 설정이 Linux 경로를 알고, Windows에서는 credential helper를 .cmd 파일로 쓴다(10.1장).
  • tool 필터 middleware가 크게 바뀌었다. tools 목록인지 확실하지 않은 응답을 받으면 v0.53.0은 본문을 버리고 끝냈지만 v0.63.0은 JSON-RPC 오류로 답하고, 압축된 채 온 본문도 같은 방식으로 막는다. 필터가 쥐고 있는 본문의 크기에도 한도가 생겼다(11.1장).
  • tool 필터와 tool 재정의의 대조 순서를 코드에서 확인해서 확인하지 못한 사항에서 뺐다(11장, 14장).
  • 자가 점검 문제의 버전 값을 고치고 connector 문제 하나를 더했다(13장).

1. 전체 흐름: 서버 한 개를 실행할 때

registry, 그룹, 클라이언트 설정은 서버 하나를 실행할 때 차례로 쓰인다. thv가 thv run --group dev fetch를 받으면 다음 순서로 동작한다.

  1. registry에서 fetch 항목을 찾는데, 짧은 이름은 끝부분이 같은 io.github.stacklok/fetch와 맞는다(source pkg/registry/provider_base.go:42).
  2. 항목의 이미지, transport, 권한 profile, 환경 변수 정의로 실행 설정을 만든다(source pkg/runner/config_builder.go:1172).
  3. 사용자가 준 flag가 있으면 그 값이 항목의 기본값보다 앞선다(source docs/arch/06-registry-system.md:249).
  4. workload를 dev 그룹에 넣는다. 그룹 이름은 RunConfig의 group 필드에 들어간다(source pkg/runner/config.go:259).
  5. proxy가 준비되면 dev 그룹에 등록된 클라이언트를 찾는다(source pkg/client/manager.go:291).
  6. 찾은 클라이언트의 설정 파일에 proxy URL을 쓴다(source pkg/runner/runner.go:687).

1~3단계는 registry를 읽고, 4~5단계는 그룹을 쓰고, 6단계는 클라이언트 설정을 고친다. 이 문서도 이 순서로 설명한다.

proxy와 transport의 동작은 02편이, 권한 profile과 provenance는 03편이 다룬다.

2. 내장 registry와 항목 형식

2.1 내장 registry의 출처

사용자가 registry를 지정하지 않으면 thv는 내장 registry를 읽는다. 내장 registry 데이터는 Go 모듈 github.com/stacklok/toolhive-catalog에서 오고, thv는 이 모듈의 catalog.Upstream()을 부른다(source pkg/registry/provider_local.go:54).

v0.63.0이 쓰는 catalog 모듈 버전은 v0.20261026.0이다(source go.mod:71). 데이터가 바이너리에 들어가므로 내장 registry 내용은 thv 버전에 묶인다. catalog에서 filesystem 같은 참고 서버가 빠져서 thv 도움말의 예시 서버는 fetch다(source cmd/thv/app/run.go:101).

이 catalog는 Stacklok이 관리하고, 서버를 추가하려면 toolhive-catalog Git 저장소에 issue나 PR을 내야 한다(docs concepts/registry-criteria).

2.2 upstream 형식

registry 파일은 upstream 형식을 따르는데, 이 형식은 MCP 공식 서버 스키마에 ToolHive 확장을 더한 것이다(docs reference/registry-schema-upstream).

파일의 최상위 키는 $schema, version, meta, data다. data.servers는 서버 항목 배열이고 data.skills는 skill 항목 배열인데, skill만 담은 파일에도 "servers": []를 넣어야 한다.

thv는 레거시 형식을 더 이상 읽지 않고, 입력이 레거시 형식으로 보이면 오류를 낸다(source pkg/registry/upstream_parser.go:35). 레거시 파일은 아래 명령으로 바꿔야 한다.

thv registry convert --in registry.json --in-place

공식 문서는 이 변환에서 값이 빠지지 않는다고 설명한다(docs guides-cli/registry).

2.4 thv 안의 변환

thv는 upstream 항목을 읽은 뒤 내부 타입으로 바꾼다(source pkg/registry/upstream_parser.go:34). 변환 규칙은 다음과 같다(source pkg/registry/provider_api.go:288).

  • remotes가 있으면 원격 서버 타입 RemoteServerMetadata가 된다.
  • packages만 있으면 컨테이너 서버 타입 ImageMetadata가 된다.
  • 둘 다 없는 항목은 건너뛴다.

코드 주석은 npm과 pypi 패키지를 건너뛴다고 적는데(source pkg/registry/provider_api.go:287), 아키텍처 문서의 설명은 이와 다르다. 그 차이는 확인하지 못한 사항에 적었다.

upstream 형식에는 registry 묶음이 없어서 변환 결과의 Groups는 항상 빈 목록이다(source pkg/registry/upstream_parser.go:61). 그래서 registry 묶음을 배포하던 thv group run은 deprecated 상태이고(source cmd/thv/app/group.go:64), 실행하면 항상 오류를 낸다(source cmd/thv/app/group.go:67).

3.2 사용자 registry 지정

thv config set-registry는 registry 위치를 thv 설정 파일에 저장하는데, 이 파일은 XDG 설정 경로 아래 toolhive/config.yaml이다(source pkg/config/config.go:171).

thv는 입력값의 종류를 다음 순서로 판단한다(source pkg/config/registry.go:38).

  1. file://로 시작하면 로컬 파일로 본다.
  2. URL이 .json으로 끝나면 원격 JSON 파일로 본다.
  3. 그 밖의 URL이면 /v0.1/servers?limit=1&version=latest로 GET 요청을 보낸다.
  4. 응답이 2xx이고 본문에 servers 배열과 metadata 객체가 있으면 API 엔드포인트로 본다. 401과 403 응답도 API로 본다.
  5. 어느 쪽도 아니면 원격 JSON 파일로 본다.
  6. URL이 아닌 입력은 로컬 파일 경로로 본다.
# 로컬 파일
thv config set-registry /path/to/registry.json
# 원격 JSON 파일
thv config set-registry https://example.com/registry.json
# registry server의 registry 하나 (API 엔드포인트)
thv config set-registry https://registry.example.com/registry/default
# 현재 값 확인과 해제
thv config get-registry
thv config unset-registry

registry server를 쓸 때는 registry 이름까지 URL에 넣어야 한다. thv가 그 URL 뒤에 /v0.1/servers를 붙이기 때문이다(source pkg/config/registry.go:80).

로컬 파일을 지정할 때도 thv는 형식을 먼저 확인하고, 레거시 형식이거나 항목이 하나도 없으면 저장하지 않는다(source pkg/config/registry.go:184).

3.3 우선순위와 캐시

set-registry는 새 값을 저장할 때 다른 종류의 값을 비우기 때문에(source pkg/config/registry.go:324) 보통은 값이 하나만 남는다.

값이 여럿 있으면 우선순위는 API, 원격 JSON, 로컬 파일, 내장 registry 순이다(source pkg/registry/factory.go:59). 지정한 API registry나 원격 JSON registry에 연결되지 않으면 thv는 내장 registry로 돌아가지 않고 오류를 낸다(source pkg/registry/factory.go:73, factory.go:80).

thv는 API registry의 응답을 1시간 동안 캐시한다(source pkg/registry/provider_cached.go:26). 캐시 파일은 XDG 캐시 경로의 toolhive/cache/registry-<hash>.json이다(source pkg/registry/auth/cache.go:21).

API가 일시적으로 실패하면 thv는 오래된 캐시를 돌려주지만, 인증 오류는 캐시로 가리지 않고 그대로 낸다(source pkg/registry/provider_cached.go:126).

thv는 원격 JSON registry를 지정할 때와 처음 읽을 때 응답을 5초까지 기다리고, 서버, skill, plugin이 하나도 없으면 오류를 낸다(source pkg/config/registry.go:242, pkg/registry/provider_remote.go:53).

사설 IP 주소의 registry를 쓰려면 -p, --allow-private-ip를 붙여야 하고, 이 flag가 있으면 thv는 HTTP 연결도 허용한다(source pkg/config/registry.go:69).

3.4 보호된 registry 로그인

registry 인증은 API registry에만 적용되고, 원격 JSON과 로컬 파일은 인증을 지원하지 않는다(source pkg/registry/factory.go:65).

set-registry에 --issuer와 --client-id를 함께 주면 thv가 OIDC 설정을 저장하고(source cmd/thv/app/config.go:125), 그다음 thv registry login이 브라우저로 OAuth 흐름을 연다.

thv config set-registry https://registry.example.com/registry/default \
  --issuer https://auth.example.com --client-id <CLIENT_ID>
thv registry login
thv registry logout

요청하는 scope의 기본값은 openid와 offline_access다(source pkg/registry/auth/login.go:23). thv는 받은 refresh token을 secret provider에 저장하는데(source pkg/registry/auth/auth.go:65), 이때 registry 전용 구역을 따로 쓴다(source pkg/registry/factory.go:146). secret provider는 03편이 다룬다.

set-registry를 다시 실행하면 thv가 저장한 인증 설정을 삭제한다(docs guides-cli/registry).

thv에는 registry 변경 직전에 부르는 확장 지점 PolicyGate가 있다(source pkg/registry/policy_gate.go:41). 기본 구현은 모든 변경을 허용하고, 코드 주석은 downstream 구현이 이 interface로 외부 정책을 적용한다고 설명한다.

4. registry server의 구조

registry server는 registry를 MCP Registry API로 내보내는 별도 서버다. Git 저장소는 stacklok/toolhive-registry-server이고 이 문서는 2026-10-14에 v1.5.2를 읽었다. 2026-11-07 갱신에서는 registry server 내용을 다시 확인하지 않았는데, 그 사이에 v1.5.3이 나왔다.

registry server에는 개념이 세 개 있다(docs guides-registry/intro).

  • 원천: 항목을 가져오는 곳으로 Git, API, File, Managed, Kubernetes 다섯 종류가 있다.
  • 항목: DB에 저장한 서버, skill, plugin 하나이고, 항목 하나는 원천 하나에 속한다.
  • registry: 원천 여러 개의 항목을 묶은 목록이다. 이름이 있고 그 이름이 URL에 들어간다.

같은 원천으로 registry를 여러 개 만들 수도 있어서, 예를 들어 회사 전체용 registry와 팀 전용 registry를 따로 두고 요구하는 claim을 달리할 수 있다.

4.1 구성 요소

registry server는 시작할 때 다음 순서로 동작한다(docs guides-registry/intro).

  1. YAML 설정 파일을 읽는다.
  2. DB migration을 실행한다.
  3. 설정한 원천에서 데이터를 바로 가져온다.
  4. 동기화 coordinator를 background로 시작한다.
  5. MCP Registry API를 연다.

주 API의 기본 포트는 8080이고, health, readiness, version 경로는 내부 포트 8081에 따로 있다(docs guides-registry/configuration).

5. 원천과 동기화

원천데이터갱신 방식게시
GitGit 저장소 안의 JSON 파일. branch, Git 태그, commit으로 고정주기 동기화불가
API다른 MCP Registry API주기 동기화불가
File로컬 경로나 URL의 JSON 파일주기 동기화불가
Managed/v1/entries로 받은 항목동기화 없음가능. registry server 하나에 하나만 둔다
Kubernetesannotation이 붙은 MCPServer 같은 리소스클러스터 감시불가

아래는 원천 세 개와 registry 두 개를 둔 설정의 일부다(docs guides-registry/configuration). 인증과 DB 설정은 6장이 다룬다.

sources:
  - name: toolhive
    git:
      repository: https://github.com/stacklok/toolhive-catalog.git
      branch: main
      path: pkg/catalog/toolhive/data/registry-upstream.json
    syncPolicy:
      interval: '30m'
    filter:
      tags:
        exclude: ['experimental']
  - name: upstream-mcp
    api:
      endpoint: https://registry.modelcontextprotocol.io
    syncPolicy:
      interval: '1h'
  - name: internal
    managed: {}

registries:
  - name: public
    sources: ['toolhive', 'upstream-mcp', 'internal']
  - name: platform-team
    sources: ['toolhive', 'internal']
    claims:
      org: 'acme'
      team: 'platform'

registry server는 oauth 모드에서 auth.authz를 설정할 때만 claim을 검사한다(6.3장). 인가를 켜면 claim이 없는 public registry는 super-admin만 본다.

원천 이름은 DNS label 규칙을 따라야 한다. Kubernetes lease 이름에 원천 이름이 붙기 때문이다(docs guides-registry/configuration).

5.1 동기화 동작

동기화 대상은 Git, API, File 원천이고, 동기화 coordinator는 다음 순서로 동작한다.

  1. 약 2분마다 할 일을 찾는데, 간격에는 ±30초 jitter가 붙는다(source toolhive-registry-server/internal/sync/coordinator/coordinator.go:27).
  2. syncPolicy.interval이 지난 원천 하나를 고른다(source toolhive-registry-server/database/queries/sync.sql:153).
  3. 원천 데이터의 hash와 항목 필터 설정을 이전 값과 비교한다.
  4. 첫 동기화이거나 바뀐 것이 있으면 데이터를 DB에 쓴다(source toolhive-registry-server/internal/sync/doc.go:24).

registry server 인스턴스를 여러 개 띄워도 두 인스턴스가 원천 하나를 함께 동기화하지는 않는다. 작업을 고르는 SQL이 FOR UPDATE ... SKIP LOCKED를 쓰기 때문이다(source toolhive-registry-server/database/queries/sync.sql:156).

Kubernetes 원천은 원천마다 leader election lease를 따로 쓴다(source toolhive-registry-server/internal/app/builder.go:627).

registry server는 Git 원천의 Git 저장소를 /data에 clone한다. 문서는 운영 환경에서 이 경로에 영구 volume을 붙이라고 권하는데, volume이 없으면 재시작할 때마다 다시 clone한다(docs guides-registry/configuration).

Git 원천의 변경을 바로 반영하려면 다음 동기화를 기다리거나 서버를 재시작해야 한다(docs guides-registry/publish-servers).

5.2 항목 필터와 우선순위

Git, API, File 원천에는 항목 필터를 설정할 수 있다. 이름 pattern과 tag로 넣을 항목과 뺄 항목을 정하고, skill과 plugin은 namespace/name 형식의 이름을 pattern과 비교한다(docs guides-registry/configuration).

필터 설정이 바뀌면 registry server는 원천 데이터가 같아도 다시 동기화한다. registry 하나가 묶은 원천들에 이름이 같은 항목이 있으면 목록 앞쪽 원천의 항목을 쓴다.

5.3 Kubernetes 원천

Kubernetes 원천은 클러스터의 MCPServer, MCPRemoteProxy, VirtualMCPServer 리소스를 감시하고, annotation이 붙은 리소스만 항목이 된다(docs guides-registry/configuration).

annotation필수뜻
toolhive.stacklok.dev/registry-export예"true"여야 항목이 된다
toolhive.stacklok.dev/registry-url예클라이언트가 접속할 외부 URL
toolhive.stacklok.dev/registry-description예목록에 보일 설명
toolhive.stacklok.dev/tools아니요tool 이름 JSON 배열
toolhive.stacklok.dev/authz-claims아니요항목 claim JSON 객체

v1.5.2부터 Kubernetes 항목의 버전은 이미지 태그를 따른다. registry-version annotation이 있으면 그 값이 먼저이고, 둘 다 규칙에 맞지 않으면 1.0.0이 된다.

operator와 함께 쓰면 이름이 default인 Kubernetes 원천이 자동으로 생긴다. operator의 동작은 07편이 다룬다.

6. 데이터베이스, 인증, 인가

6.1 데이터베이스

registry server는 PostgreSQL 14 이상을 요구한다(docs guides-registry/database). v1.5.2에는 DB 없이 도는 저장 방식이 없어서 database 설정이 없으면 시작하지 않는다(source toolhive-registry-server/internal/app/storage/factory.go:70).

registry server는 시작할 때 migration을 자동으로 실행하는데, v1.5.2 소스 트리에는 migration이 23개 있다(source toolhive-registry-server/database/migrations/).

문서는 운영 환경에서 DB 사용자를 둘로 나누라고 권한다. 일반 사용자는 데이터만 다루고 migration 사용자는 스키마를 바꾼다. registry server는 DB 비밀번호를 다음 순서로 찾는다.

  1. AWS RDS IAM 같은 동적 인증(dynamicAuth)
  2. 설정 파일의 password나 환경 변수 THV_REGISTRY_DATABASE_PASSWORD
  3. pgpass 파일

6.2 인증

인증 방식은 oauth와 anonymous 두 가지이고, 설정하지 않으면 oauth가 기본이다(source toolhive-registry-server/internal/config/config.go:373).

oauth 모드는 JWT를 IdP의 JWKS로 확인하고, JWT가 아닌 access token은 introspection(RFC 7662)으로 확인한다(docs guides-registry/authentication).

IdP를 여러 개 등록할 수 있고, Kubernetes service account token을 확인하는 provider 설정도 지원한다.

/openapi.json과 /.well-known/*는 인증 없이 열린다. 인증에 실패한 응답의 WWW-Authenticate 헤더에는 RFC 9728 메타데이터 위치가 들어 있다.

anonymous 모드는 개발과 시험용이고, 문서는 운영 환경에서 쓰지 말라고 권한다.

6.3 인가

인가는 auth.authz 설정이 있을 때 켜지고, registry server는 요청마다 다음 순서로 판단한다(docs guides-registry/authorization).

  1. access token에서 claim을 꺼낸다.
  2. auth.authz.roles 규칙으로 호출자의 role을 정한다.
  3. role이 그 작업을 허용하는지 보고, 허용하지 않으면 403을 돌려준다.
  4. 호출자 claim이 대상 리소스의 claim을 만족하는지 본다.
role허용하는 작업
superAdmin모든 작업. claim 검사를 건너뛴다
manageSources원천 생성, 수정, 삭제, 조회
manageRegistriesregistry 생성, 수정, 삭제, 조회
manageEntries항목 게시, 버전 삭제, 항목 claim 수정

claim은 세 곳에 붙는다.

위치정하는 것
registry claim/registry/{name} 전체의 접근 허용 여부
항목 claimregistry 안에서 항목 하나가 보이는지
원천 claim원천 관리, registry 연결, managed 원천 게시 권한

Git, API, File 원천의 항목은 원천 claim을 물려받는다. Kubernetes 항목은 authz-claims annotation에서, managed 항목은 게시 요청에서 claim을 받는다.

claim 비교에는 규칙이 두 개 있다.

  • 읽기, 접근 검사, 삭제: 배열 claim 값 가운데 하나만 같아도 통과한다.
  • 생성과 수정: 요청에 담은 claim 배열 값을 호출자가 모두 가져야 통과한다.

claim이 없는 원천, registry, 항목은 기본 거부 대상이라서 super-admin만 본다.

oauth 모드에서 auth.authz를 빼면 auth-only 모드가 되고, 이때는 로그인한 호출자가 모든 항목을 본다.

7. registry server에 서버 게시

registry server에 MCP 서버를 올리는 방법은 두 가지다(docs guides-registry/publish-servers).

방법맞는 경우
Git 원천이나 File 원천에 JSON 파일을 둔다코드 리뷰, CI, 변경 이력이 필요한 catalog
managed 원천에 API로 게시한다프로그램으로 게시하거나 버전마다 따로 올리는 경우

managed 원천에는 POST /v1/entries로 게시한다. 인가(auth.authz)를 켜면 claims 객체를 함께 보내야 하고, 빠뜨리면 registry server가 400을 돌려준다(source toolhive-registry-server/internal/api/v1/entries.go:60).

curl -X POST https://registry.example.com/v1/entries \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <TOKEN>" \
  -d '{
    "server": {
      "name": "io.github.acme/deploy-helper",
      "description": "Deployment assistant for internal services",
      "version": "1.0.0",
      "packages": [{
        "registryType": "oci",
        "identifier": "ghcr.io/acme/deploy-helper:1.0.0",
        "transport": { "type": "streamable-http", "url": "http://localhost:8080" }
      }]
    },
    "claims": { "org": "acme", "team": "platform" }
  }'

server 객체의 필수 필드는 name, description, version이고, packages나 remotes 가운데 하나도 있어야 한다.

registry server의 게시 규칙은 다음과 같다(docs guides-registry/publish-servers).

  • 같은 버전을 다시 게시하면 409 Conflict를 돌려준다.
  • 새 버전이 현재 latest보다 높으면 latest가 새 버전을 가리킨다.
  • 더 낮은 버전을 게시해도 latest는 바뀌지 않는다.
  • latest 버전을 삭제하면 남은 버전 가운데 가장 높은 것이 latest가 된다.
  • 같은 서버의 다음 버전은 첫 버전과 같은 claim을 가져야 한다.
curl -X DELETE \
  https://registry.example.com/v1/entries/server/io.github.acme%2Fdeploy-helper/versions/1.0.0 \
  -H "Authorization: Bearer <TOKEN>"

게시 claim은 호출자 JWT claim의 부분 집합이어야 하고, 호출자 JWT는 managed 원천의 claim도 만족해야 한다.

skill과 plugin도 같은 /v1/entries API에 skill이나 plugin 객체로 게시한다. skill은 09편이 다룬다.

문서는 Git 원천의 파일을 PR 전에 JSON Schema로 확인하라고 권하고, 예로 check-jsonschema 명령을 든다.

8. 내장 registry 수록 기준

내장 registry에 들어가는 서버는 공개된 수록 기준을 거치는데(docs concepts/registry-criteria), 이 기준은 내장 registry에만 적용된다.

분야주요 기준
오픈 소스소스 코드 전체 공개, 허용 라이선스 사용
보안provenance(Sigstore, GitHub Attestations), SLSA 수준, 의존성 고정, SBOM 공개
CI의존성 자동 갱신, 보안 검사, CVE 감시, lint
Git 저장소 지표stars, forks, commit 빈도, 기여자 활동
MCP 준수MCP 규격 지원, 프로토콜 버전 호환
품질자동 테스트, 문서, CI 기반 릴리스, semantic versioning
커뮤니티issue 응답 속도, 유지 관리자 수, 후원 조직

Stacklok은 Apache-2.0, MIT, BSD 계열 같은 permissive 라이선스만 받고, AGPL과 GPL은 받지 않는다.

점수제와 등급 세분화는 문서의 향후 검토 대상이고 아직 시행하지 않은 안이다. provenance 확인 방법은 03편이 다룬다.

9. 그룹

9.1 그룹 기록과 소속

그룹은 workload 여러 개에 붙이는 이름이다(docs concepts/groups). 로컬 thv는 그룹을 XDG 상태 경로 아래 toolhive/groups에 파일로 저장한다(source pkg/state/local.go:45).

그룹 기록에는 이름, 등록된 클라이언트, skill, plugin 목록이 있다(source pkg/groups/group.go:18).

{
  "name": "dev",
  "registered_clients": ["vscode"],
  "skills": ["code-review"]
}

workload 목록은 그룹 기록에 없고, 각 workload의 RunConfig가 자기 그룹 이름을 가진다(source pkg/runner/config.go:259). 그래서 workload 하나는 그룹 하나에만 속한다.

같은 서버를 두 그룹에 두려면 이름을 달리해 두 번 실행해야 한다(docs guides-cli/group-management).

9.2 default 그룹

thv는 시작할 때 default 그룹이 없으면 만든다(source pkg/migration/migration.go:21). Kubernetes 환경에서는 MCPGroup을 operator나 사용자가 관리하기 때문에 만들지 않는다.

thv run의 --group 기본값은 default이고(source cmd/thv/app/run_flags.go:189), thv는 default 그룹을 삭제하는 명령을 거부한다(source cmd/thv/app/group.go:154).

9.3 그룹 명령

thv group create dev
thv run --group dev --name fetch-dev fetch
thv group list
thv group rm dev                    # workload를 default 그룹으로 옮긴다
thv group rm dev --with-workloads   # workload도 삭제한다

--group으로 지정한 그룹은 미리 있어야 한다(docs guides-cli/configure-mcp-servers).

thv group rm은 기본으로 workload를 default 그룹으로 옮긴다. 이때 thv는 실행 중인 workload를 옛 그룹의 클라이언트 설정에서 빼고 default 그룹의 클라이언트 설정에 넣는다(source cmd/thv/app/group.go:318).

9.4 그룹을 입력으로 쓰는 기능

  • vMCP: 그룹 하나의 workload를 backend로 모아 endpoint 하나로 내고, 로컬에서는 thv vmcp serve --group <이름>을 쓴다(source docs/arch/vmcp-local.md:107). 08편이 다룬다.
  • Kubernetes: 그룹은 MCPGroup 리소스다. 07편이 다룬다.
  • skill과 plugin: 설치할 때 그룹 기록에 이름을 더한다(source pkg/groups/group.go:21). 09편이 다룬다.

registry 묶음은 그룹과 다른 개념이다. registry 묶음은 레거시 registry 파일 안의 배포 정의였고, 그룹은 workload에 붙이는 이름이다.

10. 클라이언트 설정

10.1 지원 클라이언트

v0.63.0 코드에는 MCP 클라이언트 26종이 정의되어 있다(source pkg/client/config.go:49). thv client register에 넣는 이름은 아래와 같고, 분류는 이 문서가 붙였다.

  • IDE: cursor, vscode, vscode-insider, vscode-server, windsurf, windsurf-jetbrains, kiro, trae, zed, antigravity, qoder
  • IDE 확장: cline, roo-code(deprecated), continue
  • CLI와 agent 도구: claude-code, codex, gemini-cli, goose, opencode, amp-cli, mistral-vibe, kimi-cli, factory, copilot-cli, pi
  • 앱: lm-studio

Claude Desktop과 Xcode는 LLM gateway 전용 도구로 정의되어 있어서 MCP 클라이언트 목록에는 없다(source pkg/client/config.go:107).

Claude Desktop처럼 stdio만 받는 클라이언트는 StdioBridge를 써야 하고, 클라이언트 설정의 command에 thv proxy stdio <workload 이름>을 넣는다(docs reference/client-compatibility).

{
  "mcpServers": {
    "osv": { "command": "thv", "args": ["proxy", "stdio", "osv"] }
  }
}

v0.63.0에는 thv client connector 명령이 있는데, 이 명령은 Claude Desktop 설정 문서의 managedMcpServers에 원격 MCP 서버를 넣는다(source pkg/client/claude_desktop_connectors.go:32). 그 서버에는 Claude Desktop이 직접 접속하고 OAuth 로그인도 직접 하므로 proxy는 끼지 않는다(source pkg/client/claude_desktop_connectors.go:19).

thv llm setup --client claude-desktop        # 먼저 한 번 실행한다
thv client connector add --client claude-desktop github-tools https://mcp.example.com/mcp
thv client connector list --client claude-desktop
thv client connector rm --client claude-desktop github-tools

connector는 thv llm setup이 만든 설정 문서에 들어가므로 그 명령을 먼저 실행해야 한다(source cmd/thv/app/client_connector.go:28). URL은 절대 https URL이어야 한다(source cmd/thv/app/client_connector.go:44). Claude Desktop은 설정을 시작할 때만 읽기 때문에, connector를 바꾼 뒤에는 앱을 완전히 끝내고 다시 열어야 한다(docs guides-cli/client-configuration).

Claude Desktop의 LLM gateway 설정은 Linux에서 ~/.config 아래 경로를 쓰고(source pkg/client/config.go:1121), Windows에서는 credential helper를 .cmd 파일로 쓴다(source pkg/client/llm_gateway_credential_helper.go:236). LLM gateway 자체는 이 문서의 범위 밖이다.

10.2 감지와 등록

thv는 클라이언트의 설정 디렉터리가 있으면 그 클라이언트가 설치된 것으로 본다(source pkg/client/discovery.go:107). Pi처럼 설정 디렉터리 환경 변수가 있는 클라이언트는 그 변수가 가리키는 디렉터리를 본다(source pkg/client/discovery.go:117). 값 앞의 ~는 홈 디렉터리로 바꾸고, 상대 경로는 현재 디렉터리 기준이다(source pkg/client/config.go:1484).

thv client status                           # 설치와 등록 상태
thv client setup                            # 대화형으로 클라이언트와 그룹 선택
thv client register claude-code --group dev
thv client list-registered
thv client remove claude-code --group dev

register의 --group 기본값은 default다(source cmd/thv/app/client.go:88).

공식 문서 guides-cli/group-management의 예시는 thv client register --client vscode를 쓰지만, v0.63.0 코드에도 thv client register에는 --client flag가 없어서 클라이언트 이름은 위치 인자로 넣어야 한다(source cmd/thv/app/client.go:50). --client flag는 thv client connector에만 있다(source cmd/thv/app/client_connector.go:102).

thv는 thv client register를 받으면 다음 순서로 동작한다(source cmd/thv/app/client.go:263).

  1. 지정한 그룹 기록의 registered_clients에 클라이언트 이름을 더한다.
  2. 실행 중인 workload 가운데 그 그룹에 속한 것을 고른다.
  3. 고른 workload의 proxy URL을 클라이언트 설정에 쓴다.

등록 뒤에는 thv가 workload를 시작할 때 서버 블록을 넣고 멈출 때 뺀다(source pkg/runner/runner.go:694, pkg/workloads/manager.go:1671). 대상은 workload가 속한 그룹에 등록된 클라이언트뿐이다(source pkg/client/manager.go:291).

workload의 그룹 이름이 비어 있으면 thv는 thv 설정 파일에 등록된 클라이언트 전체를 고치는데, 예전 버전과 맞추는 동작이다(source pkg/client/manager.go:306).

10.3 파일을 고치는 방식

thv는 클라이언트 설정 파일을 통째로 다시 만들지 않고 서버 블록 하나만 넣거나 뺀다. JSON 파일을 고칠 때는 다음 순서로 동작한다(source pkg/client/config_editor.go:86).

  1. 설정 파일 옆의 .lock 파일로 잠금을 잡는다.
  2. 파일을 hujson으로 읽는다. hujson은 주석과 끝 쉼표가 있는 JSON도 읽는다.
  3. JSON Patch add 연산으로 서버 key 경로 아래에 workload 이름의 값을 넣는다.
  4. 결과를 hujson 형식으로 정리한 뒤 원자적으로 쓴다. 파일 권한은 0600이다.

YAML 파일과 TOML 파일도 같은 잠금과 원자적 쓰기를 쓴다(source pkg/client/config_editor.go:189). YAML은 Goose와 Continue가, TOML은 Codex와 Mistral Vibe가 쓴다. 파일이 없으면 thv가 새로 만든다(source pkg/client/manager.go:266).

10.4 클라이언트별 형식과 transport

클라이언트 설정에 들어가는 값은 실행 명령이 아니라 proxy URL이다. proxy가 stdio를 HTTP로 바꿔 내보내기 때문에 stdio 서버도 클라이언트에는 HTTP 서버로 보인다(02편).

URL 형식은 transport에 따라 다르다(source pkg/transport/url.go:55).

  • streamable HTTP: http://<host>:<포트>/mcp
  • SSE: http://<host>:<포트>/sse#<workload 이름>
  • stdio: proxy mode 기본값이 streamable HTTP이므로 /mcp 형식이다.

클라이언트마다 서버 key, type 값, URL 필드 이름이 다르다. 아래 표는 주요 클라이언트의 macOS 경로만 보인다(source pkg/client/config.go:352).

클라이언트가 컨테이너 안에서 돌면 localhost 대신 host.docker.internal 같은 호스트 주소를 써야 한다(docs guides-cli/client-configuration).

11. tool 사용자화

tool 사용자화는 클라이언트가 보는 tool 목록을 줄이거나 tool 이름과 설명을 바꾸는 기능이고, CLI에서는 thv run의 flag 두 개로 설정한다(source cmd/thv/app/run_flags.go:335).

flag값기능
--toolstool 이름. 여러 번 쓴다tool 필터
--tools-overrideJSON 파일 경로tool 재정의
thv run --tools list_issues --tools get_issue github
thv run --tools-override override.json fetch
{
  "toolsOverride": {
    "fetch": {
      "name": "toolhive-docs-fetch",
      "description": "Fetches a URL from https://docs.stacklok.com/toolhive website."
    }
  }
}

JSON의 key는 원래 tool 이름이고 name은 새 이름이다(source pkg/cli/tools_override.go:19). tool마다 재정의 값에 name이나 description 가운데 하나 이상이 있어야 한다(source pkg/runner/config_builder.go:1299).

두 flag를 함께 쓰면 --tools에는 바뀐 이름을 적어야 한다. 클라이언트가 보는 이름이 바뀐 이름이기 때문이다(docs guides-cli/configure-mcp-servers). proxy의 middleware도 같은 순서로 본다. tools/list 응답에서는 먼저 tool 재정의로 이름을 바꾸고, 그다음 바뀐 이름이 tool 필터에 있는지 본다(source pkg/mcp/tool_filter.go:1714, tool_filter.go:1725). tools/call 요청은 바뀐 이름으로 tool 필터를 본 뒤 원래 이름으로 되돌린다(source pkg/mcp/tool_filter.go:1801).

registry 항목에 tool 목록이 있으면 thv가 실행 전에 이름을 대조하고, 목록에 없는 이름이면 tool ... not found in registry 오류를 낸다(source pkg/runner/config_builder.go:1305). --tools에 적은 바뀐 이름은 원래 이름으로 되돌려 대조한다(source pkg/runner/config_builder.go:1319).

11.1 proxy 안의 동작

tool 필터나 tool 재정의가 있으면 thv가 proxy에 middleware 두 개를 붙인다(source pkg/runner/middleware.go:140). 두 middleware는 다음 일을 한다.

  • tools/list 응답: 필터 밖 tool을 빼고 이름과 설명을 바꾼다.
  • tools/call 요청: 바뀐 이름을 원래 이름으로 되돌린 뒤 MCP 서버로 보낸다(source pkg/mcp/tool_filter.go:355).
  • 필터 밖 tool 호출: MCP 서버로 보내지 않는다. JSON-RPC 오류 tool not found를 HTTP 200으로 돌려준다(source pkg/mcp/tool_filter.go:345).
  • SSE 응답만 받는 클라이언트의 필터 밖 호출: HTTP 400을 돌려준다.

차단 응답은 없는 tool을 부른 경우와 같은 모양인데, 클라이언트가 숨긴 tool의 존재를 알아내지 못하게 하는 설계다(source pkg/mcp/tool_filter.go:25).

v0.63.0의 tools/list 필터는 해석하지 못하는 응답을 통과시키지 않는다. 대상은 tools 목록으로 읽힐 가능성이 있는 응답이고, tool 항목이 잘못됐거나 Content-Type이 모호하면 필터가 응답을 보류한다(source pkg/mcp/tool_filter.go:179). 보류한 응답 대신 JSON-RPC 오류 internal error를 돌려주는데(source pkg/mcp/tool_filter.go:1162), 상태 코드를 아직 보내지 않았으면 HTTP 500으로 보내고 event stream에서는 오류 event로 보낸다(source pkg/mcp/tool_filter.go:1014).

필터는 MCP 서버로 보내는 요청에서 클라이언트의 Accept-Encoding 헤더를 뺀다. 그래야 Go transport가 gzip을 스스로 풀어 필터가 본문을 읽는다(source pkg/mcp/tool_filter.go:212). 그래도 압축된 채 오거나 UTF-8이 아닌 charset을 선언한 본문은 보류한다(source pkg/mcp/tool_filter.go:848). 필터가 읽기 전에 쥐고 있는 본문에는 한도가 있어서 event stream은 16 MiB, 그 밖의 본문은 100 MiB까지다(source pkg/mcp/tool_filter.go:485, tool_filter.go:492).

CLI 문서는 tool 필터가 보안 기능이 아니라고 적지만(docs guides-cli/configure-mcp-servers), UI 문서는 노출을 줄이는 보안 효과를 장점으로 든다(docs guides-ui/customize-tools). tool 단위 접근 통제가 필요하면 05편의 인가 정책을 써야 한다.

11.2 UI와 Kubernetes

UI의 Customize Tools 화면에는 tool마다 켜고 끄는 스위치와 편집 칸이 있고, 사용자는 편집 칸에서 이름과 설명을 바꾼다(docs guides-ui/customize-tools). 이 화면은 registry 항목과 맞는 서버에서만 열린다.

UI는 저장할 때 thv API로 tools와 tools_override를 보내고(source toolhive-studio/renderer/src/features/mcp-servers/sub-pages/customize-tools/page.tsx:149), 받는 쪽은 workload 수정 경로 /api/v1beta/workloads/{name}/edit다(source pkg/api/v1/workloads.go:133).

UI는 실행 중인 서버의 tool 목록을 registry 항목의 목록과 비교해서, 이미지 태그나 tool 목록이 다르면 경고를 보인다.

Kubernetes에서는 MCPToolConfig 리소스가 toolsFilter와 toolsOverride를 담고, MCPServer는 toolConfigRef로 이 리소스를 참조한다(docs guides-k8s/customize-tools). 자세한 내용은 07편이 다룬다.

12. UI의 registry 화면과 Playground

ToolHive UI는 데스크톱 앱이고, 내부에서 thv API를 불러 CLI와 같은 기능을 쓴다. 이 문서는 2026-10-14에 v0.40.1을 읽었고 2026-11-07 갱신에서 UI는 다시 확인하지 않았다.

Registry 메뉴는 thv API로 서버 목록을 읽는데, 이때 registry 이름으로 default를 넘긴다(source toolhive-studio/renderer/src/routes/(registry)/registry.tsx:9, pkg/api/v1/registry.go:382). thv API는 이 이름 하나만 받으며 그 내용은 현재 설정된 registry다(source pkg/api/v1/registry.go:477). 상세 화면은 등급, transport, stars, tool 목록과 함께 provenance 서명 여부도 보인다(docs guides-ui/registry).

Settings의 Registry 화면에는 선택지가 네 개 있다.

  • Default Registry: 내장 registry
  • Remote Registry (JSON URL): 원격 JSON 파일
  • Local Registry (JSON File Path): 로컬 파일
  • Registry Server API: registry server URL과 선택 사항인 OIDC 로그인

Registry Server API 선택지는 사설 IP와 HTTP를 허용한다. 문서의 URL 예는 https://registry.example.com:8080/registry/default다.

Playground는 앱 안의 채팅 화면이고, 사용자는 thread마다 agent, 모델, MCP tool, skill을 고른다(docs guides-ui/playground). 모델 제공자는 다음 중에서 고른다.

  • API 키를 넣는 제공자: OpenAI, Anthropic, Google, xAI, OpenRouter
  • 로컬 서버 URL을 넣는 제공자: Ollama, LM Studio
  • OIDC로 보호된 LLM gateway: Stacklok Gateway

MCP 서버를 시험할 때도 Playground를 쓰는데, 채팅 안에 tool 호출의 인자, 상태, 응답, 걸린 시간이 보인다.

Playground의 tool 선택은 그 thread에만 적용되므로, 모든 클라이언트에 적용하려면 Customize Tools를 써야 한다.

13. 자가 점검 문제

먼저 답을 생각해 본 다음 펼쳐서 확인한다.

Q1. 사용자 registry를 지정하지 않으면 thv는 registry를 어디서 읽는가?

thv 바이너리에 들어 있는 내장 registry를 읽는다. 데이터는 Go 모듈 toolhive-catalog의 catalog.Upstream()에서 오기 때문에 내장 registry 내용은 thv 버전에 묶인다. v0.63.0은 catalog v0.20261026.0을 쓴다.

Q2. thv config set-registry https://reg.example.com/registry/default를 실행했다. thv는 이 URL을 어떤 종류로 보는가?

URL이 .json으로 끝나지 않으므로 thv는 URL 뒤에 /v0.1/servers를 붙여 GET 요청을 보내고, registry server는 /registry/default/v0.1/servers에서 목록을 돌려준다. 응답에 servers 배열과 metadata 객체가 있으면 thv는 API 엔드포인트로 본다. 인증 때문에 401이나 403이 와도 API로 본다.

Q3. 팀이 쓰던 레거시 형식 registry.json을 set-registry로 지정했다. 무엇이 일어나는가?

thv는 파일 형식을 먼저 확인하고, 레거시 형식으로 보이면 오류를 내고 설정을 저장하지 않는다. 먼저 thv registry convert --in registry.json --in-place로 upstream 형식으로 바꿔야 한다.

Q4. registry server 인스턴스 두 개가 같은 PostgreSQL을 쓴다. 두 인스턴스가 같은 Git 원천을 동시에 동기화하는가?

동시에 동기화하지 않는다. 동기화 작업을 고르는 SQL이 FOR UPDATE ... SKIP LOCKED를 쓰기 때문에, 한 인스턴스가 잠근 동기화 행은 다른 인스턴스가 건너뛴다.

Q5. auth.authz를 켠 registry server에 claim 없는 Git 원천을 두었다. 그 원천의 항목은 누가 보는가?

super-admin만 본다. Git 원천의 항목은 원천 claim을 물려받는데, 원천에 claim이 없으므로 항목에도 claim이 없다. claim이 없는 항목은 기본 거부 대상이다.

Q6. thv client register cursor를 --group 없이 실행했다. 그 뒤 thv run --group dev osv로 서버를 시작했다. osv가 Cursor 설정에 들어가는가?

들어가지 않는다. register의 --group 기본값이 default라서 cursor는 default 그룹 기록에만 등록되었고, thv는 dev 그룹에 등록된 클라이언트의 설정만 고친다. osv를 넣으려면 thv client register cursor --group dev를 실행해야 한다.

Q7. stdio transport 서버를 실행했다. Claude Code 설정 파일에는 어떤 값이 들어가는가?

실행 명령이 아니라 proxy URL이 들어간다. proxy mode 기본값에서는 proxy가 stdio를 streamable HTTP로 바꿔 내보내기 때문이다. Claude Code 서버 블록의 type 값은 http이고 URL은 /mcp로 끝난다.

Q8. tool 필터로 숨긴 tool을 클라이언트가 이름을 알고 직접 부르면 어떻게 되는가?

proxy의 middleware가 그 요청을 MCP 서버로 보내지 않고 JSON-RPC 오류 tool not found를 HTTP 200으로 돌려준다. 이 응답은 없는 tool을 부른 경우와 같다. 클라이언트가 SSE 응답만 받으면 HTTP 400을 돌려준다. CLI 문서는 tool 필터를 보안 기능으로 보지 않으므로, 접근 통제가 목적이면 인가 정책을 써야 한다.

Q9. thv group rm dev를 실행했다. dev 그룹에서 돌던 workload와 클라이언트 설정은 어떻게 되는가?

workload는 삭제되지 않고 default 그룹으로 옮겨진다. thv는 실행 중인 workload를 dev 그룹 클라이언트의 설정에서 빼고 default 그룹 클라이언트의 설정에 넣는다. workload까지 삭제하려면 --with-workloads를 붙여야 한다.

Q10. registry server의 registry 하나가 원천 A와 B를 이 순서로 묶는다. 두 원천에 이름이 같은 항목이 있으면 어느 쪽이 보이는가?

목록 앞쪽에 있는 원천 A의 항목이 보이고, 원천 B의 같은 이름 항목은 그 registry에 보이지 않는다.

Q11. thv client connector add --client claude-desktop docs https://mcp.example.com/mcp로 서버를 넣었다. 이 서버로 가는 요청은 proxy를 지나는가?

지나지 않는다. connector는 Claude Desktop이 직접 접속하는 원격 MCP 서버이고 OAuth 로그인도 Claude Desktop이 한다. thv는 thv llm setup이 만든 설정 문서에 서버 항목만 쓴다. proxy가 없으므로 tool 필터 같은 middleware도 적용되지 않는다.

2026-11-07 갱신에서는 ToolHive 소스 인용 전부를 v0.63.0 트리와 대조했고, 두 버전 사이에 바뀐 인용 파일은 diff로 읽었다. 그 파일은 pkg/client/config.go, discovery.go, pkg/mcp/tool_filter.go, pkg/runner/runner.go, cmd/thv/app/run_flags.go, docs/arch/vmcp-local.md다. 공식 문서는 reference/client-compatibility, guides-cli/client-configuration, group-management, registry 네 쪽을 다시 읽었다. 이번에도 아무것도 실행하지 않았다.

확인하지 못한 사항
  • npm, pypi 패키지 처리: 아키텍처 문서 docs/arch/06-registry-system.md:404는 npm을 npx://로 바꾼다고 적는데, 코드 주석(pkg/registry/provider_api.go:287)은 건너뛴다고 적는다. 실제 변환 함수는 toolhive-core 모듈에 있어 이 소스 트리에 없다.
  • 원격 JSON registry 인증: 아키텍처 문서는 URL 안의 Basic 인증을 적지만, 코드 주석(pkg/registry/factory.go:65)은 원격 JSON이 인증을 지원하지 않는다고 적고, 코드도 원격 JSON provider에 인증 정보를 넘기지 않는다(factory.go:78). CLI 문서 guides-cli/registry는 OAuth 로그인이 URL registry에도 적용된다고 적는다. 실제 요청은 시험하지 않았다.
  • registry server의 메모리 저장 방식: 아키텍처 문서는 in-memory backend를 언급하지만 v1.5.2 코드는 DB 설정을 반드시 요구한다.
  • thv에 넣는 registry server URL 형식(/registry/default까지 넣기)은 코드와 UI 문서에서 추론했다. CLI 문서의 예는 /api로 끝나는 URL을 쓴다(2026-11-07에도 같다). 실제 서버로 시험하지 않았다.
  • 2.3장의 fetch 항목은 registry server 예시 파일(2025-11 시점)에서 가져왔다. catalog v0.20261026.0의 실제 내용은 이 소스 트리에 없어 읽지 않았다.
  • registry server 인용(internal/ 경로, v1.5.2)은 2026-11-07 갱신에서 다시 확인하지 않았고 UI 인용(v0.40.1)도 같다. 두 저장소는 ToolHive 저장소와 별개다.
  • Pi의 SSE 미지원, connector 동작, tool 필터의 보류 응답은 v0.63.0 코드와 공식 문서에서 읽었고, 실제 클라이언트로 시험하지 않았다.
  • claim 없는 registry: 공식 문서 guides-registry/configuration과 authorization에 예시가 있다. 두 예시는 claim 없는 public registry가 모든 인증 사용자에게 열린다고 설명한다. 같은 authorization 문서의 다른 절과 v1.5.2 코드(internal/service/db/claims_filter.go:89)는 인가를 켜면 claim 없는 리소스를 거부한다. 이 문서는 코드를 따랐다.
  • 게시 claim 요구 조건: 공식 문서 guides-registry/publish-servers는 인증을 켜면 claims가 필요하다고 적지만, v1.5.2 코드는 인가를 켤 때만 요구한다(internal/api/v1/entries.go:60). 이 문서는 코드를 따랐다.
  • Windows와 Linux의 클라이언트 설정 경로는 표에 넣지 않고 코드의 macOS 경로만 옮겼다.
  • UI 문서의 "tool이 적으면 tool 선택이 빨라지고 LLM 토큰 사용이 준다"는 회사의 주장이고 수치는 없다.
  • 공식 문서 guides-cli/group-management의 --client flag 예시는 v0.63.0 코드와도 맞지 않는다(10.2장, 2026-11-07 확인).
