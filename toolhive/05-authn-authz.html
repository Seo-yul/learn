인증과 인가

ToolHive 학습 05편 · 2026-10-14 작성 · 2026-11-07 갱신

ToolHive proxy가 MCP 서버 앞에서 하는 인증과 인가를 다루는 문서로, 들어오는 인증, 내장 인가 서버, 나가는 인증, 위임, Cedar 인가를 차례로 본다. OAuth 기본 개념은 OAuth 학습 시리즈를 따르고 여기서 다시 설명하지 않는다.

기준 버전은 ToolHive v0.63.0(2026-11-06)이다. 2026-10-14에 v0.53.0 기준으로 썼고 2026-11-07에 v0.63.0 기준으로 갱신했으며, 공식 문서는 2026-11-07 상태를 읽었다. ToolHive는 자주 바뀌기 때문에 실제로 쓰기 전에 공식 문서를 다시 확인해야 한다.

한 문장 요약

ToolHive proxy는 두 경계에서 일한다. 들어오는 쪽에서는 access token을 검증하고 Cedar policy로 요청을 거르고, 나가는 쪽에서는 MCP 서버가 쓸 자격 증명을 바꾸거나 붙인다. 내장 인가 서버를 켜면 proxy가 fastmcp OAuthProxy처럼 MCP 클라이언트의 인가 서버가 된다.

v0.63.0 갱신 요약
  • 1, 2, 4, 8장의 동작, 곧 middleware 순서, 세 모드, 401과 PRM, AWS STS, 원격 MCP 서버의 OAuth는 바뀌지 않아서 행 번호만 다시 맞췄다.
  • proxy는 token session에 쓸 수 있는 upstream access token이 하나도 없어도 401을 주고, upstream ID token이 만료되면 access token이 살아 있어도 갱신한다. ToolHive refresh token으로 갱신할 때 내장 인가 서버는 upstream 자격 증명부터 본다(5장).
  • 내장 인가 서버의 DCR에 클라이언트 수 상한(기본 10000)과 24시간 미사용 만료가 생겼고, /oauth/register 속도 제한과 상한은 CRD 필드가 됐다. upstream DCR 등록은 시작할 때와 실행 중에 다시 확인한다(5, 6, 7장).
  • 동의 화면은 upstream IdP의 표시 이름을 보여 주고, Go로 내장하는 쪽은 사전 승인 클라이언트의 동의 화면을 건너뛰게 할 수 있다(6장).
  • delegate client의 RunConfig 설정이 늘어서 private_key_jwt 인증, grant 종류, 자기 발급 subject token의 출처 제한이 들어왔고, 입력 audience와 exchange grant(token exchange로 받는 refresh token)도 선언한다. CRD는 아직 예전 네 필드만 받는다. audience 거부는 invalid_target이 됐다(9장).
  • SPIFFE 설정은 여전히 시작 단계에서 거부되지만, 인가 서버용 TLS listener(8443)와 file bundle source는 들어왔다(9장).
  • 인가 middleware는 대상이 없는 요청과 정규형이 아닌 resource URI를 policy 전에 거부하고, 응답 필터는 압축된 목록 응답을 500으로 바꾼다. MCP 파서는 POST가 아닌 요청의 본문을 400으로 거부하며, vMCP의 tool은 Backend:: 부모 entity를 갖는다(10, 11장).

1. 두 경계와 middleware 순서

ToolHive의 인증은 두 경계에서 일어난다(docs concepts/auth-framework). 경계 1은 MCP 클라이언트와 proxy 사이이고, 경계 2는 proxy 뒤쪽이다. MCP 서버나 외부 API가 경계 2에 있다.

공식 문서는 두 경계를 frontend와 backend로 부르고, vMCP 문서는 같은 경계를 incoming과 outgoing으로 부른다. 이 문서에서는 들어오는 인증과 나가는 인증으로 쓴다.

proxy는 RunConfig를 읽고 middleware 목록을 만든다(source pkg/runner/middleware.go:67). 요청은 목록 순서대로 지나가고, 마지막에 넣은 항목이 가장 안쪽에서 돈다(같은 파일 283행 주석). 아래 표는 operator 경로의 순서인데, 인증과 관련된 항목만 적었다.

2. 들어오는 인증의 세 모드

들어오는 인증에는 모드가 셋 있는데, 단일 MCP 서버 경로와 vMCP 경로는 고를 수 있는 모드가 다르다. VirtualMCPServer CRD는 oidc와 anonymous만 받는다(source cmd/thv-operator/api/v1beta1/virtualmcpserver_types.go:206).

모드쓰는 곳동작근거
oidcthv run에 OIDC 설정이 있을 때. vMCP type: oidc.access token을 JWKS나 introspection으로 검증한다.pkg/auth/utils.go:69
localthv run에 OIDC 설정이 없을 때의 기본값. vmcp 설정 파일의 type: local.현재 OS 사용자 이름을 sub로 싣는다. 검증은 하지 않는다.pkg/auth/utils.go:82, pkg/auth/local.go:20
anonymousvMCP의 type: anonymous만.모든 요청에 sub: anonymous를 싣는다. 검증은 하지 않는다.pkg/auth/anonymous.go:22, pkg/vmcp/auth/factory/incoming.go:81

local과 anonymous는 가짜 claim을 만들고, Cedar policy가 이 claim으로 principal을 만든다. 그래서 인증 없이도 인가 설정을 시험할 수 있다(pkg/auth/anonymous.go:14 주석).

OIDC 설정이 없는 thv run은 모든 요청을 받고, proxy는 시작할 때 이 사실을 WARN 로그로 남긴다(pkg/auth/utils.go:82). 모든 요청이 같은 OS 사용자로 보여서 사용자별 인가도 되지 않으므로, 로컬 개발 밖에서는 OIDC를 켜야 한다.

3. access token 검증

JWKS와 introspection의 기본 개념은 OAuth 02편을 따르고, 이 장에서는 ToolHive proxy가 두 방식을 어떻게 고르는지 본다.

proxy의 TokenValidator는 요청마다 다음 순서로 검증한다(source pkg/auth/token.go:1118).

  1. 첫 요청 때 issuer의 OIDC discovery를 하고, 실패하면 다음 요청 때 다시 한다(token.go:817).
  2. access token을 JWT로 해석하고, 서명 키는 JWKS에서 찾는다(token.go:943).
  3. JWT 형식이 아니면 introspection으로 넘긴다(token.go:1141).
  4. JWT라면 issuer, audience, 만료 시각을 본다(token.go:998).
  5. claim으로 사용자 정보를 만들고 요청 context에 싣는다(token.go:1339, 1425행).

3번으로 가는 경우는 access token이 JWT 형식이 아닐 때뿐이라서, 서명이 틀린 JWT는 introspection으로 가지 않고 바로 401이 된다. 공식 문서는 "JWT를 먼저 시도하고 필요하면 introspection으로 넘어간다"고 쓰지만 코드의 실제 조건은 이보다 좁다.

4번에서 proxy는 issuer와 audience를 설정했을 때만 비교하고(token.go:998) 만료 시각은 늘 본다. audience를 빼면 같은 issuer가 발급한 다른 서비스용 JWT도 통과하기 때문에 공식 문서는 --oidc-audience를 함께 주라고 한다(docs guides-cli/auth).

introspection provider

proxy는 introspection 주소를 보고 provider를 고른다(source pkg/auth/token.go:503).

  --oidc-issuer https://auth.example.com \
  --oidc-audience https://mcp.example.com/mcp \
  --resource-url https://mcp.example.com/mcp \

Kubernetes 설정

Kubernetes에서는 MCPOIDCConfig에 IdP 설정을 한 번 두고, 각 MCPServer가 oidcConfigRef로 참조하면서 자기 audience를 정한다(docs guides-k8s/auth-k8s).

apiVersion: toolhive.stacklok.dev/v1beta1
kind: MCPOIDCConfig
metadata:
  name: production-oidc
  namespace: toolhive-system
spec:
  type: inline
  inline:
    issuer: 'https://auth.example.com'
    jwksUrl: 'https://auth.example.com/.well-known/jwks.json'
---
apiVersion: toolhive.stacklok.dev/v1beta1
kind: MCPServer
metadata:
  name: weather-server
  namespace: toolhive-system
spec:
  image: ghcr.io/stackloklabs/weather-mcp/server
  transport: streamable-http
  proxyPort: 8080
  oidcConfigRef:
    name: production-oidc
    audience: 'https://mcp.example.com/mcp'
    resourceUrl: 'https://mcp.example.com/mcp'
    scopes:
      - openid

MCPOIDCConfig에는 type: kubernetesServiceAccount도 있는데, 이 모드는 클러스터 안 pod의 service account token을 검증한다. issuer 기본값은 https://kubernetes.default.svc이고(source cmd/thv-operator/pkg/oidc/resolver.go:22), operator는 pod에 마운트된 CA와 service account token으로 JWKS를 읽게 설정한다(resolver.go:137).

공식 문서는 serviceAccount와 namespace 필드가 특정 service account만 허용한다고 쓴다. 그런데 v0.63.0의 resolver.go:102도 이 두 필드를 검증 설정으로 넘기지 않는다. 이 파일은 v0.53.0과 같고, 다른 코드 경로도 찾지 못했다. 특정 service account만 받아야 한다면 클러스터에서 직접 시험해야 하고, 시험 전에는 sub claim에 Cedar policy를 거는 안을 함께 검토해야 한다.

4. 401 응답과 PRM

PRM의 개념은 OAuth 01편 5장을 따른다. fastmcp OAuthProxy 구성에서는 MCP 서버가 401과 PRM을 내지만, ToolHive에서는 proxy가 MCP 서버 대신 낸다.

검증에 실패하면 proxy는 401과 WWW-Authenticate 헤더를 준다(source pkg/auth/token.go:1176). 헤더가 없으면 오류 코드는 invalid_request이고, access token이 틀리면 invalid_token이다(token.go:1325, 1333행).

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="https://auth.example.com",
  resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp",
  error="invalid_request", error_description="authorization header required"

resource_metadata 주소는 resource URL에서 만드는데, proxy가 호스트와 경로 사이에 /.well-known/oauth-protected-resource를 넣는 방식이다(RFC 9728 3.1절). realm에는 설정한 issuer가 들어간다.

MCP 클라이언트가 그 주소를 읽으면 proxy는 아래 JSON을 준다(source pkg/auth/token.go:1440).

{
  "resource": "https://mcp.example.com/mcp",
  "authorization_servers": ["https://auth.example.com"],
  "bearer_methods_supported": ["header"],
  "scopes_supported": ["openid"]
}
  • authorization_servers에는 설정한 issuer 하나가 들어가는데, 내장 인가 서버를 쓰면 이 값이 내장 인가 서버의 issuer가 된다.
  • resource URL을 설정하지 않으면 proxy는 404를 준다(token.go:1460).
  • 인증을 끈 proxy도 /.well-known/ 아래에 JSON 404를 주는데, Claude Code 같은 MCP 클라이언트가 응답을 해석하게 하려는 처리다(pkg/auth/well_known.go:21 주석).

5. 내장 인가 서버

내장 인가 서버는 proxy 프로세스 안에서 도는 OAuth 2.0 인가 서버다(docs concepts/embedded-auth-server). MCP 클라이언트에게는 인가 서버로 보이고 upstream IdP에게는 OAuth 클라이언트 하나로 보인다. 이 구조는 fastmcp OAuthProxy와 같다.

공식 문서는 이 기능을 두 문제의 답으로 설명한다(docs concepts/auth-framework).

  • Google, GitHub, Atlassian 같은 IdP는 OAuth 클라이언트를 미리 등록해야 하는데, MCP 클라이언트마다 등록하면 관리가 어렵다.
  • GitHub API 같은 외부 API는 회사 IdP와 연합 관계가 없어서 token exchange로는 그 API용 access token을 얻지 못한다.

공식 문서는 이 기능을 Kubernetes operator 배포에서만 지원한다고 쓰고, thv run에는 이 기능을 켜는 flag가 없다. RunConfig에는 embedded_auth_server_config 필드가 있고(source pkg/runner/config.go:317), proxy는 이 필드가 있으면 인가 서버를 만들고 그 경로를 붙인다(source pkg/runner/runner.go:370, 408행). proxy 하나에는 upstream IdP를 하나만 두고, 여러 개는 VirtualMCPServer에서만 된다(runner.go:372).

로그인 흐름

MCP 클라이언트와 내장 인가 서버는 다음 순서로 로그인한다(source pkg/authserver/server/doc.go:82, pkg/authserver/server/handlers/authorize.go:55).

  1. MCP 클라이언트가 PRM을 읽고 내장 인가 서버를 찾는다.
  2. MCP 클라이언트가 DCR로 등록하거나 CIMD URL을 client_id로 쓴다.
  3. MCP 클라이언트가 브라우저를 /oauth/authorize로 보낸다. PKCE challenge를 함께 보낸다.
  4. 내장 인가 서버가 요청을 저장하고 동의 화면을 보여 준다(authorize.go:169).
  5. 사용자가 승인하면 내장 인가 서버가 브라우저를 upstream IdP로 보낸다.
  6. upstream IdP가 인가 코드를 붙여 브라우저를 /oauth/callback으로 돌려보낸다.
  7. 내장 인가 서버가 그 코드를 upstream access token으로 바꾸고 token session에 저장한다.
  8. 내장 인가 서버가 자기 인가 코드를 MCP 클라이언트의 콜백 주소로 보낸다.
  9. MCP 클라이언트가 /oauth/token에서 JWT를 받는다. JWT에는 tsid claim이 있다.

요청에 prompt=consent가 없을 때 내장 인가 서버는 4번과 5번을 건너뛰는 경우가 있다(authorize.go:144, 153행). 사전 승인 클라이언트의 요청이거나 기억된 승인이 있으면 바로 upstream IdP로 보낸다(6장).

내장 인가 서버는 아래 경로를 연다(source pkg/authserver/server/handlers/handler.go:326, 492행).

tlsListener를 주면 proxy는 8443 포트에도 같은 경로를 연다(source pkg/runner/runner.go:1342). 포트 번호는 고정이고(pkg/authserver/runner/embeddedauthserver.go:42), MCP 트래픽은 그대로 평문 포트를 쓴다. CRD 주석은 operator가 아직 Service와 컨테이너에 8443 포트를 열지 않는다고 쓴다(cmd/thv-operator/api/v1beta1/mcpexternalauthconfig_types.go:1035). 이 listener는 SPIFFE X.509 인증에 쓸 준비 단계다(9장).

로그인 뒤의 요청

로그인 뒤에 proxy는 MCP 요청을 다음 순서로 처리한다(docs concepts/embedded-auth-server).

  1. auth middleware가 JWT 서명을 검증하는데, 공개 키는 HTTP를 거치지 않고 프로세스 안에서 읽는다(pkg/runner/runner.go:403).
  2. auth middleware가 tsid로 token session을 읽는다(pkg/auth/token.go:1356).
  3. upstream access token이 만료됐으면 refresh token으로 갱신하고, 갱신이 실패하면 401을 준다(token.go:1371). upstream ID token만 만료된 경우에도 갱신하는데, 이때는 갱신이 실패하면 살아 있는 access token을 그대로 쓴다(pkg/auth/upstreamtoken/service.go:308, 334행).
  4. token session에 쓸 수 있는 upstream access token이 하나도 없으면 401을 주고, 오류 코드는 invalid_token이다(token.go:1410). 이 경우 MCP 클라이언트는 다시 로그인해야 한다.
  5. upstreamswap middleware가 Authorization 헤더를 upstream access token으로 바꾼다(pkg/auth/upstreamswap/middleware.go:125).

MCP 클라이언트가 ToolHive refresh token으로 갱신을 요청하면 내장 인가 서버는 먼저 token session의 upstream 자격 증명을 본다. upstream refresh token이 확실히 죽었으면 invalid_grant로 거부한다. 근거는 pkg/authserver/config.go:1684 주석과 docs/arch/11-auth-server-storage.md의 "Upstream refresh guard"다. 네트워크 오류나 IdP의 5xx 같은 불확실한 실패는 거부하지 않는데, 이 검사가 없으면 MCP 클라이언트가 401과 refresh를 되풀이한다.

MCP 서버가 인증 없는 공개 서버라면 disableUpstreamTokenInjection: true를 쓰는 방법이 있다. 이 설정을 켜면 proxy는 JWT를 검증한 뒤 Authorization, Cookie, Proxy-Authorization 헤더를 지운다. 다만 token exchange나 AWS STS와는 함께 쓰지 못하는데, 그 middleware가 지운 헤더를 다시 넣기 때문이다(source pkg/runner/middleware.go:508).

Kubernetes 설정

공식 가이드는 Kubernetes Secret 세 개와 CR 세 개를 만든다(docs guides-k8s/embedded-auth-server-k8s). Secret은 upstream client secret, 서명 키, HMAC 키이고, MCPOIDCConfig의 issuer는 내장 인가 서버의 issuer와 같아야 한다.

  namespace: toolhive-system

      - name: auth-server-signing-key

      accessTokenLifespan: '1h'
      refreshTokenLifespan: '168h'
      authCodeLifespan: '10m'
    upstreamProviders:

        type: oidc
        oidcConfig:
          issuerUrl: 'https://accounts.google.com'
          clientId: '<GOOGLE_CLIENT_ID>'
          clientSecretRef:
            name: upstream-idp-secret
            key: client-secret
          redirectUri: 'https://mcp.example.com/oauth/callback'

  • 수명 기본값은 access token 1시간, refresh token 7일, 인가 코드 10분이다(source pkg/authserver/config.go:2527).
  • 서명 키와 HMAC 키를 빼면 ToolHive는 임시 키를 만드는데, 이 경우 pod가 재시작하면 이미 발급한 JWT가 모두 무효가 된다. 운영 환경에서는 두 키를 넣어야 한다.
  • type: oauth2는 GitHub처럼 OIDC discovery가 없는 IdP에 쓰고, authorize, token, userinfo 주소를 직접 적는다.
  • dcrConfig를 주면 내장 인가 서버가 upstream IdP에 DCR로 자기를 등록한다. 이것을 upstream DCR이라 부르는데, MCP 클라이언트의 DCR과는 다르다.
  • 내장 인가 서버는 시작할 때 저장해 둔 upstream DCR 등록이 아직 유효한지 upstream IdP에 확인하는데, 확인 방법은 dcrConfig.registrationProbe로 고른다(source mcpexternalauthconfig_types.go:1986). upstream IdP가 등록을 지웠으면 새로 등록한다. registrationProbeInterval을 주면 실행 중에도 되풀이한다(2006행). rotationKey 값을 바꾸면 다음 시작 때 무조건 새로 등록하고(1966행), 이때 이전 client에 묶인 upstream refresh token은 더 쓰지 못한다.
  • tokenEndpointAuthMethod를 dcrConfig와 함께 주면 그 방식으로 등록한다. 주지 않으면 upstream IdP가 알린 방식 중에서 고른다(source pkg/authserver/config.go:1228 주석).
  • omitScopeOnRefresh: true를 주면 upstream refresh 요청에 scope를 보내지 않는다(source mcpexternalauthconfig_types.go:1684). Salesforce처럼 refresh에 scope를 거부하는 IdP용이다.
  • OAuth 2.0 upstream에 userinfo도 identityFromToken도 없으면 내장 인가 서버는 사용자를 알지 못한다. 이때는 access token 해시로 tk- 접두사 subject를 만든다(source docs/arch/11-auth-server-storage.md).

6. 클라이언트 등록과 동의 화면

DCR과 CIMD

upstream IdP가 있는 내장 인가 서버는 DCR 요청을 늘 받는다(docs guides-k8s/embedded-auth-server-k8s). token exchange만 하는 구성은 예외다(9장). 기본으로는 public client만 등록한다. 즉 token_endpoint_auth_method가 none이고 client secret을 주지 않는다.

  • allowConfidentialClientRegistration: true를 켜면 client secret을 발급한다. /oauth/register는 인증이 없어서 endpoint에 닿는 사람이면 누구든 client secret을 발급받게 된다. 이 설정은 loopback이 아닌 https 콜백 주소만 허용한다.
  • /oauth/register에는 속도 제한이 있는데, 기본값은 프로세스마다 초당 1회, 순간 5회이고(source pkg/authserver/server/handlers/handler.go:145) CRD의 registrationRateLimit으로 바꾼다. maxTokens가 순간 허용 수이고 refillPeriod마다 그만큼 다시 찬다(source cmd/thv-operator/api/v1beta1/mcpexternalauthconfig_types.go:1259). pod가 N개면 전체 한도도 약 N배가 된다.
  • DCR로 만든 클라이언트 수에는 상한이 있고 기본값은 10000이다(source pkg/authserver/storage/config.go:63). storage.maxDCRClients로 바꾸며 0은 무제한이다(mcpexternalauthconfig_types.go:2223). 상한에 닿으면 등록은 503으로 실패하고, 내장 인가 서버는 기존 클라이언트를 지우지 않는다(handlers/dcr.go:151). 한 번도 /oauth/token을 성공하지 못한 DCR 클라이언트는 24시간 뒤에 사라진다(storage/config.go:56).
  • cimd.enabled: true를 켜면 https URL을 client_id로 받고, 내장 인가 서버가 그 URL에서 메타데이터 문서를 가져온다. 가져오기도 프로세스마다 초당 1회, 순간 5회이고, 넘치면 429를 준다(handler.go:431).

CIMD 문서를 가져올 때 내장 인가 서버는 다음 규칙을 지킨다(docs guides-k8s/embedded-auth-server-k8s).

  • 문서 안의 client_id는 가져온 URL과 정확히 같아야 한다.
  • token_endpoint_auth_method는 none이거나 비어 있어야 한다. 다른 값이면 지원 목록에 none이 있어야 하고 서버가 none으로 낮춘다. 공유 비밀 방식은 늘 거부한다.
  • 사설 IP를 막고 redirect를 따라가지 않는다. 시간 제한은 5초, 크기 제한은 10 KB다.
  • 캐시는 기본 256개, TTL 5분이다. Cache-Control 헤더는 아직 따르지 않는다.

upstream IdP는 MCP 클라이언트의 CIMD URL을 보지 못한다. 내장 인가 서버가 upstream IdP에 늘 자기 client_id로 가기 때문이다. 그래서 CIMD를 써도 upstream용 클라이언트 설정은 따로 있어야 하고, 이 점은 fastmcp OAuthProxy의 "등록이 두 층" 구조와 같다.

Claude Code 같은 일부 MCP 클라이언트는 DCR에 좁은 scope를 적고 나서 /oauth/authorize에서 더 넓은 scope를 요청하는데, 내장 인가 서버는 이 요청을 invalid_scope로 거부한다. baselineClientScopes는 정해진 scope를 모든 DCR 클라이언트에 더해서 이 문제를 푼다. 공식 문서는 openid, offline_access 정도로 좁게 두라고 한다.

동의 화면

v0.63.0 내장 인가 서버는 upstream IdP로 보내기 전에 동의 화면을 열고, 기억된 승인이 있거나 사전 승인 클라이언트면 이 화면을 건너뛴다. 공식 문서 사이트는 이 동작을 아직 설명하지 않아서(2026-11-07 확인) 근거는 소스와 설계 문서다(source docs/arch/11-auth-server-storage.md "Interactive client approval"). 이 화면은 fastmcp OAuthProxy 동의 화면(OAuth 01편 7장 ④)과 같은 자리에 있다.

내장 인가 서버는 동의 화면을 다음 순서로 다룬다(source pkg/authserver/server/handlers/authorize.go:55, consent.go:203).

  1. /oauth/authorize가 OAuth 클라이언트, 콜백 주소, resource 하나를 먼저 검증한다. resource는 그 클라이언트의 audience 안에 있어야 한다(authorize.go:174).
  2. 요청을 대기 기록으로 저장하고 브라우저에 일회용 쿠키를 심는다(authorize.go:168).
  3. 동의 화면을 보여 준다. 화면은 돌아갈 곳을 "this computer"처럼 사람이 읽는 말로 보여 준다. upstream IdP 이름은 RunConfig의 display_name이 있으면 그 값으로 보여 주는데(consent.go:153), CRD에는 아직 이 필드가 없다.
  4. 사용자가 버튼을 누르면 브라우저가 POST /oauth/consent를 보내고, 내장 인가 서버는 Origin과 쿠키를 확인한다(consent.go:203).
  5. 승인이면 upstream IdP로 보내고, 거부면 access_denied를 MCP 클라이언트에 돌려준다.
  • allowed audience가 여럿이면 MCP 클라이언트는 /oauth/authorize에서 resource를 하나 보내야 한다. /oauth/token에서 정하면 늦다.
  • 대기 기록은 일회용이고 수명은 10분이다.
  • 화면은 클라이언트 이름을 보여 주되 "앱이 적은 값이고 확인하지 않았다"고 표시한다.
  • 폼이 받는 값은 handle, decision, remember 셋이다(consent.go:274). scope를 하나씩 고르는 기능은 없다.

HTTPS 주소이고 저장소가 지원하면 "이 브라우저에서 다시 묻지 않기" 확인란이 생기고, 같은 앱이 같은 권한을 다시 요청하면 내장 인가 서버는 7일 동안 화면을 건너뛴다. 브라우저 기록은 7일, 사용자별 승인 기록은 30일 두고, 브라우저에는 __Host-thv_consent_<sha256> 쿠키만 남는다. MCP 클라이언트가 prompt=consent를 보내면 화면을 다시 연다.

proxy는 이 쿠키를 MCP 서버로 넘기지 않는다(source pkg/runner/runner.go:266). 승인 기억을 지우는 화면은 없고, 기록은 수명이 끝나면 사라진다.

내장 인가 서버를 Go 코드로 내장하는 쪽은 사전 승인 클라이언트 목록을 줄 수 있다(source pkg/authserver/config.go:1590). 목록에 있는 confidential 클라이언트의 code 요청은 동의 화면 없이 upstream IdP로 간다(authorize.go:252). 콜백 주소는 등록된 것 하나를 명시해야 하고, prompt=consent가 있으면 이 예외보다 화면이 우선한다. RunConfig와 CRD에는 이 설정이 없다. MCP 스펙은 동적 등록 클라이언트마다 사용자 동의를 받으라고 하는데, 설계 문서는 이 예외를 그 요구에서 일부러 벗어난 선택이라고 쓴다. 근거는 docs/arch/11-auth-server-storage.md의 "Administrator consent preauthorization"이다.

  • pod 사이에서는 compare-and-swap으로 저장해서 먼저 쓴 pod만 저장에 성공한다.

fastmcp OAuthProxy도 pod가 둘 이상이면 Redis 같은 공유 저장소가 필요하다(OAuth 01편 7장). 이유도 같은데, 로그인 한 번이 두 구간에 걸치기 때문이다. fastmcp OAuthProxy와 내장 인가 서버는 둘 다 두 구간 사이의 상태를 저장한다.

8. 나가는 인증

MCP 스펙은 MCP 서버가 외부 API에 어떻게 인증할지 정하지 않는다(docs concepts/backend-auth). ToolHive는 다음 방식 중 하나를 쓴다.

8.1 token exchange

token exchange에서 proxy는 들어온 access token을 IdP에 내고 외부 API용 access token을 받는다(docs concepts/backend-auth). sub는 그대로 두고 aud와 scope만 바뀐다. 이 변환은 IdP가 하므로 IdP가 RFC 8693을 지원해야 한다. 공식 문서는 Okta, Auth0, Keycloak을 예로 든다(docs guides-cli/token-exchange).

thv run \
  --oidc-audience mcp-server \
  --oidc-issuer https://dev-123456.okta.com/oauth2/aus1234567890 \
  --oidc-jwks-url https://dev-123456.okta.com/oauth2/aus1234567890/v1/keys \
  --token-exchange-url https://dev-123456.okta.com/oauth2/aus9876543210/v1/token \
  --token-exchange-client-id 0oa0987654321fedcba \
  --token-exchange-client-secret-file /path/to/client-secret \
  --token-exchange-audience backend-api \
  --token-exchange-scopes "api:read,api:write" \
  <서버 이름>
  • proxy는 교환한 access token을 기본으로 Authorization 헤더에 넣고, --token-exchange-header-name을 주면 그 헤더에 넣는다(source pkg/oauthproto/tokenexchange/middleware.go:29).
  • MCP 서버는 요청마다 그 헤더의 access token으로 외부 API를 불러야 하고, 고정 secret에 기대면 안 된다(docs guides-cli/token-exchange).
  • IdP 동의 화면은 나오지 않는다. 운영자가 신뢰 관계를 IdP에 미리 설정해 두기 때문이다.

8.2 AWS STS

AWS STS 방식은 OIDC access token을 AWS 임시 자격 증명으로 바꾼다(docs integrations/aws-sts). proxy는 요청마다 다음 순서로 처리한다.

  1. 들어온 JWT를 검증한다.
  2. role mapper가 claim을 보고 IAM role을 고른다(source pkg/auth/awssts/role_mapper.go:212).
  3. AssumeRoleWithWebIdentity를 불러 임시 자격 증명을 받는다(pkg/auth/awssts/exchange.go:61).
  4. 요청에 SigV4 서명을 하고 AWS MCP Server로 보낸다(pkg/auth/awssts/middleware.go:268).
apiVersion: toolhive.stacklok.dev/v1beta1
kind: MCPExternalAuthConfig
metadata:
  name: aws-mcp-sts-auth
  namespace: toolhive-system
spec:
  type: awsSts
  awsSts:
    region: us-east-1
    service: aws-mcp
    fallbackRoleArn: arn:aws:iam::<ACCOUNT_ID>:role/DefaultMCPRole
    roleMappings:
      - claim: s3-readers          # groups claim 안의 값
        roleArn: arn:aws:iam::<ACCOUNT_ID>:role/S3ReadOnlyMCPRole
        priority: 10               # 작은 수가 먼저
  • role mapper는 기본으로 groups claim을 보는데(pkg/auth/awssts/config.go:14), roleClaim으로 바꿀 수 있다.
  • 규칙은 priority 순서로 보고 처음 맞는 규칙의 IAM role을 쓴다. 맞는 규칙이 없으면 fallbackRoleArn을 쓴다.
  • matcher에 CEL 식을 쓸 수도 있다. 예: "admins" in claims["groups"].
  • claim 규칙에서 role claim은 문자열이나 문자열 목록이어야 한다. 다른 모양이면 그 규칙은 오류가 되고, 다른 규칙이 맞지 않으면 403으로 거부한다(role_mapper.go:272). claim이 없으면 규칙이 맞지 않은 것으로 본다(role_mapper.go:125).

AWS STS middleware는 Cedar 인가 뒤에 돌기 때문에 proxy는 거부된 요청으로는 STS를 부르지 않는다(source pkg/runner/middleware.go:245 주석).

8.3 헤더 주입과 Vault

원격 MCP 서버에는 고정 헤더를 붙이는 기능이 있다(docs guides-cli/run-remote-mcp-servers).

thv secret set my-api-key
thv run https://api.example.com/mcp \
  --name my-server \
  --remote-forward-headers "X-Tenant-ID=tenant123" \
  --remote-forward-headers-secret "X-Api-Key=my-api-key"

평문 헤더 값은 설정 파일에 남으므로 비밀 값은 --remote-forward-headers-secret으로 secret을 참조해야 한다. Host나 X-Forwarded-For 같은 헤더는 설정하지 못한다. Kubernetes에서는 MCPRemoteProxy의 headerForward가 같은 일을 한다.

Vault 연동에서는 Vault Agent Injector가 secret 파일을 만든다(docs integrations/vault). 파일은 proxy pod 안에 생기고, 이 방식을 쓰면 Kubernetes 매니페스트에 비밀 값을 적지 않아도 된다. secret 관리는 03편이 다룬다.

8.4 원격 MCP 서버의 OAuth

원격 MCP 서버가 OAuth를 요구하면 proxy가 OAuth 클라이언트가 되는데, OAuth 01편에서 플랫폼 core가 하는 일을 여기서는 proxy가 한다. proxy는 다음 순서로 자격 증명을 고른다(source pkg/auth/remote/handler.go:62).

  1. 고정 bearer token이 설정됐으면 그것을 쓴다.
  2. 원격 서버를 불러 401의 WWW-Authenticate를 읽는다. 헤더가 없으면 well-known PRM 주소 두 곳을 차례로 읽는다.
  3. PRM에서 인가 서버를 찾고 RFC 8414 메타데이터를 읽는다.
  4. 저장한 refresh token이 있으면 그것으로 로그인 상태를 되살린다.
  5. 없으면 브라우저를 열어 PKCE 흐름을 시작한다.

5번에서 proxy는 client_id를 이렇게 정한다.

  • --remote-auth-client-id를 주면 그 값을 쓴다.
  • 인가 서버가 CIMD 지원을 알리면 https://toolhive.dev/oauth/client-metadata.json을 쓴다(source pkg/oauthproto/cimd.go:16, pkg/auth/remote/handler.go:712).
  • CIMD가 없거나 거부되면 DCR로 등록한다.

proxy는 refresh token과 DCR 결과를 ToolHive secret 저장소에 남긴다(source pkg/runner/runner.go:909). 그래서 proxy를 다시 시작해도 사용자가 다시 로그인할 필요가 없다. 다만 secret 저장소가 없으면 저장하지 않고 WARN 로그만 남긴다. RFC 8707 resource 값은 기본으로 원격 서버 URL을 정규화해서 쓴다(source docs/remote-mcp-authentication.md).

thv run https://remote-mcp.example.com/mcp \
  --name my-remote \
  --remote-auth-issuer https://auth.example.com \
  --remote-auth-client-id my-client-id \
  --remote-auth-client-secret-file ./client-secret \
  --remote-auth-scopes "openid,profile"

9. 위임과 workload identity

act claim 읽기

RFC 8693 위임 access token에는 act claim이 있는데, 이 claim은 "누가 누구를 대신하는지"를 적는다. ToolHive는 발급한 인가 서버와 상관없이 검증한 모든 JWT에서 act를 읽는다(source pkg/auth/context.go:228).

  • Cedar에서는 principal.claim_act.sub로 읽는다.
  • 감사 로그는 요청마다 위임 체인 전체를 남기고 체인은 10단계까지 둔다. 자세한 내용은 06편이 다룬다.

delegate client로 위임 access token 발급

내장 인가 서버에는 act를 넣은 access token을 직접 발급하는 기능도 있다(source docs/arch/17-token-exchange-delegation.md). 에이전트가 사용자를 대신해 MCP 서버를 부르는 경우를 겨냥한 기능이고, delegate client를 미리 선언해서 켠다.

spec:
  embeddedAuthServer:
    inboundGrants:
      tokenExchange:
        delegateClients:
          - clientId: coding-agent
            clientSecretRef:
              name: coding-agent-secret
              key: client-secret
            audiences: ['https://mcp.example.com']
            scopes: [openid]

delegate client가 사용자의 access token을 subject_token으로 내면 위임 access token을 받는다.

  • sub는 사용자 그대로이고, act.sub에는 교환한 delegate client가 들어간다.
  • scope와 audience는 delegate client 설정과 원래 access token의 교집합으로 줄어든다.
  • 만료는 원래 access token의 남은 시간과 위임 수명 중 짧은 쪽이고, 위임 수명 기본값은 15분이다(source pkg/authserver/config.go:2539).

외부 IdP가 발급한 access token도 교환할 수 있는데, 이때는 trustedIssuers에 issuer를 적고 issuerPolicies로 조건을 붙인다.

token_exchange.exchange_refresh_tokenstoken exchange로 refresh token을 발급한다. 아래에서 설명한다.459행

교환할 때 내장 인가 서버는 restricted 검사를 동의 신호 검사보다 먼저 한다(source pkg/authserver/server/tokenexchange/handler.go:732, 743행). grant_types를 적거나 private_key_jwt를 쓰는 client는 token_exchange 블록을 꼭 적어야 한다(config.go:904). 설정에서 뺀 delegate client는 다음 재시작부터 응답하지 않지만 저장된 행은 남는다(docs/arch/11-auth-server-storage.md "Configured clients across restarts"). 요청한 audience가 client의 audience 밖이면 오류 코드는 invalid_target이다(handler.go:956).

exchange grant는 다음 순서로 연다(source pkg/authserver/server/tokenexchange/refresh_token_handler.go:118). 설계 문서 17번의 "Refresh tokens through token exchange"가 전체를 설명한다.

  1. delegate client가 사용자의 로그인 access token을 subject_token으로 내고, requested_token_type에는 refresh token을 적는다.
  2. subject token의 client_id는 allowed_source_clients에 있어야 한다. 이 경로에서는 delegate client 자신의 access token을 받지 않는다.
  3. subject token의 scope에 offline_access나 offline이 있어야 한다(refresh_token_handler.go:80).
  4. 내장 인가 서버가 subject token의 jti를 grant와 함께 기록하고, 같은 access token으로 두 번째 grant를 열면 token_used로 거부한다(43행).
  5. 받은 refresh token은 grant_type=refresh_token으로 쓰지 못하고, token exchange의 subject_token으로 내서 자식 grant를 받는다.

authorization_details(RFC 9396)는 Go 코드로 registry를 등록했을 때만 처리한다(source config.go:1788). exchange grant 요청이 이 파라미터로 발급 종류와 만료를 적는다.

신뢰 경계

설계 문서는 서명, issuer, audience만으로는 부족하다고 쓴다. 이 셋은 그 access token이 ToolHive용이라는 사실만 증명하고, 어느 OAuth 클라이언트가 대신 행동해도 되는지는 증명하지 않기 때문이다. 이 틈을 두면 confused deputy가 되므로(CWE-863) 내장 인가 서버는 명시적 동의 신호를 요구한다(source pkg/authserver/server/tokenexchange/handler.go:840).

그 밖거부한다.

  • allowedActors에는 ToolHive의 client ID가 아니라 외부 IdP의 client ID를 적는다. 설계 문서는 이것을 가장 흔한 설정 실수로 꼽는다.
  • actorMatcher는 사용자가 고칠 수 있는 claim에 걸면 안 되고, 부서 이름 대신 azp 같은 클라이언트 식별자를 써야 한다.
  • any 모드 delegate client는 어떤 사용자의 ToolHive access token도 교환하는데, 운영자가 시작 설정에서 선언한 클라이언트만 이 권한을 받는다. v0.63.0에서는 restricted로 이 범위를 좁힐 수 있고, 좁히지 않은 client가 있으면 내장 인가 서버는 시작할 때 WARN 로그를 남긴다. 근거는 설계 문서 17번의 "Source policy and subject token audiences"다.
  • access token 교환에는 jti 일회 사용 검사가 없어서 재사용은 수명으로만 제한한다. exchange grant를 열 때만 subject token을 한 번만 받는다(refresh_token_handler.go:102 주석).

upstream IdP 없이 token exchange만 하는 내장 인가 서버를 만들 수도 있는데, 이때 /oauth/authorize는 unsupported_response_type을 준다. allowPrivateKeyJWTRegistration을 켜면 에이전트가 공개 키를 DCR로 등록하고, 그 뒤로는 client secret 없이 서명한 assertion으로 인증한다.

SPIFFE

SPIFFE ID로 OAuth 클라이언트를 인증하는 설계가 있다(source docs/arch/18-spiffe-association-declarations.md). 설정은 spiffeTrustDomains와 inboundGrants.spiffeClientAuth이고, SPIFFE ID 패턴 하나를 client_id 하나에 묶는다. 이렇게 묶인 클라이언트는 token exchange grant만 받는다.

v0.63.0에서도 이 설정은 시작 단계에서 거부된다(source pkg/authserver/config.go:647). 실제 SVID를 검증하는 코드가 아직 연결되지 않았기 때문이다. 설정만 받으면 운영자가 인증이 켜졌다고 오해할 가능성이 있어서 ToolHive는 이 설정을 일부러 막았고, 이 기능은 아직 켤 수 없는 설계로 남아 있다.

v0.63.0은 준비 단계를 더 들여서, 인가 서버용 TLS listener가 8443 포트에 열린다(5장). 그 listener의 middleware는 클라이언트 인증서의 SPIFFE ID를 읽어 요청 context에 싣기만 하고 인증서를 검증하지는 않는다(source pkg/authserver/spiffe/middleware.go:20). bundle source에는 ConfigMap 파일을 읽는 type: file이 생겼다(source cmd/thv-operator/api/v1beta1/mcpexternalauthconfig_types.go:611). 설계 문서는 X.509-SVID 검증이 아직 없고 SPIFFE 인증은 배포할 수 없다고 쓴다(docs/arch/18-spiffe-association-declarations.md).

인가 middleware는 MCP 파서 뒤에서 돌고, authorizer 종류는 둘이다(source docs/authz.md). cedarv1은 proxy 안에서 Cedar policy를 평가하고, httpv1은 외부 PDP에 판정을 맡긴다.

평가 규칙과 policy 예

Cedar는 세 규칙으로 판정한다(docs concepts/cedar-policies).

  1. 맞는 forbid가 하나라도 있으면 거부한다.
  2. 그렇지 않고 맞는 permit가 있으면 허용한다.
  3. 맞는 policy가 없으면 거부한다.

없는 속성을 읽으면 평가 오류가 나고, ToolHive는 평가 오류를 거부로 다룬다. 그래서 annotation이나 선택 claim은 has로 먼저 확인해야 한다.

// 누구나 weather tool을 부른다
permit(principal, action == Action::"call_tool", resource == Tool::"weather");

// IdP 그룹 engineering은 analytics 서버의 모든 tool을 부른다
permit(principal in THVGroup::"engineering",
       action == Action::"call_tool",
       resource in MCP::"analytics-server");

// admin role이 아니면 파괴적 tool을 막는다
forbid(principal, action == Action::"call_tool", resource)
when { resource has destructiveHint && resource.destructiveHint == true &&
       !(principal.claim_roles.contains("admin")) };

// calculator는 add와 subtract만 허용한다
permit(principal, action == Action::"call_tool", resource == Tool::"calculator")
when { resource.arg_operation == "add" || resource.arg_operation == "subtract" };

// 특정 에이전트가 위임받은 요청만 허용한다
permit(principal, action == Action::"call_tool", resource)
when { principal has claim_act && principal.claim_act.sub == "agent-orchestrator" };

설정 파일은 JSON이나 YAML이다(docs reference/authz-policy-reference).

{
  "version": "1.0",
  "type": "cedarv1",
  "cedar": {
    "policies": [
      "permit(principal, action == Action::\"call_tool\", resource == Tool::\"weather\");"
    ],
    "entities_json": "[]",
    "group_claim_name": "",
    "role_claim_name": "",
    "multi_valued_claims": ["scope", "scp"]
  }
}

multi_valued_claims는 scope처럼 문자열이나 배열로 오는 claim을 맞춘다. 이 목록에 넣은 claim은 claimset_<이름> 집합 속성이 생기고, 기존 claim_<이름>는 공백으로 이은 문자열이 된다. 기존 like policy가 더 넓게 맞을 가능성이 있으므로 넣기 전에 policy를 점검해야 한다.

외부 PDP

type: httpv1을 쓰면 proxy가 외부 PDP에 판정을 묻는다(source docs/authz.md). proxy는 <url>/decision에 PORC JSON을 POST하고(source pkg/authz/authorizers/http/http_client.go:24), PDP는 {"allow": true}나 false로 답한다.

PORC 필드값의 형식
principalsub, roles, groups, scopes. 이름 규칙은 claim_mapping이 정한다.
operationmcp:<feature>:<operation>. 예: mcp:tool:call
resourcemrn:mcp:<서버>:<feature>:<id>(porc.go:118)

claim_mapping은 mpe(Manetu PolicyEngine)와 standard 둘 중 하나이고, 판정 한 번의 기본 시간 제한은 30초다. VirtualMCPServer는 cedarv1 MCPAuthzConfig만 받는다(docs guides-k8s/authorization-k8s).

Kubernetes에서는 policy를 세 곳에 둔다. MCPServer 안에 직접 쓰거나, ConfigMap에 두거나, MCPAuthzConfig CR로 공유한다. MCPAuthzConfig는 MCPServer, MCPRemoteProxy, VirtualMCPServer가 함께 참조한다.

11. 통합 예: Okta와 vMCP

Okta로 role 기반 인가

공식 튜토리얼은 GitHub MCP 서버에 Okta 인증과 Cedar 인가를 붙인다(docs integrations/okta). 운영자는 다음 순서로 설정한다.

  1. Okta에 OIDC Web Application을 만든다.
  2. IdP 그룹 mcp-read와 mcp-write를 만든다. Alice는 read에만, Bob은 둘 다에 넣는다.
  3. Okta authorization server에 groups claim을 더하고 access token에도 들어가게 한다.
  4. MCPOIDCConfig에 issuer와 JWKS 주소를 적고, MCPServer는 oidcConfigRef로 audience api://default를 정한다.
  5. Cedar policy를 ConfigMap에 넣고 MCPServer authzConfig로 참조한다.
"permit(principal, action, resource) when { principal.claim_groups.contains(\"mcp-write\") };",
"permit(principal, action == Action::\"call_tool\", resource == Tool::\"list_commits\") when { principal.claim_groups.contains(\"mcp-read\") };"

결과를 보면 Bob의 tools/list에는 모든 tool이 보이고, Alice에게는 읽기 tool 7개만 보인다. Alice가 create_pull_request를 부르면 proxy가 403을 준다. 튜토리얼은 claim_groups.contains를 쓰는데, principal in THVGroup::"mcp-write"로 써도 같게 판정한다.

vMCP의 인증

vMCP는 같은 두 경계를 vmcp 프로세스 하나에서 처리한다(docs guides-vmcp/authentication). VirtualMCPServer는 들어오는 인증을 oidc나 anonymous로 명시해야 한다. vMCP는 Cedar 판정을 HTTP middleware가 아닌 내부 단계에서 하지만, 거부 결과는 단일 서버와 같은 403이다(source docs/authz.md). 나가는 인증은 backend마다 다르게 정한다. vMCP의 내장 인가 서버는 upstream IdP 여럿을 차례로 거치는 설정을 지원한다. VirtualMCPServer의 authServerUpstreamFilter는 뒤따르는 upstream 목록을 줄이는데(source cmd/thv-operator/api/v1beta1/virtualmcpserver_types.go:136), 기준은 첫 upstream이 준 groups claim이다. vMCP 자체 Cedar policy에서 MCP:: entity 이름은 backend 이름이 아니라 vMCP 이름이고, backend 이름은 Backend:: 부모 entity로 온다(10장). incoming OIDC 설정에는 client secret을 담은 환경 변수 이름을 적는 칸이 있다. vmcp 프로세스가 그 변수를 읽어 introspection에 쓰고, 변수가 비어 있으면 시작이 실패한다(source pkg/vmcp/auth/factory/incoming.go:268). 자세한 내용은 08편이 다룬다.

12. 자가 점검 문제

먼저 답을 생각해 보고, 그다음 펼쳐서 확인한다.

Q1. thv run에 OIDC flag 없이 MCP 서버를 띄우고 Cedar policy만 걸었다. 사용자별 인가가 되나?

되지 않는다. OIDC 설정이 없으면 proxy는 local 모드로 돌아서 모든 요청이 현재 OS 사용자 이름을 sub로 갖고, Cedar는 모든 요청을 같은 principal로 본다. 사용자별로 나누려면 OIDC를 켜야 한다.

Q2. --oidc-issuer만 주고 --oidc-audience를 뺐다. 어떤 JWT가 통과하나?

그 issuer가 서명했고 만료되지 않은 JWT는 모두 통과한다. proxy는 audience를 설정했을 때만 aud를 비교하기 때문이다. 같은 IdP가 다른 서비스용으로 발급한 JWT도 들어오므로 audience를 함께 주어야 한다.

Q3. 서명이 틀린 JWT가 왔다. introspection 주소도 설정돼 있다. proxy는 introspection을 부르나?

부르지 않는다. proxy는 access token이 JWT 형식이 아닐 때만 introspection으로 넘긴다. 서명이 틀린 JWT는 형식은 맞기 때문에 proxy는 그 자리에서 401을 준다.

Q4. 내장 인가 서버를 쓰는 MCPServer에서 MCP 서버 컨테이너는 Authorization 헤더로 무엇을 받나?

upstream IdP가 발급한 upstream access token을 받는다. MCP 클라이언트가 보낸 ToolHive JWT는 proxy에서 멈추고, upstreamswap middleware가 tsid로 찾은 값으로 헤더를 바꾼다. disableUpstreamTokenInjection을 켜면 헤더 없이 받는다.

Q5. 내장 인가 서버를 쓰는 proxy를 pod 두 개로 늘렸다. 저장소는 memory다. 어떤 문제가 생기나?

두 pod는 상태를 나누지 못해서, 한 pod가 저장한 진행 중 로그인과 token session을 다른 pod는 모른다. 콜백이나 이후 요청이 다른 pod로 가면 실패할 가능성이 있다. 재시작하면 상태도 모두 사라진다. pod를 늘리려면 Redis 저장소를 써야 한다.

Q6. tools/list 응답에 어떤 tool이 보일지는 무엇이 정하나?

call_tool policy가 정한다. tools/list 요청은 Cedar 판정 없이 MCP 서버로 간다. proxy는 응답을 받은 뒤 tool마다 call_tool을 판정하고 허용된 tool만 남긴다. 그래서 목록용 policy는 따로 쓰지 않는다.

Q7. readOnlyHint가 true인 tool만 허용하는 policy가 있다. 악성 클라이언트가 tools/call 요청에 readOnlyHint: true를 넣으면 통과하나?

통과하지 않는다. proxy는 annotation을 MCP 서버의 tools/list 응답에서만 가져오고 클라이언트 요청 본문의 값은 쓰지 않는다. MCP 서버가 준 값이 true가 아니거나 값이 없으면 permit 조건은 거짓이 되고, 맞는 permit가 없으므로 proxy는 거부한다.

Q8. 외부 IdP의 access token을 내장 인가 서버에서 교환하려 한다. trustedIssuers에 issuer를 넣고 audience도 맞췄다. 이것으로 교환이 되나?

되지 않는다. 서명과 audience는 그 access token이 ToolHive용이라는 사실만 증명하고 어느 클라이언트가 대신 행동해도 되는지는 증명하지 않아서, 동의 신호가 따로 있어야 한다. allowedActors나 actorMatcher가 그 신호이고, allowMayAct를 켠 issuer에서는 may_act claim도 신호가 된다. allowedDelegateClients도 꼭 적어야 한다.

Q9. fastmcp OAuthProxy와 ToolHive 내장 인가 서버의 공통점과 차이를 하나씩 말하라.

공통점은 구조다. 둘 다 MCP 클라이언트에게는 인가 서버로 보이고 upstream IdP에게는 OAuth 클라이언트 하나로 보이며, IdP 쪽 access token은 서버에 두고 자기 JWT를 준다. 차이는 위치다. ToolHive는 이 일을 MCP 서버 밖의 proxy에서 하기 때문에 MCP 서버 코드에 OAuth 처리가 없어도 되고, MCP 서버는 헤더로 upstream access token을 받는다.

Q10. AWS STS 설정에서 사용자의 groups claim 값이 숫자 하나다. 어떻게 되나?

claim 규칙만 있다면 요청이 403으로 실패한다. role claim은 문자열이나 문자열 목록이어야 하는데 숫자는 지원하지 않는 모양이다. role mapper는 이때 fallback을 쓰지 않고 거부한다. 다만 CEL matcher 규칙이 맞으면 그 규칙의 IAM role을 쓴다. fallbackRoleArn은 오류 없이 맞는 규칙이 하나도 없을 때 쓴다.

공식 문서와 소스가 다르거나 문서에 없는 것

  • 동의 화면과 사전 승인 클라이언트는 공식 문서 사이트에 없다(2026-11-07 확인). 설계 문서 11번과 handlers/authorize.go, consent.go만 근거다. 공식 문서 사이트는 refresh grant 거부와 ID token 만료 갱신은 설명하고, DCR 상한과 속도 제한은 필드 이름 없이 언급한다.
  • MCPOIDCConfig kubernetesServiceAccount의 serviceAccount, namespace가 검증에 쓰이는 코드를 찾지 못했다. resolver.go는 v0.53.0과 같다. 공식 문서의 "특정 service account만 허용" 설명은 시험하지 않았다.

  • MCP resource URI는 v0.63.0 코드에서도 바꾸지 않고 entity ID가 된다. 공식 문서 사이트는 2026-11-07 기준으로 변환 규칙도 정규형 검사도 적지 않는다.

  • introspection 전환 조건은 공식 문서보다 코드가 좁다. 이 문서는 코드를 따랐다.
  • upstream access token이 opaque일 때 공식 문서 사이트는 거부한다고 쓰지만(2026-11-07 확인), 코드(cedar/core.go:715)와 docs/authz.md는 요청 JWT의 claim으로 돌아간다고 쓰므로 이 문서는 코드를 따랐다.

  • 동의 화면의 upstream 표시 이름과 delegate client의 추가 설정(9장)은 RunConfig에만 있고 v0.63.0 CRD와 공식 문서 사이트에는 없다.
