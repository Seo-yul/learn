vMCP와 optimizer

ToolHive 학습 08편 · 2026-10-14 작성

이 문서는 여러 MCP 서버를 endpoint 하나로 묶는 vMCP를 다룬다. backend 발견, 집계, 요청 처리, 세션을 차례로 보고, composite tool과 optimizer, code mode도 소스 기준으로 설명한다. 인증의 세부 흐름은 05편에서 다룬다.

기준 버전은 ToolHive v0.63.0(2026-11-06)이다. 2026-10-14에 v0.53.0 기준으로 썼다가 2026-11-07에 v0.63.0 기준으로 갱신했고, 공식 문서도 2026-11-07 상태를 읽었다. ToolHive는 자주 바뀌므로 실제로 쓰기 전에 공식 문서를 다시 확인해야 한다.

한 문장 요약

vMCP는 MCPGroup에 속한 MCP 서버를 backend로 모아 endpoint 하나로 내놓고, 이름 충돌을 정리한 라우팅 테이블로 호출을 backend에 보낸다. optimizer를 켜면 tool 목록 대신 find_tool과 call_tool 두 개만 보여 준다.

v0.63.0 갱신 요약
  • 요청 파이프라인에 loopback Host 검사와 세션 소유자 검사가 들어가서, 다른 identity가 세션 ID를 쓰면 404를 받는다(6장, 7장).
  • Cedar 판정이 tool의 backend ID를 함께 받게 되어 backend 단위 permit과 forbid를 쓸 수 있다(6장).
  • vMCP 안의 decorator가 돌려주는 URL elicitation 응답을 Modern 클라이언트에게 input_required로 주고, 선언하지 않은 capability의 -32021은 HTTP 400으로 보낸다(5장, 8장).
  • 클라이언트가 끝낸 세션은 바로 닫고, POST가 TTL 동안 없는 세션의 pod 복사본도 거둔다(7장).
  • elicitation의 skip_remaining이 남은 step을 건너뛰고 workflow를 성공으로 끝낸다(8장).
  • 내장 인가 서버에 그룹 기반 upstream filter와 TLS listener가 생겼다(6장).
  • backend의 phase가 변해도 vMCP pod의 rollout이 일어나지 않고, resource URI의 template 대조에는 2,048바이트 상한이 생겼다(5장, 7장, 11장).

1. vMCP가 필요한 이유와 위치

MCP 서버가 늘면 MCP 클라이언트가 연결할 endpoint도 늘어난다. 서버마다 인증 설정과 tool 목록이 따로 있고, 이름이 같은 tool이 서로 다른 서버에 있을 가능성도 있다.

vMCP는 이 문제를 줄이는 ToolHive 구성 요소다. 그룹 하나에 속한 MCP 서버를 backend로 묶어 주므로 MCP 클라이언트는 vMCP의 endpoint 하나에만 연결하면 된다(docs concepts/vmcp). 공식 문서는 vMCP를 ToolHive 플랫폼의 gateway 계층이라고 부른다(docs guides-vmcp/index).

vMCP는 두 연결 사이에 서 있어서 MCP 클라이언트에게는 MCP 서버이고 backend에게는 MCP 클라이언트다(source docs/arch/10-virtual-mcp-architecture.md). 그래서 두 연결을 따로 관리하고, 인증 방식과 MCP 개정판도 연결마다 따로 정해진다.

vMCP가 하는 일은 다음과 같다.

  • 집계: backend의 capability를 모아 목록 하나로 합친다.
  • 이름 충돌 처리: 같은 이름의 tool을 설정한 전략으로 정리한다.
  • 두 경계 인증: 들어오는 인증과 나가는 인증을 따로 처리한다.
  • composite tool: 여러 backend tool 호출을 workflow 하나로 묶는다.
  • optimizer와 code mode: LLM 컨텍스트에 들어가는 tool 정의를 줄인다.

backend는 세 kind 중 하나로 정의하는데, kind마다 vMCP가 연결하는 곳이 다르다(docs guides-vmcp/backend-discovery).

kind정의하는 것vMCP가 연결하는 곳
MCPServerToolHive가 실행하는 MCP 서버 컨테이너그 서버 앞 proxy의 Service URL
MCPRemoteProxy원격 MCP 서버 앞에 둔 proxy pod그 proxy의 Service URL
MCPServerEntry원격 endpoint 선언. pod를 만들지 않는다.원격 MCP 서버(remoteUrl)

vMCP가 늘 필요한 것은 아니다. 공식 문서는 그런 예로 MCP 서버 하나만 쓰는 경우와 단계가 하나뿐인 작업을 든다(docs concepts/vmcp). proxy와 MCP 서버의 관계는 02편에서 다룬다.

2. backend 발견

vMCP는 backend 목록을 만든 뒤에 집계를 시작하는데, 목록을 만드는 방식은 동적 발견과 정적 목록 두 가지다. Kubernetes에서는 spec.outgoingAuth.source 필드가 방식을 정하고 기본값은 discovered다(source cmd/thv-operator/api/v1beta1/virtualmcpserver_types.go:240).

필드 이름이 인증을 가리키는 데는 이유가 있는데, 공식 문서는 인증 설정과 backend 출처가 묶여 있다고 설명한다. 동적 발견은 backend가 참조하는 MCPExternalAuthConfig를 찾아 쓰고, 정적 목록은 backend마다 MCPExternalAuthConfig 참조를 outgoingAuth.backends에 적는다(docs guides-vmcp/backend-discovery).

2.1 동적 발견의 순서

동적 발견에서 vMCP는 다음 순서로 backend를 찾는다(docs guides-vmcp/backend-discovery).

  1. 참조한 MCPGroup이 있는지 확인한다.
  2. 그룹에 속한 MCPServer, MCPRemoteProxy, MCPServerEntry를 조회한다(source pkg/vmcp/workloads/k8s.go:87).
  3. backend마다 URL, transport, 인증 설정을 꺼낸다.
  4. backend마다 capability를 묻는데, Legacy backend는 initialize 핸드셰이크를 먼저 거친다.
  5. 결과를 VirtualMCPServer의 status에 기록한다.

operator는 MCPGroup이 없거나 Ready가 아니면 reconcile을 멈추고(source cmd/thv-operator/controllers/virtualmcpserver_controller.go:1111), 공식 문서는 MCPServersChecked 조건이 True여야 한다고 적는다(docs guides-vmcp/configuration). vMCP 프로세스는 다르게 동작해서, Kubernetes에서 그룹이 없으면 backend 0개로 시작한다(source pkg/vmcp/cli/serve.go:808).

backend 변경의 반영 방식은 문서와 소스가 다르다. 공식 문서는 동적 발견도 그룹 변경을 자동으로 반영하지 않는다고 적고, 그래서 vMCP pod를 재시작하라고 안내한다(docs guides-vmcp/backend-discovery, 2026-11-07 확인).

v0.63.0 소스는 다르게 동작한다. source: discovered이면 vMCP가 pod 안에서 informer로 그룹을 지켜보다가(source pkg/vmcp/cli/serve.go:230), backend가 추가되거나 빠지면 backend 목록을 고친다(source pkg/vmcp/k8s/manager.go:52). 운영자는 실제 클러스터에서 이 동작을 확인해야 한다.

2.2 정적 목록

정적 목록은 backend의 이름, URL, transport를 설정에 직접 적는 방식이고, transport는 sse나 streamable-http만 받는다(docs guides-vmcp/backend-discovery). 이 방식에서 vMCP pod는 backend를 찾으려고 Kubernetes API를 부르지 않는다.

apiVersion: toolhive.stacklok.dev/v1beta1
kind: VirtualMCPServer
metadata:
  name: my-vmcp
  namespace: toolhive-system
spec:
  groupRef:
    name: my-group          # inline에서도 필수. status 보고에 쓴다
  config:
    backends:
      - name: github-mcp
        url: http://github-mcp.toolhive-system.svc.cluster.local:8080
        transport: sse
      - name: fetch-mcp
        url: http://fetch-mcp.toolhive-system.svc.cluster.local:8080
        transport: streamable-http
  incomingAuth:
    type: anonymous
  outgoingAuth:
    source: inline
    backends:
      github-mcp:
        type: externalAuthConfigRef
        externalAuthConfigRef:
          name: github-token-config

2.3 로컬 CLI의 발견

로컬 CLI(thv vmcp serve)도 같은 두 방식을 쓴다. 설정 파일에 backends가 있으면 정적 목록을 쓰고, 없으면 로컬 ToolHive 그룹에서 실행 중인 workload를 찾는다(source pkg/vmcp/cli/serve.go:750). 그룹은 04편에서 다룬다.

3. health check와 장애 처리

3.1 health check

vMCP의 health monitor는 backend마다 health check를 주기적으로 보낸다. health check는 ListCapabilities 호출이라서 연결부터 capability 조회까지 MCP 통신 전체를 거치고(source pkg/vmcp/health/checker.go:97), Legacy backend면 initialize 핸드셰이크도 포함한다. 응답이 5초를 넘으면 vMCP는 그 backend를 degraded로 본다(source pkg/vmcp/health/monitor.go:227). health check는 MCP를 POST로만 말하고 standalone GET stream은 열지 않으므로, 세션 없는 GET을 거절하는 backend도 healthy로 본다(source pkg/vmcp/client/getreject_realbackend_test.go:79).

health 상태판정 조건CRD status 값
healthyhealth check가 5초 안에 성공했다.ready
degraded성공했으나 5초를 넘었다. 또는 최근에 회복했다.degraded
unhealthy응답 없음이나 timeout이 unhealthyThreshold번 이어졌다.unavailable
unauthenticated401이나 403을 받았다. 나가는 인증 설정은 없다.unauthenticated

health check는 사용자 access token 없이 나간다. 그래서 나가는 인증이 있는 backend가 401이나 403을 주면 vMCP는 healthy로 보는데, 인증 계층이 응답했다는 사실을 연결 성공으로 해석하기 때문이다(source pkg/vmcp/health/checker.go:76). unauthenticated는 나가는 인증 설정이 빠졌다는 뜻이고, 이 상태의 backend는 집계에서 빠진다(docs guides-vmcp/backend-discovery). vMCP의 /health는 backend 상태와 관계없이 200을 주고, backend별 상태는 /api/backends/health가 준다(source pkg/vmcp/server/server.go:664). backend의 health나 phase가 바뀌어도 operator는 vMCP pod를 다시 띄우지 않는다(11.2절).

3.2 circuit breaker와 부분 실패

공식 문서는 circuit breaker를 요청 경로의 장치로 설명한다. 실패가 이어지는 backend로 가는 요청을 timeout 전에 거절한다는 설명이고(docs guides-vmcp/failure-handling), 2026-11-07에도 같다. v0.63.0 코드의 동작은 이와 다르다. circuit breaker는 health check 실패만 세고(source pkg/vmcp/health/status.go:326), 열린 동안 vMCP는 그 backend의 health check를 건너뛴다(source pkg/vmcp/health/monitor.go:510). 요청은 간접적으로만 영향을 받는데, backend가 unhealthy가 되면 집계에서 빠지기 때문이다.

circuit breaker의 상태는 세 가지이고, health monitor는 다음 순서로 상태를 바꾼다(source pkg/vmcp/health/circuit_breaker.go:137).

  1. closed: health check를 보내면서 연속 실패를 센다.
  2. open: 연속 실패가 failureThreshold에 이르면 열린다. timeout 동안 health check를 보내지 않는다.
  3. half-open: timeout이 지나면 시험 health check 하나만 보낸다. 성공하면 closed, 실패하면 다시 open이 된다.

partialFailureMode도 문서와 코드가 다르다. 공식 문서는 fail이면 요청 전체가 실패하고 best_effort면 살아 있는 backend의 결과만 준다고 설명한다. v0.63.0 코드는 이 값을 설정 검사에만 쓰고(source pkg/vmcp/config/validator.go:525), 집계는 값과 관계없이 실패한 backend를 건너뛴다(source pkg/vmcp/aggregator/default_aggregator.go:185). 집계가 오류로 끝나는 것은 모든 backend가 실패할 때뿐이다.

3.3 세션을 열 때의 backend 선택

vMCP는 health 상태를 두 곳에서 다른 기준으로 쓴다(source pkg/vmcp/health/policy.go).

  • 세션을 열 때: unhealthy와 unauthenticated backend만 건너뛰고, degraded와 unknown backend는 연결을 시도한다(policy.go:73).
  • 집계할 때: healthy와 degraded backend만 넣고, unknown backend는 빠진다(policy.go:18, core_vmcp.go:628).

세션을 열 때 unknown을 시도하는 이유는 vMCP가 첫 health check가 끝나기 전에도 세션을 열기 때문이다. 이때 unknown을 건너뛰면 세션이 backend 0개에 연결된다(source pkg/vmcp/health/policy.go:73).

회복한 backend의 처리는 두 문서가 다르게 적는다. 장애 처리 문서는 기존 세션에 붙지 않으니 다시 연결하라고 적는다(2026-11-07 확인). 아키텍처 문서는 health 변화가 생기면 기존 세션의 tool 목록을 다시 만든다고 적는데, optimizer를 끈 경우와 tool에만 해당한다(source docs/arch/10-virtual-mcp-architecture.md). 두 동작의 관계는 이 문서에서 확인하지 못했다.

4. 집계 파이프라인과 이름 충돌

4.1 파이프라인

aggregator는 backend 목록을 받아 다음 순서로 집계한다(source pkg/vmcp/aggregator/aggregator.go:38).

  1. 발견: health 상태로 거른 backend 목록을 받는다.
  2. 질의: backend마다 capability를 묻는데, 동시에 최대 10개까지 묻는다(source pkg/vmcp/aggregator/default_aggregator.go:171). 실패한 backend는 로그만 남기고 건너뛴다.
  3. override 적용: backend별 이름, 설명 변경을 먼저 적용한다(source pkg/vmcp/aggregator/default_aggregator.go:123).
  4. 충돌 처리: 설정한 전략으로 tool 이름을 정한다.
  5. 병합: 라우팅 테이블을 만들고, filter 설정으로 노출 목록을 정한다(source pkg/vmcp/aggregator/default_aggregator.go:705).

집계 결과는 identity별 캐시에 30초 동안 남는다(source pkg/vmcp/server/server.go:97). 캐시 key가 identity, 전달 header, backend 집합을 합친 해시라서 한 호출자의 결과를 다른 호출자에게 주지 않는다. 캐시 항목은 최대 1,024개이고(source pkg/vmcp/aggregator/caching_aggregator.go:25), 이 문서는 이 캐시를 capability 캐시라고 부른다.

4.2 충돌 처리 전략 세 가지

전략은 spec.config.aggregation.conflictResolution으로 정하고 기본값은 prefix다(source pkg/vmcp/config/config.go:503).

전략동작주의할 점
prefix (기본)모든 tool 이름 앞에 backend 이름을 붙인다. 기본 형식은 {workload}_다.충돌이 없는 tool도 이름이 바뀐다.
prioritypriorityOrder에서 앞선 backend의 tool만 남긴다.목록에 없는 backend가 충돌에 끼면 후보를 모두 뺀다.
manual충돌한 tool마다 사용자가 이름을 정한다.하나라도 빠지면 집계가 오류로 끝난다.
# prefix: github의 create_issue는 github_create_issue로 노출된다
spec:
  config:
    aggregation:
      conflictResolution: prefix
      conflictResolutionConfig:
        prefixFormat: "{workload}_"     # "{workload}." 이면 github.create_issue
---
# priority: github과 jira가 모두 create_issue를 내면 github 것만 남는다
spec:
  config:
    aggregation:
      conflictResolution: priority
      conflictResolutionConfig:
        priorityOrder: ["github", "jira", "slack"]
---
# manual: 충돌한 tool마다 override가 있어야 한다
spec:
  config:
    aggregation:
      conflictResolution: manual
      tools:
        - workload: github
          overrides:
            create_issue:
              name: gh_create_issue
        - workload: jira
          overrides:
            create_issue:
              name: jira_ticket

priority 전략의 규칙은 엄격하다. 충돌한 backend 중 하나라도 priorityOrder에 없으면 vMCP는 그 이름의 후보를 모두 빼고 ERROR 로그를 남긴다(source pkg/vmcp/aggregator/priority_resolver.go:92). 이유는 Cedar 정책이 노출 이름으로 tool을 가리킨다는 데 있다. 이름을 목록 안의 backend에 넘기면 정책이 다른 backend의 tool에 걸릴 가능성이 있다(docs guides-vmcp/tool-aggregation).

manual 전략은 override가 빠진 충돌을 오류로 돌려주고(source pkg/vmcp/aggregator/manual_resolver.go:60), 공식 문서는 이때 vMCP가 시작하지 않는다고 적는다.

4.3 filter와 override

충돌 처리와 별도로 tool의 노출을 조정하는 설정이 있다(docs guides-vmcp/tool-aggregation).

  • tools[].filter: 적은 tool만 노출한다.
  • tools[].excludeAll: 그 backend의 tool을 모두 숨긴다.
  • excludeAllTools: 모든 backend의 tool을 숨긴다. composite tool만 노출할 때 쓴다.
  • defaultToolVisibility: deny: tools에 적지 않은 backend의 tool을 숨긴다. 기본값은 allow처럼 동작한다(source pkg/vmcp/config/config.go:549).
  • tools[].overrides: tool 이름, 설명, annotation을 바꾼다.

이 설정은 모두 노출만 바꾸고, 숨긴 tool도 라우팅 테이블에 남는다. 그래서 composite tool step이 숨긴 tool을 호출하면 vMCP는 그 호출을 backend로 보내지만, MCP 클라이언트가 숨긴 tool을 직접 부르면 unknown-tool 오류를 받는다(docs guides-vmcp/tool-aggregation). resource와 prompt에는 영향을 주지 않고, 호출자별 접근 제어는 Cedar 정책이 맡는다.

spec:
  config:
    aggregation:
      defaultToolVisibility: deny     # 목록에 없는 backend의 tool은 숨긴다
      tools:
        - workload: github
          filter: ["create_issue", "list_issues"]
          overrides:
            create_issue:
              description: "엔지니어링 팀 저장소에 GitHub 이슈를 만든다"
        - workload: jira
          excludeAll: true            # composite tool에서만 쓴다

4.4 resource와 prompt의 처리

resource와 prompt는 tool 전략과 따로 처리한다(source pkg/vmcp/aggregator/capability_conflicts.go).

  • prompt: 기본으로 모든 prompt 이름 앞에 backend 접두사를 붙이고, priority 전략이면 priorityOrder에 있는 backend만 원래 이름을 쓴다.
  • resource URI와 resource template: 이름을 바꾸지 않는다. 같은 URI가 여럿이면 backend ID 정렬에서 앞선 backend 하나만 남긴다.
  • 잘못된 항목: resource URI가 URL로 파싱되지 않으면 vMCP는 그 resource 하나만 버리고, 크기 한도를 넘는 resource template도 그 하나만 버린다. 다른 capability는 그대로 넣는다(source pkg/vmcp/client/client.go:1458).
  • manual 전략: tool에만 적용한다.

4.5 이름 되돌리기

MCP 클라이언트가 github_create_issue를 부르면 vMCP는 라우팅 테이블에서 backend를 찾고, backend에는 원래 이름 create_issue로 호출을 보낸다(source docs/arch/10-virtual-mcp-architecture.md). 그래서 backend는 이름이 바뀐 사실을 모른다.

5. 제공하는 capability와 MCP 개정판

5.1 capability

vMCP는 tool 말고도 여러 capability를 제공한다. 모든 capability가 core를 거치므로 tools/list를 거르는 core 인가 판정이 읽기와 호출에도 똑같이 적용된다(source docs/arch/10-virtual-mcp-architecture.md).

capabilityMCP 메서드제공 수준
tooltools/list, tools/call제공한다. backend의 list_changed 알림은 추가와 삭제를 모두 전한다.
resourceresources/list, resources/read제공한다. list_changed는 추가만 전한다.
resource templateresources/templates/list제공한다. 읽기는 resource 경로로 간다.
promptprompts/list, prompts/get제공한다. list_changed는 추가만 전한다.
completioncompletion/complete제공한다. 경로를 못 찾으면 빈 결과를 준다.
구독resources/subscribe, subscriptions/listen수락 응답만 준다. 변경 알림은 보내지 않는다.

list_changed 전달은 Legacy backend에만 적용한다. vMCP는 Legacy backend와 세션마다 지속 연결을 열고, 이 연결로 backend가 보내는 알림을 받는다.

resource URI에는 길이 상한이 있어서 2,048바이트를 넘는 URI는 resource template과 대조하지 않는다. 이때 읽기와 구독은 not found, completion은 빈 결과를 받는다. 정확히 일치하는 resource나 template 문자열은 길이와 관계없이 찾는다(source pkg/vmcp/types.go:682).

5.2 MCP 개정판 분류

MCP 명세는 2026-07-28 판에서 세션과 initialize 핸드셰이크를 없앴다. 소스는 2025-11-25 판을 Legacy, 2026-07-28 판을 Modern이라고 부르고, vMCP는 두 판을 동시에 지원한다(source docs/arch/10-virtual-mcp-architecture.md). transport의 세부 내용은 02편에서 다룬다.

클라이언트 쪽은 요청마다 판을 분류하고, backend 쪽은 backend마다 한 번 확인해서 결과를 캐시에 둔다. vMCP는 다음 순서로 backend의 판을 정한다(source pkg/vmcp/client/client.go:1192).

  1. transport가 SSE인 backend는 바로 Legacy로 정한다.
  2. 나머지 backend에는 server/discover를 POST로 보낸다.
  3. 응답의 supportedVersions에 2026-07-28이 정확히 있으면 Modern으로 정한다.
  4. 401, 403, 5xx, timeout이면 판단 근거가 없으므로 이번 호출만 Legacy로 처리하고 캐시에 두지 않는다.
  5. 그 밖의 응답이면 Legacy로 정한다.

캐시가 틀리면 vMCP가 스스로 고친다. 판이 맞지 않아 실패한 호출은 다시 확인한 뒤 재시도하는데, 이미 실행됐을 가능성이 있는 요청은 다시 보내지 않는다. 확인한 판은 VirtualMCPServer의 status.discoveredBackends[].mcpRevision에 나온다.

5.3 Modern 클라이언트를 받는 조건

vMCP는 Modern 클라이언트를 조건부로 받는다. 켜진 기능 중 Modern 경로가 처리하지 못하는 기능이 있으면 Modern을 끄는데, v0.63.0에서 이 목록에 든 기능은 optimizer 하나다(source pkg/vmcp/server/modern_gate.go:49).

  • Modern을 끄면 server/discover 응답에서 Modern 판이 빠지고, go-sdk 클라이언트는 이 응답을 보고 Legacy로 연결한다.
  • 그 밖의 Modern 요청은 HTTP 400과 -32022 오류를 받는다.
  • Legacy 요청은 영향을 받지 않는다.

backend가 호출 도중에 보내는 elicitation과 sampling은 Modern 연결로 전달하지 않는다. 예외는 vMCP 자신이 만드는 URL elicitation 응답 하나이고, 이 한계는 8.3절의 MRTR과 함께 설명한다.

6. 요청 처리 파이프라인과 두 경계 인증

6.1 middleware 순서

MCP 요청 하나는 HTTP middleware를 거쳐 core에 닿는다. 순서는 Server.Handler 함수가 정하고(source pkg/vmcp/server/server.go:629), 실행 순서는 그 함수 안의 주석에 적혀 있다(server.go:703). vMCP는 MCP 요청을 다음 순서로 처리한다.

  1. recovery: panic을 잡아 HTTP 500을 돌려준다.
  2. body 크기 제한: 너무 큰 요청 body를 413으로 거절한다.
  3. WriteTimeout: backend 작업 중에는 쓰기 제한 시간을 멈추고, SSE 연결은 길게 둔다.
  4. Accept header 검사: Accept: text/event-stream이 없는 GET을 거절한다.
  5. header 전달 준비: passthroughHeaders에 적은 header를 backend 호출용으로 담아 둔다.
  6. audit: 설정한 경우 결과를 기록하고, 인증 실패 401도 기록한다.
  7. 들어오는 인증: 자격 증명을 확인하고 MCP 메시지를 파싱한다.
  8. telemetry: 설정한 경우 OpenTelemetry 계측을 붙인다.
  9. loopback Host 검사: loopback 연결의 Host header가 loopback 이름이 아니면 403을 줘서 DNS rebinding을 막는다(source pkg/vmcp/server/loopback_host_guard.go:66).
  10. 개정판 분류: Modern 요청은 core로 바로 보내고 Legacy 요청은 MCP SDK로 보낸다.
  11. 세션 소유자 검사: Legacy 요청에만 동작한다. 세션을 만든 identity가 아닌 호출자가 그 세션 ID를 쓰면 404를 준다(source pkg/vmcp/server/session_ownership.go:47).
  12. 인가 gate: Cedar 정책이 있을 때 Legacy 요청에 동작하고, 거부한 호출을 HTTP 403으로 끝낸다. 소유자 검사가 먼저이므로 남의 세션에서는 403 대신 404를 받는다. Modern 요청은 core로 가는 dispatch가 같은 판정을 한다(source pkg/vmcp/server/modern_dispatch.go:509).
  13. core: core 인가 판정, 라우팅, 나가는 인증, backend 호출을 처리한다.

아키텍처 문서의 middleware 표에는 discovery와 authorization 행이 아직 있는데, 표 아래 주석은 이 행들이 Serve 경로에서 독립 middleware가 아니라고 적는다. v0.63.0 코드 주석은 세 계층을 지웠다고 적고(source pkg/vmcp/server/server.go:721), 그 세 계층은 authz, annotation-enrichment, discovery다. 이 문서는 코드를 따랐다. rate limit은 middleware가 아니라 core를 감싸는 decorator이고 tools/call만 센다. 관측과 사용 제한은 06편에서 다룬다.

6.2 core 인가 판정

core 인가 판정은 Cedar 판정 하나를 목록과 호출에 함께 쓴다(source pkg/vmcp/core/core_checks.go). 그래서 목록에는 보이는데 호출은 막히는 어긋남이 생기지 않는다.

  • 인가 gate는 tools/call, resources/read, prompts/get을 미리 판정한다(source pkg/vmcp/server/call_gate.go).
  • 거부 응답은 HTTP 403과 JSON-RPC 코드 403이다. 메시지는 대상 이름을 밝히지 않는다.
  • 기본 거부 정책이면 정책이 거른 tool과 없는 tool이 같은 403을 받으므로, 거부 응답으로 tool의 존재를 알아낼 수 없다.
  • authorizer가 오류를 내면 거부로 처리한다.
  • Cedar 판정은 tool의 backend ID를 함께 받으므로, 정책은 Backend::"<id>"로 backend 단위 permit이나 forbid를 쓸 수 있다(source pkg/vmcp/core/admission.go:165).
  • composite tool은 backend가 없다. backend 단위 permit은 composite tool을 허용하지 않고 backend 단위 forbid도 막지 않는다. composite tool의 step은 core 인가 판정을 따로 받지 않기 때문이다(source docs/arch/10-virtual-mcp-architecture.md).
  • 정규형이 아닌 resource URI는 정책을 보기 전에 거부한다(source pkg/vmcp/core/admission.go:230).

6.3 두 경계 인증

vMCP는 인증을 두 경계에서 따로 처리한다. 들어오는 인증은 MCP 클라이언트를 확인하는 단계로 OIDC나 anonymous 방식을 쓰고, 나가는 인증은 vMCP가 backend에 자격 증명을 내미는 방식이다. 나가는 인증의 전략은 unauthenticated, header_injection, token_exchange, upstream_inject, aws_sts, xaa이고(source pkg/vmcp/auth/types/types.go:26), obo는 오픈소스 빌드에서 오류만 돌려준다. vMCP는 교환한 access token을 캐시에 둔다(source pkg/vmcp/cache). 공식 문서는 IdP에서 사용자를 막으면 모든 backend 접근이 끊긴다고 설명한다(docs concepts/vmcp). 전략별 흐름과 내장 인가 서버는 05편에서 다룬다.

v0.63.0에서 두 경계에 더해진 것은 세 가지다. 첫째, 들어오는 OIDC 설정이 CA ConfigMap을 참조하면 operator가 그 참조를 검사하고 결과를 CABundleRefValidated 조건에 적는다(source cmd/thv-operator/controllers/virtualmcpserver_cabundle.go:30). 둘째, spec.authServerUpstreamFilter는 내장 인가 서버의 upstream provider가 둘 이상일 때 쓰는 설정으로, 첫 provider가 준 그룹 claim으로 사용자가 거칠 나머지 provider를 줄인다. 첫 provider는 늘 거친다. 이 filter는 로그인에서 모을 자격 증명만 정하고, backend와 tool의 인가는 Cedar가 맡는다(source cmd/thv-operator/api/v1beta1/virtualmcpserver_types.go:136). 셋째, 내장 인가 서버의 TLS listener를 켜면 vMCP가 그 listener도 함께 시작하는데, listener 포트가 vMCP 포트와 겹치면 시작을 거부한다(source pkg/vmcp/cli/serve.go:689).

7. 세션과 확장 한계

7.1 vMCP 세션

Legacy 클라이언트는 initialize로 vMCP 세션을 연다. 세션을 등록할 때 vMCP는 호출자 identity로 capability를 집계하고, Legacy backend와는 세션마다 지속 연결을 연다(source docs/arch/10-virtual-mcp-architecture.md). Modern 클라이언트는 세션이 없고, vMCP도 Modern 요청의 상태를 저장하지 않는다.

세션은 만든 identity의 iss와 sub에 묶여서, 다른 identity가 그 세션 ID로 요청하면 vMCP는 404를 준다. 소유자는 저장소에서 읽으므로 어느 replica에서도 같은 판정이 나온다(source pkg/vmcp/server/session_ownership.go:47).

세션 캐시가 차면 vMCP는 가장 오래 쓰지 않은 세션을 내보내면서 그 세션의 backend 연결을 닫고, 그 세션에서 처리 중이던 요청은 실패한다(source docs/arch/13-vmcp-scalability.md). Redis 세션 저장소가 있으면 vMCP는 같은 세션 ID의 다음 요청에서 세션을 다시 만드는데, 이때 저장된 메타데이터로 세션을 다시 만드는 함수가 RestoreSession이다. 공식 문서는 Redis가 없으면 내보낸 세션을 잃는다고 적는다(docs guides-vmcp/scaling-and-performance, 2026-11-07 확인).

세션이 끝나는 길은 두 가지가 더 있다. 클라이언트가 DELETE로 세션을 끝내면 vMCP는 저장소의 기록을 지우고 그 pod의 세션 항목도 바로 지우므로, backend 연결이 LRU 내보내기를 기다리지 않고 닫힌다(source pkg/vmcp/server/sessionmanager/session_manager.go:594). 또 transport는 POST가 세션 TTL 동안 없는 세션의 pod 복사본을 거두는데, 열어 둔 GET stream만으로는 활동으로 치지 않는다. 저장소의 기록은 그대로 두므로 TTL 안에 돌아온 클라이언트는 세션을 다시 받는다(source pkg/vmcp/server/server.go:648).

7.3 Redis 세션 저장소

replica가 둘 이상이면 Redis 세션 저장소가 필요하다. 세션 메타데이터가 Redis에 있으면 어느 pod든 세션을 다시 만들지만, Redis가 없으면 다른 replica로 간 요청은 실패한다(docs guides-vmcp/scaling-and-performance). operator는 이때 SessionStorageWarning 조건을 걸고 replica 수는 그대로 적용한다(source cmd/thv-operator/controllers/virtualmcpserver_controller.go:659).

spec:
  replicas: 3
  sessionStorage:
    provider: redis
    address: redis.toolhive-system.svc.cluster.local:6379
    db: 0
    keyPrefix: vmcp-sessions
    passwordRef:
      name: redis-password
      key: password
  • 만료: vMCP는 세션을 읽을 때마다 GETEX로 만료 시간을 다시 건다(source pkg/transport/session/storage_redis.go:160). TTL 안에 요청이 오면 세션은 계속 유지되고 최대 수명은 없다.
  • identity 바인딩: 세션 메타데이터에 iss와 sub를 이은 값이 평문으로 들어간다(source pkg/vmcp/session/binding/binding.go:23). 자격 증명은 아니지만 개인을 식별하는 정보다.
  • 보호: 운영자는 Redis에 ACL이나 비밀번호를 걸고, NetworkPolicy로 접근 경로도 좁혀야 한다.
  • TLS: spec.sessionStorage.tls를 적지 않으면 vMCP는 Redis 연결을 암호화하지 않는다. operator 전체의 기본 Redis는 Helm 값 operator.defaultRedis.tls로 TLS를 켜지만, 명시한 sessionStorage는 이 기본값을 물려받지 않는다(source docs/arch/13-vmcp-scalability.md).
  • 크기: 공식 문서는 세션 하나를 10~50KB로 어림한다. fleet 전체 세션 상한은 replica 수 곱하기 1,000이다.

7.4 sessionAffinity와 file descriptor

VirtualMCPServer Service의 sessionAffinity 기본값은 ClientIP다(source cmd/thv-operator/api/v1beta1/virtualmcpserver_types.go:73). 클라이언트가 NAT 뒤에 있으면 모든 요청의 출발 IP가 같아서 모든 세션이 pod 하나로 몰린다(docs guides-vmcp/scaling-and-performance). 상태가 없는 backend만 쓰면 None이 낫고, 상태가 있는 backend는 수직 확장을 먼저 고려해야 한다.

호출 도중 elicitation과 sampling을 쓰는 구성도 affinity가 필요하다. 클라이언트로 가는 요청은 그 클라이언트의 SSE stream을 가진 replica만 전달하기 때문이다(source docs/arch/10-virtual-mcp-architecture.md).

backend 연결 하나는 file descriptor 하나를 쓰므로 필요한 수는 대략 동시 세션 수 곱하기 세션당 backend 수다. Linux의 기본 nofile soft limit은 보통 1,024라서(source docs/arch/13-vmcp-scalability.md), 세션 1,000개에 닿기 전에 이 한계에 먼저 닿을 가능성이 있다.

7.5 pod가 갑자기 종료될 때

pod가 갑자기 종료되면 처리 중이던 tool 호출은 응답 없이 사라진다. Redis가 있어도 브라우저 세션, DB 트랜잭션, 열린 파일 같은 backend 쪽 상태는 돌아오지 않는다(docs guides-vmcp/scaling-and-performance). 그래서 외부 상태를 바꾸는 tool을 부르는 쪽은 재시도와 멱등성 장치를 갖춰야 한다.

8. composite tool과 MRTR

8.1 정의 위치와 실행 모델

composite tool은 vMCP 안에서 정의하는 tool이다. MCP 클라이언트에게는 tool 하나로 보이고, 호출을 받으면 vMCP가 step을 실행한다(docs guides-vmcp/composite-tools).

정의는 두 곳에 둘 수 있다. 권장 방식은 별도 리소스 VirtualMCPCompositeToolDefinition으로, VirtualMCPServer가 spec.config.compositeToolRefs로 같은 namespace의 정의를 참조한다. 짧은 실험에는 spec.config.compositeTools에 바로 적는다.

step의 dependsOn은 DAG를 이룬다. 실행기는 위상 정렬로 step을 레벨로 나누고 같은 레벨의 step은 동시에 실행하는데, 다음 레벨은 앞 레벨의 step이 모두 끝나야 시작한다(source pkg/vmcp/composer/dag_executor.go:63). 동시에 실행하는 step은 최대 10개다(source pkg/vmcp/composer/dag_executor.go:19).

아래 예는 그림 3의 workflow이고, tool 이름은 설명용 예다.

apiVersion: toolhive.stacklok.dev/v1beta1

  timeout: 30m

    type: object

      incident_id:
        type: string

  steps:
    - id: get_logs
      tool: logging.search_logs       # workload.원래이름 형식
      arguments:
        query: "incident_id={{.params.incident_id}}"
    - id: get_metrics
      tool: monitoring_get_metrics    # 노출 이름 형식
      arguments:
        filter: error_rate
    - id: get_alerts
      tool: pagerduty_list_alerts
      arguments:
        incident: "{{.params.incident_id}}"

      onCancel:

    - id: create_issue
      tool: github_create_issue
      arguments:
        title: "Incident {{.params.incident_id}}"
        body: "{{json .steps.get_logs.output}}"
      condition: '{{eq .steps.approval.output.action "accept"}}'
      dependsOn: [approval]
      onError:
        action: retry
        retryCount: 3

8.2 step, 파라미터, 결과

step의 tool 값은 두 형식을 받는다. 하나는 충돌 처리 뒤의 노출 이름이고 다른 하나는 workload.원래이름 형식인데(source pkg/vmcp/router/session_router.go:91), 두 번째 형식은 충돌 전략을 바꿔도 그대로 동작한다.

arguments, condition, output 값에는 Go template 식을 쓴다. .params는 입력 파라미터이고 .steps.ID.output은 앞 step의 결과이며, json, fromJson, quote 함수도 쓴다(source docs/operator/composite-tools-quick-reference.md). 많은 MCP 서버는 결과를 JSON 문자열로 text 필드에 담는데, 이때는 fromJson으로 풀어야 한다.

  • parameters: JSON Schema로 입력을 정의한다.
  • output: 없으면 마지막으로 끝난 step의 결과를 돌려준다. 있으면 property마다 type과 value 식을 적고, vMCP가 문자열 결과를 선언한 type으로 바꾼다.
  • defaultResults: condition이나 continue로 건너뛰는 step이 대상이다. 뒤 step이나 output이 그 결과를 참조하면 적어야 하고, 빠지면 설정 검사가 실패한다.
  • annotations: 적지 않으면 step tool의 annotation에서 보수적인 값을 도출한다. 도출한 값보다 안전해 보이는 값을 적으면 그 composite tool은 목록에서 빠진다(source pkg/vmcp/config/config.go:900).
  • onError.action: abort(기본), continue, retry 중 하나다. 재시도 횟수는 retryCount로 정한다(source pkg/vmcp/config/config.go:1032).

8.3 elicitation과 MRTR

elicitation step은 workflow 중간에 사용자에게 입력을 묻는 step으로, message와 schema를 적는다. 사용자의 응답 action은 accept, decline, cancel 중 하나이고, decline과 cancel의 기본 처리는 abort다. onDecline, onCancel에 continue를 적으면 다음 step으로 가는데, 이때 쓰기 step에는 accept를 확인하는 condition을 걸어야 한다(docs guides-vmcp/composite-tools). 세 번째 값 skip_remaining은 남은 step을 건너뛰고 workflow를 성공으로 끝낸다. 이때 elicitation step에 의존하는 step은 실행하지 않고, 건너뛴 step은 defaultResults를 결과로 쓴다(source pkg/vmcp/config/config.go:1048, pkg/vmcp/composer/workflow_engine.go:190).

v0.63.0에서 composite tool의 elicitation은 Legacy 세션에서만 동작한다. vMCP가 Legacy 세션으로 클라이언트에게 직접 묻기 때문이다. Modern 클라이언트가 이 tool을 부르면 오류를 받는데, capability를 선언하지 않았으면 -32021, 선언했으면 -32603이다(source pkg/vmcp/server/modern_gate.go:37). -32021은 명세대로 HTTP 400으로 나간다(source pkg/vmcp/server/modern_dispatch.go:721).

Modern 개정판은 서버가 먼저 보내는 요청을 없애고 대신 MRTR을 쓴다. MRTR은 다음 순서로 동작한다(source docs/arch/16-vmcp-mrtr.md).

  1. 서버는 입력이 필요하면 resultType: "input_required" 결과를 돌려준다. 결과에는 inputRequests와 requestState가 들어 있다.
  2. 클라이언트가 사용자에게 입력을 받는다.
  3. 클라이언트가 원래 요청을 새 JSON-RPC id로 다시 보내면서 inputResponses와 받은 requestState를 함께 싣는다.
  4. 서버는 두 요청을 서로 독립된 요청으로 처리하므로, 다시 보낸 요청은 어느 replica든 처리한다.

v0.63.0의 MRTR 상태는 다음과 같다.

  • vMCP는 Modern backend 호출에 빈 clientCapabilities를 선언하므로, 입력이 필요한 Modern backend는 -32021 오류를 낸다.
  • Modern backend의 input_required 결과를 typed 오류로 읽는 부분만 들어갔다(source pkg/vmcp/mrtr.go). 설계 문서의 slice 1에 해당한다.
  • vMCP 프로세스 안의 decorator가 URL elicitation 응답을 돌려주면 vMCP는 input_required 결과를 만든다. Modern 클라이언트가 elicitation.url capability를 선언했을 때만 그렇고, 선언하지 않았으면 -32021을 HTTP 400으로 준다. Legacy 세션은 URL 없이 isError 결과를 받는다. backend가 보낸 요청은 이 경로를 타지 않는다(source pkg/vmcp/server/modern_dispatch.go:623, pkg/vmcp/conversion/errors.go:34).
  • Legacy 클라이언트는 호출 도중의 elicitation과 sampling 요청을 그대로 받는다(source pkg/vmcp/forwarding.go).

9.2 검색 방식

optimizer는 세션을 등록할 때 그 세션의 노출 tool을 메모리 SQLite에 넣는다. 테이블에는 이름, 설명, 임베딩이 들어가고 FTS5 색인은 Porter 어간 추출을 쓴다(source pkg/vmcp/optimizer/internal/toolstore/schema.sql:34). 검색은 그 세션에 노출된 tool 안에서만 한다.

optimizer는 find_tool 요청을 다음 순서로 처리한다(source pkg/vmcp/optimizer/internal/toolstore/sqlite_store.go:543).

  1. 키워드 식을 만든다. tool_keywords가 있으면 그 값을 쓰고, 없으면 tool_description의 단어를 쓴다.
  2. 임베딩 서비스가 없으면 키워드 검색만 하고, 결과는 최대 maxToolsToReturn개다.
  3. 임베딩 서비스가 있으면 결과 한도를 비율로 나눈다. 기본값이면 의미 검색 4개, 키워드 검색 4개다(source sqlite_store.go:916).
  4. 두 검색을 동시에 실행한다. 의미 검색은 tool_description을 임베딩한 뒤 cosine 거리를 잰다.
  5. 거리가 semanticDistanceThreshold보다 큰 후보는 버린다.
  6. 의미 검색 결과를 앞에, 키워드 검색 결과를 뒤에 둔 다음, 중복을 빼고 maxToolsToReturn개로 자른다(source sqlite_store.go:821).

9.3 EmbeddingServer

의미 검색에는 임베딩을 만드는 서비스가 필요하다. Kubernetes에서는 EmbeddingServer 리소스가 이 서비스를 띄우는데, operator가 HuggingFace TEI 서버를 StatefulSet으로 만든다(source cmd/thv-operator/controllers/embeddingserver_controller.go:197).

  • 기본 모델: BAAI/bge-small-en-v1.5(source cmd/thv-operator/api/v1beta1/embeddingserver_types.go:45).
  • 기본 이미지: ghcr.io/huggingface/text-embeddings-inference:cpu-latest. x86_64 전용이라서 ARM64 노드에는 cpu-arm64-latest를 적어야 한다(docs guides-vmcp/optimizer).
  • 모델 캐시: modelCache로 PVC를 붙이면 재시작해도 모델을 다시 받지 않는다.

VirtualMCPServer에 embeddingServerRef를 적으면 operator가 optimizer를 기본값으로 켜고 EmbeddingServer의 URL을 optimizer.embeddingService에 채운다(source cmd/thv-operator/controllers/virtualmcpserver_vmcpconfig.go:162). embeddingService를 직접 적은 상태에서 ref도 있으면 ref의 URL이 이기고, 그 경고는 spec이 바뀐 reconcile에서 한 번만 낸다(source virtualmcpserver_vmcpconfig.go:212). operator는 EmbeddingServer가 준비된 뒤에 vMCP Deployment를 만든다.

apiVersion: toolhive.stacklok.dev/v1beta1
kind: EmbeddingServer
metadata:
  name: my-embedding
  namespace: toolhive-system
spec: {}                      # 기본 모델과 기본 이미지
---
apiVersion: toolhive.stacklok.dev/v1beta1
kind: VirtualMCPServer
metadata:
  name: my-vmcp
  namespace: toolhive-system
spec:
  groupRef:
    name: my-group
  incomingAuth:
    type: anonymous
  embeddingServerRef:
    name: my-embedding        # 이 한 줄로 optimizer가 켜진다
  config:
    optimizer:                # 선택. 조정할 때만 적는다
      maxToolsToReturn: 10
      hybridSearchSemanticRatio: "0.6"
      semanticDistanceThreshold: "0.8"

optimizer는 OpenAI 호환 /embeddings API에서도 임베딩을 받는다. 이때 운영자는 embeddingProvider: openai, embeddingService, embeddingModel을 적어야 하고, API 키는 vmcp 컨테이너의 OPENAI_API_KEY 환경 변수로만 받는다(source pkg/vmcp/optimizer/optimizer.go:41). 이 방식은 embeddingServerRef와 함께 쓰지 못한다(docs guides-vmcp/optimizer).

9.4 로컬 CLI의 tier

로컬 CLI는 optimizer를 네 tier로 나눈다(source docs/arch/vmcp-local.md).

tier켜는 방법검색외부 서비스
0없음없음. 모든 tool을 노출한다.없음
1--optimizer키워드 검색없음
2--optimizer-embedding혼합 검색ToolHive가 관리하는 TEI 컨테이너

tier 2에서 ToolHive는 TEI 컨테이너 thv-embedding-HASH를 띄우는데, HASH는 모델 이름 SHA-256의 앞 8자다. 컨테이너 런타임(Docker, Podman 등)이 있어야 한다. thv vmcp serve가 끝날 때 ToolHive는 자신이 띄운 컨테이너만 멈추고, 이미 실행 중이던 컨테이너는 다시 쓰되 멈추지 않는다(source pkg/vmcp/cli/embedding_manager.go).

9.5 제약

  • optimizer를 켠 인스턴스는 Legacy 개정판만 받는다. 메타 tool이 세션 단위이기 때문이다(5.3절).
  • v0.63.0 코드는 Cedar 인가 설정과 optimizer를 함께 받지 않아서 server.New가 설정 오류를 돌려준다(source pkg/vmcp/server/server.go:498).
  • v1beta1 이행 안내 문서의 v0.15.0 항목은 Cedar가 메타 tool도 거른다고 적지만(docs guides-k8s/migrate-to-v1beta1), 이 내용은 v0.63.0 코드와 맞지 않는다. v0.63.0에서는 둘을 함께 쓰지 못한다.
  • backend health가 바뀌어도 기존 세션의 optimizer 색인은 다시 만들지 않는다(source docs/arch/10-virtual-mcp-architecture.md).
  • Kubernetes에서 tei provider를 쓰면서 embeddingService를 직접 적지 않았다면 EmbeddingServer가 꼭 있어야 한다. 의미 검색 비율이 0이어도 마찬가지다(docs guides-vmcp/optimizer).

9.6 절감 효과의 근거

find_tool 응답의 token_metrics는 추정치로, 전체 tool 정의와 돌려준 tool 정의의 LLM 토큰 수를 비교한다. LLM 토큰 수는 tool 정의 JSON의 바이트 수를 4로 나눈 값이라서(source pkg/vmcp/optimizer/internal/tokencounter/counter.go:42), 실제 tokenizer의 결과와 다를 가능성이 있다.

Stacklok은 optimizer가 요청당 LLM 토큰을 60~85% 줄인다고 주장하고(docs blog/toolhive-updates/2026-03-09-updates), README는 최대 85%라고 적는다(source README.md:31). 두 수치는 회사의 주장이고 이 문서는 수치를 시험하지 않았다. 공식 튜토리얼은 backend가 둘뿐이면 절감이 거의 없다고 적는다(docs tutorials/mcp-optimizer).

10. code mode

code mode를 켜면 vMCP는 메타 tool execute_tool_script를 하나 더 노출한다. 에이전트가 이 tool에 Starlark 스크립트와 선택 입력 data를 보내면 vMCP는 스크립트를 자기 프로세스 안에서 실행하고, 스크립트가 만든 값은 tool 결과 하나로 돌아간다(docs guides-vmcp/code-mode).

code mode는 기본으로 꺼져 있는데, codeMode.enabled의 기본값이 false이기 때문이다(source pkg/vmcp/config/config.go:1216).

# 에이전트가 보내는 script. deps는 data 인자로 받는다
results = parallel([
    lambda d=d: osv_query_vulnerability(package=d["name"], version=d["version"])
    for d in deps
])
vulnerable = [r for r in results if r.get("vulns")]
return {"checked": len(results), "vulnerable": vulnerable}
spec:
  config:
    codeMode:
      enabled: true
      stepLimit: 100000             # Starlark 연산 횟수 한도
      parallelMaxConcurrency: 10    # parallel()의 동시 실행 수
      toolCallTimeout: 30s          # 안쪽 tool 호출 하나의 제한 시간

스크립트 전체의 실행 시간은 1분으로 고정돼 있고, 이 값은 설정으로 바꾸지 못한다(source pkg/vmcp/codemode/decorator.go:34).

code mode는 호출자의 접근 범위를 넓히지 않는다(source pkg/vmcp/codemode/config.go).

  • 스크립트가 부르는 tool 목록은 core가 호출자 identity로 거른 목록이다.
  • 안쪽 호출마다 core 인가 판정을 실제 이름으로 다시 받는다.
  • execute_tool_script 자체는 Cedar 정책이 아니라 enabled 설정으로 열린다.
  • backend가 같은 이름의 tool을 내면 vMCP는 목록 제공을 거부한다. 오류 이름은 ErrReservedToolName이다(source pkg/vmcp/codemode/decorator.go:26).
  • 스크립트 오류는 isError: true인 tool 결과로 돌아가고, 에이전트는 스크립트를 고쳐 다시 보낸다.
원하는 일쓰는 기능내용을 정하는 쪽
요청 시점에 여러 tool 호출을 즉석에서 묶는다code mode에이전트가 요청마다 정한다
파라미터와 승인 단계가 있는 고정 workflow를 만든다composite tool운영자가 미리 정한다
요청마다 노출 tool 수를 줄인다optimizer운영자는 켜기만 한다

code mode와 optimizer는 함께 켜도 된다. optimizer는 execute_tool_script도 다른 tool처럼 색인에 넣는다(docs guides-vmcp/code-mode).

11. 로컬 CLI와 Kubernetes 배포

11.1 로컬 CLI (thv vmcp)

아키텍처 문서는 Kubernetes 밖에서 thv vmcp를 권하고, 예전 독립 vmcp 바이너리는 하위 호환용으로 남아 있다(source docs/arch/10-virtual-mcp-architecture.md). 하위 명령은 세 개다.

하위 명령하는 일
thv vmcp init실행 중인 그룹에서 시작용 YAML 설정을 만든다.
thv vmcp validateYAML 설정의 문법과 의미 오류를 검사한다.
thv vmcp servevMCP를 실행한다. 기본 주소는 127.0.0.1:4483, endpoint는 /mcp다.

quick 모드는 --config 없이 --group만 주는 방식이다. vMCP가 메모리에 설정을 만드는데, 들어오는 인증은 anonymous, 충돌 전략은 prefix다(source pkg/vmcp/cli/serve.go:643). 인증이 없으므로 vMCP는 loopback이 아닌 bind 주소를 거부한다(source pkg/vmcp/cli/serve.go:96).

vMCP는 loopback으로 들어온 요청의 Host header도 검사해서, Host가 localhost나 loopback IP가 아니면 403을 준다(source pkg/vmcp/server/loopback_host_guard.go:66). reverse proxy가 127.0.0.1로 전달하면서 클라이언트의 Host를 유지하면 403이 나므로, 이런 proxy는 Host를 localhost:4483으로 바꿔야 한다. host.docker.internal로 접속하는 클라이언트도 403을 받는다(source docs/arch/vmcp-local.md).

# quick 모드: 그룹 하나를 바로 묶는다
thv group create my-group
thv run --group my-group fetch
thv run --group my-group github
thv vmcp serve --group my-group --optimizer

# 설정 파일 모드: 만들고, 고치고, 검사하고, 실행한다
thv vmcp init --group my-group --output vmcp.yaml
thv vmcp validate --config vmcp.yaml
thv vmcp serve --config vmcp.yaml --session-ttl 2h

pkg/vmcp는 Go 라이브러리로도 쓴다. config, aggregator, router, server 등은 Stable이고 optimizer, cli, composer는 Experimental이다(source docs/arch/vmcp-library.md).

11.2 Kubernetes (VirtualMCPServer)

operator는 VirtualMCPServer 하나를 받으면 다음 리소스를 만든다(source cmd/thv-operator/controllers/virtualmcpserver_controller.go:1274).

  1. RBAC: ServiceAccount, Role, RoleBinding을 만든다.
  2. HMAC Secret: 세션 바인딩에 쓰는 NAME-hmac-secret을 만든다(source virtualmcpserver_controller.go:1493).
  3. ConfigMap: NAME-vmcp-config에 vMCP 설정 파일을 담는다. backend의 phase는 여기에 넣지 않으므로 backend health가 바뀌어도 설정 checksum이 그대로이고 pod rollout도 없다(source virtualmcpserver_controller.go:3089).
  4. Deployment: vmcp 컨테이너가 serve --config=/etc/vmcp-config/config.yaml로 시작한다(source virtualmcpserver_deployment.go:332).
  5. Service: vmcp-NAME을 4483 포트로 만든다. 종류는 serviceType으로 정하고 기본값은 ClusterIP다.

12. 자가 점검 문제

먼저 답을 생각해 본 다음 펼쳐서 확인한다.

Q1. 기본 설정에서 backend github의 create_issue는 어떤 이름으로 노출되는가? vMCP는 backend를 부를 때 어떤 이름을 쓰는가?

기본 전략은 prefix이고 기본 형식은 {workload}_라서 github_create_issue로 노출된다. vMCP는 라우팅 테이블로 backend를 찾고, backend에는 원래 이름 create_issue로 호출을 보낸다.

Q2. priorityOrder: [github, jira]다. slack도 create_issue를 낸다. 결과는 무엇인가? 왜 그렇게 동작하는가?

충돌에 목록 밖의 backend slack이 끼었으므로 vMCP는 세 후보를 모두 빼고 ERROR 로그를 남긴다. Cedar 정책은 노출 이름으로 tool을 가리키는데, 이름을 목록 안의 backend에 넘기면 기존 정책이 다른 tool에 붙을 위험이 있기 때문이다.

Q3. filter로 숨긴 tool을 composite tool step이 부를 수 있는가? MCP 클라이언트는 어떤가?

composite tool step이 부르면 vMCP는 그 호출을 backend로 보낸다. filter는 노출만 바꾸고 라우팅 테이블에는 tool을 남기기 때문이다. 반면 MCP 클라이언트가 직접 부르면 unknown-tool 오류를 받는다.

Q4. composite tool에 step A, B, C가 있다. A와 B는 의존이 없다. C는 A에만 의존한다. A는 1초, B는 10초 걸린다. C는 언제 시작하는가?

v0.63.0 실행기는 레벨 단위로 실행한다. A와 B는 레벨 0이고 C는 레벨 1인데, 레벨 1은 레벨 0의 step이 모두 끝나야 시작한다. 그래서 C는 B가 끝난 뒤, 약 10초 뒤에 시작한다.

Q5. replica 3개로 배포했는데 Redis 세션 저장소를 설정하지 않았다. 무슨 일이 생기는가?

operator는 SessionStorageWarning 조건을 걸고 replica 3개를 그대로 띄운다. 세션 메타데이터가 세션을 만든 replica의 메모리에만 있어서, 다른 replica로 간 요청은 실패한다.

Q6. pod 하나에 세션이 1,001번째로 들어오면 어떻게 되는가? Redis가 있을 때와 없을 때를 나눠 답한다.

세션 캐시 상한이 1,000개라서 vMCP는 가장 오래 쓰지 않은 세션을 내보내고 그 세션의 backend 연결을 닫는다. 내보낸 세션에서 처리 중이던 요청은 실패한다. Redis가 있으면 그 세션의 다음 요청에서 RestoreSession이 세션을 다시 만든다. 공식 문서는 Redis가 없으면 클라이언트가 세션을 새로 열어야 한다고 적는다.

Q7. optimizer 기본값에서 find_tool은 tool을 최대 몇 개 돌려주는가? 두 검색은 결과를 어떻게 나누는가?

최대 8개다. 의미 검색 비율이 0.5이므로 의미 검색과 키워드 검색이 각각 4개 한도로 찾는다. vMCP는 의미 검색 결과를 앞에 두고, 중복을 뺀 뒤 8개로 자른다.

Q8. optimizer를 켠 vMCP에 Modern 개정판을 먼저 시도하는 go-sdk 클라이언트가 연결한다. 어떻게 되는가?

optimizer를 켜면 vMCP는 Modern을 끈다. server/discover 응답에 Modern 판이 없으므로 클라이언트는 Legacy로 연결하고, 연결 뒤에는 Legacy 세션으로 find_tool과 call_tool을 쓴다. 그 밖의 Modern 요청은 -32022 오류를 받는다.

Q9. code mode를 켜면 스크립트가 호출자에게 허용되지 않은 tool을 부를 수 있는가?

부르지 못한다. 스크립트가 보는 tool 목록은 core가 호출자 identity로 거른 목록이고, 안쪽 호출도 core 인가 판정을 실제 이름으로 다시 받는다. execute_tool_script 자체만 codeMode.enabled 설정으로 열린다.

Q10. Modern 클라이언트가 elicitation step을 가진 composite tool을 부른다. v0.63.0은 무엇을 돌려주는가? MRTR 중계는 지금 동작하는가?

v0.63.0은 composite tool의 elicitation을 Legacy 세션으로만 처리하므로 Modern 클라이언트는 오류를 받는다. elicitation capability를 선언하지 않았으면 HTTP 400과 -32021, 선언했으면 -32603이다. backend의 round를 중계하는 MRTR은 지금 동작하지 않고, vMCP 자신이 만드는 URL elicitation 응답만 input_required로 돌려준다. 설계 문서의 slice 2부터 slice 5까지는 제안 단계다.

Q11. 사용자 A가 연 Legacy 세션의 ID를 사용자 B가 자기 access token과 함께 보낸다. vMCP는 무엇을 돌려주는가?

404 "Session terminated"를 돌려준다. 세션은 만든 identity의 iss와 sub에 묶여 있고, 세션 소유자 검사가 인가 gate보다 먼저 동작하므로 Cedar 정책과 관계없이 404다. A의 세션은 영향을 받지 않는다.

대조한 내용

v0.63.0 Go 코드와 대조한 항목은 충돌 전략, filter, health 상태, 기본값, 세션 한계, composite tool 한계, optimizer 검색, code mode 한계다. 줄 번호는 v0.63.0 트리(2026-11-06, 커밋 01f96bf)에서 확인했다. 2026-11-07 갱신에서는 v0.53.0과 v0.63.0 사이에 바뀐 인용 파일 13개의 diff를 읽었고, 바뀌지 않은 인용 파일은 줄 번호만 다시 확인했다. 공식 문서는 2026-11-07에 guides-vmcp/failure-handling, backend-discovery, scaling-and-performance 세 쪽을 다시 읽었고, 그 밖의 공식 문서 인용은 2026-10-13에 읽은 docs-website 912bc05 기준이다.

문서와 코드가 다른 곳

이 문서는 아래 일곱 곳에서 코드를 따랐다.

  • circuit breaker: 공식 문서는 요청을 거절하는 장치로 설명하고 2026-11-07에도 같다. 코드는 health check 실패만 세고 health check만 건너뛴다.
  • partialFailureMode: 코드는 이 값을 검사만 하고, 집계는 늘 실패한 backend를 건너뛴다. 공식 문서는 2026-11-07에도 fail과 best_effort의 동작 차이를 설명한다.
  • 동적 발견의 변경 반영: 공식 문서는 2026-11-07에도 재시작이 필요하다고 적지만, 코드는 vMCP pod 안에서 informer로 그룹을 지켜본다.
  • optimizer와 Cedar: 코드는 둘을 함께 받지 않는다(server.go:498). v1beta1 이행 안내 문서의 v0.15.0 항목은 Cedar가 메타 tool을 거른다고 적는다. 이 문서는 2026-11-07에 다시 읽지 않았다.
  • composite tool 필드: docs/operator의 빠른 참조는 failureMode, maxRetries를 쓰고 v0.63.0 트리에서도 같다. 설정 구조체에는 두 필드가 없다.
  • middleware 표: 아키텍처 문서의 표는 v0.63.0에서 14행이 됐고, discovery와 authorization 행과 discovery timeout 15초는 그대로 있다. 코드 주석은 이 세 계층을 지웠다고 적는다(server.go:721).
  • capability 캐시: 아키텍처 문서는 Modern 요청이 캐시 없이 backend를 매번 훑는다고 적지만, server.New는 core에 30초 캐시를 감싼다. Modern 경로가 이 캐시를 실제로 쓰는지는 실행으로 확인하지 않았다.
확인하지 못한 내용

클러스터나 로컬에서 vMCP를 실행하지 않았다. 회복한 backend가 기존 세션에 붙는지는 두 문서가 다르게 적는다. Redis 세션 크기 10~50KB는 공식 문서의 어림값이고, optimizer의 LLM 토큰 절감률 60~85%와 최대 85%는 회사의 주장이다. MRTR의 slice 2부터 5까지는 설계 문서의 제안이며 배포되지 않았다. 세션 소유자 검사, URL elicitation 응답, skip_remaining의 동작은 코드와 아키텍처 문서로만 확인했다. v0.60.0의 "/health를 마지막 health check 결과로 답한다"는 변경은 proxy의 pkg/healthcheck에 들어갔고, vMCP의 /health 코드는 바뀌지 않았다. v0.57.0의 MCPRemoteProxy pod readiness 분류 변경은 operator의 상태 계산이라서 이 문서는 다루지 않았다.
