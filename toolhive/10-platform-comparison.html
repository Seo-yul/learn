우리 MCP 플랫폼과 비교

ToolHive 학습 10편 · 2026-10-14 작성 · 2026-11-07 갱신

이 문서는 01편부터 09편까지 본 ToolHive를 우리 MCP 플랫폼과 나란히 놓고, 같은 문제를 두 플랫폼이 어떻게 다르게 푸는지 본다. 우리가 가져올 만한 점은 추천으로 정리한다.

ToolHive 쪽 기준은 v0.63.0(2026-11-06)이고, 우리 쪽 기준은 각 저장소의 개발 브랜치다. 두 쪽 모두 2026-11-07에 다시 읽고 갱신했으며, 우리 쪽에서 읽은 커밋의 날짜는 다음과 같다.

  • 우리 operator: 2026-11-05 커밋
  • MCP 서버 이미지: 2026-11-05 커밋
  • core: 2026-11-06 커밋
한 문장 요약

ToolHive는 남이 만든 MCP 서버를 안전하게 실행하는 데서 출발하고, 우리 플랫폼은 OpenAPI 스펙으로 MCP 서버를 만들어 내는 데서 출발한다. 그래서 ToolHive의 격리 기능은 우리에게 덜 급하지만, 나가는 인증과 인가, 관측은 바로 참고할 만하다.

v0.63.0 갱신 요약
  • 우리 쪽: 위임 설계가 MCP 서버 이미지와 core에 구현됐다. 동의 화면이 scope 체크박스를 보여 주고, tool 호출과 tool 목록을 위임된 scope로 거른다. 이에 맞춰 9장과 추천 4를 다시 썼다.
  • 우리 쪽: core가 CR에 채우는 MCP 서버 자원 기본값이 CPU 100m/500m, 메모리 256Mi로 바뀌어서 3장 표에 행을 더했다.
  • ToolHive 쪽: 동의 화면이 upstream의 표시 이름을 보여 주고, 미리 허용한 클라이언트는 동의 화면을 건너뛴다. DCR 클라이언트 수에도 상한이 생겼다. 7장에 적었다.
  • ToolHive 쪽: 내장 인가 서버가 token exchange grant로 위임 토큰을 내고, authorization_details와 exchange 전용 refresh token도 다룬다. 7장에 적었다.

  • ToolHive 쪽: 인가 서버에 TLS listener가 생겨서 7장 표에 행을 더했다.
  • 5장, 8장, 10장, 11장의 결론은 그대로이고, 인용 행 번호는 새 커밋에 맞췄다.

1. 출발점의 차이

두 플랫폼은 MCP 서버의 코드를 누가 쓰는지가 다르고, 뒤에 나오는 차이 대부분이 여기서 생긴다.

질문ToolHive우리 플랫폼

tool은 어디서 오나?MCP 서버 구현이 정한다.OpenAPI 스펙의 API를 고르면 tool이 된다.

우리 쪽 내용은 operator와 core의 코드에서 확인했다. ConfigMap과 Secret은 core의 Kubernetes 리소스 관리 코드가 만들고, 객체 소유와 ConfigMap 마운트, 해시 계산은 operator의 McpServer controller에 있다. spec 필드는 operator의 CRD 타입 정의에 있다.

ToolHive가 proxy와 MCP 서버를 다른 객체로 나눈 이유는 4장에서 보는데, 우리는 MCP 서버 이미지를 직접 만들기 때문에 이 분리가 필요 없었다.

4. transport와 proxy

ToolHive는 MCP 서버의 코드를 고치지 못해서 인증, 인가, 감사, telemetry를 MCP 서버 밖의 proxy에 둔다. proxy는 stdio 서버를 HTTP로 바꾸는 일도 한다(02편 6장).

우리 플랫폼은 MCP 서버 이미지를 직접 만들기 때문에 같은 기능을 fastmcp의 middleware와 OAuthProxy로 프로세스 안에 넣었다. 우리 이미지는 처음부터 streamable HTTP로 응답하므로 stdio를 바꿀 일도 없다.

관점별도 proxy (ToolHive)프로세스 안 (우리)
적용 대상어떤 MCP 서버에도 같은 기능을 건다.우리 이미지에만 건다.
홉 수요청마다 proxy를 한 번 더 지난다.추가 홉이 없다.
기능 추가 비용proxy 하나만 고치면 모든 서버가 얻는다.이미지를 고치고 모든 MCP 서버를 다시 배포해야 한다.
외부 MCP 서버원격 서버 앞에도 proxy를 둔다(02편 8장).우리 이미지가 아닌 서버에는 같은 기능을 걸지 못한다.

표에서는 마지막 행이 중요하다. 우리 플랫폼에도 외부 MCP 서버를 McpRegistry에 등록하는 기능이 있고, 항목의 resource_type이 external이면 외부 서버다. 이런 서버에는 우리 인증과 관측이 닿지 않는다.

5. 격리와 secret

ToolHive는 믿을 수 없는 코드를 전제로 한다. 로컬 실행에서는 컨테이너마다 권한 프로필을 걸고, 네트워크 격리도 기본으로 켜져 있어서 egress proxy가 프로필의 허용 목록대로 나가는 연결을 거른다(03편 2장~6장). 다만 기본 network 프로필은 나가는 연결을 모두 허용한다.

Kubernetes에서는 사정이 다르다. operator는 권한 프로필을 무시하고 네트워크 격리도 하지 않는 대신 컨테이너 보안 기본값을 넣는다(03편 6장, 7장). 아래 표는 이 Kubernetes 경로를 우리 McpServer pod와 비교한 것이다.

ToolHive 열은 03편 6장과 7장을 따랐고, 우리 열은 operator 개발 브랜치 코드에서 securityContext와 NetworkPolicy를 검색한 결과다. operator README도 securityContext를 넣지 않는다고 적고 있다. 실행 사용자 행의 근거는 MCP 서버 이미지의 Dockerfile이다. podOverrides는 노드 배치와 이미지 pull secret만 다루는 필드라서 여기에도 보안 필드가 없다.

추천 1. pod 보안 기본값을 operator에 넣는다

우리는 MCP 서버 이미지를 직접 만들기 때문에 ToolHive보다 호환성을 확인하기 쉽다. 비용이 작고 효과도 분명하다.

다만 전제가 있다. 이미지는 root가 아닌 사용자로 돌아야 하고 디스크에 쓰는 경로에는 emptyDir을 붙여야 한다. 우리 이미지는 Redis가 없으면 OAuth 상태를 /application/.fastmcp/server/oauth-proxy에 쓴다.

나가는 연결 제한은 비용이 크다. Kubernetes NetworkPolicy는 IP와 포트로 거르고 host 이름을 모르기 때문에, REST API 서버가 클러스터 밖에 있으면 egress proxy 같은 구성 요소가 필요할 가능성이 있다. ToolHive operator도 이 기능을 넣지 않았다. 그래서 이 항목은 검토 후보로만 둔다.

6. registry와 클라이언트 설정

ToolHive의 registry 항목은 upstream 형식을 따르고, ToolHive만의 필드는 _meta의 publisher-provided 영역에 둔다(04편 2장). registry server는 이 형식을 /registry/{name}/v0.1/servers 경로로 낸다(04편 4장).

우리 McpRegistry는 자체 형식이고, 주요 필드는 다음과 같다.

  • 설명: description, usage_doc, categories, icon_url
  • 연결: mcp_server_json, internal_mcp_server_json, transport_type
  • 인증: oauth_required, mcp_server_dcr_supported
  • 공개: is_published, shared_target
  • 내용: tools, profile_id, profile_version

mcp_server_json은 MCP 클라이언트 설정에 붙여 넣을 JSON 조각이고, 여기에는 REST API 서버별 자격 증명 헤더 자리가 들어 있다. 헤더 이름은 <REST API 서버 이름>---<헤더 이름> 형식이다. 이 헤더를 쓰는 조건과 방법은 8장에서 본다.

추천 2. McpRegistry를 upstream 형식으로도 낸다

upstream 형식 API가 있으면 다른 도구가 우리 목록을 읽을 가능성이 생긴다. 예를 들어 thv는 지정한 URL 뒤에 /v0.1/servers를 붙여 목록을 읽는다(04편 3.2절). 우리만의 필드(usage_doc, shared_target)는 ToolHive처럼 _meta에 넣으면 되고, 기존 studio API는 그대로 둔다.

7. 들어오는 인증

두 플랫폼이 가장 비슷한 영역이다. ToolHive의 내장 인가 서버는 fastmcp OAuthProxy와 같은 일을 하는데(05편 5장), 둘 다 MCP 클라이언트에게는 인가 서버처럼 보이고 뒤에서는 IdP 앱 하나로 IdP에 붙는다.

8. 나가는 인증

두 플랫폼의 차이가 큰 영역이다. 우리 MCP 서버 이미지는 REST API 서버마다 아래 세 방식 중 하나로 자격 증명을 붙이는데, 어느 방식을 쓸지는 프로필의 인증 설정이 정한다.

  1. 프로필의 API 키. 인증 방식이 API 키이고 프로필에 키 값이 있으면 그 값을 헤더로 붙인다.
  2. 클라이언트가 보낸 API 키. 프로필에 키 값이 없으면 6장의 <REST API 서버 이름>---<헤더 이름> 헤더를 쓰는데, 이미지가 앞부분을 떼고 그 헤더를 붙인다.
  3. access token 전달. 인증 방식이 Bearer이고 토큰 전달 설정이 켜져 있으면 IdP access token을 그대로 붙인다.

core는 프로필에 API 키의 헤더 이름만 넣고 값은 넣지 않아서, core가 배포한 MCP 서버에서 API 키는 2번 방식으로 들어온다. 토큰 전달 설정 값은 core가 프로필의 MCP 서버 노드 설정에서 읽어 환경 변수로 넣는다. core의 설정 조각에는 Basic과 Bearer용 헤더 자리도 있지만, MCP 서버 이미지에는 이 두 헤더를 바꿔 붙이는 코드가 없다.

ToolHive는 3번 대신 token exchange를 쓴다(05편 8.1). proxy가 들어온 access token을 IdP에 내고 외부 API용 access token을 새로 받는 방식이고, 이때 sub는 그대로 두고 aud와 scope만 바뀐다.

추천 3. access token 전달 대신 token exchange를 둔다

지금 REST API 서버가 받는 access token은 MCP 서버의 IdP 앱 앞으로 발급된 것이라서, REST API 서버를 대상으로 발급되었다는 보장이 없다. REST API 서버가 aud를 검사하지 않으면 다른 서비스용 access token도 받아들일 가능성이 있다. token exchange는 aud와 scope를 REST API 서버에 맞춘다.

전제는 IdP가 RFC 8693을 지원해야 한다는 점이다. ToolHive 문서는 Okta, Auth0, Keycloak을 예로 든다(05편 8.1). 기존 전달 방식은 설정으로 남겨 두는 안이다.

9. 인가

ToolHive는 Cedar policy로 tool 호출마다 판정한다(05편 10장). principal은 access token의 sub이고 resource는 tool 이름이며, claim은 claim_ 접두사를 붙여 판정에 쓴다. 허용되지 않은 tool은 목록 응답에서도 지운다(pkg/authz/middleware.go:207~211). v0.63.0은 이 응답 필터를 다시 썼는데, 압축 인코딩이 남아 있어 거를 수 없는 목록 응답은 통과시키지 않고 500으로 막는다(pkg/authz/response_filter.go:96~105). vMCP에서는 tool의 원래 backend가 Cedar resource의 부모가 되기 때문에 backend 하나의 tool을 한 정책으로 허용할 수 있다(pkg/authz/authorizers/cedar/core.go:1100~1106, docs/authz.md:361~379).

우리 MCP 서버 이미지는 프로필에 scope가 없으면 서버 단위로만 검사한다. IdP access token에 required_scopes가 모두 있어야 통과한다. 이 scope 목록은 core가 환경 변수로 넣는다.

프로필에 scope가 있으면 위임 설계가 동작한다. 이 설계는 2026-10-27에 MCP 서버 이미지에 들어갔고, 동작 순서는 다음과 같다.

  1. core는 tool마다 필요한 scope를 프로필에 적고, scope가 있는 프로필은 mcp_profile_v2_ 이름으로 ConfigMap에 넣는다. 옛 이미지는 이 파일을 읽지 못해 시작하지 않는다.
  2. 이미지는 scope가 있는 tool에 <접두사>:<scope> 형식의 tag를 붙인다.
  3. 동의 화면은 프로필의 scope를 체크박스로 보여 주고, 사용자가 고른 scope만 MCP 서버가 발급하는 access token에 들어간다. IdP에는 로그인 scope만 요청한다.
  4. fastmcp AuthMiddleware가 tool의 tag와 access token의 scope를 검사한다. 맞지 않는 tool은 tools/list에서 빠지고 호출은 거부된다(fastmcp server/middleware/authorization.py:170~196, :198~254).

추천 4. 위임 설계에 목록 필터링을 넣는다(구현됨)

호출만 막고 목록에는 남기면 LLM이 쓸 수 없는 tool을 고를 가능성이 있고, 그러면 호출이 실패해서 대화가 한 번 더 돈다. 그래서 ToolHive처럼 tools/list 응답에서 위임되지 않은 tool을 지우는 편이 낫다. 정책 언어는 지금처럼 scope로 충분한데, 우리 목표가 사용자 권한 판정이 아니라 위임된 scope 판정이기 때문이다.

이 추천은 2026-10-27에 MCP 서버 이미지에 구현됐다. 위임되지 않은 tool이 목록에서 빠지는지는 이미지의 시험 코드가 확인한다.

10. 관측, 감사, 사용 제한

ToolHive proxy는 telemetry, 감사, 사용 제한 middleware를 설정에 따라 붙인다(06편 1장). 감사 middleware는 거의 맨 바깥에 있어서 401, 403, 429 응답도 기록한다. 사용 제한은 Kubernetes에서만 있고 Redis가 필요하다(06편 9장).

우리 MCP 서버 이미지의 개발 브랜치 코드에서는 OpenTelemetry와 Prometheus 설정을 찾지 못했고, 2026-11-07에 다시 검색해도 같았다. 우리 operator는 controller metric을 내지만 tool 호출 단위의 trace와 감사 로그는 없다.

fastmcp 4.0.3은 OpenTelemetry 계측을 내장하고 있어서 tool 호출마다 tools/call <tool 이름> span을 연다(fastmcp server/server.py:1455). 이 이름 형식은 ToolHive span 이름과 같다(06편 4장). 다만 SDK와 exporter를 설정하지 않으면 span은 기록되지 않는다(fastmcp settings.py:154). 우리 이미지의 의존성에는 SDK가 없고, fastmcp를 따라 OpenTelemetry API 패키지만 들어온다.

추천 5. tool 호출 단위의 trace와 감사 로그를 넣는다

지금은 어떤 사용자가 어느 tool을 불렀고 결과가 무엇이었는지 MCP 서버 쪽에서 볼 수 없다. trace는 fastmcp에 들어 있는 계측을 켜는 안이 비용이 가장 작은데, 이미지에 SDK와 exporter를 넣고 설정하면 span이 기록된다. 감사 로그는 새로 만들어야 하고, ToolHive의 감사 이벤트 형식(06편 7장)을 참고할 수 있다.

사용 제한은 그다음 순서다. 우리 이미지는 Redis를 이미 선택적으로 쓰고 있어서 전제 조건 하나는 갖춘 셈이다.

11. 집계와 optimizer

vMCP는 그룹에 속한 MCP 서버를 endpoint 하나로 묶는다(08편). 그래서 외부 MCP 클라이언트는 설정 하나로 여러 서버를 쓴다.

우리 플랫폼에는 이 집계 계층이 없고, core 에이전트는 MCP 서버를 하나씩 노드로 연결한다. 노출 방식 gateway도 집계가 아니다. core 코드는 이 방식을 "비활성 Ingress에 host만 둔 상태"로 정의하고, 이때 우리 operator는 Ingress를 만들지 않는다.

그래서 vMCP 자체는 지금 들여올 이유가 약하지만 optimizer는 사정이 다르다. 에이전트에 tool이 많으면 LLM 토큰이 많이 드는데, optimizer는 tool 목록 대신 find_tool과 call_tool 두 개만 보여 준다(08편 9장). 이 방식은 에이전트 쪽에서도 쓸모가 있을 가능성이 있다. 다만 절감 수치는 Stacklok의 주장이므로 우리 데이터로 다시 재야 한다.

13. 자가 점검 문제

먼저 답을 생각해 본 다음 펼쳐서 확인한다.

Q1. ToolHive MCPServer와 우리 McpServer의 가장 큰 차이 하나는?

ToolHive MCPServer는 제3자가 만든 이미지를 실행하고 앞에 별도 proxy pod를 둔다. 우리 McpServer는 우리 MCP 서버 이미지 하나를 실행하고, 어떤 tool을 낼지는 프로필 ConfigMap이 정한다.

Q2. ToolHive가 인증과 감사를 MCP 서버 밖의 proxy에 두는 이유는?

ToolHive는 MCP 서버의 코드를 고치지 못하기 때문에, 어떤 서버에도 같은 기능을 걸려면 밖에서 걸어야 한다. 우리는 이미지를 직접 만들므로 같은 기능을 프로세스 안에 넣었다.

Q3. 우리 MCP 서버 pod에 읽기 전용 루트 파일 시스템을 켜려면 무엇을 먼저 확인해야 하나?

이미지가 디스크에 쓰는 경로를 확인해야 한다. Redis가 없으면 OAuth 상태를 /application/.fastmcp/server/oauth-proxy에 쓰므로 그 경로에 emptyDir을 붙여야 한다. Dockerfile이 만드는 /application/files의 쓰임도 확인해야 한다.

Q4. NetworkPolicy로 나가는 연결을 막을 때 ToolHive egress proxy와 다른 한계는?

NetworkPolicy는 IP와 포트로만 거르기 때문에 host 이름으로 허용하려면 egress proxy 같은 구성 요소가 따로 필요하다. REST API 서버가 클러스터 밖에 있고 IP가 자주 바뀌면 NetworkPolicy만으로는 관리하기 어렵다.

Q5. 토큰 전달 설정을 켜면 REST API 서버는 어떤 access token을 받나? 무엇이 위험한가?

MCP 서버가 받은 IdP access token을 그대로 받는다. 이 access token은 MCP 서버의 IdP 앱 앞으로 발급된 것이라서 REST API 서버를 대상으로 발급되었다는 보장이 없다. REST API 서버가 aud를 검사하지 않으면 다른 서비스용 access token도 받아들일 가능성이 있다.

Q6. McpRegistry를 upstream 형식으로 낼 때 usage_doc 같은 우리 필드는 어디에 두나?

_meta의 publisher-provided 영역에 둔다. ToolHive도 자기만의 필드를 그곳에 두고 있다.

Q7. 우리 MCP 서버 이미지는 위임되지 않은 scope의 tool을 어떻게 다루나?

fastmcp AuthMiddleware가 tools/list 응답에서 그 tool을 지우고 호출도 거부한다. 호출만 막고 목록에 남기면 LLM이 쓸 수 없는 tool을 고를 가능성이 있고, 그러면 호출이 거부되어 대화가 한 번 더 돈다. 이 동작은 위임 설계와 함께 MCP 서버 이미지에 들어갔다.

Q8. 노출 방식 gateway는 vMCP 같은 집계인가?

집계가 아니다. core는 gateway를 "비활성 Ingress에 host만 둔 상태"로 정의하고, 우리 operator는 이때 Ingress를 만들지 않는다. 여러 MCP 서버를 하나로 묶는 기능은 없다.

Q9. ToolHive의 위임 토큰과 우리 위임 설계는 무엇이 다른가?

ToolHive의 위임 토큰은 내장 인가 서버가 token exchange로 발급하는 access token이고, sub는 사용자, act는 대신 행동하는 클라이언트다. 우리 위임 설계는 사용자가 동의 화면에서 고른 scope만 클라이언트의 access token에 싣는다. 둘 다 클라이언트의 권한을 좁히지만 수단이 다르다.

ToolHive 쪽 사실은 이 시리즈의 각 편을 따랐고, 이 문서가 직접 인용한 v0.63.0 파일은 소스 트리에서 읽었다. 5장의 Kubernetes 격리 설명은 ToolHive 설계 문서 05의 Kubernetes 절에 대조했고(docs/arch/05-runconfig-and-permissions.md:789), 보안 기본값은 pkg/container/kubernetes/security.go:31~36에서도 확인했다.

2026-11-07에 v0.63.0 소스 트리에서 대조한 것은 다음과 같다.

  • 2장과 3장: ToolHive operator가 만드는 객체, RunConfig checksum, Redis 세션 저장소 조건, CRD 수(14종)
  • 5장: 보안 기본값과 operator에 NetworkPolicy가 없다는 점
  • 7장: 동의 화면, DCR 클라이언트 상한, TLS listener, token exchange grant
  • 9장: 목록 필터링, 응답 필터, vMCP backend 단위 인가
  • 10장: 사용 제한이 Redis 세션 저장소를 요구하는 CRD 규칙
  • 11장: optimizer의 tool 이름

fastmcp 쪽 사실은 MCP 서버 저장소의 로컬 가상 환경에 설치된 fastmcp 4.0.3에서 읽었다. 이 버전은 2026-11-07에도 uv.lock이 고정한 버전과 같다. MCP 클라이언트가 보낸 헤더는 fastmcp가 REST API 서버 요청에 복사하는데(fastmcp server/providers/openapi/components.py:218), authorization과 cookie 같은 헤더는 복사하지 않는다(fastmcp server/dependencies.py:561). 목록 필터링은 fastmcp server/middleware/authorization.py:170~196과 utilities/authorization.py:197에서 읽었다.

API 키 값은 프로필 ConfigMap에 들어가지 않는다. core가 프로필을 만들 때 헤더 이름만 넣기 때문이다.

확인하지 못한 내용도 있다. 추천 1의 호환성은 실행해서 시험하지 않았고, fastmcp span이 SDK 설정 뒤 실제로 기록되는지도 시험하지 않았다. 위임 설계의 동작은 이미지의 시험 코드로 확인했고, 이 문서를 갱신하면서 배포 환경에서 다시 실행하지는 않았다. ToolHive v0.63.0의 동의 화면 건너뛰기와 token exchange grant는 코드와 설계 문서로만 확인했다. ToolHive의 registry server 경로는 별도 저장소의 내용이라 이번에 다시 확인하지 않았다. 추천의 효과는 모두 추정이다.

이 문서가 ToolHive 학습의 마지막 편이다. 전체 목록은 목차에 있다.
