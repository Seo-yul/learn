격리와 secret, 공급망 보안

ToolHive 학습 03편 · 2026-10-14 작성 · 2026-11-07 갱신

이 문서는 ToolHive가 제3자 MCP 서버를 가두는 방법을 다룬다. 권한 프로필, 네트워크 격리, 컨테이너 기본 설정, secret, 이미지 검증을 차례로 보고, 주장마다 소스 줄 번호나 공식 문서 경로를 붙였다.

인용 표기는 세 가지다. "소스"는 toolhive v0.63.0 저장소의 파일 경로와 줄 번호이고, "설계 문서 NN"은 그 저장소의 docs/arch/NN-*.md, "공식 문서"는 docs.stacklok.com/toolhive 아래의 페이지 경로다. 경로 없이 쓴 client.go는 pkg/container/docker/client.go를 가리킨다.

기준 버전은 ToolHive v0.63.0(2026-11-06)이다. 2026-10-14에 v0.53.0 기준으로 쓴 문서를 2026-11-07에 v0.63.0 기준으로 갱신했고, 공식 문서도 2026-11-07 상태를 읽었다. ToolHive는 자주 바뀌므로 실제로 쓰기 전에 공식 문서를 다시 확인해야 한다.

한 문장 요약

ToolHive는 MCP 서버 컨테이너마다 권한 프로필을 적용하는데, 프로필의 네트워크 규칙은 네트워크 격리가 켜져 있을 때만 egress proxy가 집행한다. workload 설정에는 secret 이름만 저장하고 값은 실행할 때 환경 변수로 넣는다. 이미지 검증의 기본 모드는 warn이라서 검증에 실패해도 서버가 실행된다.

v0.63.0 갱신 요약
  • egress proxy가 기본으로 거부하는 호스트 이름에 Podman의 host.containers.internal이 더해졌다. Podman에서는 DNS 컨테이너의 /etc/hosts에서 세 호스트 이름에 매핑된 주소도 모아서 거부한다(4장, 5장, 6장).
  • Podman에서 그 파일에 host.containers.internal이 없으면 격리 배포가 실패하고, --allow-docker-gateway를 줘도 마찬가지다(5장). 이 변경은 v0.55.2의 보안 권고에서 왔다.
  • Docker client는 DNS 컨테이너를 먼저 만든 다음에 gateway 주소를 모은다(4장).
  • registry가 요구하는 값을 터미널에서 물을 때 한 줄 전체를 읽고, 값을 못 받으면 경고 대신 오류를 낸다(9장).
  • proxy는 원격 인증의 refresh token 참조를 저장할 때 RunConfig를 다시 저장하는데, 이때 디스크의 RunConfig를 읽어 secret 값을 지운 뒤 저장한다(9장).
  • toolhive-core는 v0.0.58이고, 권한 프로필 타입과 이미지 검증기 코드는 v0.0.52와 같다(2장, 10장).
  • 나머지 장은 줄 번호만 v0.63.0 트리에 맞게 고쳤고 동작 설명은 그대로다.

1. 위협 모델과 대응 기능

핵심

권한 프로필은 선언이고, 네트워크 규칙을 실제로 집행하는 주체는 egress proxy다. 그래서 네트워크 격리를 끄면 네트워크 규칙을 집행하는 주체가 없다(4장).

대응 기능은 대부분 로컬 Docker 경로에 있고, Kubernetes 경로는 Kubernetes 자체 기능에 맡긴다(6장, 7장).

2. 권한 프로필의 구조와 선택 순서

권한 프로필은 MCP 서버 하나에 주는 권한을 적은 JSON이고, 타입은 별도 모듈 toolhive-core의 permissions.Profile이다. ToolHive v0.63.0은 toolhive-core v0.0.58을 쓰는데(소스 go.mod:72), 이 타입은 v0.0.52와 같다.

// toolhive-core permissions/profile.go (주석과 yaml 태그 생략)
type Profile struct {
    Name       string              `json:"name,omitempty"`
    Read       []MountDeclaration  `json:"read,omitempty"`
    Write      []MountDeclaration  `json:"write,omitempty"`
    Network    *NetworkPermissions `json:"network,omitempty"`
    Privileged bool                `json:"privileged,omitempty"`
}
type NetworkPermissions struct {
    Mode     string                      `json:"mode,omitempty"` // host, bridge, none
    Outbound *OutboundNetworkPermissions `json:"outbound,omitempty"`
    Inbound  *InboundNetworkPermissions  `json:"inbound,omitempty"`
}
type OutboundNetworkPermissions struct {
    InsecureAllowAll bool     `json:"insecure_allow_all,omitempty"`
    AllowHost        []string `json:"allow_host,omitempty"`
    AllowPort        []int    `json:"allow_port,omitempty"`
}
type InboundNetworkPermissions struct {
    AllowHost []string `json:"allow_host,omitempty"`
}
필드뜻누가 집행하는가
read읽기 전용 bind mountDocker client
write읽기·쓰기 bind mountDocker client
network.modenetwork mode컨테이너 런타임
network.outbound나가는 연결의 허용 목록egress proxy(격리를 켰을 때만)
network.inboundingress proxy가 받는 이름 목록Squid ingress proxy만(5장)
privilegedprivileged 컨테이너 여부Docker client

내장 프로필 두 개

내장 프로필은 none과 network인데, 둘 다 파일 시스템 권한이 없다. 아래 JSON은 toolhive-core의 BuiltinNoneProfile과 BuiltinNetworkProfile을 그대로 옮긴 것이다.

// none: 나가는 연결 허용 목록이 비어 있다
{"name": "none", "read": [], "write": [],
 "network": {"outbound": {"insecure_allow_all": false, "allow_host": [], "allow_port": []},
             "inbound":  {"allow_host": []}},
 "privileged": false}

// network: 나가는 HTTP(S)를 모두 허용한다
{"name": "network", "read": [], "write": [],
 "network": {"outbound": {"insecure_allow_all": true, "allow_host": [], "allow_port": []},
             "inbound":  {"allow_host": []}},
 "privileged": false}

ToolHive는 --permission-profile stdio도 none과 같게 처리한다(소스 pkg/runner/config_builder.go:1391).

프로필 선택 순서

ToolHive는 다음 순서로 권한 프로필을 고른다(소스 pkg/runner/config_builder.go:1382-1411).

  1. 코드가 직접 넘긴 프로필 객체를 쓴다(WithPermissionProfile).
  2. --permission-profile 값을 쓴다. none, network, stdio가 아니면 파일 경로로 읽는다.
  3. registry 항목의 permissions를 쓴다.
  4. 위가 모두 없으면 network 프로필을 쓴다.

설계 문서 05의 내장 프로필 절은 none에 "Default profile"이라고 적었지만, 같은 문서의 선택 순서 절과 코드는 기본값을 network로 둔다. 이 문서는 코드를 따른다.

--volume과 privileged

ToolHive는 --volume 값을 권한 프로필의 mount 목록에 넣는데, :ro가 붙은 값은 read에, 나머지 값은 write에 더한다(소스 config_builder.go:1473-1517). 같은 컨테이너 경로가 이미 있으면 그 값은 건너뛴다(소스 config_builder.go:1507-1510).

ToolHive는 privileged: true를 Docker의 privileged 설정에 그대로 넘긴다(소스 pkg/container/docker/client.go:895). 설계 문서 05는 이 설정이 호스트 머신의 root 권한과 같다고 경고한다.

Kubernetes에서는 권한 프로필을 쓰지 않는다. MCPServer의 permissionProfile 필드는 호환성 때문에 남아 있을 뿐이고 operator는 이 필드를 무시한다(소스 cmd/thv-operator/api/v1beta1/mcpserver_types.go:298-301). 그래서 Kubernetes에서는 podTemplateSpec의 securityContext와 NetworkPolicy를 써야 한다(설계 문서 05).

3. 파일 시스템 접근과 .thvignore

MCP 컨테이너는 기본으로 호스트 머신의 파일을 보지 못하고, 기본 registry의 어떤 서버도 파일 시스템 권한을 기본값으로 갖지 않는다(공식 문서 guides-cli/custom-permissions).

mount 선언 형식

형식예v0.63.0 동작
경로 하나/home/user/data같은 경로로 mount한다
호스트:컨테이너/home/user/data:/data다른 경로로 mount한다
자원 URIvolume://my-data:/data경고를 남기고 건너뛴다

설계 문서 05는 자원 URI를 지원 형식으로 적지만, Docker client는 이 형식을 아직 처리하지 않는다(소스 client.go:731-735).

read 항목은 읽기 전용 bind mount가 되고(소스 client.go:718-753), write 항목은 읽기·쓰기 bind mount가 된다. 같은 컨테이너 경로가 두 목록에 모두 있으면 쓰기 가능으로 바뀐다(소스 client.go:781-790).

toolhive-core는 mount 경로에서 셸 특수 문자와 null 바이트를 거부하는데, 대상 문자는 $ & ; | $( `다(toolhive-core validatePath). ..를 따로 거부하는 코드는 없고, 경로는 filepath.Clean으로 정리만 한다. 설계 문서 05는 ..도 막는다고 적었지만 코드와 다르다.

공식 문서는 프로필에 절대 경로만 쓰라고 한다. Docker client가 상대 경로를 현재 디렉터리 기준 절대 경로로 바꿔 주기는 하지만(소스 client.go:853-874), 이 변환에 기대지 말고 절대 경로를 써야 한다.

.thvignore로 일부 파일 가리기

.thvignore는 mount한 디렉터리 안의 일부 경로를 컨테이너에서 가리고, 나머지 파일은 bind mount로 그대로 보인다(공식 문서 guides-cli/thvignore). Docker client는 mount 하나마다 다음 순서로 overlay mount를 만든다(소스 client.go:808-849, pkg/ignore/processor.go:168-254).

  1. 전역 패턴 파일을 읽는다. 위치는 XDG 설정 디렉터리의 toolhive/thvignore다(소스 processor.go:88).
  2. mount 원본 디렉터리의 .thvignore를 읽는다.
  3. 패턴마다 원본 디렉터리 바로 아래에서 맞는 경로를 찾는다.
  4. 맞은 경로가 디렉터리면 빈 임시 디렉터리를 그 위치에 bind mount한다.

4. 네트워크 격리의 구조

네트워크 격리는 MCP 컨테이너의 나가는 연결을 허용 목록으로 제한하는 기능이다. v0.63.0에서 --isolate-network의 기본값은 true이고(소스 run_flags.go:302), REST API도 값이 없으면 격리를 켠다(소스 pkg/api/v1/workload_types.go:271-276). 공식 문서는 이 기본값이 v0.30.1부터라고 적는다(공식 문서 guides-cli/network-isolation).

구성 요소

구성 요소컨테이너 이름붙는 네트워크하는 일

Docker client의 DeployWorkload는 격리가 켜져 있으면 다음 순서로 만든다(소스 client.go:175-368).

  1. 외부 네트워크 toolhive-external을 만든다. 이미 있으면 그대로 쓴다(client.go:229, :1863-1869).
  2. 내부 네트워크를 Internal: true인 bridge network로 만든다(client.go:260, :1214-1218).
  3. DNS 컨테이너를 만들고 내부 네트워크의 IP를 얻는다(client.go:267-273).
  4. 지금 있는 모든 bridge network의 gateway IP를 모은다(client.go:277). Podman이면 DNS 컨테이너의 /etc/hosts에서 호스트 이름에 매핑된 주소도 모은다(client.go:281-289, 5장).
  5. egress proxy를 준비하고 HTTP_PROXY 계열 환경 변수를 받는다(client.go:304-308).
  6. MCP 컨테이너를 내부 네트워크에만 붙인다. DNS 서버는 DNS 컨테이너 IP로 둔다(client.go:1720-1726, :1749-1752).
  7. SSE나 streamable HTTP면 ingress proxy를 만든다. 호스트 쪽 포트는 127.0.0.1에만 연다(client.go:352-367, :1814-1821).

v0.53.0은 gateway IP를 모은 뒤에 DNS 컨테이너를 만들었는데, v0.63.0은 두 단계의 순서를 바꿨다. DNS 컨테이너를 만드는 단계가 빠진 네트워크를 다시 만들 때가 있어서, 그 뒤에 gateway 주소를 모으는 것이다(소스 client.go:275-276).

MCP 컨테이너에 넣는 HTTP_PROXY 계열 환경 변수

ToolHive는 아래 환경 변수를 대문자와 소문자 이름으로 모두 MCP 컨테이너에 넣는다(소스 client.go:1771-1783).

HTTP_PROXY=http://<이름>-egress:3128
HTTPS_PROXY=http://<이름>-egress:3128
http_proxy=http://<이름>-egress:3128
https_proxy=http://<이름>-egress:3128
NO_PROXY=localhost,127.0.0.1,::1
no_proxy=localhost,127.0.0.1,::1

ToolHive는 iptables로 트래픽을 가로채지 않기 때문에, MCP 서버가 위 환경 변수를 따라야 연결이 egress proxy로 간다. 환경 변수를 무시한 연결은 내부 네트워크에서 나갈 경로가 없어 실패한다(공식 문서 guides-cli/network-isolation, 설계 문서 15).

격리를 끄면 생기는 일

--isolate-network=false를 주면 보조 컨테이너를 만들지 않고 MCP 컨테이너가 외부 네트워크에 바로 붙는다(소스 client.go:1753-1757). 이때는 권한 프로필의 outbound 규칙을 집행하는 주체가 없어서, --permission-profile none을 함께 줘도 나가는 연결이 열린다.

ToolHive UI는 No isolation, Host networking, Isolate behind an HTTP proxy의 세 선택지를 주고, 기본값은 마지막 선택지다(공식 문서 guides-ui/network-isolation).

5. 허용 목록의 집행: Squid와 Envoy

egress proxy의 구현은 두 가지다. 환경 변수 TOOLHIVE_NETWORK_PROXY가 비어 있거나 squid면 Squid를, 값이 envoy면 Envoy를 쓰고, 다른 값이면 시작할 때 오류를 낸다(소스 pkg/container/docker/networkproxy.go:102-112). 설계 문서 15는 Envoy를 실험 단계로 적는다.

Squid 설정을 만드는 순서

ToolHive는 workload마다 squid.conf를 다음 순서로 쓴다(소스 pkg/container/docker/squid.go:245-295).

  1. 공통 설정을 쓴다. 포트는 3128이고 캐시는 끈다(squid.go:297-319).
  2. Docker gateway 주소 규칙을 쓴다. 기본은 거부 규칙이다(squid.go:255-263).
  3. network 블록이 없거나 insecure_allow_all이면 http_access allow all을 쓴다(squid.go:265-266).
  4. 그 밖에는 포트 ACL과 이름 ACL을 만든다. 두 ACL을 한 줄에 적어 AND로 묶는다(squid.go:322-352).
  5. 끝에 http_access deny all을 쓴다(squid.go:272).

Squid는 처음 맞는 규칙을 적용하기 때문에 ToolHive는 gateway 규칙을 허용 규칙보다 먼저 쓴다(소스 squid.go:188-191). 아래는 arxiv registry 항목의 프로필로 코드가 만들 설정을 손으로 옮긴 예이고, gateway IP는 예시 값이다.

http_port 3128
visible_hostname arxiv-egress
access_log stdio:/dev/stdout squid
cache deny all

Envoy RBAC 정책을 만드는 규칙

Envoy 경로는 컨테이너 하나에 egress listener와 ingress listener를 두는데, stdio transport면 ingress listener가 없다(소스 envoy.go:1001-1018). egress listener는 3128 포트의 forward proxy다(설계 문서 15). 이 listener의 RBAC 정책은 HTTP :authority 헤더를 정규식으로 비교하고, HTTPS에서는 CONNECT 대상 이름이 비교 대상이다.

ToolHive는 RBAC 정책을 다음 규칙으로 만든다(소스 pkg/container/docker/envoy.go:633-696).

  • network나 outbound 블록이 없으면 정책이 비어 모두 거부한다.
  • insecure_allow_all이면 모두 허용하는 정책 하나를 둔다.
  • allow_port만 있으면 모든 이름을 그 포트에서만 허용한다.
  • allow_host가 있으면 이름마다 정책을 하나씩 둔다. allow_port도 있으면 포트를 정규식에 넣는다.
# allow_host ".github.com", allow_port 없음 (hostMatchRegex)
(?i)(.*\.)?github\.com\.?(:[0-9]+)?
# allow_host ".github.com", allow_port [443] (hostPortMatchRegex)
(?i)(.*\.)?github\.com\.?:(?:443)
# allow_port에 80이 있으면 포트 없는 Host도 받는다
(?i)(.*\.)?github\.com\.?(:(?:443|80))?

Envoy는 정규식이 문자열 전체와 맞아야 통과시키므로 github.com.attacker.com은 맞지 않는다(소스 envoy.go:778-779).

공식 문서 guides-cli/custom-permissions는 이런 프로필도 --isolate-network를 주면 네트워크가 막힌다고 적지만, Squid 구현의 코드는 이 설명과 다르다. 허용 목록을 적용하려면 프로필에 network.outbound 블록을 적어야 한다.

Docker gateway 주소

egress proxy는 Docker gateway 주소를 기본으로 거부하고, insecure_allow_all이어도 거부한다(소스 run_flags.go:305-311). 대상은 배포 시점의 모든 bridge gateway IP와 host.docker.internal, gateway.docker.internal, host.containers.internal의 세 호스트 이름이다(소스 pkg/container/docker/hostdiscovery.go:22, squid.go:196-205).

Podman에서는 거부 대상이 더 있다. Docker client는 DNS 컨테이너가 뜬 뒤에 그 컨테이너의 /etc/hosts를 읽고, 세 이름에 매핑된 주소를 모두 거부 목록에 더한다(소스 client.go:281-289, hostdiscovery.go:33-42, :89-95). rootless Podman에서는 호스트 머신의 주소가 bridge gateway가 아닐 수 있어서, v0.55.1까지는 workload가 그 이름이나 주소로 호스트 머신의 서비스에 닿는 경로가 있었다. 이 빈틈은 v0.55.2에서 막혔고(v0.55.2 보안 권고), 설계 문서 05의 Host gateway protection 절이 이 동작을 설명한다.

그 파일에 host.containers.internal이 없으면 Docker client는 배포를 중단하고, --allow-docker-gateway를 줘도 마찬가지다(소스 hostdiscovery.go:100-104, client.go:282-285). Podman의 containers.conf에 no_hosts = true가 있으면 이 경우에 해당한다(v0.55.2 릴리스 노트). Docker에서는 이 파일을 읽지 않는다(소스 client.go:281).

--allow-docker-gateway를 주면 이 주소를 명시적으로 허용하는데, 이 허용은 allow_port와 무관하게 모든 포트에 적용된다(소스 squid.go:207-235, 공식 문서 guides-cli/network-isolation). Envoy는 gateway IP로 풀리는 DNS 응답도 버린다(소스 envoy.go:245-257).

ToolHive는 gateway 목록을 배포할 때 한 번 모으고, 그 뒤에 만든 bridge network와 바뀐 Podman 호스트 매핑은 반영하지 않는다. 반영하려면 workload를 지우고 다시 실행해야 한다(소스 client.go:275-289, 공식 문서 guides-cli/network-isolation).

들어오는 쪽 규칙(inbound)

Squid ingress proxy는 inbound.allow_host를 dstdomain ACL로 쓰고(소스 squid.go:469-477), 목록이 없으면 컨테이너 이름, localhost, 127.0.0.1만 받는다(소스 squid.go:478-486). 설계 문서 15가 dstdomain을 목적지 이름 비교로 설명하는 것을 보면, 이 규칙은 보낸 쪽 주소가 아니라 요청이 가리키는 이름을 비교하는 것으로 보인다.

Envoy ingress listener는 inbound.allow_host를 쓰지 않고, virtual host 이름이 항상 *다(소스 envoy.go:872-881). 두 구현 모두 호스트 쪽 포트를 127.0.0.1에만 열기 때문에(소스 client.go:1814-1821, envoy.go:1065) 다른 컴퓨터에서는 ingress proxy에 닿지 않는다(설계 문서 15).

6. 네트워크 격리의 한계와 플랫폼 차이

network mode에 따른 동작

보조 컨테이너는 MCP 컨테이너가 bridge network에 있을 때만 트래픽을 받기 때문에, ToolHive는 network mode에 따라 격리를 조정한다(소스 config_builder.go:1342-1380, client.go:207-222).

network mode--isolate-network동작

host 등기본값격리를 버리고 경고를 남긴다

거르는 프로토콜의 범위

네트워크 격리는 HTTP와 HTTPS만 지원하고, 데이터베이스 같은 직접 TCP 연결은 실패한다(공식 문서 guides-cli/network-isolation). egress proxy는 TLS를 풀지 않으므로 HTTPS 요청은 이름과 포트로만 거르고, URL 경로로는 거르지 못한다(설계 문서 15).

DNS 질의 처리

ToolHive는 DNS 컨테이너에 허용 목록을 넘기지 않는다. 이 컨테이너는 명령, 환경 변수, 설정 mount 없이 이미지 기본값으로 실행되기 때문에(소스 client.go:1632-1653), 허용 목록에 없는 이름의 DNS 질의도 밖으로 나갈 가능성이 있다. 다만 이 문서는 이 동작을 시험하지 않았다. v0.63.0이 Podman에서 이 컨테이너의 /etc/hosts를 읽는 것은 거부 목록을 채우려는 것이고(5장), DNS 질의를 거르는 설정은 여전히 없다.

그 밖의 알려진 제한

  • Envoy의 DNS 조회는 IPv4만 쓰기 때문에 IPv6 주소만 있는 이름은 허용해도 닿지 않는다(소스 envoy.go:246).
  • Envoy bootstrap 파일은 workload를 지워도 OS 임시 디렉터리에 남고, 파일 모드는 0644다(설계 문서 15).
  • Squid 설정 파일도 OS 임시 디렉터리에 0644로 쓴다(소스 squid.go:274-292). squid.go와 client.go에서 이 파일을 지우는 코드는 찾지 못했다.
  • Envoy에서 allow_port에 443만 두면 일반 HTTP 요청은 거부된다(설계 문서 15).
  • Envoy는 CONNECT 접근 로그를 연결이 끝날 때 남기기 때문에 로그가 몇 분 늦을 가능성이 있다(설계 문서 15).

Kubernetes에서 나가는 연결을 막으려면 NetworkPolicy를 따로 정의해야 한다(설계 문서 05). 설계 문서 15는 operator에 별도 egress gateway 경로가 있다고 적지만, v0.63.0 operator 코드에서도 그 구현은 찾지 못했다.

7. 컨테이너 기본 보안 설정

ToolHive는 권한 프로필과 별도로 컨테이너에 기본 보안 설정을 넣는데, Docker 경로와 Kubernetes 경로의 값이 다르다.

항목Docker MCP 컨테이너Kubernetes MCP 컨테이너

privileged프로필 값(기본 false)false

Docker 열의 근거는 소스 client.go:889-896과 :1709-1719이고, Kubernetes 열의 근거는 소스 pkg/container/kubernetes/security.go:27-87과 pkg/container/kubernetes/client.go:1346이다.

  • Kubernetes 기본값은 사용자가 비워 둔 필드만 채우고, podTemplateSpec에 적은 값이 우선한다(소스 pkg/container/kubernetes/client.go:1462-1499).
  • OpenShift에서는 UID와 GID를 비워서 OpenShift의 SCC가 값을 정하게 둔다(소스 security.go:41-47).
  • ToolHive가 protocol scheme으로 만든 이미지는 일반 사용자 appuser로 실행하는데, 대상은 npx://, uvx://, go://다(소스 pkg/container/templates/npx.tmpl:118, uvx.tmpl:158, go.tmpl:123).
  • 보조 컨테이너는 설정이 다르다. Squid는 CAP_SETUID와 CAP_SETGID를 더하고 아무것도 제거하지 않고(소스 squid.go:159-160), DNS 컨테이너는 capability 설정이 없으며(소스 client.go:1647-1648), Envoy는 모두 제거한다(소스 envoy.go:1073).

설계 문서 05는 Docker 경로에 no-new-privileges를 넣는다고 적었지만, v0.63.0 코드의 보안 옵션은 label:disable 하나다(소스 client.go:894). label:disable은 SELinux 라벨 분리를 끄는 Docker 옵션인데, 이 설명은 소스가 아니라 Docker 일반 지식에서 왔다.

Docker 경로에는 실행 사용자 지정, 읽기 전용 루트 파일 시스템, 자원 제한이 없으므로, 신뢰도가 낮은 서버를 Docker로 실행할 때는 이 점을 감안해야 한다.

8. secret provider와 암호화 저장소

secret은 MCP 서버가 쓰는 API key 같은 비밀 값이고, ToolHive CLI는 secret provider 셋 중 하나를 쓴다(소스 pkg/secrets/factory.go:50-59).

provider값이 있는 곳읽기쓰기목록조건
encrypted암호화 저장소 파일예예예OS keyring 필요
1password1Password vault예아니오예op:// 이름, service account access token
environmentTOOLHIVE_SECRET_<이름> 환경 변수예아니오아니오setup 없이 동작

environment provider는 다른 환경 변수를 훑어보지 못하도록 목록 기능을 일부러 막았다(소스 pkg/secrets/environment.go:56-59).

provider 선택 순서

ToolHive는 다음 순서로 provider를 정한다(소스 pkg/config/config.go:129-162).

  1. 환경 변수 TOOLHIVE_SECRETS_PROVIDER가 있으면 그 값을 쓴다. setup 전에는 environment만 받는다.
  2. 없으면 config.yaml의 provider_type을 쓴다. 이때 setup_completed가 true여야 한다.
  3. 둘 다 없으면 thv secret setup을 먼저 하라는 오류를 낸다.

기본 provider는 없다(소스 pkg/config/config.go:181). 설계 문서 04의 "Default: encrypted"는 v0.63.0 코드와 다르고, 설계 문서 05는 기본 provider가 없다고 적어 코드와 맞는다.

thv secret setup                 # 대화형으로 provider를 고른다
thv secret provider environment  # 스크립트용
gh auth token | thv secret set github
thv secret list

fallback

ToolHive는 encrypted와 1password provider를 fallback으로 감싼다(소스 factory.go:245-249). 주 provider가 "없음" 오류를 내면 TOOLHIVE_SECRET_<이름>을 찾고(소스 pkg/secrets/fallback.go:31-53), 다른 오류에서는 fallback으로 넘어가지 않는다. TOOLHIVE_DISABLE_ENV_FALLBACK=true는 이 동작을 끈다(소스 factory.go:375-383).

암호화 저장소의 구조

encrypted provider는 다음 방식으로 값을 저장한다.

  1. 파일은 XDG 데이터 디렉터리의 toolhive/secrets_encrypted다(소스 factory.go:223). Linux에서는 ~/.local/share/toolhive/ 아래다(설계 문서 04).
  2. 비밀번호는 OS keyring에 둔다. 기본 keyring 라이브러리가 macOS, Windows, Linux D-Bus를 처리하고, Linux에서는 keyctl을 예비로 둔다(소스 pkg/secrets/keyring/composite.go:24-45).
  3. 암호화 키는 Argon2id로 만든다. 반복 2회, 메모리 19 MiB, 병렬 1, 키 길이 32바이트다(소스 pkg/secrets/kdf.go:22-31).
  4. salt는 파일마다 16바이트를 무작위로 만든다(소스 kdf.go:33-40, pkg/secrets/encrypted.go:391-397).
  5. 암호화는 AES-256-GCM이고, 쓸 때마다 새 nonce를 만든다(소스 pkg/secrets/aes/aes.go:20-45).
  6. 모든 secret을 JSON map 하나로 묶어 통째로 암호화한다(소스 encrypted.go:79, :376).
  7. 파일 모드는 0600이고, 쓰기는 원자적으로 한다(소스 encrypted.go:386, :402).
magic    "THVSEC"  6 bytes
version  0x01      1 byte
salt               16 bytes
body               nonce | ciphertext | tag   (AES-256-GCM)

위 형식은 소스 encrypted.go:22-27의 주석에 있다. Argon2id 비용 값은 파일에 넣지 않고 형식 버전으로 정하는데, 공격자가 바꾼 값이 Argon2id 메모리 할당에 닿지 않게 하려는 설계다(소스 kdf.go:16-21, 설계 문서 04).

코드 주석은 키 하나를 만드는 데 약 16 ms와 19 MiB가 든다고 적는다. API server가 요청마다 키를 다시 만들면 서비스 거부 공격 경로가 되기 때문에, ToolHive는 마지막에 만든 키 하나를 프로세스 메모리에 둔다(소스 kdf.go:48-61).

OS keyring이 없으면 ToolHive는 encrypted provider를 만들지 않고 오류를 낸다(소스 factory.go:285-287). ToolHive UI는 무작위 비밀번호를 만들어 OS keyring에 두고, 1Password provider는 지원하지 않는다(공식 문서 guides-ui/secrets-management).

옛 형식과 업그레이드

옛 파일은 salt 없는 SHA-256 키를 쓰는데, 지금 버전도 이 파일을 읽고 그 형식을 유지한다(소스 encrypted.go:360-364). thv secret upgrade-protection은 파일을 새 형식으로 바꾼다. 이 변경은 한 방향이라서 옛 바이너리는 새 파일을 읽지 못한다(공식 문서 guides-cli/secrets-management).

업그레이드 전에 만든 백업은 여전히 약한 형식이다. 비밀번호가 같아서 옛 백업에서 비밀번호를 찾으면 새 파일도 열리므로(설계 문서 04), 옛 백업도 함께 폐기해야 한다.

ToolHive 내부 secret 분리

ToolHive는 자기가 쓰는 secret을 사용자 secret과 나누고, 내부 secret 이름에는 __thv_<구역>_ 접두사를 붙인다(소스 pkg/secrets/scoped.go:34-47, :172). secret 구역은 registry, workloads, auth, llm이다. CLI와 API가 쓰는 user provider는 이 접두사의 이름에 접근하지 못한다(소스 factory.go:333-345).

9. secret이 MCP 서버에 닿는 경로

CLI와 Docker 경로

proxy 프로세스는 workload를 시작할 때 다음 순서로 secret을 푼다(소스 pkg/runner/runner.go:292-315).

  1. RunConfig에서 이름,target=환경변수 문자열을 읽는다. RunConfig에는 값이 없다(설계 문서 04).
  2. provider 종류를 정하고 provider를 두 개 만드는데, 하나는 workloads 구역용이고 다른 하나는 사용자용이다(runner.go:297-309).
  3. 사용자용 provider로 이름마다 값을 찾는다(소스 pkg/environment/environment.go:19-36).
  4. 값을 EnvVars[target]에 넣는다(소스 pkg/runner/config.go:676-691).
  5. Docker client가 이 환경 변수로 MCP 컨테이너를 만든다(소스 client.go:1696-1699).

ToolHive는 환경 변수를 다섯 단계 순서로 합치고, secret 값이 가장 마지막에 덮어쓴다(설계 문서 05).

proxy는 원격 MCP 서버의 OAuth refresh token을 저장할 때 RunConfig도 다시 저장하고, client 자격 증명을 저장할 때도 마찬가지다. v0.53.0은 이때 메모리의 RunConfig를 그대로 저장했는데, 메모리의 RunConfig에는 위 4단계에서 넣은 secret 값이 들어 있다. v0.63.0은 디스크의 RunConfig를 다시 읽고, secret의 대상 환경 변수와 secret에서 온 헤더 값을 지운 다음 그 결과를 저장한다(소스 runner.go:952-973, :1007, :1050). 풀린 secret 값이 저장 파일에 남지 않게 하는 조치다.

thv secret set github     # 값은 화면에 보이지 않게 입력한다
thv run --secret github,target=GITHUB_PERSONAL_ACCESS_TOKEN github

1Password

1Password provider는 op://가 들어간 이름만 받고(소스 pkg/secrets/1password.go:30-33), 환경 변수 OP_SERVICE_ACCOUNT_TOKEN에 service account access token이 있어야 한다(소스 1password.go:118-121).

OP_SERVICE_ACCOUNT_TOKEN=<service-account-access-token> thv run \
  --secret op://MCPVault/slackbot/token,target=SLACK_BOT_TOKEN \
  --secret op://MCPVault/slackbot/team_id,target=SLACK_TEAM_ID \
  slack

registry가 요구하는 secret

registry 항목의 환경 변수에 secret: true와 required: true가 있으면 ToolHive가 값을 찾는다. 먼저 provider에서 같은 이름을 찾고, 없으면 터미널에서 값을 묻는다(소스 pkg/runner/env.go:123-153). v0.63.0은 터미널 입력을 한 줄 전체로 읽기 때문에 공백이 든 값도 받는다(소스 env.go:170-195). 입력을 읽지 못하거나 빈 값이면 오류를 내고 실행을 멈추는데, v0.53.0은 이때 경고만 남기고 그 변수를 건너뛰었다. 오류 문구는 --env나 --secret으로 값을 주는 방법을 알려 준다(소스 env.go:145-152, :200-211).

ToolHive는 입력값을 registry-user-<소문자 이름> secret으로 저장하고, RunConfig에는 그 참조만 넣는다(소스 env.go:238-253). 저장에 실패하면 값을 일반 환경 변수로 넣는다(소스 env.go:245-249). detached 모드와 Kubernetes에서는 값을 묻지 못하므로 값이 없으면 오류가 난다(소스 env.go:58-59, 설계 문서 04).

detached 프로세스

thv run은 기본으로 detached 프로세스를 실행한다(소스 run_flags.go:333). 부모 프로세스는 keyring에서 비밀번호를 꺼내 TOOLHIVE_SECRETS_PASSWORD 환경 변수로 자식에게 넘기는데(소스 pkg/workloads/manager.go:763-772), v0.53.0의 pkg/secrets에서 이 변수를 읽는 코드는 찾지 못했다. 자식은 keyring을 직접 다시 읽는 것으로 보인다(소스 factory.go:392-399).

Kubernetes 경로

Kubernetes에서는 secret provider 대신 Kubernetes Secret을 쓴다(설계 문서 04).

apiVersion: toolhive.stacklok.dev/v1beta1
kind: MCPServer
metadata:
  name: github
spec:
  image: ghcr.io/github/github-mcp-server
  transport: stdio
  proxyPort: 8080
  secrets:
    - name: github-token          # Kubernetes Secret 이름
      key: token                  # Secret 항목 이름
      targetEnvName: GITHUB_PERSONAL_ACCESS_TOKEN

operator와 proxy runner는 다음 순서로 secret을 넣는다.

  1. operator가 spec.secrets마다 SecretKeyRef 환경 변수를 만든다. targetEnvName이 없으면 key를 이름으로 쓴다(소스 cmd/thv-operator/pkg/controllerutil/podtemplatespec_builder.go:61-85).
  2. 이 환경 변수를 mcp 컨테이너의 pod template patch에 넣는다(소스 mcpserver_controller.go:1266-1269).
  3. patch를 --k8s-pod-patch 인자로 proxy runner에 넘긴다(소스 mcpserver_controller.go:1271-1276).
  4. proxy runner가 patch를 적용한 StatefulSet을 만든다(소스 pkg/container/kubernetes/client.go:438).
  5. Kubernetes가 Secret 값을 MCP 컨테이너의 환경 변수로 넣는다(설계 문서 04).

이 경로에서 secret 값은 proxy runner 프로세스를 지나지 않는다. proxy runner 자신에게 secret이 필요하면 TOOLHIVE_SECRET_* 환경 변수를 쓰고, operator는 이런 변수를 보면 TOOLHIVE_SECRETS_PROVIDER=environment도 넣는다(소스 controllerutil/resources.go:127-140).

Vault와 External Secrets Operator

External Secrets Operator는 외부 저장소의 값을 Kubernetes Secret으로 동기화하고, 그다음은 위 경로와 같다(공식 문서 guides-k8s/run-mcp-k8s).

Vault Agent Injector는 annotation으로 동작하는데, annotation은 proxy runner pod에 붙여야 한다(공식 문서 integrations/vault).

spec:
  resourceOverrides:
    proxyDeployment:
      podTemplateMetadataOverrides:
        annotations:
          vault.hashicorp.com/agent-inject: 'true'
          vault.hashicorp.com/role: 'toolhive-mcp-workloads'
          vault.hashicorp.com/agent-inject-secret-github-config: 'workload-secrets/data/github-mcp/config'
          vault.hashicorp.com/agent-inject-template-github-config: |
            {{- with secret "workload-secrets/data/github-mcp/config" -}}
            GITHUB_PERSONAL_ACCESS_TOKEN={{ .Data.data.token }}
            {{- end -}}

Vault Agent는 값을 /vault/secrets/ 아래 파일로 쓰고, proxy runner는 RunConfig에 env_file_dir가 있으면 그 디렉터리의 파일을 환경 변수로 읽는다(소스 cmd/thv-proxyrunner/app/run.go:233-240). 공식 문서는 annotation을 보면 ToolHive가 이 디렉터리를 자동으로 설정한다고 적지만, v0.63.0 operator 코드에서도 그 설정 부분은 찾지 못했다.

secret 전달의 한계

secret은 결국 MCP 컨테이너의 환경 변수가 되고, 컨테이너 안의 코드는 그 값을 읽는다. 설계 문서 04도 악성 컨테이너는 막지 못한다고 적는다. 그래서 secret을 받는 서버에는 네트워크 격리와 좁은 허용 목록을 함께 적용해야 한다.

"ghcr.io/stacklok/dockyard/uvx/arxiv-mcp-server:0.3.1": {
  "permissions": {
    "network": {
      "outbound": {
        "allow_host": ["arxiv.org", "export.arxiv.org"],
        "allow_port": [443, 80]
      }
    }
  },
  "provenance": {
    "sigstore_url": "tuf-repo-cdn.sigstore.dev",
    "repository_uri": "https://github.com/stacklok/dockyard",
    "signer_identity": "/.github/workflows/build-containers.yml",
    "runner_environment": "github-hosted",
    "cert_issuer": "https://token.actions.githubusercontent.com"
  }
}

검증 단계

toolhive-core 검증기는 다음 순서로 확인한다(toolhive-core container/verifier/verifier.go).

  1. sigstore_url의 TUF 저장소에서 trusted root를 받는다. 값이 없으면 tuf-repo-cdn.sigstore.dev를 쓴다(New).
  2. 이미지 저장소에서 그 이미지의 cosign 서명과 attestation을 모은다(getSigstoreBundles).
  3. 각 서명을 이미지 digest에 묶어 확인한다. 이 단계에서는 서명자 identity를 고정하지 않는다(WithoutIdentitiesUnsafe).
  4. 통과한 인증서의 값을 provenance 필드와 비교한다. 비어 있는 필드는 비교하지 않는다(compareBaseProperties).
  5. provenance에 attestation이 있으면 predicate type과 내용을 비교한다(compareAttestation).
  6. 결과가 하나라도 맞으면 통과다. 확인을 통과한 서명이 하나도 없으면 ErrImageNotSigned를 낸다. 맞는 결과가 없으면 ErrProvenanceMismatch를 낸다(VerifyServer).

인증서 발급자가 GitHub Actions면 검증기는 SAN에서 workflow 경로만 꺼낸다. 저장소 주소와 @ref를 떼고 남은 경로를 signer_identity와 비교하는데, 위 예의 /.github/workflows/build-containers.yml이 그 형식이다(toolhive-core signerIdentityFromCertificate).

기본 registry의 항목은 toolhive-catalog 저장소에서 관리한다. 아래 표는 공식 문서가 적은 심사 항목을 줄인 것이다(공식 문서 concepts/registry-criteria).

점수 체계와 "Verified" 등급은 공식 문서의 향후 검토 항목이고 아직 적용한 기준이 아니다. ToolHive는 자체 registry로 로컬 파일, 원격 JSON 파일, registry server를 받고, 위치는 thv config set-registry로 정한다(소스 cmd/thv/app/config.go:52). registry 형식과 registry server는 04편이 다룬다.

이미지 검증이 다루지 않는 것

  1. 기본 검증 모드 warn은 검증에 실패해도 서버를 실행한다.
  2. provenance가 없으면 warn 모드는 검증을 건너뛴다. registry 밖의 이미지와 npx://, uvx://, go:// 빌드 이미지가 여기에 속한다(소스 retriever.go:81-93, :120). 반면 enabled 모드는 이런 서버를 실행하지 않는다.
  3. provenance 필드가 비면 그 비교도 빠진다. 모든 필드가 비면 trusted root가 인정하는 서명은 서명 주체와 무관하게 통과한다. 근거는 toolhive-core의 compareBaseProperties인데, 이 결론은 코드에서 얻은 것이고 실제로 시험하지는 않았다.
  4. 보조 컨테이너 이미지는 검증하지 않는다. dnsmasq는 dockurr/dnsmasq:latest, Squid는 latest 태그를 쓰고(소스 client.go:42, squid.go:23), Envoy만 digest로 고정했다(소스 envoy.go:27-30).
  5. 검증과 pull은 같은 이미지 참조 문자열로 따로 한다(소스 retriever.go:120, :136). 두 단계가 digest를 공유하는 코드는 찾지 못했는데, 그 사이 태그가 바뀌면 다른 이미지가 올 가능성이 있다.
  6. 원격 MCP 서버는 이미지가 없어 검증 대상이 아니다(소스 retriever.go:113-115).
  7. v0.63.0에서 검증 함수를 부르는 곳은 thv CLI, TUI, REST API뿐이다(소스 retriever.go:120, workload_service.go:278). operator와 proxy runner 코드에는 호출이 없어서 Kubernetes 경로에서는 이미지 검증이 일어나지 않는다.
  8. 서명은 누가 어디서 빌드했는지를 보증할 뿐이고, 서버 코드가 안전한지는 보증하지 않는다.

정책 hook

ToolHive는 이미지를 pull하기 전에 정책 hook의 CheckCreateServer를 부르는데(소스 retriever.go:164-185), 기본 구현은 모두 허용한다(소스 pkg/runner/policy_gate.go:21-39). ToolHive를 확장하는 프로그램은 RegisterPolicyGate로 자기 hook을 등록하는 구조다(소스 policy_gate.go:41-48).

12. 자가 점검 문제

먼저 답을 생각해 본 다음에 펼쳐서 확인한다.

Q1. thv run --isolate-network=false --permission-profile none fetch로 실행했다. 서버의 요청이 외부 API에 닿는가?

닿는다. 격리를 끄면 egress proxy를 만들지 않고 MCP 컨테이너가 외부 네트워크에 바로 붙기 때문에(소스 client.go:1753-1757), none 프로필의 빈 허용 목록을 집행하는 주체가 없다.

Q2. 파일 권한만 적은 사용자 프로필을 기본 설정으로 쓴다. 나가는 연결은 어떻게 되는가?

이 프로필에는 network 블록이 없어서, 기본 구현인 Squid는 이 경우 나가는 HTTP(S)를 모두 허용한다(소스 squid.go:265-266). Envoy 구현이었다면 모두 거부한다. 막으려면 프로필에 "network": {"outbound": {}}처럼 빈 outbound 블록을 적어야 한다.

Q3. 프로젝트 맨 위의 .thvignore에 .env를 적었다. src/.env도 가려지는가?

가려지지 않는다. 패턴은 mount 원본 디렉터리 바로 아래만 보고(소스 processor.go:371-400), 공식 문서는 **/*.env 같은 재귀 패턴도 지원하지 않는다고 적는다.

Q4. --allow-docker-gateway를 켜고 allow_port를 [443]으로 두었다. 호스트 머신의 8080 포트 HTTP 개발 서버에 닿는가?

MCP 서버가 HTTP_PROXY를 따르면 닿는다. gateway 허용은 allow_port와 무관하게 모든 포트에 적용되기 때문이다(소스 squid.go:207-235). Linux Docker Engine이면 host.docker.internal 대신 bridge gateway IP로 접속해야 하고, Podman이면 host.containers.internal로 접속한다. HTTP_PROXY 계열 환경 변수를 무시하는 연결은 이 플래그와 관계없이 경로가 없다.

Q5. 암호화 저장소의 암호화 키는 어디서 오는가? OS keyring에 키가 그대로 있는가?

OS keyring에는 비밀번호가 있다. ToolHive는 이 비밀번호와 파일의 16바이트 salt로 Argon2id를 돌리고, 그 결과인 32바이트 값이 AES-256-GCM 암호화 키가 된다(소스 kdf.go:22-46). 키 자체는 OS keyring에 두지 않고 프로세스 메모리에만 둔다.

Q6. setup 없이 TOOLHIVE_SECRETS_PROVIDER=encrypted만 설정했다. --secret을 쓰면 어떻게 되는가?

오류가 난다. setup을 마치지 않았으면 환경 변수로는 environment provider만 받기 때문에(소스 pkg/config/config.go:139-149), 먼저 thv secret setup을 해야 한다.

Q7. Kubernetes에서 spec.secrets로 넣은 값이 proxy runner 프로세스의 메모리를 지나는가?

지나지 않는다. operator는 mcp 컨테이너에 SecretKeyRef 참조만 넣고(소스 podtemplatespec_builder.go:61-85), 값은 Kubernetes가 MCP 컨테이너에 직접 넣는다.

Q8. --image-verification enabled로 uvx://some-package를 실행하면 어떻게 되는가?

실행하지 않는다. protocol scheme으로 빌드한 이미지에는 registry 항목이 없어서 provenance도 없고, enabled 모드는 이 경우 오류를 낸다(소스 retriever.go:81-93, :353-358).

Q9. registry 항목의 provenance에 sigstore_url만 있다. 이 항목의 검증은 무엇을 보장하는가?

코드상으로는 이미지에 그 trusted root가 인정하는 유효한 서명이 있다는 것만 보장한다. 비교할 provenance 필드가 비어 있어 서명 주체는 비교하지 않으므로(toolhive-core compareBaseProperties), 누가 서명했는지는 보장하지 않는다.

Q10. Envoy 구현에서 inbound.allow_host를 설정했다. 어떤 효과가 있는가?

효과가 없다. Envoy ingress listener는 virtual host 이름을 항상 *로 두기 때문이다(소스 envoy.go:872-881). 접근 제한은 호스트 쪽 포트를 127.0.0.1에만 여는 설정이 맡는다.

Q11. rootless Podman에서 격리를 켜고 실행했다. containers.conf에 no_hosts = true가 있다. 어떻게 되는가?

배포가 실패한다. Docker client는 DNS 컨테이너의 /etc/hosts에서 host.containers.internal을 찾는데, 이 이름이 없으면 오류를 내고 egress proxy와 MCP 컨테이너를 만들지 않는다(소스 hostdiscovery.go:100-104, client.go:281-285). --allow-docker-gateway를 줘도 마찬가지다.
